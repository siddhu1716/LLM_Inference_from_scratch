Measure two requests on your CPU.

From the repository root, use Python 3.10 or newer in a virtual environment. The first command installs the teaching package and its test tools. The walkthrough runs two sequences through an in-process scheduler with a deterministic next-token callback. The two tests check the metric arithmetic and exercise the HTTP server on loopback.

python -m pip install -e ".[dev]"
python examples/engine_walkthrough.py
python -m pytest -q tests/test_engine.py::test_metrics_compute_ttft_inter_token_latency_and_throughput tests/test_serving.py::test_http_completion_and_health

Check the denominator by hand

The timing test submits at 0 s, starts at 1 s, emits at 2 s and 3 s, and finishes at 4 s. First-token latency is 2 − 0 = 2 s. The only inter-token gap is 3 − 2 = 1 s. The collector uses the first engine start to the last finish, giving 2 ÷ (4 − 1) = 0.67 generated tokens/s. A client measuring from submission would get 2 ÷ (4 − 0) = 0.50 tokens/s. Send eight short HTTP requests to the teaching model

Start python -m mini_infer.cli serve --port 8765 in a terminal. In a second terminal run the Python snippet below as a script. It sends eight non-streaming completions, with at most two in flight and four generated tokens each. Stop the server with Ctrl+C when done.

from concurrent.futures import ThreadPoolExecutor
import json
from time import perf_counter
from urllib.request import Request, urlopen

def complete(number):
    body = json.dumps({"prompt": f"Hi {number}", "max_tokens": 4}).encode()
    request = Request("http://127.0.0.1:8765/v1/completions", data=body,
                      headers={"Content-Type": "application/json"})
    with urlopen(request, timeout=30) as response:
        return json.load(response)["usage"]["completion_tokens"]

start = perf_counter()
with ThreadPoolExecutor(max_workers=2) as pool:
    counts = list(pool.map(complete, range(8)))
seconds = perf_counter() - start
print(f"{len(counts)} replies, {sum(counts)} generated tokens")
print(f"{len(counts) / seconds:.2f} req/s, {sum(counts) / seconds:.2f} tok/s")

A successful run prints eight replies and 32 generated tokens. The rate depends on the host. This exercise times complete HTTP responses. The teaching server builds all output pieces before writing its streaming events, so their spacing cannot reveal per-step model decode latency. Teaching server implementation.

Time a tiny forward pass without an HTTP server

Run this Python snippet in the same environment. It builds the pure-Python model once and passes two token IDs with a fresh cache at each invocation. Each of three trials runs three forward passes. Dividing the trial time by three gives seconds per pass.

from timeit import repeat
from mini_infer.backends.python import Transformer
from mini_infer.common import ModelConfig

model = Transformer(ModelConfig(vocab_size=256, dim=16, n_layers=1,
                                n_heads=2, n_kv_heads=1, hidden_dim=32))
trials = repeat(lambda: model.forward_with_cache([72, 105]), number=3, repeat=3)
print("Milliseconds per two-token pass:", [round(t * 1000 / 3, 2) for t in trials])

Save all three values. The timed region includes cache construction and the forward computation. It omits model initialization, HTTP and sampling. Reference model and cache example.

The other included demonstrations inspect Python/PyTorch output shapes, incremental KV-cache shapes, quantization, attention and speculative verification. The PyTorch comparison is optional. The two timing snippets above are page exercises. Production engine packages, model weights, MLPerf datasets and published GPU campaign logs come from the upstream projects. vLLM benchmark CLI

One engine, three clocks.

Use an isolated vLLM environment with its benchmark dependencies, a supported device and a small supported causal model with tokenizer files already saved in ./model. Run the commands from the same working directory. The examples use a POSIX shell. Each online test needs its own terminal alongside the server. Stop that server before starting a separate offline engine on the same GPU. vLLM installation extra and CLI reference.

1. Time the complete HTTP path

vllm serve ./model --host 127.0.0.1 --port 8000
vllm bench serve --model ./model --base-url http://127.0.0.1:8000 \
  --backend openai --endpoint /v1/completions --dataset-name random \
  --random-input-len 64 --random-output-len 16 --ignore-eos \
  --num-prompts 8 --max-concurrency 2 --request-rate 2 --num-warmups 1 \
  --save-result --result-filename vllm-smoke.json

The client targets two arrivals per second, caps in-flight work at two, and requests sixteen output tokens per measured request. Ignoring an early end-of-sequence token helps keep the output shape fixed. Inspect successes, failures, actual output tokens, request rate and first-token latencies in the report. Initialization checks and warm-up add traffic outside those eight measured prompts. Pinned serving runner.

2. Measure offline throughput

vllm bench throughput --model ./model --dataset-name random \
  --random-input-len 64 --random-output-len 16 --num-prompts 8

The engine receives the prompt set locally. Its output distinguishes requests/s, total tokens/s and output tokens/s. With eight 64-token inputs and sixteen actual outputs each, a four-second run would yield (512 + 128) ÷ 4 = 160 total tokens/s, including 32 generated tokens/s. Verify the measured lengths before using that example. Pinned throughput runner and token accounting.

3. Time one batch repeatedly

vllm bench latency --model ./model --batch-size 1 \
  --input-len 64 --output-len 16 --num-iters-warmup 1 --num-iters 3

This reports elapsed time for processing the batch across repeated iterations, with prefix caching disabled by default in this runner at the source pin. Three trials are enough to check configuration. Tail estimates require far more observations. Pinned batch-latency runner · Trace vLLM’s scheduler and model runner.

NVIDIA AIPerf and GenAI-Perf

With AIPerf installed in the client environment, reuse a running local OpenAI-compatible chat server that advertises ./model and has a working chat template. Use the same tokenizer as the server. This example requests a small synthetic workload and enables streaming so the client can observe first text and subsequent gaps.

aiperf profile --model ./model --url http://127.0.0.1:8000 \
  --endpoint-type chat --streaming --concurrency 2 --request-count 8 \
  --synthetic-input-tokens-mean 64 --output-tokens-mean 16

Check realized lengths and successful requests in the exported profile. A chat template can add prompt tokens and early stopping can shorten replies. GuideLLM

GuideLLM can compare synchronous, concurrent, constant-rate and Poisson traffic against a serving API. A sweep locates the region where added load no longer improves usable throughput. For a small local check, the following command bounds a constant-rate profile to eight requests. Configure the served model and matching tokenizer if the endpoint does not advertise an identifiable model.

guidellm run --backend kind=openai_http,target=http://127.0.0.1:8000 \
  --profile kind=constant,rate=2 --constraint kind=max_requests,count=8 \
  --data kind=synthetic_text,prompt_tokens=64,output_tokens=16

Read the per-profile summaries and keep the exported JSON or CSV. When measuring a paid provider, check its request and token limits, record the region and model revision it exposes, and count failed attempts and retries. This page’s commands target loopback. Inputs and traffic

What kind of day are you replaying?

A workload specifies both what arrives and when it arrives. The same average of 100 tokens per request could describe many short prompts or a mix of short chats and long documents. Keep input sequence length (ISL) and output sequence length (OSL) together for each request. Record output caps and actual generation lengths separately. Workload options.

Fixed lengths, conversations and traces

Fixed or random token IDs isolate repeatable shapes. Use 64 in / 16 out for a smoke check, then vary one dimension. ShareGPT supplies conversational text and a length distribution. Sampling first-turn pairs alone omits the repeated history of a multi-turn chat. Trace replay preserves recorded arrival gaps and lengths where the trace contains them. Some traces contain only metadata. Preserve shared prefixes or real conversation turns when testing cache reuse. vLLM dataset and timed-trace controls · SGLang multi-turn replay.

Burst, open-loop rate and closed-loop concurrency

A burst submits a group at once. In an open loop, the arrival schedule advances independently of completed responses. At 5 requests/s the expected arrivals in 20 s are 5 × 20 = 100. Poisson inter-arrival gaps vary. In a closed loop, each of C clients can issue more work when a request finishes. At C = 4, four continuously busy clients with 0.5 s average response time sustain about 4 ÷ 0.5 = 8 requests/s. Record achieved concurrency and any client-side waiting caused by a cap. Arrival patterns and concurrency controls.

Long context, active memory and prefix hits

Lengthen the prompt while holding the output cap and offered load fixed. Record first-token latency, live sequences, resident KV, evictions and peak memory. For a dense decoder caching full keys and values, KV bytes/token = 2 × layers × KV heads × head dimension × bytes/element. At 32 layers, 8 KV heads, head dimension 128 and two-byte elements, one token consumes 128 KiB and 8,192 unique resident tokens consume 1 GiB before pool overhead. A shared prefix, sharding or a sliding window changes the resident total. Test quality across the same context lengths. KV storage and prefix sharing · Long-context accuracy tests.

For a workload-level reuse fraction, divide reused prompt tokens by all prompt tokens. Reusing 400 out of 1,000 is 40%. Engine counters may cover only tokens queried for caching. Label their own denominator and reset or difference cumulative counters over each run. Compare cold and warmed prefixes separately. vLLM metric definitions.

Speculative decoding and variable draft acceptance

Hold the target model and decoding policy fixed. Record quality, draft lengths, target verification steps, accepted draft tokens, emitted tokens, TTFT and output tokens/s under load. If a draft proposes 40 tokens and the target accepts 24 across ten verification steps, acceptance = 24 ÷ 40 = 60%. If the target supplies one recovery or bonus token per step, the result is (24 + 10) ÷ 10 = 3.4 emitted tokens/step. Report actual emitted counts with EOS or length truncation. Extra draft computation and memory can outweigh the saved target steps. Repeat with conversational, code and less predictable text. Acceptance metric definitions · SGLang SPEED-Bench workload.

Worked case · Llama 2 70B, release 5.0

Offline. The generator issues the workload in one query. The score is generated tokens ÷ whole-query duration in seconds. LoadGen uses the maximum sample latency in that query. If the set produces 1,200,000 tokens in 600 s, its rate is 2,000 tokens/s. There is no per-user TTFT target for Offline. LoadGen’s rate calculation · Llama 2 result fields.

Server. LoadGen targets a Poisson arrival rate in samples/s. For this LLM, the reported score is completed generated tokens ÷ elapsed time through final completion. The v5.0 configuration sets a 99th-percentile target, 2,000 ms TTFT and 200 ms TPOT. A high token rate that fails the applicable latency, duration, minimum-query or other validity checks is ineligible. Inspect mlperf_log_summary.txt and the detailed logs. Other models and releases have their own units, arrival rules and thresholds. v5.0 scenario configuration · LoadGen validity checks.

Accuracy. Llama 2 70B uses OpenOrca and evaluates ROUGE-1, ROUGE-2 and ROUGE-L against reference targets. For the 99.9 tier, the ROUGE-1 threshold is 44.4312 × 0.999 ≈ 44.3868. The v5.0 checker also bounds mean generated tokens per sample against 294.45. Shortening replies can invalidate an apparently fast system. Compare submitted systems within the same division, release and quality tier. Release-specific quality and length targets · Llama 2 reference dataset and accuracy.

What about Interactive and SingleStream?

The later MLCommons rules linked here distinguish conversational and interactive Server limits. For Llama 2 70B the interactive TTFT/TPOT pair is 450/40 ms. SingleStream schedules the next query after the last one completes. Scenario availability is model- and release-specific. Use the matching rule set and published results table when comparing systems. Published campaign

What does a 1.11× result mean?

Plow’s project-run campaign tested text-only Gemma 4 E4B against vLLM 0.29.0 on one H100. The strict report used greedy decoding, 1,000 input tokens, 128 output tokens and two repeats. Ratios divide a Plow measurement by the matching vLLM value. At concurrency 32, total throughput was 1.11×, p99 TTFT 0.74× and p99 TPOT 0.93×. Thus throughput was 11% higher and p99 first-token latency was 26% lower in that cell. At concurrency one, p99 TTFT was 1.51× and the report flagged high repeat-to-repeat variation.

Check the model, binary and packet hashes, KV/cache settings, device, client, correctness gate, sample size and flagged cells in the report. A batch-one decode microbenchmark can exclude prefill and queueing. A serving campaign includes their effect. For an SGLang comparison, a new matched run is required. Reporting a result

Find the highest usable load.

  1. Write the service target first.

    For example, require a valid reply, TTFT ≤ 500 ms and per-request average output gap ≤ 50 ms. Define the observed token event, treatment of one-token completions and any separate task-quality target. Save the scoring policy. Latency definitions · Task quality.

  2. Match the experiment.

    Record model/tokenizer revisions, chat template, sampling, output caps, weights and KV precision, GPU count, parallelism, power policy and software versions. Replay the same requests and arrival schedule from the same client. Label each run as cold or warm. Confirm the actual generated lengths and compare quality after precision or decoding changes.

  3. Sweep offered load.

    Try 1, 2, 4 and 8 requests/s with the same prompt mix. At each point warm separately, wait for outstanding requests to finish and retain timestamps, successes, failures and timeouts. Repeat measured runs. Eight requests demonstrate the harness, while a production p99 needs enough samples to expose a tail. Percentile conventions and sample size.

  4. Apply the target to each request.

    Suppose 64 requests are offered over a 60 s measured window including drain, 60 finish successfully and 54 meet every target. Throughput is 60 ÷ 60 = 1.00 successful request/s. Goodput is 54 ÷ 60 = 0.90 qualifying requests/s. The share of all offered work meeting the target is 54 ÷ 64 ≈ 84.4%. Separate p99 statistics cannot identify which requests passed both limits. Throughput and goodput worksheet.

  5. Report the operating point and its cost.

    Show accepted quality, completed requests/s, generated tokens/s, TTFT and token-gap percentiles, peak memory and cost at the same load. For a fully attributed $3 hardware-hour and 9,000 qualifying replies in that hour, cost per 1,000 qualifying replies = $3 × 1,000 ÷ 9,000 ≈ $0.33. State the actual billing window, retries and idle time. Memory and deployment budgets.
