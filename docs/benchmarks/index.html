Worked formulas

What goes in the denominator?

Use these examples to read a result table. Each uses small, invented counts so you can check the arithmetic by hand.

Task accuracy / resolution rate

Grade each task against its verifier. With one verdict per task, the denominator includes every evaluated task, including unsuccessful attempts. Report skipped tasks separately and follow the benchmark’s failure policy.

Score (%) = 100 × passed tasks / evaluated tasks

18 / 24 = 75% of tasks passed.

How engineering-task verifiers grade a patch

Pass@k from sampled programs

Generate n programs for one problem. The tests pass for c of them. Of all groups of k candidates, what fraction contain at least one passing program? Average the per-problem estimates for the suite score. This measures the opportunity to find a solution when given multiple tries.

pass@k = 1 − C(n − c, k) / C(n, k)

C(a, b) counts ways of choosing b items from a without replacement. If fewer than k failures exist, every group contains a pass. The formula requires n ≥ k ≥ 1.

pass@2 = 70%. A single draw from these five samples passes 40% of the time.

HumanEval estimator and aggregation

Token overlap for a short answer

After the evaluator’s text normalization, count the tokens shared between the prediction and reference, respecting repeated-token counts. For “river silt sample” versus “river silt”, two of three predicted words match both reference words.

Precision = overlap / predicted · Recall = overlap / reference
F1 = 2 × overlap / (predicted + reference)

Precision 66.7% · Recall 100% · F1 80%.

These are evaluator word tokens. In SQuAD v2’s token-F1 rule, two empty normalized answers score 1 and just one empty answer scores 0. Exact match requires the entire normalized answer to match. SQuAD v2 scorer

Macro and pooled accuracy by length

Suppose the short-context group has ten examples and the long-context group has two. Pooling gives each example equal weight. A macro average gives each group equal weight. Report group sizes and the suite’s aggregation convention.

Pooled = (short correct + long correct) / total items
Macro = (short accuracy + long accuracy) / 2

Short 90% · Long 50% · Pooled 83.3% · Macro 70%.

Application benchmarks

What counts as a good answer?

The same reply can be graded by its words, the facts it contains, or a human preference. Choose a rule that captures the failure your users would notice.

NIST OpenASR · transcription error

Align the transcript to the human reference using word edits. Corpus word error rate (WER) = 100 × (substitutions + deletions + insertions) / reference words, summed over the corpus before division. Ten substitutions, four deletions and two insertions across 200 reference words give 8% WER. Lower is better. Many insertions can take WER above 100%. Fix the language-specific normalization rules before comparing systems. NIST evaluation plan.

DocVQA · reading answers from document images

The original DocVQA benchmark asks questions about document images. Its ANLS score gives credit for small spelling errors. For two nonempty strings, let d = character edit distance / longer string length. The scorer below assigns 1 − d when d < 0.5 and zero otherwise. Take the best score among accepted references for each question, then average across questions.

Reading “INV03” as “INV08” costs one substitution in five characters. The similarity is 0.8 and exact match is zero. For invoice identifiers, a product may require exact match even when the benchmark grants partial credit. Original DocVQA paper · Pix2Struct ANLS scorer.

Chatbot Arena · human preference

A voter compares two anonymous responses to the same prompt. In the basic Bradley–Terry model, fitted strengths a and b give predicted preference P(A over B) = 1 / (1 + exp(b − a)). On this natural-log scale, a − b = ln(3) gives a predicted 75% preference. Public ratings may rescale the fitted values. Record the opponent pool, tie treatment, uncertainty and whether style controls were enabled. Arena team’s scoring method.

WikiText · next-token prediction and perplexity

Give a causal language model held-out text and score the probability it assigns to each true next token. For N scored positions, perplexity = exp(−Σ ln P(true token | preceding context) / N). If a model assigns 0.5 and 0.125 to the two true next tokens, perplexity = 1 / √(0.5 × 0.125) = 4. Lower is better under the same tokenizer, text and context-window protocol. Count only positions used in the loss; overlapping windows can otherwise double-count targets. Worked WikiText evaluation.

Reading the results

Compare two runs fairly.

Task and grader
Record the suite version, split, denominator, scoring script and task-level results. A coding agent’s retries, tools and time budget can change its score with identical model weights.
Model and input
Pin the checkpoint, tokenizer, prompt template, precision and generation settings. Publish input and output length distributions and what happened to prompts exceeding the context window.
Serving conditions
Match hardware, runtime versions, traffic arrivals and cache warm-up. Say where timing starts and ends. Separate cold starts, warm requests, timeouts and cancellations.
Decision
Publish quality and latency alongside throughput, the number of tasks or requests, and variation across repeated runs. If the goal is a responsive service, count the successful responses that meet your stated deadline per second.
Work out speedup, GPU efficiency, energy and cost

Speedup for the same work = baseline time / candidate time. Going from 50 to 40 ms gives 1.25× speedup. The latency reduction uses a different denominator: (50 − 40) / 50 = 20%.

Output throughput per GPU = generated tokens / (wall seconds × GPU count). Suppose a four-GPU deployment generates 2,400 tokens in 30 s. Its rate is 80 output tokens/s across the system and 20 output tokens/s/GPU. Report the GPU models alongside a per-device average, especially for a mixed fleet.

Energy per output token = measured energy in joules / generated tokens. If mean whole-node power during those 30 s is 1,200 W, energy is 1,200 × 30 = 36,000 J, or 15 J/output token. Record the measurement boundary, duration and treatment of idle power. MLCommons power measurement setup.

Cost per million output tokens = allocated run cost × 1,000,000 / generated tokens. At an illustrative combined rate of $8/hour, the 30 s window costs $8 × 30/3,600. That gives $27.78 per million output tokens. Count idle capacity or additional infrastructure when the question is the cost to operate the service over a billing period.
