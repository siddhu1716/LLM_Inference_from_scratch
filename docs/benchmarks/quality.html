Benchmark field guide

Measuring answer quality

A model writes a function, finds a fact in a book, or changes an order through a tool. Each task leaves different evidence of success. Choose the evidence first, then read the score.

From one response to a score

Keep the item, the attempt and the grader separate

An item is one question, program specification, or task environment. An attempt is one sampled answer or agent trajectory. A grader maps the submitted result to a number. Record which items were attempted and how parsing failures, timeouts and missing results enter the denominator.

Exact match and accuracy

Let N be the number of evaluated items. The indicator I equals 1 when a condition holds and 0 otherwise. Let f be the benchmark’s specified normalization, such as parsing a final answer letter.

EMᵢ = I[f(predictionᵢ) = f(referenceᵢ)]
Accuracy (%) = 100 × Σ EMᵢ / N

If 72 of 80 questions are correct and the other eight include three unparseable answers scored wrong, accuracy is 90%. Normalizing “The Blue Door” to “blue door” may be valid for an English QA task. Case, punctuation and spacing can be meaningful in code or identifiers. Use the evaluator for the task.

Three different meanings of normalization
  • Normalize the text. A QA scorer may lowercase and remove articles before matching. For multiple gold aliases, take the maximum match over allowed references.
  • Normalize a multiple-choice likelihood. For a scorer that divides by string length, choose argmaxj log P(choicej | prompt) / length(choicej), then compute accuracy. With log scores −2 and −3 for strings of one and three characters, raw likelihood picks the first. Length normalization picks the second (−1 > −2). Check the harness and task for the length unit and prompt delimiters. EleutherAI scoring implementation
  • Adjust a reported score for chance. When a report specifies this adjustment, score = (accuracy − chance) / (1 − chance). For a four-choice task, 55% raw accuracy becomes (0.55 − 0.25)/0.75 = 0.40, meaning 40% of the gap from chance to perfect accuracy. Below-chance accuracy can give a negative result.

Sampled programs, a selector, and repeated reliability

For one item, generate n candidates and let c pass the official tests. C(n, k) counts distinct groups of k candidates. For 1 ≤ k ≤ n, the share of groups containing at least one passing candidate is

pass@k estimate = 1 − C(n − c, k) / C(n, k)

Compute it per item, then average across items. At k = 1 the estimate is c/n. When c = 0 it is zero. If fewer than k failures exist, every group contains a pass and the estimate is one. With fewer than k attempts, this estimate is undefined. State the sampling temperature and sample count. HumanEval estimator

What reaches the user?

Selected best-of-k. A selector S must choose one output from the k candidates using information available at selection time. Selected success = Σ I[the chosen output passes] / N. If the selector chooses a failing patch when another candidate passes, that item scores zero. Record the selector and its cost. Using held-out answers to choose measures an oracle.

pass^k. In the original τ-bench convention, all k runs must succeed. Its per-item estimate is C(c, k)/C(n, k), with zero when c < k. In the five-run example with two passes, pass^2 = 1/10 = 10%, compared with 70% for pass@2. τ-bench estimator

Average the intended unit

Micro accuracy = Σ correct / Σ items. An equally weighted macro average = Σ group accuracy / number of groups. If a run gets 90/100 in one language and 1/10 in another, micro accuracy is 91/110 ≈ 82.7%. Macro accuracy is (90% + 10%)/2 = 50%. Show the subgroup scores and counts alongside either aggregate.

Executable feedback

From one function to a repository change

For a function, the scorer can often call the output directly. For a repository task, a harness must restore the correct base revision, apply the proposed change, and verify behavior. Tools, context, environment and time limits become part of what earns the score.

HumanEval, MBPP and EvalPlus
HumanEval asks for Python function completions. MBPP uses short programming specifications with tests. A candidate passes an item when the benchmark’s required tests pass. Use pass@1 for a single-sample estimate and pass@k for sampled coverage. EvalPlus supplies stronger test suites for these families. An implementation that handles positive integers but fails on zero can pass the base tests and fail additional cases. Report the named dataset, split, test suite and generation protocol. HumanEval · MBPP paper · EvalPlus harness
LiveCodeBench
Programming contest problems arrive in dated releases. In code generation, a submitted program must pass the tests under the evaluation limits. The suite also includes code execution, test-output prediction, and self-repair scenarios. Compare the same scenario and date interval. Recent release dates help investigate training overlap, while hidden tests check only the cases they exercise. LiveCodeBench scenarios and releases
SWE-bench Verified
An agent receives a repository snapshot and an issue. The harness grades the submitted patch using the designated fail-to-pass tests and pass-to-pass regression tests. Verified is a 500-instance human-reviewed subset of SWE-bench. For a fixed split, resolved (%) = 100 × fully resolved instances / evaluated instances. One failed required test can make the item unresolved. If 64 of 100 scheduled issues resolve and four time out, reporting 64% includes those failures. Reporting 64/96 describes a different denominator. Official harness overview · Verified selection process
SWE-bench Pro
Pro is a separate long-horizon repository benchmark. Its public V2 release has 642 validated tasks and includes a named HARD-51 subset. Pin the split and protocol, including how the agent workspace becomes a patch and how a clean verifier grades it. Two “resolved” percentages are comparable only against matching task sets and grading rules. SWE-bench Pro releases and protocol

Which DeepSWE?

Datacurve DeepSWE is a benchmark. Its published collection contains 113 original long-horizon tasks in existing open-source repositories. In v1.1, the agent works in an isolated environment, then its committed patch is applied to a pristine verifier environment. The verifier emits a binary reward and diagnostic pass fractions. Mean binary reward × 100 gives the percentage solved under that protocol. Passing eight of ten checks can help debug a failed item, while its binary reward can still be zero. Datacurve task format and verifier · DeepSWE benchmark paper

Agentica DeepSWE-Preview is a coding agent. Its checkpoint is based on Qwen3-32B and trained using reinforcement learning with R2E-Gym tasks. Its model card reports 42.2% for its agent protocol on SWE-bench Verified, averaging single-attempt performance over 16 runs, and 59% with a hybrid selector over 16 candidates. These are two inference budgets on SWE-bench Verified. The evaluation name, candidate budget and selector belong next to each number. Agentica model card and evaluation table

Context quality

Can the model use the evidence it receives?

Recording a server’s maximum accepted input length tells you which prompts fit. To learn what the model can recover, vary document length, evidence position and task. Record the tokenizer, input truncation or retrieval strategy, actual input tokens and output budget. A benchmark may measure source length in words.

LongBench v1 and v2 ask different questions

LongBench v1 combines English and Chinese tasks including QA, summarization, classification, retrieval and code completion. The official script dispatches to a metric per dataset. For example, NarrativeQA uses token-overlap F1, while a summarization dataset such as GovReport uses a ROUGE-L scorer. With multiple references, the script takes the best per-item reference score, then averages the items for that dataset. LongBench paper · Task-to-metric mapping

Compute a LongBench QA score

After the specified text normalization and tokenization, let m be the number of shared tokens, with multiplicity limited by their counts in both texts. Precision P = m / predicted tokens. Recall R = m / reference tokens. F1 = 2PR/(P + R), with zero when there is no overlap in the v1 QA scorer. “Blue access badge” against “blue badge” has P = 2/3, R = 1 and F1 = 0.8. The dataset percentage is 100 × meanitems(maxreferences F1). Preserve the scorer’s Chinese segmentation and normalization where applicable. LongBench metric definitions

How ROUGE-L handles word order

For a single candidate/reference sequence pair, let L be their longest common subsequence length. Its matched tokens must have the same order and may have intervening words. ROUGE-L F1 uses P = L / candidate length, R = L / reference length, and 2PR/(P + R). For candidate “server restarts safely” and reference “server safely restarts”, L = 2, so F1 = 2/3. An unordered token-overlap score would be 1. Follow the released scorer for tokenization, empty inputs, and multi-sentence summary variants.

LongBench v2 has 503 four-option questions across six task families, including long dialogues, code repositories and structured data. Its published bands are short (up to approximately 32K words), medium (32K–128K words) and long (128K–2M words). Use the supplied length label. With the default uncompensated scoring, overall accuracy is 100 × correct extracted choices / all questions. Slice accuracy is 100 × correct in slice / items in slice. For example, 8/10 short and 2/5 long gives 10/15 = 66.7% overall and 40% on the long slice. Keep direct-answer, chain-of-thought and retrieval settings visible. LongBench v2 task and length definitions · Official aggregation

Needle-in-a-haystack and RULER

Plant a rare fact, such as “locker 47 uses cobalt”, at several depths and lengths. For a controlled exact-keyword variant, cell hit rate = trials returning the expected keyword / trials in that cell. Draw a length-by-depth grid. The original Needle implementation can use an evaluator model, so record its rubric when reproducing a heatmap. Original Needle implementation

RULER adds synthetic tracking, aggregation and QA to retrieval probes. For its multi-reference retrieval matcher, item score = number of reference strings found case-insensitively / number required. The QA matcher awards one if any allowed reference appears. Two targets found out of three therefore give 2/3 on the first kind of item. Report each length, alongside the task average and distractor construction. RULER · Exact string-match rules

HELMET and InfiniteBench

HELMET compares multiple context lengths on task families such as retrieval, reranking, citation, summarization and long-document QA. Inspect the metric attached to each family. A list containing the right passage but placing it last can earn full set recall and poor ranked utility. HELMET tasks, configurations and graders

HELMET’s MS MARCO reranking evaluation reports nDCG@10. For one query, DCG@k = Σ gainr / log₂(r + 1), summing ranks r = 1 through k. nDCG@k divides this by the ideal DCG@k from ordering known items by decreasing relevance. For a binary example with one relevant item, returning it second gives 1/log₂(3) ≈ 0.631. Returning it first gives 1. Use the harness’s relevance labels, gain convention and handling for queries without positive gains. HELMET passage-ranking protocol

InfiniteBench mixes synthetic and real-world long-input tasks beyond 100K tokens. Its release specifies distinct scorers for tasks such as passkey retrieval, book QA and English summarization. For English book summaries it uses ROUGE-Lsum, which uses longest common subsequences across summary sentences. Reuse its implementation and sentence handling when comparing runs. InfiniteBench data and metrics · Paper

Answer evaluation

Match the answer checker to the skill

Knowledge and reasoning · MMLU, MMLU-Pro, GPQA

These use answer choices across different domains and difficulty levels. MMLU spans academic subjects, MMLU-Pro adds more candidates per question, and GPQA emphasizes expert science. For ordinary choice accuracy, compare the selected option with the key. State whether the harness uses option likelihoods or a generated letter, whether invalid outputs score zero and how subjects are aggregated. Option shuffling, chat formatting, few-shot examples and output budgets can all change what gets selected. MMLU · MMLU-Pro · GPQA

Mathematical answers · GSM8K, MATH, AIME

GSM8K uses grade-school word problems. MATH includes competition-style solutions and final answers. AIME has year- and event-specific problems with integer answers. State the answer extractor, allowed equivalences and exact year or split. An exact checker can accept “004” as 4 if it parses integers, while two equivalent algebraic expressions need an appropriate equivalence test. A correct final answer scores one even if its rationale contains a mistake under an answer-only protocol. GSM8K · MATH · AIME format

Majority vote. When a run samples several solutions, select the most frequent extracted answer, then grade that single answer. For samples [4, 6, 6] with gold 4, coverage is successful and majority voting selects 6. Record tie-breaking, the candidate count, and total generated tokens.

Instruction following · IFEval

IFEval uses verifiable instructions such as required keywords or a response-length condition. Prompt-level strict accuracy averages I[all instructions in a prompt pass]. Instruction-level strict accuracy averages individual checks. If two prompts have two and three checks and only the last check fails, prompt accuracy is 1/2 = 50%, while instruction accuracy is 4/5 = 80%. The loose protocol also tests specified output transformations. Publish the named variant. IFEval paper · Official checker

Multilingual and multimodal work · MGSM and MMMU

MGSM translates grade-school math items into multiple languages. Compare matched item IDs, prompt language and rationale policy, then report per-language answer accuracy. A macro average gives each language equal influence. MMMU tests expert-level multimodal reasoning across academic subjects, including image-based questions. Preserve image preprocessing, question format, and its official answer parser when comparing checkpoints. MGSM · MMMU

Tool use and grounded generation

Inspect the action and the state it leaves behind

Function callingBerkeley Function Calling Leaderboard
A tool response can have valid JSON and still call the wrong function. BFCL uses category-specific checks, including abstract-syntax-tree matching and executable or stateful evaluation. For example, a task requesting a forecast for Pune should distinguish the named city and the required units. For a binary category, accuracy = accepted calls or tasks / evaluated items. Use the published category aggregation and version for an overall result. BFCL methodology and versions
Multi-turn service agentsτ-bench and τ²-bench
A simulated customer and an agent interact through policy-constrained tools. Evaluate the task’s required actions or final database state. A polished confirmation can leave a reservation unchanged. Use repeated trials to report pass^k reliability and fix the user simulator, domain version, tool schema and step budget. τ² adds dual-control tasks in which the user can also act. τ-bench · τ²-bench
Browser and assistant tasksWebArena and GAIA
WebArena evaluates tasks in controlled websites with functional checks. GAIA asks realistic questions that may require retrieval, files and tools, ultimately producing a gradable answer. Record initial site state, allowed tools and whether evaluation checks the final state or extracted answer. A correct GAIA answer and a successful browser workflow measure different outcomes. WebArena environments · GAIA paper
Retrieval-augmented QACRAG
Score evidence retrieval separately from the generated answer. With labeled relevant documents, recall@k = relevant documents in the top k / all relevant documents. Finding two of three supporting documents gives 2/3, even if the final answer is wrong. CRAG’s automatic answer evaluation gives +1 for correct, 0 for missing and −1 for incorrect. For the simple unweighted sample mean, 60 correct, 25 missing and 15 incorrect give (60 − 15)/100 = 0.45. Preserve any official weighting when reproducing a published aggregate. CRAG task and grading rules
When an evaluator model supplies the label

For an explicitly tie-split, direct pairwise comparison, the candidate’s raw win fraction is (wins + 0.5 × ties) / comparisons. Four wins, two ties and four losses yield 50%. Other leaderboards fit a rating model or adjust for response length, so a raw win fraction may use a different scale. Save the judge model, prompt, reference answer, ordering and version. Swap answer order, inspect ties and manually review a sample of disputed judgments. AlpacaEval evaluation protocols

Applying the results

Compare a serving change on the same items

  1. Pick a decision and freeze the inputs.

    For a weight-precision change, keep checkpoint revision, tokenizer, prompts, few-shot examples, dataset release, tools and grading code fixed. Include the application’s real prompt lengths and languages.

  2. Match the inference budget.

    Record sampling configuration, seeds or replicate IDs, reasoning budget, context limit, stop conditions, agent timeouts, allowed tool calls, retries and candidates per task. Save task IDs and attempted outputs, including failures.

  3. Compare paired changes.

    If version B fixes eight of 100 items that A missed but regresses five that A solved, its accuracy delta is (8 − 5)/100 = +3 percentage points. Show both sets. For uncertainty, resample paired item IDs together and recompute the difference. Keep related translations or attempts together when they share the same underlying problem.

  4. Measure the cost of the decision.

    A selector using 16 candidates adds serving work. Report total input and generated tokens, time to final usable answer, completed items, and the quality score for the same run. Calculate serving metrics · Benchmark field guide
