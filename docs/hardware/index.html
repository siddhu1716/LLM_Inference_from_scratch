Physical device

Recognize the module

The interactive board represents the 80 GB H100 SXM5 in a conventional PCIe-hosted HGX H100 server. SXM is the module form factor. HBM3 is the device's stacked high-bandwidth memory. The CPU keeps its own DRAM. The PCIe host link and the NVLink paths between GPUs serve different endpoints.

The shipping SXM5 configuration has eight GPU processing clusters, 66 texture processing clusters and two streaming multiprocessors (SMs) per texture processing cluster. NVIDIA lists 3.35 TB/s of peak device-memory bandwidth for the 80 GB SXM. Its 900 GB/s NVLink figure is aggregate bidirectional peer bandwidth. PCIe Gen5 ×16 has approximately 64 GB/s per direction before protocol overhead. These product figures express different transfers and cannot be added to estimate token throughput. Data movement

Follow one weight tile

  1. Load the checkpoint

    In this path a CPU-side loader reads checkpoint shards, prepares the selected device tensors and transfers them across PCIe. A pinned host buffer can support asynchronous DMA. The host must respect the buffer's lifetime until the operation finishes. Other systems can use direct storage paths or different host interconnects.

  2. Keep the weights resident

    The allocator reserves device addresses for the weights, runtime workspaces and KV cache. With a fully resident model, later decode steps reuse the weights in GPU memory. The new token ID, small control messages, and streamed output cost far less host traffic than reloading a model each token. Offloaded deployments have a different path.

  3. Read a tile

    A projection kernel loads weight and activation tiles from global addresses. A cache hit can satisfy a load without going out to HBM. A miss can bring a cache line through L2 from HBM. The kernel, address pattern and cache policy govern L1 behavior. Coalesced accesses group nearby addresses from a warp into fewer memory transactions.

  4. Stage and reuse operands

    Shared memory is explicitly managed scratch space for a block. Registers hold per-thread values and accumulators. A tiled kernel can load a chunk once and reuse it across many products. Hopper's Tensor Memory Accelerator can issue asynchronous multidimensional transfers into shared memory in suitable kernels. A consumer waits for the transfer barrier before reading the tile.

  5. Write the output

    The block computes its output tile and stores it to global addresses or passes a fused intermediate to the next operation on chip. A store may remain cached. The visibility and ordering needed by later work follow CUDA's memory and stream rules. The animation compresses this into one highlighted route. Hopper memory and tuning guide

Engine page vs. physical memory. A vLLM or SGLang KV allocator maps a request's token positions to cache locations inside large tensors. A GPU kernel ultimately reads device addresses. Cache lines, HBM transactions and engine KV block boundaries have different sizes and lifetimes. Follow the engine's KV address mapping

A block's threads execute on one SM and share its resources for the lifetime of the block. A 256-thread block contains eight warps. More than one block can reside on a single SM when register, shared-memory and thread limits permit it. On H100 the upper limit is 64 concurrent warps per SM. Resident warps can be waiting on dependencies. An SM scheduler selects eligible work.

Regular instructions use execution pipelines for loads, arithmetic and other operations. Matrix instructions can engage Tensor Cores with specific operand shapes and types. Hopper's wgmma.mma_async coordinates a warp group of four warps, or 128 threads, on supported kernels. The kernel can interleave tile preparation and computation. It must wait for async results before using their accumulators. CUDA programming model · Hopper occupancy limits · PTX warp-group matrix instructions

Count bytes and work for a toy tile

For C = A × B, multiply a 16 × 16 BF16 tile of A by a 16 × 16 BF16 tile of B. Each input contains 256 two-byte values, so the two inputs occupy 1,024 bytes. The tile produces 256 outputs with 16 multiply-adds each, or 8,192 floating-point operations when a multiply and add count separately. A separate FP32 store of C adds 1,024 output bytes.

This is arithmetic accounting for one mathematical tile. Real kernels can reuse A or B across tiles, accumulate across a longer K dimension and fuse the store. It establishes neither a specific hardware instruction nor an achieved throughput.

Data exchange

Choose the correct scope

Within one block Ordinary shared memory
One warp writes a shared tile and another warp in the same block reads it. A block-wide barrier such as __syncthreads() can order that producer–consumer exchange when participating threads reach it correctly. Other blocks separately allocate their own shared storage.
Across arbitrary SMs Global memory plus ordering
Kernel A writes a partial tensor. Kernel B in the same stream runs after A finishes and can read those addresses, possibly from L2. Different streams need an explicit dependency such as an event. Concurrent producer/consumer designs require a valid synchronization protocol and suitable memory scope. Calling a block barrier cannot synchronize a whole grid. An ordinary launch cannot rely on all blocks being resident simultaneously.
Within a Hopper cluster Distributed shared memory (DSM)
A cluster launch guarantees its blocks are co-scheduled within one GPC. A block can map another participating block's shared-memory segment and perform a remote access. A barrier establishes that the peer storage is initialized. Another synchronization point can ensure the remote accesses complete before block exit. The reachable storage belongs to the cluster's resident blocks. Hopper thread-block clusters and DSM
Across peer GPUs NVLink, NVSwitch and collectives
Each GPU has private device memory and its own SMs. In the eight-GPU HGX H100 platform, NVLink connects GPUs through NVSwitch. A tensor-parallel output projection may require a sum all-reduce of rank-local partial vectors. NCCL chooses transport and collective algorithms for the topology. PCIe or a network may carry traffic on other systems. Slow ranks can delay all participants. HGX physical topology · Work through a per-token reduction

Inference workload

Connect the board to a token

Prefill. Many known prompt positions can share a matrix multiply and reuse weights. The projection and FFN kernels can keep Tensor Cores busy. Attention kernels traverse the prompt with a causal mask, can tile the score calculation, and write per-layer KV. Very long contexts can make the attention portion dominate.

Decode. A single request adds one new position per ordinary forward step. Its queries read earlier KV, its projections read the weights, and it appends new KV for that position. At a small batch size, memory traffic can dominate. Continuous batching lets one weight tile serve more sequences in the same iteration. The actual bottleneck depends on batch, context, precision and kernels. Inspect embeddings, attention and FFN · Diagnose a serving bottleneck

Estimate an optimistic decode bandwidth floor

Suppose a hypothetical decoder reads 16 GB of weights from HBM for one isolated single-sequence forward step. At the product's 3.35 TB/s peak, bytes ÷ bandwidth gives about 4.78 ms for that assumed transfer. Include KV traffic, kernel execution, scheduling, communication, and imperfect use of bandwidth when comparing against a measured token gap. If the weights are reused across a batch, this floor describes that batch's weight-read time. NVIDIA H100 bandwidth specification
