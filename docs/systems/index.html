Memory budget

What has to fit?

The model's weights stay on the device across requests. Each active sequence also needs a key–value cache (KV) holding attention history for its tokens. The runtime needs room for temporary results, graph buffers and other allocations. Budget all three before increasing concurrency.

Consider a hypothetical dense decoder with 8 billion parameters. At two bytes per weight it needs 16 billion bytes, or 14.90 GiB. Each cached token in our example uses 128 KiB across all layers. With 4,096 cached tokens, one conversation needs another 0.50 GiB.

Derive the result and check its assumptions

KV bytes/token = 2 × layers × KV heads × head dimension × bytes/element

The leading 2 counts keys and values. Use KV heads from the model configuration. With grouped-query attention, several query heads share each KV head. For 32 layers, 8 KV heads, 128 dimensions and two-byte elements, this gives 131,072 bytes. Multiply by the sum of cached tokens across sequences. This example assumes equal lengths and full attention in every layer.

The worksheet models dense, unsharded weights and private, uncompressed KV. The reserve is your estimate for runtime overhead. Block rounding, quantization scales, replicated tensors, alignment, prefix sharing, sliding windows and latent-attention caches can change the measured result. A GiB is 2³⁰ bytes. Confirm headroom against your actual engine allocations.

Single-GPU tuning

Follow the expensive operation

Prefill evaluates the known prompt positions together and produces the logits for the first output token. Each subsequent decode step consumes the most recently sampled token. It reads the relevant history and appends fresh KV. A long prefill can keep the arithmetic units busy. A small decode batch often spends more time moving weights and KV through device memory.

Requests queue behind long prompts

Continuous batching lets finished sequences leave and waiting requests enter at scheduling boundaries. Chunked prefill gives a long prompt a slice of the iteration's token budget so short decode steps can also run. A smaller slice can smooth token gaps while lengthening the wait for a long prompt's first token. Sweep the budget using the same prompt mix. Record time to first token and p95 inter-token latency. vLLM tuning guide

Many prompts begin with the same document

Arrange the stable document before the changing question. A prefix cache can reuse KV for matching leading token sequences when model and cache settings agree. Two articles with similar meaning may tokenize differently and miss immediately. Compare cold and warm runs, matched prompt tokens and eviction rates. Reuse reduces prompt processing while output tokens still require decoding. Automatic prefix caching

Weights or growing KV exhaust memory

First separate weight memory from per-request KV using the worksheet. Weight quantization reduces the persistent footprint. Weight-only quantization leaves KV precision independently configurable. Availability of suitable kernels and scale metadata affects speed and size. Compare held-out accuracy with the same prompts and decoding settings. For KV pressure, cap active tokens or use compatible KV quantization. Paged allocation lets a sequence grow by blocks, with possible waste in each partly filled final block. Quantization notes · PagedAttention paper

Attention spills large intermediates to memory

For standard full attention over a long prompt, explicitly writing the score matrix costs memory proportional to sequence length squared. FlashAttention processes tiles and maintains an online normalization so the full score matrix can stay out of high-bandwidth memory. Full attention still evaluates the causal query–key pairs. Compare memory traffic and wall time at several prompt lengths. FlashAttention paper

One conversation emits tokens slowly

With speculative decoding, a cheaper proposer drafts several tokens and the target model scores them together. A matching accept/reject procedure preserves the target sampling distribution. When drafts frequently diverge or verification competes with other work, the extra computation can erase the gain. Measure accepted tokens per verification, wall time, and output throughput under load. Speculative decoding paper · Worked sampling example

The GPU timeline has gaps between short kernels

Trace the CPU launch thread and its GPU stream together. For recurring shapes, CUDA Graph replay can reduce repeated launch work. Capture requires compatible execution paths and may reserve extra memory. Compare warmed-up decode latency, capture coverage and the KV budget with graph replay enabled and disabled. Kernel and graph notes · Nsight Systems guide

GPU topologies

What crosses the link?

A rank is a participating process, usually assigned to a GPU. A replica is a complete model-serving group and may contain several ranks. Trace one request to see which ranks must exchange data before the next token is ready.

Explore a parallel strategy

Tensor parallelism

Several GPUs compute pieces of the same layer for the same batch.

CollectiveCombine partials

In a row-sharded output projection, each rank computes a partial sum for the same output. An all-reduce can sum the partials and make the complete result available to all participants. Repeating collectives in the token loop makes link latency matter. Try TP when a model exceeds one GPU's memory and the GPUs share a fast link.

Assign consecutive groups of layers to different GPUs or nodes.

For a 32-layer model, stage A sends an activation tensor after layer 15 to stage B. Independent microbatches can occupy different stages at once. A lone request still traverses both stages before sampling. Uneven stage times leave bubbles. Time each stage before choosing the split.

With two independent dense replicas, each stores a complete model and its own KV. The router can send a new chat to the shorter queue. Place four GPUs on two nodes

Suppose a model needs 60 GiB for weights. Each node has two 40 GiB GPUs on a fast local fabric, and each replica needs 12 GiB of runtime and KV space in total. With even sharding, two local TP ranks each need about (60 + 12) ÷ 2 = 36 GiB. Put one replica on each node and route requests between them. Each reply requires only local TP communication.

If the total grows above 80 GiB, that replica no longer fits on one node. A candidate with TP 2 inside each node and PP 2 across nodes spreads one model over all four GPUs. Hidden states now cross nodes at the stage boundary. Measure individual rank memory, stage balance and tail latency on the actual interconnect. vLLM parallelism and scaling

Prefill handoff

Move a conversation between pools

Tensor and pipeline parallelism partition a model's calculation. Prefill/decode disaggregation assigns two phases in the life of the same request to separately sized worker pools. Long prompts can be processed away from workers streaming existing replies.

Follow the cache handoff and its failure path · Trace attention–FFN dispatch and combine · Estimate link traffic

  1. Route and reserve

    The serving layer pairs a prefill worker with a decode destination. The system must identify the request and reserve enough destination space before the incoming cache can be installed.

  2. Evaluate the prompt

    The prefill group builds the prompt KV. Its last prompt position also yields the logits for the first generated token.

  3. Transfer the KV and continuation state

    A connector copies the necessary KV blocks and communicates which sequence, token positions and destination slots they belong to. Depending on the engine, transfer can overlap portions of prompt execution.

  4. Resume, stream and reclaim

    The decode worker consumes the sampled token with the transferred context, then repeats until the stop condition. The service must release transfer reservations and local blocks on completion, cancellation or a failed handoff.

Estimate the price of the handoff

Our 4,096-token prompt has 0.50 GiB of KV. A dedicated link delivering 25 GiB/s needs at least 20 ms to move that payload in isolation. Queueing, software setup, layout conversion and competing transfers can raise the cost. Measure time until the decode worker is ready, along with the gap between the first and second streamed tokens.

If long prefills disturb ongoing decodes, compare disaggregation with a colocated, chunked-prefill baseline. A saturated connector or an empty decode pool can reverse the result. Compare requests meeting both latency targets per GPU. DistServe study · SGLang disaggregation guide

Serving measurements

Prove the change helped

Calculate TTFT, ITL, TPOT and end-to-end latency from a stream, then choose an online or offline benchmark runner.

Give the serving system a workload and a target before changing a knob. For example, replay a mix of short chats and document questions, with a target first token within 1 s and average time per subsequent token within 50 ms for each qualifying request.

Read one client trace

  1. 0 msSent
  2. 320 msToken 1
  3. 360 msToken 2
  4. 420 msToken 3

TTFT is 320 ms. The two inter-token gaps are 40 and 60 ms. Average time per output token after the first is (420 − 320) ÷ 2 = 50 ms. A one-token reply has no such average. If the server bundles tokens, timestamped chunks measure delivery gaps. vLLM benchmark definitions

  1. Record the workload. Pin the model revision, engine version, device layout, precision and sampling settings. Record input and output length distributions, shared-prefix frequency and the arrival pattern. Separate startup, cold-cache and warm-cache trials.
  2. Find the load limit. Sweep offered requests per second, then replay a burst. Record completed requests, errors, cancellations, queue time and p50/p95/p99 latency. Serving 90 qualifying requests in 30 seconds gives 3 requests/s of goodput under your stated targets.
  3. Attribute the delay. If time to first token rises, split queue wait from prompt processing. For decode stalls, inspect active tokens, free KV blocks, preemptions, per-stage work, and communication time. Place scheduler events and GPU kernels on the same timeline. Nsight Systems reference
  4. Test one explanation. Repeat the trace with exactly one change. Compare output quality for precision changes. For distributed changes, compare goodput per GPU and actual time in collectives. Report run-to-run variability and rejected requests with the throughput figure.
Diagnose three failure signatures
  • Out of memory during startup. Identify whether loading weights, capturing graphs or allocating KV failed. Check the largest rank. A second data-parallel replica has the same per-replica fit requirement.
  • Requests slow down as conversations grow. Plot live tokens and preemptions while holding the arrival rate fixed. Recompute after cache eviction can consume time that would otherwise serve new work. Retry with a smaller concurrent token budget.
  • One node stalls the whole group. Compare the same collective across ranks and inspect which rank arrived late. A slow upstream kernel, an imbalanced expert or a congested link can look similar in the aggregate. For a failed worker, drain its serving group and bound retries to avoid adding traffic to an overloaded queue.

Reproduce the memory worksheet and the four-rank plan

After installing the package, start python and enter this example. The first line of output should be 131072 4.0, giving bytes per cached token and total GiB. The following tuples identify the global, replica and tensor ranks for two two-GPU replicas.

from mini_infer.optimizations.kv_cache_estimator import estimate_kv_cache
from mini_infer.optimizations.parallel_planning import ParallelismConfig, plan_parallelism

cache = estimate_kv_cache(
    num_layers=32, num_kv_heads=8, head_dim=128,
    sequence_length=4096, batch_size=8, bytes_per_element=2,
)
print(cache.bytes_per_token_per_sequence, cache.total_gib)

plan = plan_parallelism(
    num_layers=32, hidden_size=4096, num_attention_heads=32,
    num_experts=1, config=ParallelismConfig(data=2, tensor=2),
)
print([(r.rank, r.data_rank, r.tensor_rank) for r in plan.ranks])

Ranks 0 and 1 process one replica together. Ranks 2 and 3 serve the other replica. Try changing the config to ParallelismConfig(pipeline=2, tensor=2) and printing r.layer_range for each rank. The two groups now own successive halves of one model.
