    Keep two distinctions in mind. Utilization is the fraction of a resource doing useful work during an interval: for example, a GPU busy 60 seconds in a 100-second window has 60% busy-time utilization. Saturation means demand has reached the resource's effective service limit, so additional work waits or is rejected. A system can show modest average utilization and still be saturated for short bursts, on one memory channel, or on one queue. Conversely, high utilization can be healthy when queues remain short and objectives are met. Never diagnose saturation from one utilization gauge.

    Latency percentiles describe a distribution. p50 is the median: half of observations are faster. p95 leaves five percent slower, and p99 leaves one percent slower. If p50 is 400 ms and p99 is 8 s, “average latency” hides a painful tail. In streaming generation, measure TTFT (time from arrival until the first token) separately from ITL (time between successive output tokens). Goodput counts work that is both correct and within the promised objective; raw throughput counts late, retried, or unusable work too.

    Day 19 · Hardware foundations

    GPU architecture: a factory for parallel math

    Learn why the fastest kernel is usually the one that moves fewer bytes, how warps turn threads into execution, and why “peak FLOPS” is a ceiling rather than a prediction.

    By the end, you can: trace data from HBM to a register; explain SMs, warps, occupancy, coalescing, and divergence; estimate a memory-bandwidth lower bound; and choose the next metric when a GPU appears “underutilized.”

    A beginner analogy: the restaurant tower

    Imagine a tower containing many identical restaurant kitchens. The whole tower is the GPU; each kitchen is a streaming multiprocessor, or SM. A kitchen has several workstations for ordinary chopping and specialized machines for rapidly preparing trays of the same dish. Those machines resemble CUDA cores and Tensor Cores. Orders arrive as large groups of tiny tasks called threads. The head chef does not schedule each task independently: workers move in synchronized teams, like a warp of commonly 32 threads.

    Ingredients may sit in a cook's hand (registers), on the kitchen counter (shared memory), in a shared pantry downstairs (L2 cache), or in a vast warehouse outside the tower (HBM). The warehouse is large and fast compared with ordinary computer memory, yet the trip is expensive compared with reaching a counter. Great GPU programs reuse ingredients near the cooks. Poor programs repeatedly send someone to the warehouse. This analogy also explains branch divergence: if half a team prepares soup while half prepares bread, the synchronized team may execute one path and then the other, leaving workers idle.

    Terminology

    TermPractical meaning
    SMA hardware cluster that schedules warps and owns execution units, registers, and on-chip shared memory.
    WarpA fixed group of threads issued together. Threads are logically separate but execute instructions in lockstep-like fashion.
    RegisterThe smallest and fastest per-thread storage. Too many registers per thread can reduce resident warps.
    Shared memorySmall programmer-managed on-chip memory shared by threads in one block. It supports deliberate data reuse.
    L2 cacheA larger on-chip cache shared across SMs. Hardware manages it and it can reduce trips to HBM.
    HBMHigh Bandwidth Memory holding weights, KV cache, and large tensors. It offers capacity but is far away relative to on-chip storage.
    OccupancyResident active warps divided by the architecture's maximum resident warps. It helps hide stalls but is not itself performance.
    CoalescingNeighboring threads access neighboring addresses, allowing memory requests to combine efficiently.

    The data lifecycle, step by step

    1. HBMweights and tensors
    2. L2shared cache lines
    3. SM tileshared-memory reuse
    4. Registersthread operands
    5. Unitsmatrix/scalar work
    6. Storeresult or next tile
    1. The host launches a kernel with a grid of thread blocks. Hardware assigns each block to one SM; a block does not migrate midway.
    2. The SM divides its block into warps. Warp schedulers choose a ready warp each issue opportunity, often switching when another warp waits on memory.
    3. Loads request cache lines. A hit in L2 avoids HBM; a miss travels to HBM. Coalesced addresses need fewer transactions than scattered addresses.
    4. Threads stage a reusable tile in shared memory and synchronize. Computation then consumes values from shared memory and registers many times.
    5. Tensor Cores accelerate supported matrix operations, while other units handle indexing, activation functions, and general arithmetic.
    6. Results remain in registers when a fused next operation can consume them; otherwise they are written outward. A write to HBM may later become another kernel's read.

    Worked example: the bandwidth floor

    Consider an illustrative 7-billion-parameter model stored with 2 bytes per parameter. Its weights occupy roughly 14 GB. Suppose one decode step must stream those weights once and the device sustains, not merely advertises, 2.8 TB/s for this access pattern. Ignore KV traffic and overhead for a lower bound.

    time ≥ bytes moved ÷ sustained bandwidth = 14 GB ÷ 2,800 GB/s = 0.005 s = 5 ms

    The ideal upper bound is therefore about 1 ÷ 0.005 = 200 decode steps/s for the entire batch. If the batch has 20 sequences and each step produces one token per sequence, the ideal aggregate is 4,000 tokens/s, before overhead. Batch size improves weight reuse across sequences; it does not make the 14 GB disappear. A measured 9 ms step implies an effective 14/0.009 ≈ 1,556 GB/s, suggesting incomplete bandwidth use or additional bytes. Symbols: time is seconds per step, bytes moved includes required reads/writes, and sustained bandwidth is measured for the real workload.

    Equations and operational metrics

    arithmetic intensity I = operations ÷ bytes moved; bandwidth roof = I × sustained bandwidth

    Compare the bandwidth roof with the compute roof. The smaller is the first-order limit. Low-intensity decode is commonly memory-bound; large prefill matrix multiplications can be compute-bound. Watch SM active time, Tensor Core activity, HBM throughput, L2 hit rate, achieved occupancy, register spills, warp stall reasons, kernel duration, and power/thermal throttling. Utilization answers “was something scheduled?” or “was this unit active?” depending on the metric definition. Saturation is evidenced by full service capacity plus queue growth, latency growth, or admission rejection. Always read the vendor/tool definition.

    Failure modes and common mistakes

    • Treating peak TFLOPS as expected application throughput.
    • Increasing occupancy while causing register spills to local memory.
    • Using uncoalesced access that multiplies memory transactions.
    • Adding branches inside hot warps and creating divergence.
    • Optimizing arithmetic while profiles show memory stalls.
    • Comparing GPU utilization between tools with different sampling semantics.

    Decision guide

    HBM near ceiling, compute low: reduce bytes, quantize, fuse, cache, or batch. Compute near ceiling: use supported lower precision, improve tiling, or add compute. Both low: inspect tiny kernels, launch gaps, synchronization, CPU feeding, and dependencies. Tail spikes only: inspect contention, clock changes, page faults, and co-tenants rather than averages.

    Review questions and answers

    1. Why can shared memory help even though HBM is called “high bandwidth”?

    “High” is relative to normal external memory. Shared memory is physically on the SM and can serve reused tiles with much lower latency and far higher local bandwidth. The win appears when one HBM load supports many calculations.

    2. Is 100% occupancy always the goal?

    No. Enough resident warps can hide latency, but chasing maximum occupancy may require smaller tiles or fewer registers and make each warp less efficient. Optimize measured kernel time and useful throughput, not the occupancy gauge alone.

    3. What is warp divergence?

    Threads in one warp choose different control paths. Hardware must execute the relevant paths under masks, so some lanes do no useful work during each path. Different warps may take different paths without the same within-warp penalty.

    4. Why is decode often memory-bound?

    Each step performs a relatively small amount of work for each byte of model weight fetched, particularly at a small batch. That low arithmetic intensity reaches the bandwidth roof before the compute roof.

    5. What proves saturation better than GPU utilization?

    A resource operating near its measured service ceiling while pending work, latency, or rejection grows. Queue depth and service rate connect demand to capacity; a single averaged utilization percentage does not.

    Hands-on exercises without a GPU

    1. Use a spreadsheet to vary model bytes, sustained bandwidth, and batch size in the worked example. Plot tokens/s and mark which assumptions are optimistic.
    2. Write a short JavaScript or spreadsheet simulation in which 32 lanes take two branches with different probabilities. Count active-lane instruction slots to visualize divergence.
    3. Draw four memory tiers on paper and place model weights, attention tiles, accumulators, and KV pages in the most plausible tier.

    Day 20 · Hardware selection

    GPU generations: compare workloads, not headlines

    Hopper, Ada, and Blackwell belong to different product goals. A responsible comparison pins the exact SKU, form factor, precision, software, power envelope, and workload before drawing conclusions.

    By the end, you can: describe the inference-relevant direction of recent architectures; distinguish datacenter and client products; build a benchmark scorecard; and reject comparisons that mix unsupported precision, theoretical peaks, or unverifiable specifications.

    A beginner analogy: choosing a delivery fleet

    Comparing “a Hopper” with “an Ada” or “a Blackwell” is like comparing a freight locomotive, a delivery van, and a newer family of vehicles using only top speed. The locomotive may carry far more cargo and couple to other locomotives; the van may be easier to buy and fit in a garage; the new family may include both giant datacenter systems and smaller products. The correct question is not “Which generation wins?” It is “Which exact product completes my route, cargo, reliability, and budget objective?”

    Hopper datacenter products made FP8-oriented transformer execution and high-speed scale-up central design points. Ada products are widely encountered in workstation or consumer settings and can be excellent for development and models that fit local memory, but generally target a different deployment envelope. Blackwell products extend low-precision and large-system options, yet capability, memory, interconnect, availability, price, and supported software differ by SKU and date. Specifications change with product variants and software releases. This chapter intentionally avoids promising a fixed performance multiplier or repeating unverified figures: consult the current official datasheet and reproduce a workload benchmark.

    PrecisionNumeric format such as FP16, BF16, FP8, or a 4-bit format. Support and accuracy procedures matter as much as nominal bits.
    Transformer EngineHardware/software machinery that manages supported lower-precision transformer operations and scaling.

    A responsible comparison lifecycle

    1. Definemodel and SLO
    2. Verifyexact SKU specs
    3. Qualifyquality and software
    4. Benchmarksame envelope
    5. Costgood tokens/$
    6. Stresstails and failures
    1. Freeze the model version, sequence-length distribution, output lengths, quality tolerance, TTFT/ITL objectives, and availability target.
    2. Record exact orderable products, memory size, form factor, interconnect topology, host requirements, driver/runtime matrix, and provider quota. Date every source.
    3. Confirm the engine actually has optimized kernels for the desired precision and shape. Run quality evaluation; lower precision is not “free speed.”
    4. Warm both systems, replay identical requests, and report p50/p95/p99 TTFT and ITL plus goodput. Keep batching policy and power settings visible.
    5. Include acquisition rate, host/network/storage, replicas needed for redundancy, idle capacity, engineering effort, and rejected work.
    6. Test long contexts, mixed prompts, cache misses, thermal steady state, failures, and a full hour rather than one favorable minute.

    Worked example: goodput beats peak throughput

    Team North tests exact device A and device B with one model and the same quality score. A completes 1,800 output tokens/s, but only 72% of tokens belong to requests meeting TTFT ≤ 1.0 s and ITL ≤ 60 ms. B completes 1,500 tokens/s, and 94% meet both limits. Device-hour rates are illustrative: A costs $4.20/h and B costs $4.80/h.

    goodput = raw throughput × success-within-SLO fraction

    A goodput = 1,800 × 0.72 = 1,296 tokens/s. B goodput = 1,500 × 0.94 = 1,410 tokens/s. A costs $4.20 ÷ (1,296 × 3,600) × 1,000,000 ≈ $0.90 per million good tokens. B costs about $0.95. A remains slightly cheaper here, while B delivers more useful tokens per second and may need fewer replicas to satisfy a demand peak. The “winner” depends on the capacity and SLO constraint, not a generation label. Symbols: success-within-SLO fraction is between 0 and 1; cost includes a device-hour rate only in this simplified example.

    Operational metrics, evidence, and generation-aware reasoning

    Track goodput per device, per watt, and per dollar; p50/p95/p99 TTFT; p50/p95/p99 ITL; input and output tokens/s; first-pass quality; memory headroom; scale-up collective time; power; thermal clocks; error rate; cold-start duration; and engine compilation time. Hopper may be attractive where mature FP8 paths and tightly coupled datacenter scaling matter. Ada can be sensible for small, local, lower-concurrency deployments where purchase accessibility dominates. Blackwell may be compelling where its supported low-precision paths, memory system, or system topology match the workload. Those are decision hypotheses, not universal rankings.

    Failure modes and common mistakes

    • Comparing one architecture name to another without exact SKUs.
    • Quoting sparse or low-precision peak numbers when the model uses a different mode.
    • Assuming a numeric format preserves quality without calibration and evaluation.
    • Ignoring interconnect topology for tensor-parallel models.
    • Using averages while one candidate violates p99 TTFT.
    • Copying price, availability, or prerelease specifications without source dates.
    • Benchmarking different engine versions, context distributions, or batching policies.

    Decision guide

    Development and fits locally: prioritize accessibility, adequate memory, and software support. Latency-critical scale-up: prioritize mature kernels, memory headroom, topology, and tail benchmarks. Throughput service: compare goodput per dollar at the required quality. New generation: add supply risk, qualification work, and fallback capacity. Unknown future spec: model a range and mark it as an assumption; do not present it as fact.

    Review questions and answers

    1. Why is an architecture name insufficient for capacity planning?

    A generation contains multiple products with different memory, clocks, form factors, power, and links. Cloud instances add host and topology differences. Planning needs an exact deployable unit.

    2. What must accompany a peak FLOPS number?

    Precision, operation shape, sparsity assumption, clock/power condition, and whether it is theoretical or measured. Then show application goodput under a defined workload.

    3. How do you compare FP8 with a 4-bit path?

    First qualify both against the same model-quality suite. Then benchmark with supported kernels and identical service objectives. Bit width alone neither proves speed nor acceptable accuracy.

    4. Why might a slower device be the fleet choice?

    It might be available sooner, cheaper after utilization, easier to operate, sufficiently memory-rich, or more stable in the chosen software. Fleet economics include supply and tails, not only single-device speed.

    5. What makes a comparison reproducible?

    Publishing exact hardware, software versions, model/checkpoint, precision, quality method, request distribution, batching, warm-up, measurement interval, power state, and percentile results.

    Hands-on exercises without a GPU

    1. Create a scorecard with quality, TTFT p99, ITL p99, goodput, memory headroom, hourly cost, availability, and engineering risk. Score three hypothetical SKUs.
    2. Find two official current datasheets and list every condition attached to their headline numbers. Do not copy the numbers into your scorecard until the units and modes match.
    3. Recalculate the worked example while varying the SLO pass fraction. Find when device B becomes cheaper per good token.

    Day 21 · Placement and isolation

    MIG and capacity planning: make fit, speed, and resilience agree

    Memory fit is the admission ticket, not the finish line. A sound plan reserves KV space, respects interconnect boundaries, protects failure domains, and leaves enough headroom for real traffic.

    By the end, you can: estimate model and KV memory; distinguish partitioning from parallelism; explain MIG's isolation value; compute replica demand; and build a capacity plan with N+1 headroom.

    A beginner analogy: an apartment building

    A physical GPU resembles an apartment building. Giving one tenant the whole building offers every room and hallway. MIG—Multi-Instance GPU—creates supported, hardware-isolated apartments with assigned rooms and utilities. One tenant cannot wander through another tenant's memory. That is different from placing several roommates in one open loft using software process limits: the loft may be efficient, but contention and isolation are less predictable.

    Tensor parallelism is not apartment partitioning. It is one very large tenant spreading a job across several buildings and exchanging partial results repeatedly. Fast private walkways make that cooperation practical; slow city roads add delay at every layer. Replication is different again: several independent restaurants serve separate customers. Capacity planning chooses among partition, parallelize, and replicate, sometimes combining all three.

    Terminology

    TermMeaning
    MIGA supported hardware partition mode that divides eligible GPUs into isolated instances with assigned compute and memory resources.
    ProfileA vendor-defined partition shape. Available profiles depend on the exact GPU and configuration; verify current documentation.
    VRAM/HBM headroomMemory intentionally left for KV cache, temporary workspaces, fragmentation, and bursts.
    Tensor parallelism (TP)One model operation is split across devices, requiring frequent communication.
    Pipeline parallelismDifferent model stages reside on different devices; activations pass between stages.
    ReplicaAn independent serving copy that can process separate requests and improve availability.
    Failure domainA set of resources likely to fail together, such as one host, power domain, zone, or region.
    N+1Enough capacity for normal demand plus one defined unit failure.

    Capacity-planning lifecycle

    1. Measuretraffic and lengths
    2. Fitweights + KV + work
    3. Topologyplace parallel ranks
    4. Partitionwhole GPU or MIG
    5. ReplicateSLO and failures
    6. Validateload and failover
    1. Build distributions, not a single average: arrivals by minute, input/output length, model mix, tenant, and percentile latency objectives.
    2. Estimate weight bytes as parameters × bytes per parameter plus quantization metadata. Add runtime workspace and a fragmentation reserve.
    3. Estimate KV bytes from layers, KV heads, head dimension, two tensors (K and V), bytes per element, and active cached tokens. Confirm against the real engine because layouts vary.
    4. If the model cannot meet fit or latency on one device, choose parallelism inside the fastest available fabric boundary. Benchmark collective time.
    5. Use MIG when supported profiles fit independent smaller workloads and isolation/packing outweighs the loss of flexible pooling. Do not assume every GPU or mode supports every profile.
    6. Replicate across failure domains, reserve maintenance and N+1 room, then test loss of a device or host at peak-safe demand.

    Worked example: memory and service capacity

    An illustrative slice offers 40 GiB. A 13B model at 2 bytes/parameter needs about 26 GB for raw weights. Budget 3 GiB for engine workspaces and 3 GiB as a safety/fragmentation reserve, leaving about 8 GiB for KV. Suppose the engine's measured KV footprint is 0.5 MiB per cached token across the full model. Then the slice holds approximately 8 × 1,024 MiB ÷ 0.5 MiB = 16,384 cached tokens.

    With a planning context of 2,048 cached tokens/request, memory allows 8 active requests. Load testing shows the SLO-safe target is only 6 concurrent requests and each request spends 3 seconds in service. By Little's Law, one slice safely supports about 6 ÷ 3 = 2 requests/s at that latency envelope. Forecast peak is 7 requests/s, so the service needs ceiling(7 ÷ 2) = 4 slices for traffic. N+1 adds one slice, yielding 5 slices. Fit said eight requests; measured tail performance reduced the operational target to six. That difference is headroom, not waste.

    KV bytes = active cached tokens × measured bytes/token; replicas = ceil(peak arrival rate ÷ safe rate/replica) + failure reserve

    Operational metrics and equations

    Symbols: P is parameter count, b is storage bytes/parameter, L layers, Hkv KV heads, d head dimension, and T cached tokens. A planning approximation is weight bytes ≈ P × b and KV bytes ≈ 2 × L × Hkv × d × b × T; “2” represents key and value. Engine paging, alignment, quantization, and parallel sharding can change reality. Monitor allocated/reserved/free HBM, KV occupancy, allocation failures, fragmentation, per-slice SM activity, throttling, queue depth, OOM restarts, collective latency, link throughput, and per-tenant p99. Capacity is SLO-safe goodput, not a count of partitions.

    Failure modes and common mistakes

    • Fitting weights exactly and leaving no KV or workspace room.
    • Assuming memory isolation guarantees identical latency under every shared-host condition.
    • Stretching tensor parallelism across a slow link without measuring collectives.
    • Putting all replicas on one host, creating one failure domain.
    • Planning from maximum context for every request—or from average context for all requests—without distribution-aware admission.
    • Hard-coding MIG profiles from another GPU model.

    Decision guide

    One model nearly fills the GPU: keep the whole device. Several small, independent tenants need isolation: evaluate MIG. One model spans devices: keep TP inside the fastest fabric where possible. Throughput scales independently: add replicas. Traffic is uncertain: preserve flexible whole-GPU pools unless measured packing savings justify fixed partitions.

    Review questions and answers

    1. How does MIG differ from tensor parallelism?

    MIG divides one physical GPU into isolated instances for independent workloads. Tensor parallelism combines multiple devices or partitions to execute one model operation and requires communication.

    2. Why is “the model fits” insufficient?

    Serving also needs KV cache, activations/workspaces, allocator reserve, and enough performance headroom to meet tails. An exact weight fit may fail on the first real request.

    3. What is N+1 capacity?

    The fleet can carry planned demand after losing one specified capacity unit. The unit must be explicit—a slice, GPU, host, or zone—because each produces a different requirement.

    4. When can more tensor-parallel GPUs hurt?

    When reduced compute time is smaller than added collective and synchronization time, particularly across slower links or for small batches.

    5. Why use measured KV bytes per token?

    The formula is useful for intuition, but engines add page size, alignment, metadata, sharding, and data-type details. Measurement catches implementation reality.

    Hands-on exercises without a GPU

    1. Build a spreadsheet with model size, workspace, reserve, bytes/token, and context distribution. Compute concurrency under p50, p95, and maximum contexts.
    2. Draw three placements for six replicas across three hosts. Remove each host in turn and calculate surviving capacity.
    3. Model TP communication as fixed latency plus bytes/bandwidth. Find the tensor size at which two hypothetical interconnects differ materially.

    Day 22 · Reproducible serving

    Containers, the NVIDIA runtime, and NIM concepts

    A container packages user-space software; it does not contain a magical GPU. Production readiness depends on the host driver, runtime plumbing, model loading, probes, immutable versions, and clean termination.

    By the end, you can: distinguish image from container; trace GPU access; explain NIM as a productized inference microservice concept; design startup, liveness, and readiness probes; and identify unsafe image and secret practices.

    A beginner analogy: a sealed kitchen kit

    A container image is a sealed kitchen kit containing recipes, utensils, and labeled ingredient versions. A container is one kitchen opened from that kit. The building still supplies gas and electricity—the host kernel and GPU driver. The NVIDIA container tooling is the certified connector that makes selected GPU devices and driver libraries visible inside the kitchen. Packing a stove manual inside the box does not create a gas line; similarly, bundling a CUDA user-space runtime does not replace the compatible host driver.

    NVIDIA NIM can be understood as an opinionated, supported inference microservice package: an API contract, optimized runtime/engine choices for supported combinations, health endpoints, and operational integration. Its exact model catalog, licensing, profiles, and features evolve, so treat current vendor documentation as the authority. NIM can shorten time-to-service for a supported path; a custom image preserves control over kernels, scheduling, APIs, and unusual models.

    Terminology

    TermOperational meaning
    ImageImmutable layered filesystem plus metadata used to create containers.
    ContainerAn isolated process tree running from an image with configured mounts, network, limits, and devices.
    Registry/digestA distribution service and a content-addressed immutable identifier. Pinning a digest avoids a moving tag.
    Host driverKernel-level software controlling the GPU. Containers usually rely on it rather than shipping a replacement.
    NVIDIA Container ToolkitHost-side integration that injects requested GPU devices and compatible driver components into a container.
    Startup probeAllows a slow-loading process time to initialize before liveness failures count.
    Liveness“Should this process be restarted?” It detects a deadlocked or irrecoverable process.
    Readiness“Should this instance receive new traffic now?” It can be alive but not ready while loading, draining, or overloaded.

    Container-to-ready lifecycle

    1. Pullverify digest/signature
    2. Createmounts, limits, GPU
    3. Startprocess and config
    4. Loadweights and engine
    5. Warmcompile and test
    6. Readyjoin endpoints
    1. A build creates reproducible layers from a pinned base and locked dependencies. Security scanning and a software bill of materials run before promotion.
    2. The node pulls by digest. The orchestrator sets a read-only root where possible, a non-root user, secrets, model volume/cache, memory/CPU limits, and an explicit GPU request.
    3. The container runtime creates namespaces and cgroups; NVIDIA runtime hooks expose only allocated devices and suitable driver libraries.
    4. The server validates configuration, loads tokenizer and weights, reserves KV pages, creates or selects an engine, and may compile kernels. Liveness can be true while readiness stays false.
    5. A startup probe protects this long initialization. A warm-up request exercises representative paths. Readiness turns true only after dependencies and admission capacity are usable.
    6. During shutdown, readiness turns false first, endpoint removal propagates, active streams drain, state/metrics flush, and the process exits before the grace deadline.

    Readiness versus liveness, precisely

    A model server at PID 1 can answer a tiny local health request while still loading 100 GB of weights. It is live but not ready. Restarting it because readiness is false would reset loading forever. Conversely, a server can be ready for hours and then deadlock: liveness should fail and trigger replacement. Overload usually makes readiness false only if the instance intentionally sheds new traffic; do not make liveness depend on a remote database or temporary queue spike, or a shared dependency outage will restart the whole fleet.

    Worked example: cold pull and readiness budget

    An image has 11 GiB of layers. A fresh node pulls at an effective 220 MiB/s: 11 × 1,024 ÷ 220 ≈ 51 seconds. It unpacks in 18 seconds. A 28 GiB model downloads from a local cache at 700 MiB/s, about 41 seconds, then engine initialization and warm-up take 35 seconds. Total estimated startup is 51 + 18 + 41 + 35 = 145 seconds.

    Configure a startup window comfortably above observed p99, perhaps 240 seconds in this illustrative environment, rather than making liveness kill the process at 30 seconds. Readiness remains false until warm-up succeeds. With four layers unchanged and only a 20 MiB application layer updated, warm-node deployment transfer becomes roughly 20/220 ≈ 0.09 seconds plus metadata instead of another 51-second full pull. Symbols: size and throughput must use matching units; effective throughput includes network, registry, disk, decompression, and concurrency.

    cold-start time ≈ provision + pull + unpack + model fetch + engine build/load + warm-up

    Operational metrics and operating signals

    Measure image pull and unpack time, model download/cache hit, engine build/load time, start-to-live, start-to-ready, readiness transitions, probe latency/failures, container restarts, OOM kills, GPU discovery errors, driver/runtime version labels, resident memory, HBM allocation, warm-up result, and termination drain duration. Record image digest and model digest on every request trace. That makes “which artifact served this token?” answerable.

    Failure modes and common mistakes

    • Using an unpinned latest tag or broad dependency ranges.
    • Baking credentials into image layers or build arguments.
    • Assuming container CUDA user space works with any host driver.
    • Marking ready when the HTTP socket opens but before weights load.
    • Using the same remote-dependent endpoint for liveness and readiness.
    • Embedding frequently changed giant weights in the application image without evaluating cache tradeoffs.
    • Running as root with every GPU exposed.

    Decision guide: NIM or custom?

    Prefer an evaluated NIM path when the exact supported model/GPU combination, API, quality, licensing, and operational contract fit and deployment speed matters. Prefer custom for novel models, kernels, schedulers, APIs, portability, or deep observability needs. In both cases, pin artifacts, qualify performance, scan supply chain, and own readiness/draining behavior.

    Review questions and answers

    1. Does a container include the GPU driver?

    Normally it includes compatible user-space CUDA libraries while using the host kernel driver. Runtime integration exposes driver libraries and allocated device nodes. Compatibility must be checked.

    2. Why can liveness be true while readiness is false?

    The process may be healthy but temporarily unable to serve—loading weights, warming kernels, draining, or intentionally out of rotation. Restarting a live initializer would be harmful.

    3. Why pin an image digest?

    A tag can point to different bytes later. A digest identifies exact content, enabling reproducibility, audit, controlled rollback, and artifact-to-request tracing.

    4. What does the NVIDIA runtime layer do?

    It arranges explicit GPU device access and needed driver-side libraries for the container. It does not make an incompatible host or unsupported application automatically valid.

    5. When is a startup probe important?

    When legitimate initialization is longer than the normal liveness interval. It prevents repeated restarts during model loading or engine construction while still bounding a truly stuck startup.

    Day 23 · Elastic capacity

    Autoscaling, concurrency, batching, and cold starts

    LLM replicas are stateful for the life of a request, expensive to warm, and limited by KV memory. Scale on demand signals early enough to act—not on a late utilization alarm alone.

    By the end, you can: distinguish concurrency, batch size, throughput, utilization, and saturation; size a replica target from demand and latency; explain continuous batching; design warm pools; and read TTFT, ITL, percentile, and goodput metrics.

    A beginner analogy: buses at a station

    Requests are passengers. A replica is a bus that takes time to drive from the depot, inspect, and enter service—a cold start. Concurrency is the number of passengers currently assigned to a bus. A batch is the group the driver advances during one stop; with continuous batching, passengers leave at different stops and waiting passengers fill freed seats. Throughput is passengers moved per minute. Utilization says how much the bus is working; saturation appears when arrivals exceed useful seat service and the station queue grows.

    Sending every bus at maximum occupancy may maximize raw passenger movement while making an urgent rider wait too long. LLM operators similarly trade batch efficiency against TTFT and ITL. A service objective turns that trade into goodput: tokens only count as operationally useful if their requests succeed and meet the latency/quality contract.

    Terminology

    TermMeaning

    Batch sizeSequences or tokens executed together in one engine iteration; it may change every iteration.
    Continuous batchingFinished sequences leave and queued sequences enter between decode iterations, reducing empty slots.
    TTFTTime to first token: arrival through queueing, prefill, and first sampled/streamed output.
    ITLInter-token latency: elapsed time between adjacent output tokens, reflecting decode cadence and stalls.
    GoodputSuccessful work completed within defined latency and quality constraints per unit time.
    Cold startTime for absent capacity to become ready, including provisioning, image, model, engine, and warm-up.
    Warm poolPre-provisioned or partly initialized capacity kept ready to shorten scale-up.

    Request and autoscaling lifecycle

    1. Observearrivals and queue
    2. Forecastdemand at ready time
    3. Decidedesired replicas
    4. Warmprovision to ready
    5. Batchadmit and execute
    6. Drainsafe scale-down
    1. Record arrival rate, queued tokens, active tokens, prompt/output distributions, and SLO pass rate over a window. Separate model and tenant classes.
    2. Forecast demand at now + cold-start time. Queue depth is a leading symptom; GPU utilization often rises only after demand has already queued.
    3. Compute desired replicas from SLO-safe goodput or concurrency per replica, then apply minimum, maximum, step, cooldown, quota, and availability constraints.
    4. Provision capacity. Pull artifacts, load the model, warm representative shapes, and publish readiness. Until ready, it contributes zero service capacity.
    5. Admission limits protect KV memory. Continuous batching refills freed slots; token budgets prevent one long prefill from monopolizing an iteration.
    6. Scale-down first marks a replica unready, stops new assignments, drains streams, then releases it. Stabilization windows prevent repeated up/down flapping.

    TTFT, ITL, percentiles, and goodput

    TTFT answers “How long did the user stare at an empty screen?” It includes queue time and prompt prefill. ITL answers “Once text began, how smooth was it?” Compute ITL between each pair of emitted tokens, then aggregate carefully: a per-token distribution weights long outputs more than a per-request summary. p50 is typical, p95 exposes a broad tail, and p99 exposes the slowest one percent. Report enough samples and a window; a p99 from fifty requests is unstable. Goodput requires a declared gate, for example: requests that return successfully with TTFT ≤ 1.5 s and p95 per-request ITL ≤ 80 ms. A token from a timed-out request is throughput but not goodput.

    Worked example: replicas and a warm pool

    A load test shows one ready replica supports 8 concurrent requests while meeting both TTFT and ITL goals. Mean in-service time is 4 seconds. Its SLO-safe request rate is approximately 8/4 = 2 requests/s. Forecast demand 6 minutes ahead—the p95 cold start—is 13 requests/s. Base replicas = ceiling(13/2) = 7. Add one replica for a host-safe reserve: 8 desired ready replicas.

    The current fleet has 6 ready replicas, so the shortfall is 2. Reactive scale-up started only when demand arrived would expose six minutes of queue growth. A two-instance warm pool that has image and weights cached but is not yet serving can become ready in 50 seconds. If forecast error is ±20%, test 10.4 to 15.6 requests/s: the upper case needs ceiling(15.6/2)+1 = 9 replicas, so either keep a third warm slot or admit/reject by priority during surprise demand.

    Decision guide

    Predictable daily peaks: scheduled/predictive pre-warming. Unpredictable bursts shorter than cold start: minimum headroom, admission control, and warm pools. Rare asynchronous jobs: queue and scale-to-zero may fit. Interactive service: preserve a ready floor. Memory-full but compute-light: lower context/concurrency or improve KV management; adding batch work can worsen OOM.

    Review questions and answers

    1. How do utilization and saturation differ?

    Utilization is a measured fraction of resource activity over time. Saturation means effective service capacity is exhausted so extra demand waits, sheds, or harms latency. Queue growth is strong saturation evidence.

    2. Why separate TTFT from ITL?

    Queueing and prefill dominate the wait before output, while decode scheduling and per-step work shape token cadence. A service can have a fast first token and choppy continuation, or the reverse.

    3. What does continuous batching improve?

    It reuses execution slots immediately when sequences finish rather than waiting for an entire static batch. This improves occupancy and goodput under varied output lengths.

    4. Why are warm pools expensive?

    They reserve some combination of nodes, memory, downloaded weights, or loaded GPUs before work arrives. That shortens readiness delay but pays idle resource cost.

    5. Why scale on tokens as well as requests?

    One long prompt or output can cost hundreds of short requests. Token-aware demand better predicts prefill work, decode duration, KV consumption, and queue delay.

    Day 24 · Work distribution

    Routing, load balancing, and queueing

    Connections are not equal work. Route by health, cost, locality, and deadlines; use queues as measured shock absorbers, never as invisible storage for unlimited demand.

    By the end, you can: apply Little's Law; explain why tails explode near saturation; compare routing policies; use prefix/cache affinity safely; and describe sticky handling and graceful draining for Server-Sent Events.

    A beginner analogy: supermarket lines with reusable shopping lists

    A naive greeter sends each shopper to the next cashier. But one cart holds two items and the next holds two hundred. A workload-aware greeter counts estimated items, current carts, and cashier speed. Now imagine repeat shoppers whose long shopping lists are already prepared at one desk. Sending them back to that desk saves setup time: this is cache affinity. Yet if that cashier's line becomes enormous, locality is no longer worth the wait. Affinity should be a preference with an overload escape hatch, not a prison.

    The front door load balancer chooses reachable, healthy regions or services. A model-aware router selects among eligible replicas using queue/token load, model version, adapter availability, and prefix-cache hints. A queue orders work that cannot start immediately. After an SSE streaming response begins, the selected connection remains with that replica; moving half a byte stream to another server is not ordinary retry.

    2. The service filters replicas by readiness, model/checkpoint, precision, adapter, protocol, tenant permissions, and drain state.
    3. A score combines estimated queued tokens, active decode work, prompt length, prefix-cache hit value, and replica speed. Stale telemetry requires conservative fallbacks.
    4. Admission checks deadline, KV room, quota, and maximum queue age. Work enters a bounded priority/fairness queue or receives an explicit overload response.
    5. The scheduler batches prefill and decode. Traces record queue, prefill, first token, per-token cadence, and cache result.
    6. For SSE, headers begin a long-lived response. Proxies must avoid buffering, preserve idle timeouts, and pass disconnect cancellation. A draining replica serves existing streams but receives no new ones.

    Little's Law and tail latency

    L = λW, therefore W = L/λ

    L is average requests in the system, λ is average completed/arrival requests per second in stable equilibrium, and W is average seconds in the system. If λ = 12 requests/s and W = 2.5 s, average in-flight work L = 30 requests. Little's Law does not promise a percentile, assume Poisson traffic, or tell you how many replicas are sufficient by itself. It is an accounting identity under stability. If arrivals exceed departures for long enough, no stable average exists; the queue grows.

    Near saturation, a small service-time fluctuation finds no spare capacity, so it becomes waiting time for everything behind it. Variability compounds: long prompts, retries, synchronized clients, cache misses, and mixed hardware produce p99 far above p50. Keeping utilization below a tested threshold is not waste; it buys the slack that absorbs variance.

    Worked example: affinity with an overload escape

    Four replicas each safely process 500 queued-token-equivalents per second. A request has a 600-token shared prefix and expects 120 generated tokens. Replica A holds the prefix; its queue is 900 token-equivalents. Replica B misses the prefix but has only 150 queued. Estimate A's wait as 900/500 = 1.8 seconds, followed by almost no prefix recompute. Estimate B's wait as 150/500 = 0.3 seconds plus a measured 0.45-second prefill, totaling 0.75 seconds before decode eligibility. Choose B even though A has affinity.

    A simple score is estimated queue delay + miss penalty. For A: 1.8 + 0 = 1.8 s. For B: 0.3 + 0.45 = 0.75 s. Add uncertainty margins and a maximum-affinity queue threshold. After routing, suppose the service observes λ = 10 requests/s and average total W = 3 s; Little's Law predicts 30 average in flight. If dashboards show 70, investigate a changing workload, retry amplification, unstable measurement window, or growing queue.

    Operational metrics and failure modes

    Watch queue depth in requests and tokens, oldest age, abandon/deadline drops, arrival/departure rates, estimated versus actual service cost, router decision latency, imbalance coefficient, cache hit rate and saved prefill time, fallback rate, retries, per-route p50/p95/p99 TTFT/ITL, stream disconnects, active SSE connections, and drain age. High cache hit rate can be harmful if it creates one hot replica; pair locality with load.

    Common mistakes

    • Round-robin across highly variable token workloads.
    • Unbounded queues that convert overload into timeouts and memory pressure.
    • Retrying timed-out requests immediately and amplifying load.
    • Strict cache stickiness with no overload fallback.
    • Mixing premium and batch work without quotas or aging.
    • Proxy-buffering SSE, making tokens appear in large delayed chunks.
    • Removing a pod before endpoint propagation, then killing active streams.

    Decision guide

    Uniform short work: least-connections may suffice. Variable lengths: least estimated tokens/work. Shared prefixes: bounded cache affinity. Adapters: prefer loaded adapter, with capacity fallback. Multiple tiers: bounded priority plus fairness and deadlines. Severe overload: reject early, degrade max output/context, or queue only asynchronous work.

    Review questions and answers

    1. What does Little's Law tell an operator?

    It links average in-system concurrency, throughput/arrival rate, and average total time. It is useful for sanity checks and capacity intuition, but does not directly predict p99 or remain stable under unbounded growth.

    2. Why does p99 rise sharply near saturation?

    There is little spare service capacity to absorb normal variance. A long request or burst creates waiting that propagates; retries and synchronization can amplify it.

    3. When should cache affinity be ignored?

    When estimated waiting on the hit replica exceeds recomputation plus waiting elsewhere, when telemetry is stale, or when health, version, residency, or quota makes that replica ineligible.

    4. Why are SSE streams special during routing?

    They are long-lived ordered HTTP responses. Once started, the connection is bound to the serving instance; failover generally requires reconnect/retry semantics rather than transparent midstream movement.

    5. What is a safe queue?

    Bounded by size and age, observable, deadline-aware, fair by policy, and paired with explicit rejection. It absorbs brief bursts but never pretends finite capacity is infinite.

    Day 25 · Capacity across clouds

    Multi-cloud capacity, procurement, failover, and compliance

    Multi-cloud is not a discount switch. It is an option portfolio and a failure-boundary design that adds operational complexity in exchange for supply, geographic reach, and resilience.

    By the end, you can: combine reserved, on-demand, and spot capacity; separate global control from regional data paths; calculate failover headroom; account for egress and heterogeneity; and make compliance an eligibility rule rather than a routing afterthought.

    A beginner analogy: groceries from several suppliers

    A restaurant buys staple rice through a discounted annual contract, fresh surprises from an on-demand wholesaler, and bargain surplus that can disappear with notice. These resemble reserved, on-demand, and spot capacity. Depending on one supplier risks shortages; using five suppliers without common recipes, quality checks, and inventory tracking creates chaos. The restaurant keeps a tested menu and local stock while headquarters negotiates contracts. Likewise, regional workload planes should keep serving if the global control plane is temporarily unavailable.

    Multi-cloud is justified when it addresses a quantified constraint: one provider lacks supply, users need lower regional latency, an outage target requires independent failure domains, or law/contract restricts data location. It is not automatically more available. A shared identity provider, DNS operator, model registry, control plane, or networking dependency can remain a hidden single point of failure.

    A service needs 20 capacity units on average and 32 at a normal peak. If one region fails, the survivor cannot carry all 28; it has 6 spare units and a 22-unit ceiling if an emergency burst pool adds 2. The plan must shed or reroute 6 units elsewhere. A third provider has 8 qualified on-demand units and 5-minute readiness, covering the gap only after five minutes. Therefore the immediate policy reserves 6 units of low-priority shed capacity or maintains warmer third-site capacity. “Multi-cloud” did not remove arithmetic.

    Review questions and answers

    1. Why mix reserved, on-demand, and spot?

    They price different risks. Commitments cheaply cover a stable base, on-demand absorbs forecast error and failover, and interruptible supply lowers suitable batch cost. One mechanism rarely fits all work.

    2. Why must workload planes survive control-plane loss?

    Existing regional traffic should not fail because global orchestration is unreachable. Cached desired state, local routing, and bounded autonomy keep the request path available.

    3. What is wrong with counting GPUs across providers?

    Devices, software paths, memory, topology, and measured SLO goodput differ. Normalize to a tested capacity unit for a specific workload.

    4. How does compliance affect failover?

    It restricts which healthy destinations are legally and contractually eligible. Capacity planning must maintain sufficient compliant alternatives or explicitly accept a lower availability objective.

    5. What hidden dependency can defeat multi-cloud?

    Any shared critical service: DNS, identity, certificate authority, artifact registry, control database, telemetry gate, or model store. Map and test them as failure domains.

    Day 26 · Safe change

    Zero-downtime deployment, draining, rollback, and cost

    “Zero downtime” does not mean zero risk. It means capacity stays available, new traffic reaches only qualified replicas, in-flight work completes or follows an explicit recovery contract, and regression signals can stop and reverse the change.

    By the end, you can: compare rolling, blue-green, and canary releases; design readiness gates and graceful shutdown; handle SSE streams; choose rollback metrics; and calculate cost per million good tokens including deployment headroom.

    A beginner analogy: replacing a bridge while traffic flows

    Blue-green builds a second bridge, tests it, then redirects every car; rollback restores the old bridge, but two bridges cost more. A rolling update closes and rebuilds one lane at a time; it uses less extra material but temporarily reduces capacity and mixes old and new lanes. A canary first directs a small, representative traffic sample over the new structure, watches sensors, then increases the share. The canary discovers defects under real load while limiting exposure.

    For inference, structural safety includes semantic quality. A new checkpoint may return HTTP 200 quickly but produce worse answers, broken tool JSON, changed refusal behavior, or tokenization drift. Release gates therefore combine system metrics, model-quality samples, compatibility, and cost. “No 5xx errors” is necessary and dramatically insufficient.

    Graceful shutdown and SSE streams, clearly

    On termination intent, the server first flips readiness to false. The orchestrator/load balancer stops selecting it, but propagation is not instantaneous, so the server should also reject new requests with a retryable status while draining. Existing non-streaming calls continue. Existing SSE responses keep their TCP/HTTP connection and must continue emitting complete data: events, heartbeats if used, and a final completion marker when normal.

    Track active requests and connections. When the count reaches zero, exit cleanly. At a configured deadline, choose an explicit policy: finish only requests likely to complete, send a structured terminal error when the protocol allows, or close and rely on client retry/resume semantics. Never assume a different replica can transparently continue an arbitrary model stream: it lacks sampling RNG state and KV state unless the architecture explicitly externalizes them. Set the grace period above measured p99 stream duration plus endpoint-propagation and flush buffers, while enforcing maximum generation and cancellation so one abandoned connection cannot block forever.

    Worked example: canary gates, headroom, and cost

    A fleet has 10 replicas. Normal peak uses 70% of SLO-safe capacity. A rolling update with one unavailable replica leaves 9 replicas: equivalent load becomes 70% × 10/9 ≈ 77.8%, still below a tested 82% safe threshold. Losing a second replica would produce 87.5%, so set maximum unavailable to one and maintain surge or pause on readiness failure.

    The canary receives 5% of 20,000 requests: 1,000 samples. Control error rate is 0.4%, canary 0.6% (six errors), control p99 TTFT 1.2 s, canary 1.7 s, and the gate is error ≤ 0.8% and p99 TTFT ≤ 1.5 s. Error passes; TTFT fails, so rollback traffic to zero and retain canary telemetry. Do not average the two gates.

    Each replica costs an illustrative $4/hour and produces 1,200 raw tokens/s; 85% are good tokens. Ten replicas cost $40/hour and deliver 10,200 good tokens/s. Cost = 40 ÷ (10,200 × 3,600) × 1,000,000 ≈ $1.09 per million good tokens. A 20-minute blue-green overlap adds 10 × $4 × 1/3 = $13.33 per deployment. Include that deployment overhead in monthly cost rather than claiming only steady state.

    Failure modes and common mistakes

    • Replacing old capacity before new replicas are genuinely ready.
    • Canarying too few requests or only easy traffic.
    • Gating averages while p99 or one cohort regresses.
    • Killing after SIGTERM without readiness change and drain.
    • Forgetting proxy endpoint propagation and SSE timeout behavior.
    • Rolling back code but not model, tokenizer, or configuration.
    • Ignoring surge/overlap cost and temporary cache coldness.

    Decision guide

    High-risk model/engine change: canary, often with blue-green capacity. Low-risk patch and many replicas: careful rolling update. Need near-instant switch/rollback: blue-green. Insufficient overlap capacity: reduce traffic, create temporary capacity, or accept a slower roll—never hide overload behind a “zero downtime” label. Irreversible state change: design compatibility before release.

    Review questions and answers

    1. What does zero downtime require beyond a healthy process?

    Qualified new capacity, correct readiness, preserved service capacity, controlled traffic shift, complete or explicitly recoverable in-flight work, rollback, and observability of system plus model quality.

    2. Why does graceful shutdown begin with readiness?

    New assignments must stop before waiting for active work. Otherwise arrivals replace completions and the replica never drains. Endpoint propagation and local admission both matter.

    3. Can an SSE stream move to another replica mid-generation?

    Not ordinarily. The replica owns connection, KV cache, sampler and RNG state. A reconnect can retry or resume only if the application explicitly designs and externalizes enough state.

    4. Why compare canary with a concurrent control?

    Traffic mix, load, and dependencies change over time. A simultaneous control distinguishes release effects from a global spike or external incident.

    5. Why calculate cost per good token?

    Raw tokens can be late, erroneous, retried, or low quality. Good-token cost aligns infrastructure spending with useful service and exposes “fast” configurations that violate the contract.

    Hands-on exercises without a GPU

    1. Simulate canary steps 1%, 5%, 20%, 50%, 100% in a spreadsheet. Generate error and TTFT distributions; implement hold and rollback rules.
    2. Build a tiny local streaming server and add shutdown handling: mark unready, reject new work, count active streams, wait with a deadline, then exit.
    3. Calculate steady, rolling-surge, and blue-green monthly cost for several deployment frequencies. Include cache-warm penalties and failed canaries.
    Course bridge: Days 19-26 form one loop: hardware limits shape capacity; capacity becomes containers and replicas; routing turns replicas into a service; multi-cloud turns service into a resilient fleet; safe deployment changes that fleet without violating its contract.

    Practice under pressure

    Incident scenarios

    Start with user impact, preserve evidence, reduce blast radius, and test one hypothesis at a time.

    Incident A: p99 TTFT rises, GPU average looks low

    Clues: p50 unchanged, one replica has a deep token queue, cache-affinity routing is strict. Response: cap affinity, rebalance by estimated work, inspect telemetry freshness, and compare per-replica queue age. Lesson: fleet-average utilization concealed a hot spot and saturation.

    Incident B: deployment causes broken streams

    Clues: ordinary requests succeed, SSE disconnects align with pod termination at 30 seconds. Response: pause rollout, restore old replicas, lengthen grace based on p99 stream duration, mark unready before drain, and verify proxy endpoint propagation. Lesson: HTTP health did not represent connection lifecycle.

    Incident C: autoscaler adds replicas but queue grows

    Clues: desired count increases, pending replicas take eight minutes to become ready, traffic burst lasts four. Response: shed low priority, apply output limits, use warm capacity, and forecast at cold-start horizon. Lesson: nominal replicas are not ready capacity.

    Incident D: one cloud region fails

    Clues: healthy alternate region is not residency-eligible for half the tenants. Response: apply tenant-specific routes, preserve compliant traffic, communicate degraded SLO, and activate qualified capacity. Lesson: healthy and eligible are different sets.

    Incident E: new GPU appears slower

    Clues: benchmark used a fallback kernel, different engine version, and power cap. Response: freeze the envelope, verify supported precision and shape, inspect kernel selection, warm thoroughly, and report clocks. Lesson: generation names do not execute workloads—complete systems do.

    Incident F: container restart loop

    Clues: liveness begins at 20 seconds; model needs 150 seconds to load. Response: add a startup probe, separate liveness/readiness, and measure start-to-ready p99. Lesson: health probes are control inputs, not decorative endpoints.

    Universal first ten minutes

    1. Declare severity, affected models/regions/cohorts, start time, and user-visible symptom.
    2. Freeze risky deploys and configuration changes; preserve logs, traces, metric labels, and artifact digests.
    3. Reduce blast radius: rollback, shift traffic within eligibility, shed low priority, or cap expensive request shapes.
    4. Check demand versus departures, queue age, ready capacity, saturation by bottleneck, and p50/p95/p99 TTFT/ITL.
    5. Communicate current facts, uncertainty, mitigation, and next update time. Do not wait for root cause before protecting users.

    Ship deliberately

    Production deployment checklist

    A checklist is useful only when every box points to evidence, an owner, and a rollback condition.

    Artifact and runtime

    • Image and model are immutable, signed/verified, scanned, and pinned by digest.
    • Driver, CUDA user space, engine, kernels, and exact GPU SKU are qualified together.
    • Tokenizer, chat template, adapter, precision, and configuration versions are recorded.
    • Secrets arrive at runtime with least privilege; no secret exists in an image layer.
    • Non-root, read-only filesystem, device restriction, network policy, and resource limits are tested.

    Capacity and traffic

    • Weights, KV, workspace, fragmentation, and surge fit with measured headroom.
    • Safe concurrency and goodput come from representative load including long prompts.
    • N+1 or declared failure capacity is ready across appropriate domains.
    • Queues are bounded by size/age; quotas, deadlines, retry budgets, and shedding are configured.
    • Prefix/adapter affinity has load-aware fallback; SSE proxy buffering is disabled.

    Health and rollout

    • Startup, liveness, and readiness answer distinct questions and have tested timing.
    • Canary/control cohorts are stable and representative; gates include quality and tails.
    • Maximum unavailable/surge preserves capacity at peak-safe load.
    • Rollback restores image, model, tokenizer, config, routes, and compatible state.
    • Readiness-off, endpoint propagation, ordinary drain, SSE drain, flush, and forced deadline are rehearsed.

    Observability and governance

    • Dashboards show queue, ready capacity, TTFT/ITL percentiles, goodput, KV, errors, and cost by version.
    • Alerts map to user-impacting SLOs and contain runbook links.
    • Residency, retention, access, encryption, audit, and failover eligibility are enforced.
    • On-demand quota and interruption playbooks are tested; hidden shared dependencies are documented.
    • Owners, incident channel, decision log, and post-release observation window are named.

    Final exercise

    Capstone: design a production inference service

    No GPU is required. The deliverable is a reasoned architecture, capacity workbook, failure analysis, and rollout plan.

    Scenario

    Build “TutorStream,” a streaming educational assistant serving two model classes: a small interactive model and a larger premium model. Peak demand is 18 requests/s, p95 prompt is 2,000 tokens, p95 output is 500 tokens, and 30% of traffic shares one of twenty system prompts. The product requires TTFT p95 ≤ 1.5 s, ITL p95 ≤ 80 ms, 99.9% monthly request success, EU residency for EU schools, and a maximum 15-minute regional recovery. Traffic has a predictable weekday peak plus occasional 3× five-minute bursts. A new model ships weekly.

    Required architecture

    Global edgeidentity, residency, region
    Regional routermodel, token load, cache
    Bounded queuestier, deadline, shedding
    Model poolsready replicas + warm pool
    TelemetrySLO, traces, quality, cost
    Release planecanary, drain, rollback

    Work products

    1. Assumption register: exact model sizes, precision, measured bytes/token, safe goodput/replica, cold-start percentiles, prices, and source dates. Mark unknowns as ranges.
    2. Capacity workbook: weights + KV + workspace; concurrency under p50/p95 lengths; replicas from goodput; N+1 host and regional failover; warm-pool size for the 3× burst.
    3. Hardware plan: whole GPU versus MIG for each pool, any tensor-parallel boundary, and a responsible Hopper/Ada/Blackwell qualification scorecard without unverified claims.
    4. Container contract: artifact digests, GPU runtime compatibility, startup/liveness/readiness truth table, model cache, security controls, and start-to-ready budget.
    5. Routing policy: residency eligibility, premium fairness, estimated-token load, bounded prefix affinity, queue size/age, retry budget, and SSE behavior.
    6. Supply portfolio: reserved baseline, on-demand buffer, optional spot batch work, provider quota, egress assumptions, and a control-plane outage mode.
    7. Release plan: canary cohorts and steps, concurrent control, quality/system/cost gates, maximum unavailable/surge, graceful stream draining, and complete rollback unit.
    8. Incident game: simulate one host loss, EU region loss, registry outage, 8-minute cold start, cache-hot replica overload, and a canary quality regression.
