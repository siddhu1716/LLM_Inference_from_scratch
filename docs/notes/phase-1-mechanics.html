    Before Day 1

    Tensors and shapes, very gently

    A shape is a compact description of how numbers are arranged, not a mysterious property of neural networks.

    You already know several tensors under everyday names. One number, such as 3.5, is a scalar and has no axes. A Python list such as [0.2, 0.8, -0.1] is a one-dimensional tensor, often called a vector. A rectangular list of lists is a two-dimensional tensor, or matrix. Add another nesting level and you have a three-dimensional tensor. A dimension or axis is one direction along which you can move; the size of an axis says how many choices exist in that direction.

    ShapePlain-language readingPossible meaning
    []One valueA loss, temperature, or probability
    [4]Four values in a rowOne tiny token vector
    [3, 4]Three rows, four values per rowThree tokens, each with width four
    [2, 3, 4]Two groups of three rows of four valuesTwo sequences, three tokens each, width four

    Brackets are read from broadest grouping to most detailed. For [batch, sequence, feature], choose a request in the batch, choose a token position in that request, then choose one numeric feature for that token. Indexing removes the axes you select. If x has shape [1, 9, 50257], then x[0] has shape [9, 50257], x[0, -1] has shape [50257], and x[0, -1, 17] is one number. The index -1 means “the last item” in Python.

    Shape-reading habit: Say both the numbers and their meanings aloud. “One sequence, nine positions, 50,257 vocabulary scores” is far more useful than “a three-dimensional tensor.”
    Day 01

    Inference is a one-token loop

    Tokenize → forward pass → choose → append → repeat → stop.

    Beginner intuition: an extremely capable autocomplete

    Imagine writing on a whiteboard while a helper repeatedly studies everything currently written. The helper does not draft a hidden paragraph. Instead, it hands you a ranked menu for the very next text fragment. You choose one fragment, write it on the board, and ask again. That repeated interaction is autoregressive inference. “Auto” means the model’s own previous outputs become part of its next input; “regressive” refers to predicting from earlier values.

    This matters because almost every serving concern sits around this loop. Latency depends on how fast each pass runs. Memory depends on weights and saved attention state. Quality depends partly on how logits are converted into a chosen token. Stopping determines whether generation ends cleanly. Batching decides which users take a turn. If the loop is fuzzy, later optimizations sound like unrelated tricks. If the loop is clear, they become targeted improvements to a specific step.

    Terminology for today

    • Prompt: the input text supplied before generation.
    • Token: a vocabulary item represented by an integer ID; it may be a word, word piece, punctuation mark, or byte.
    • Vocabulary: the complete ID-to-token inventory understood by a tokenizer and model.
    • Forward pass: one execution of model math on supplied token positions.
    • Logit: an unrestricted score for one vocabulary item. A logit is not yet a probability.
    • Sampler or decoder: policy that turns next-token scores into one token ID.
    • EOS: an end-of-sequence token that can signal completion.
    • Prefill: processing prompt positions together to establish state and produce the first next-token prediction.
    • Decode: processing newly generated positions, usually one position per active sequence per iteration.

    Step by step, including [1, 9, 50257]

    1. EncodeTurn prompt text into token IDs, for example nine IDs.
    2. PrefillRun those nine positions through the model in one forward pass.
    3. Read logitsSelect the vocabulary-score row at the final input position.
    4. ChooseApply greedy selection or a sampling policy to obtain one ID.
    5. ContinueAppend, check stopping rules, and decode another token if needed.

    Suppose the model receives one prompt containing nine token IDs and uses GPT-2’s 50,257-item vocabulary. Its output logits have shape [1, 9, 50257]. The first axis has size 1 because there is one sequence in the batch. The second has size 9 because the prompt occupies nine positions. The third has size 50257 because the model produces one score for every possible vocabulary item at every position.

    A causal language model is trained so the row at position i predicts the token after position i. Earlier rows are useful during training because many next-token examples can be scored in parallel. During generation, however, positions 0 through 7 correspond to predictions inside the already known prompt. Only the row after the complete visible prefix answers our current question: “What follows all nine prompt tokens?” Therefore logits[0, -1, :] selects batch item 0, last sequence position, and every vocabulary entry. Its shape is [50257]. It is not because other rows are invalid; they answer earlier questions that we no longer need.

    Logits, probabilities, and the softmax equation

    Logits can be negative, positive, large, or small and need not sum to anything. Only their relative differences matter. Softmax exponentiates and normalizes them into nonnegative probabilities that sum to one:

    p(i) = exp(z_i) / Σ_j exp(z_j)

    Here z_i is the logit for candidate token i; exp is the exponential function, which preserves ordering while emphasizing differences; j ranges across all vocabulary entries; the denominator sums their exponentials; and p(i) is token i’s probability. Real code subtracts the largest logit before exponentiating for numerical stability. The subtraction changes neither the final ratios nor the probabilities.

    Temperature changes the distribution before softmax: p(i) = softmax(z_i / T). With T < 1, differences grow and the distribution becomes sharper. With T > 1, differences shrink and more candidates remain plausible. Temperature zero is not a valid division; deterministic systems use argmax rather than pretending that zero-temperature softmax is ordinary arithmetic.

    Greedy

    Choose the largest logit. It is deterministic for fixed inputs and weights, but not automatically the best text policy.

    Top-k

    Keep only the k highest-scoring IDs, mask the rest, renormalize, then sample.

    Top-p

    Sort by probability and keep the smallest leading set whose cumulative mass reaches p. Its candidate count adapts.

    Temperature

    Rescale logits before filtering or sampling. It controls sharpness, not which facts the model learned.

    Worked toy example: a four-token vocabulary

    Let the possible next tokens be [" cat", " dog", ".", " runs"] with logits [2.0, 1.0, 0.0, -1.0]. Subtracting the maximum gives [0, -1, -2, -3]. Their exponentials are approximately [1.000, 0.368, 0.135, 0.050]; the sum is 1.553. Dividing each by the sum gives probabilities near [0.644, 0.237, 0.087, 0.032]. Greedy chooses " cat". Top-k with k=2 removes the last two candidates and renormalizes the first two to about 73% and 27%. Top-p with p=0.8 also keeps the first two because 64.4% alone is insufficient but 64.4% + 23.7% exceeds 80%.

    After choosing token ID 0, append it to the input sequence. The next model call now conditions on the prompt plus " cat". Stop when an EOS token is selected, a configured stop-token sequence is a suffix of generated IDs, max_new_tokens is reached, the context limit would be exceeded, the client cancels, or a server deadline/error terminates the request. A robust engine records the finish reason rather than merely falling out of a loop.

    Connection to code, and why gradients are disabled

    The educational project separates policy into inspectable pieces: greedy.py, temperature.py, top_k.py, top_p.py, and stopping.py. Phase classification lives in engine/phases.py. The synchronous engine demonstrates request transitions and EOS/length finishing in engine/sync_engine.py.

    Training needs gradients so an optimizer can change weights. Inference does not. In PyTorch, torch.no_grad() prevents gradient recording, reducing memory and bookkeeping. torch.inference_mode() goes further by disabling additional autograd-related tracking for inference-only tensors. Neither changes the learned weights, performs sampling, or creates a KV cache. They remove training machinery. You still need model.eval() for layers whose behavior differs between training and evaluation, and you still need explicit decoding and stopping logic.

    Performance view: Prefill handles many prompt positions and tends to expose parallel matrix work. Decode advances each sequence by one token and repeatedly reads weights plus growing state, so it often becomes memory-bandwidth and scheduling sensitive. The pure-Python project clarifies control flow; it does not emulate production GPU speed.

    Common beginner mistakes

    • Calling every vocabulary score a probability before applying softmax.
    • Using all nine logit rows to choose one next token instead of selecting the final row.
    • Believing sampling generates several future tokens from one ordinary next-token distribution.
    • Assuming low temperature guarantees truth or high temperature creates knowledge.
    • Forgetting EOS, length, cancellation, stop-sequence, and context-limit conditions.
    • Thinking no_grad automatically enables evaluation mode, caching, or faster kernels.
    • Comparing benchmark numbers without warm-up, synchronization, fixed hardware, or repeated trials.

    Check your understanding

    What does each axis of [1, 9, 50257] mean?
    One batch item, nine sequence positions, and 50,257 vocabulary logits per position.
    Why use logits[0, -1, :]?
    It selects all vocabulary scores predicted after the complete visible prefix for the first sequence.
    Do logits sum to one?
    No. Softmax converts unrestricted logits into probabilities that sum to one.
    How do top-k and top-p differ?
    Top-k fixes the candidate count; top-p adapts the count to reach a probability-mass threshold.
    What separates prefill from decode?
    Prefill processes prompt positions to establish state; decode advances an active sequence with newly generated positions.
    Name three valid stop conditions.
    Examples: EOS, maximum new tokens, stop sequence, cancellation, deadline, error, or context limit.

    Day 02

    A model is configuration plus named tensors

    Then a tokenizer supplies the integer language those tensors expect.

    Beginner intuition: blueprint, warehouse, and dictionary

    Think of deployment as opening a prefabricated workshop. The configuration is the blueprint: number of floors, width of hallways, number of attention heads, and maximum supported sequence length. The weight file is a warehouse of numbered parts arranged into named rectangular arrays. The tokenizer is the receiving dictionary that turns outside text into the exact part numbers accepted at the entrance. A model file is therefore not a Python program that contains intelligence as instructions. It is mostly learned numbers plus metadata describing how to interpret them.

    This matters operationally. A wrong vocabulary maps text to wrong rows. A wrong dimension makes matrix multiplication impossible. A mismatched RoPE setting changes positional behavior. A missing tensor prevents a layer from loading. Quantization changes representation and storage but must preserve the logical shapes expected by execution. “The model loaded” is meaningful only when configuration, tokenizer, tensor names, data types, and architecture agree.

    Terminology for today

    • Weight: a learned numeric value used by the forward pass.
    • Parameter: a learned value; a tensor’s parameter count is the product of its axis sizes.
    • Activation: a temporary value computed from inputs and weights.
    • Data type or dtype: numeric representation such as float32, float16, or an integer format.
    • SafeTensors: a file format with metadata describing tensor names, shapes, types, and byte ranges followed by tensor data.
    • Tokenizer: deterministic encoder/decoder between text and token IDs.
    • BPE: byte pair encoding, which repeatedly applies ranked adjacent-piece merges.
    • Special token: a reserved item such as EOS whose role is part of the model contract.

    Step-by-step model internals and shapes

    1. Read configResolve vocabulary, residual width, layers, heads, and position settings.
    2. Read metadataMap each tensor name to dtype, shape, and bytes in the weight file.
    3. Allocate or mapExpose stored bytes as correctly shaped numeric arrays.
    4. Assemble layersConnect embeddings, repeated blocks, final norm, and output projection.
    5. ValidateReject divisibility, missing-tensor, dtype, tokenizer, and context mismatches.

    Consider a tiny decoder with vocabulary V=8, residual width D=4, two layers, two query heads, and feed-forward width F=12. Its token embedding table has shape [V, D] = [8, 4], so it stores 32 parameters. Selecting one token ID returns one row of shape [4]; selecting three IDs returns [3, 4]. A bias-free linear projection is often stored as [out, in]. A query projection that preserves width is [4, 4]. A feed-forward up projection could be [12, 4], taking a four-feature token to twelve hidden features. Its down projection is [4, 12].

    Repetition is central: the architecture creates a list of blocks, but each block has its own learned tensors. Temporary activations scale with current batch and sequence shapes; persistent weights do not. Parameter count is found by multiplying tensor dimensions and summing. Storage is approximately parameter count times bytes per parameter, plus metadata and any quantization scales. This rough arithmetic is one reason shapes are an engineering tool rather than decorative notation.

    Tokenization mechanics: text is not fed directly to the model

    A byte-level BPE tokenizer first represents text as bytes through an encoding such as UTF-8. A reversible byte-to-symbol mapping may make all bytes safe to store in vocabulary files. The encoder then examines adjacent pieces, finds the pair with the best available merge rank, combines every eligible occurrence according to the algorithm, and repeats until no ranked pair remains. Finally, each remaining piece is looked up in the vocabulary to obtain an integer ID. Decoding reverses IDs to pieces, concatenates them, converts symbols back to bytes, and decodes text.

    The integer magnitude carries no semantic measurement: ID 700 is not “twice” ID 350. IDs are addresses. Frequent strings often have merged pieces and therefore require fewer tokens; unusual words, whitespace patterns, code, or some languages may split differently. More input tokens increase prefill work and occupy more KV-cache positions later. More output tokens require more autoregressive decode iterations. Tokenization therefore influences latency, capacity, truncation, and billing, but a larger vocabulary also enlarges embedding and output projection dimensions. It is a design tradeoff, not a free compression switch.

    Important distinction: The project’s ByteTokenizer maps each UTF-8 byte directly to an ID from 0 through 255. It is wonderfully transparent and reversible, but it is not BPE and is not token-efficient for realistic language-model serving.

    Worked toy example: merging “banana”

    Start with character-like pieces [b, a, n, a, n, a]. Suppose ranked rules prefer (a,n) → an first and (an,a) → ana second. Applying the first rule produces [b, an, an, a]. Applying the second where it matches produces a possible final segmentation [b, an, ana]. If the vocabulary maps these pieces to IDs [5, 11, 19], the model receives those addresses. The exact result depends on the tokenizer’s formal pre-tokenization and merge rules; this tiny example illustrates ranking rather than reproducing a production tokenizer.

    Now use the Day 2 tiny model. Looking up IDs [5, 11, 19] in an embedding table shaped [20, 4] yields activations shaped [3, 4]. If that table uses float32, it stores 20 × 4 × 4 = 320 bytes. The example shows the contract: tokenizer IDs must be below 20, and every selected row has exactly four values because the residual width is four.

    Equations, symbol by symbol

    parameters(W) = ∏ shape_axis = rows × columns for a matrix

    The product symbol ∏ means multiply every axis size. For W shaped [12, 4], the parameter count is 48.

    storage_bytes ≈ parameter_count × bytes_per_parameter

    storage_bytes is approximate file or memory payload; parameter_count is the number of stored values; and bytes_per_parameter depends on dtype. Metadata, alignment, quantization scales, and runtime copies can make real usage differ.

    head_dim = model_dim / number_of_query_heads

    model_dim is the residual width, and head_dim is each query head’s feature width. Division must be exact. RoPE implementations that rotate pairs also require an even head dimension.

    Connection to mini_infer and performance

    Read common/config.py to see configuration validation: residual width divisibility, even head width for RoPE, and query-head divisibility by KV heads. Then read common/tokenizer.py for the dependency-free byte tokenizer. The model assembly in backends/python/model.py creates one embedding, repeated blocks, a final RMSNorm, and an output weight that may be tied to the input embedding.

    During prefill, token count determines how many prompt positions pass through every layer and how large attention’s position-by-position work becomes. During decode, the tokenizer determines the number of loop iterations needed to express an answer. Vocabulary size affects the embedding table and final vocabulary projection. The nested-list backend is intentionally readable and deterministic; production runtimes use optimized tensor libraries, fused kernels, accelerator memory layouts, and sophisticated weight loading.

    Common beginner mistakes

    • Calling a checkpoint “the model code” when it is mainly learned tensors and metadata.
    • Assuming token IDs have numeric distance or order that represents meaning.
    • Using a tokenizer from a different checkpoint because its vocabulary size happens to match.
    • Confusing parameters, which persist, with activations, which are computed per request.
    • Calculating memory from parameter count while ignoring dtype and runtime copies.
    • Assuming BPE simply merges the first adjacent pair rather than following ranked rules and pre-tokenization.
    • Assuming fewer tokens always wins without considering vocabulary projection and embedding cost.

    Check your understanding

    What is the difference between a weight and an activation?
    A weight is learned and persistent; an activation is computed temporarily from request inputs and weights.
    How many parameters are in a [8, 4] embedding table?
    32 parameters, because 8 × 4 = 32.
    Why must tokenizer and model agree?
    The model associates meaning with specific vocabulary rows; mismatched ID assignments select the wrong rows.
    What does BPE use to choose a merge?
    A ranked merge table over adjacent pieces, after the tokenizer’s pre-tokenization and byte mapping rules.
    Why can token count affect both latency and memory?
    It sets prompt positions processed in prefill, output decode iterations, and positions stored in the KV cache.

    1. For V=256, D=32, calculate embedding parameters and float32 bytes.
    2. Encode an emoji with ByteTokenizer, inspect its IDs, and verify decode returns the same text.
    3. Draw a table of expected shapes for embedding, query projection, and an MLP up/down pair.
    4. Explain what validation should fail when D=30 and there are eight query heads.

    We now have IDs and weight tables, but IDs themselves contain no geometry. Day 3 follows the embedding lookup that turns addresses into vectors and the output projection that turns final vectors back into vocabulary logits.

    Day 03

    Embeddings enter the model; logits leave it

    The same vocabulary can be viewed as rows at both ends of the network.

    Beginner intuition: addresses become coordinates

    A token ID is like a library card number: useful for finding a record but not itself a description of the book. An embedding table replaces the integer address with a learned list of features. Do not expect a single feature to mean “animal” or “past tense.” Meaning is distributed across many coordinates and becomes context-sensitive after transformer blocks. Tokens that the model uses similarly may develop useful geometric relationships, but the raw table is only the starting representation.

    This matters because nearly every model operation preserves or transforms a common residual width. Shapes such as [sequence, dim] become the thread you can follow through normalization, attention, MLPs, and residual additions. At the far end, an output projection compares each final token representation with one learned row per vocabulary item to produce logits. Input and output are therefore two views of the same vocabulary contract.

    Terminology for today

    • Embedding: a dense learned vector selected for an ID.
    • Embedding table: matrix shaped [vocab, dim].
    • Residual stream: the width-D representation carried through blocks and updated by residual additions.
    • Position representation: information that distinguishes where otherwise similar tokens occur.
    • Output projection or unembedding: map from final width D to V logits.
    • Weight tying: reusing the token embedding table as the output projection weight.
    • Cosine similarity: normalized directional similarity between vectors.

    Step-by-step mechanics with shapes

    1. Look upIDs [S] select rows from [V,D], producing [S,D].
    2. Add positionUse learned position vectors or encode position later with RoPE.
    3. TransformSend [S,D] through repeated width-preserving blocks.
    4. NormalizeStabilize each final width-D token vector.
    5. ProjectMultiply by vocabulary weights to produce logits [S,V].

    With a batch axis included, IDs usually have shape [B,S], embeddings [B,S,D], and logits [B,S,V]. The pure-Python backend handles one sequence, so it uses [S], [S,D], and [S,V]. Omitting a batch axis is an implementation choice, not a change in model mathematics.

    Lookup is array indexing, not multiplication by the integer ID. A useful mathematical fiction is to represent ID t as a one-hot row vector of length V whose only 1 is at position t. Multiplying that one-hot vector by E ∈ ℝ^(V×D) selects row E_t. Real code indexes directly because constructing mostly-zero one-hot vectors would waste time and memory.

    Equations, explained symbol by symbol

    x_s = E[token_id_s]

    s is a sequence position; token_id_s is the ID at that position; E is the [V,D] embedding table; and x_s is the selected [D] row.

    z_s = W_out h_s

    h_s is the final normalized [D] hidden vector; W_out is shaped [V,D] under the project’s out-by-in storage convention; and z_s is the [V] logit vector. Each output row takes a dot product with h_s. If weights are tied, W_out = E.

    cos(a,b) = (a · b) / (||a||₂ ||b||₂)

    a · b is the dot product, multiplying matching coordinates and summing. ||a||₂ is the Euclidean length. The result compares direction rather than raw magnitude and ranges from -1 to 1 when both vectors are nonzero. Similarity is a probe, not proof that one coordinate has a clean human interpretation.

    Worked toy example: lookup, then unembed

    Use four vocabulary items with a two-dimensional tied embedding table: 

    ID  token     embedding
0   "red"     [ 1.0,  0.0]
1   "blue"    [ 0.0,  1.0]
2   "warm"    [ 0.8,  0.2]
3   "cold"    [-0.2,  0.9]

    IDs [0,2] look up to a [2,2] activation: [[1,0],[0.8,0.2]]. Pretend the transformer’s final hidden vector for the last position is h=[0.9,0.1]. Taking a dot product with each tied row gives logits: red 1×0.9 + 0×0.1 = 0.9; blue 0.1; warm 0.8×0.9 + 0.2×0.1 = 0.74; cold -0.2×0.9 + 0.9×0.1 = -0.09. The shape is [4]. Greedy would choose “red.” Softmax would turn these scores into probabilities. Real dimensions and relationships are far larger and more complicated, but the row-wise dot products are the same idea.

    Where order enters

    A bare token lookup gives the same starting row every time an ID appears. A model still needs position. GPT-2 adds a learned position table P ∈ ℝ^(max_seq_len×D), making the initial activation at position s equal to E[token_s] + P[s]. The addition is legal because both rows have shape [D]. Learned tables have a configured row limit. Modern decoder designs often use RoPE instead: token embeddings enter without an added position table, and position-dependent rotations are applied to queries and keys inside attention. Day 4 explains why that still changes which positions match.

    Connection to mini_infer and performance

    In backends/python/embedding.py, Embedding.__call__ validates each ID and copies the selected row, returning [sequence, dim]. In backends/python/model.py, the hidden vectors traverse blocks and RMSNorm, then linear(vector, output_weight) creates one vocabulary-logit row per supplied token. Read backends/python/matrix.py to see the dot products explicitly.

    Prefill creates embeddings and logits for many prompt positions, though a generation API usually retains only the last logit row for selection. Decode creates the same kind of embedding and vocabulary row for one new position at a time. Large vocabularies make the final projection and probability processing noticeable; optimized systems may fuse or specialize these steps. Again, nested Python lists optimize for inspectability, not production throughput.

    Common beginner mistakes

    • Multiplying an embedding vector by the integer token ID instead of selecting a table row.
    • Assuming ID proximity implies embedding proximity.
    • Confusing embedding dimension D with vocabulary size V.
    • Thinking an embedding remains unchanged through layers; contextual hidden states evolve.
    • Assuming cosine similarity fully explains what a model “believes.”
    • Forgetting final normalization before the output projection in architectures that require it.
    • Assuming tied weights mean input embeddings and final hidden states are identical objects.

    Check your understanding

    What shape results when five IDs index E[1000,64]?
    [5,64]: one 64-value row per ID.
    Why is lookup not ordinary multiplication by an ID?
    The ID is a discrete address selecting a learned row; its numeric magnitude has no scaling meaning.
    What does the output projection produce?
    One unrestricted logit per vocabulary item for each supplied sequence position.
    What does weight tying save?
    It avoids storing a separate [V,D] output matrix and links input/output vocabulary geometry.
    Why does position information matter?
    Without it, attention cannot distinguish different orders containing the same token representations.

    Day 04

    Transformer blocks mix context and transform features

    Attention communicates across positions; the MLP works within each position.

    Beginner intuition: a searchable meeting notebook

    Picture each token as a participant carrying a notebook. A participant writes a query describing what information it needs. Every visible participant exposes a key describing what its note is about and a value containing the information to share. Query-key compatibility decides attention, and the weighted mixture of values becomes the gathered message. Several heads are several simultaneous search strategies. A causal rule closes future notebook pages, so generation cannot peek at tokens that do not exist yet.

    This matters because attention is both the context mechanism and a major systems cost. During prompt prefill, many query positions compare against many key positions. During cached decode, one new query compares with all retained keys. RoPE carries relative positional structure into those comparisons. GQA reduces the number of key/value histories without reducing query-head count, directly reducing cache memory.

    Terminology for today

    • RMSNorm: scale normalization based on root mean square, without subtracting a mean.
    • Residual connection: addition of a sublayer update back to its input.
    • Query, key, value: projected vectors used to request, match, and retrieve information.
    • Attention head: one independent query/key/value matching subspace.
    • Causal mask: rule blocking a position from attending to later positions.
    • MHA: multi-head attention with one key/value head per query head.
    • GQA: grouped-query attention where groups of query heads share key/value heads.
    • RoPE: rotary position embedding, a position-dependent rotation applied to query and key feature pairs.
    • MLP or FFN: per-position feed-forward network, often expanding then contracting feature width.

    Inside one pre-normalized block

    1. NormalizeRMSNorm each [D] token row.
    2. AttendProject Q/K/V, rotate Q/K, mix visible values, and output width D.
    3. AddResidual-add the attention update to the block input.
    4. TransformNormalize again, pass each position through the gated MLP.
    5. Add againResidual-add the MLP update, preserving [S,D].

    Let B=1, S=3, D=8, two query heads, and head width H=4. Input is [1,3,8]. Query projection remains [1,3,8], then reshapes to [1,2,3,4]: batch, heads, sequence, head features. With MHA, keys and values have the same shape. For each head, Q × Kᵀ turns [3,4] × [4,3] into a [3,3] score matrix. Every row is a query position; every column is a key position. Masking, row-wise softmax, and multiplication by V[3,4] return [3,4] per head. Concatenating two heads returns width 8; an output projection mixes the heads.

    Scaled dot-product attention, symbol by symbol

    Attention(Q,K,V) = softmax((QKᵀ / √d_h) + M) V

    Q contains query rows, K key rows, and V value rows. Kᵀ transposes keys so every query dot-products every key. d_h is head width. Dividing by its square root prevents dot-product magnitude from growing so much with width that softmax becomes extremely saturated. M is the mask: allowed entries add zero; blocked future entries add negative infinity, yielding probability zero. Softmax is row-wise, so each query’s weights over visible keys sum to one. Multiplication by V makes a weighted sum of value vectors.

    The causal score matrix is triangular. Query position 0 can use only key 0. Query 1 can use keys 0 and 1. Query 2 can use keys 0, 1, and 2. During full prefill this rule must be explicit because multiple query positions run together. During one-token decode with a correctly bounded cache, all stored positions are in the past or present, so there are no future cache entries to block.

    RoPE: position as rotation

    RoPE groups adjacent query and key features into two-dimensional pairs. For one pair (x₀,x₁) at position p, use angle φ = p × θ^(-r/d_h) for a frequency determined by pair index r, head width d_h, and base θ. The project expresses the rotation as:

    x'₀ = x₀ cos(φ) − x₁ sin(φ)
    x'₁ = x₀ sin(φ) + x₁ cos(φ)

    p changes the angle, while different feature pairs rotate at different frequencies. Rotation preserves the pair’s length. Applying related rotations to queries and keys makes their dot product depend on positional difference, giving attention useful relative-position structure. Values are not rotated in this implementation because position affects matching; the retrieved content can remain in its value representation. Cached keys must already contain the correct rotation for their absolute positions, and a new decode token must use start_pos = cached_token_count.

    GQA: many questions, fewer shared indexes

    Suppose n_heads=8 and n_kv_heads=2. There are eight query heads but only two key heads and two value heads. The grouping factor is 8/2=4: query heads 0–3 use KV head 0, and heads 4–7 use KV head 1. Query shape remains [B,8,S,H]; key and value shapes become [B,2,S,H]. Compared with MHA, key/value projection output and KV-cache storage fall by a factor of four in this example.

    queries_per_kv = n_query_heads / n_kv_heads

    The numerator counts query heads and the denominator key/value heads. Exact divisibility gives equal contiguous groups. GQA preserves multiple query perspectives while sharing the information index and content store. It is a model architecture decision reflected in checkpoint shapes; a server cannot arbitrarily turn an MHA checkpoint into GQA without changing weights and behavior.

    Worked toy example: one query attends to two values

    Let head width be 2. The current query is q=[1,0]. Visible keys are k₀=[1,0] and k₁=[0,1]; values are v₀=[10,0] and v₁=[0,6]. Dot products are 1 and 0. Divide by √2 ≈ 1.414 to get scores [0.707,0]. Exponentials are approximately [2.028,1], so softmax weights are about [0.670,0.330]. The output is 0.670[10,0] + 0.330[0,6] = [6.70,1.98]. Attention did not select a single value; it formed a weighted mixture. If key 1 were a future position, masking would set its score to negative infinity, making the result exactly [10,0].

    Connection to mini_infer and prefill/decode performance

    The complete reference path is split across attention.py, rope.py, and block.py. Attention creates query heads for every input token, appends rotated key heads and value heads to the cache, computes only through last_visible, maps each query head to a KV group, and projects concatenated attended heads. The block wraps it with RMSNorm, SwiGLU, and two residual additions.

    Full prefill attention compares many prompt queries with many prompt keys, giving quadratic score-pair growth with sequence length in the straightforward algorithm. Decode with a cache has one new query per sequence, so attention-score work per layer grows roughly linearly with retained context rather than recomputing a square for all earlier queries. FlashAttention improves memory traffic and kernel execution for exact attention; it does not change the mathematical dependency that queries must account for visible keys. The reference nested loops are a simulation for learning, not a production kernel benchmark.

    Common beginner mistakes

    • Thinking Q, K, and V are separate input texts rather than learned projections of activations.
    • Applying softmax over the wrong axis; each query row must normalize over visible keys.
    • Forgetting the √d_h scale or using total model width instead of head width.
    • Believing attention outputs only the highest-value token rather than a weighted mixture.
    • Rotating values with RoPE in an architecture that specifies rotation only for queries and keys.
    • Assuming GQA reduces query heads; it reduces KV heads while query-head count can remain high.
    • Calling all quadratic work “the Transformer”; MLP and projections have different scaling behavior.

    Day 05

    The KV cache trades memory for avoided recomputation

    Compute past keys and values once; let each new query read them again.

    Beginner intuition: keep the catalog cards

    Imagine answering a sequence of research questions from the same growing document. Without notes, you rebuild an index card for every old paragraph before answering each new question. With a cache, you file each paragraph’s key and value cards once. The next question needs one new query card, one new key card, and one new value card; it then searches all filed key cards and mixes the corresponding values. The archive grows, but old cards are never reconstructed.

    This matters because autoregressive generation can otherwise repeat large amounts of layer work. The optimization preserves attention mathematics when implemented correctly: old K/V vectors are deterministic functions of earlier layer inputs, weights, and positions. The price is persistent per-request memory, allocation complexity, fragmentation risk, and additional reads. At serving scale, KV capacity can limit concurrent sequences even when model weights fit comfortably.

    Terminology for today

    • KV cache: retained key and value vectors for every layer and processed position.
    • Cache entry: one position’s K/V heads at one layer.
    • Cache length: number of processed positions represented in every layer cache.
    • Prefill cache: K/V state created while processing prompt tokens.
    • Incremental decode: forwarding only new positions while supplying earlier cache state.
    • Cache capacity: token positions that available memory can hold for active sequences.
    • Cache correctness: equivalence of cached and uncached logits within expected numerical tolerance.

    Step-by-step mechanics with shapes

    1. Prefill promptCompute all layer K/V vectors for S prompt positions.
    2. Store per layerRetain keys and values shaped [S,H_kv,D_h].
    3. Choose tokenUse the prompt’s final logit row to select the first generated ID.
    4. Decode oneEmbed the new ID and compute only its new Q/K/V at each layer.
    5. Append and attendAdd new K/V to each cache; the new Q reads the complete K/V history.

    In the project’s single-sequence representation, one layer cache has keys and values each shaped conceptually [tokens, kv_heads, head_dim]. A model cache is a list with one such cache per transformer layer. With batch dimensions and production layouts, axes may be reordered and split into pages, but the logical information is the same.

    Suppose a prompt has five tokens. Prefill fills positions 0 through 4. The first decode input begins at start_pos=5. Its query uses position 5, its key is rotated for position 5, and the key/value pair is appended. The cache length becomes 6. Passing the entire six-token sequence together with that cache would double-count history; the cached path should receive only positions not already represented. Every layer must agree on cache length because a token cannot be at position 6 in one layer and position 5 in another.

    KV memory equation, symbol by symbol

    cache_bytes = 2 × L × B × S × H_kv × D_h × bytes_per_element

    The factor 2 stores both keys and values. L is transformer-layer count. B is active batch or number of equally sized sequences in this simple estimate. S is cached sequence length. H_kv is KV-head count. D_h is head width. The final factor is numeric storage per element, often two bytes for a 16-bit cache. Since H_kv × D_h equals the total KV width, the estimate is also often written 2 × L × B × S × kv_width × bytes.

    For L=4, B=1, S=10, H_kv=2, D_h=4, and two-byte elements: 2×4×1×10×2×4×2 = 1,280 bytes. Each additional token costs 2×4×2×4×2 = 128 bytes. With four sequences of equal length, multiply by four. Real allocators reserve blocks and metadata, so physical usage may exceed this logical payload.

    Worked toy example: two decode steps

    Use one layer, one head, and head width two. After a two-token prefill, let cached keys be [[1,0],[0,1]] and values be [[4,0],[0,8]]. A new token at position 2 produces q₂=[1,1], k₂=[1,1], and v₂=[2,2]. Append k₂ and v₂; now attention for q₂ uses all three keys and values. On the next decode step, a new q₃ uses four entries after k₃,v₃ are appended. The old pairs are read but not recomputed.

    An uncached full forward over tokens 0–2 would recreate K/V for all three positions and produce the same final-position logits in exact arithmetic. A correctness test should run both paths with identical weights and IDs, compare last-position logits or selected IDs across several steps, and allow only expected floating-point tolerance. Speed without equivalence is not an optimization; it is a model change or bug.

    What computation is actually saved?

    Without caching, decode step t forwards the whole prefix of length t through every layer, recreating projections and intermediate states for old positions. Across many generated steps, this repeatedly pays for earlier work. With caching, the model processes one new token through normalization, projections, attention, MLP, and output projection. Attention still compares the new query with an increasingly long key history and mixes an increasingly long value history. Cached decode is therefore not constant-work in a strict algorithmic sense, even if short benchmark curves look flat; per-token KV reads and attention operations grow with context length.

    Prefill remains distinct. It handles the prompt in parallel and creates the initial cache; time to first token includes this work. Decode reuses that cache and influences inter-token latency. A long prompt may make prefill compute-heavy, while many concurrent decoders can make memory bandwidth and KV capacity dominant. This distinction explains why engines schedule prompt tokens and decode tokens differently.

    Connection to mini_infer

    The KVCache dataclass and append/read behavior are visible in backends/python/attention.py. forward_with_cache in backends/python/model.py checks that there is one cache per block, all block caches contain the same number of tokens, and start_pos equals that number. Those validations turn silent positional corruption into an explicit error. Memory arithmetic is isolated in optimizations/kv_cache_estimator.py, which computes bytes per token and maximum tokens for a memory budget.

    Simulation honesty: The reference cache uses Python objects and nested lists, so its physical memory and speed do not match the estimator’s dense-tensor assumptions or a production engine. Production systems use contiguous or paged device buffers, block allocators, specialized kernels, and batch metadata. Use this code to learn invariants and shapes, not to forecast GPU throughput.

    Common beginner mistakes

    • Saying the KV cache stores attention probabilities; it stores projected keys and values.
    • Passing old tokens again while also passing their cache, duplicating positions.
    • Using the wrong start_pos, which applies wrong RoPE angles and breaks equivalence.
    • Forgetting the factor of two for both K and V or the layer count in memory estimates.
    • Using query-head count instead of KV-head count for a GQA cache.
    • Claiming cached decode has no context-length cost; it still reads and attends over history.
    • Benchmarking only steady-state decode and calling it total latency while ignoring prefill and queue time.

    Check your understanding

    What is retained in the KV cache?
    Per-layer projected key and value vectors for already processed positions.
    What does a new decode token still compute?
    Its embedding and per-layer normalization, Q/K/V, attention output, MLP updates, final normalization, and logits.
    Why must start_pos equal cache length?
    The new token’s position and RoPE rotation must immediately follow the positions represented by cached keys and values.
    How does GQA affect KV memory?
    Memory scales with KV heads, so fewer KV heads reduce K/V projection width and cache payload.
    Does caching change correct model output?
    It should not; cached and uncached paths should be mathematically equivalent aside from expected numerical effects.
    Why can memory limit concurrency?
    Every active sequence retains per-layer K/V data that grows with processed token count.

    Phase summary

    One end-to-end story

    If you can narrate this without skipping shapes, Phase 1 has done its job.

    1. Text is encoded by the checkpoint-compatible tokenizer into IDs shaped [B,S].
    2. IDs select embedding rows, producing hidden activations shaped [B,S,D].
    3. Every block normalizes, attends to causally visible positions, residual-adds, applies a per-position MLP, and residual-adds again.
    4. RoPE rotates Q/K pairs by position; GQA allows groups of query heads to share fewer K/V heads.
    5. Final normalization and vocabulary projection produce logits shaped [B,S,V].
    6. The final sequence row logits[b,-1,:] predicts the next token after that sequence’s full visible prefix.
    7. A decoding policy transforms or filters logits and chooses one token ID, then stopping rules decide whether to continue.
    8. Prefill processes prompt positions and establishes per-layer K/V state; decode forwards only new positions while reading history.
    9. The KV cache removes repeated K/V construction but consumes memory proportional to layers, sequence length, KV width, batch, and bytes per element.

    Glossary

    Forty compact definitions for review.

    A–C

    Activation
    Temporary tensor computed during a forward pass.
    Argmax
    Index of the largest value; used by greedy decoding.
    Attention
    Query-dependent weighted mixing of value vectors using query-key scores.
    Autoregressive
    Generating while conditioning on previously generated outputs.
    Batch
    Group of sequences processed in shared execution.
    BPE
    Tokenization method that applies ranked adjacent-piece merges.
    Causal mask
    Restriction preventing a position from seeing future positions.
    Checkpoint
    Stored model configuration and learned tensors, often with tokenizer artifacts.
    Context length
    Number of token positions visible or supported for a sequence.

    D–H

    Decode phase
    Incremental generation after prompt state exists.
    Dimension
    Either an axis of a tensor or, contextually, the size of a feature space.
    Dtype
    Numeric representation and precision used to store values.
    Embedding
    Learned dense vector selected for a token ID.
    EOS
    Special end-of-sequence token used as one possible stop signal.
    Forward pass
    Applying model operations to input activations to produce outputs.
    GQA
    Grouped-query attention: multiple query heads share fewer KV heads.
    Head
    One attention subspace with its own query matching behavior.
    Head dimension
    Feature width of one attention head.
    Hidden state
    A token’s intermediate or final width-D representation.

    K–P

    Key
    Projected vector matched against a query.
    KV cache
    Per-layer history of keys and values for processed positions.
    Logit
    Unnormalized vocabulary score.
    MLP/FFN
    Per-token feature transformation inside a transformer block.
    MHA
    Multi-head attention with matching query and KV head counts.
    Parameter
    Learned persistent scalar stored in a weight tensor.
    Position
    A token’s index in its sequence.
    Prefill
    Prompt processing that creates initial logits and cache state.
    Probability
    Normalized nonnegative value; categorical probabilities sum to one.
    Prompt
    Input token sequence present before generated output.

    Q–W

    Query
    Projected vector describing what a position seeks from visible keys.
    Residual connection
    Addition of a sublayer update to its input.
    Residual stream
    Width-preserving sequence of token representations through blocks.
    RMSNorm
    Normalization by root mean square followed by learned scaling.
    RoPE
    Position-dependent rotations of query/key feature pairs.
    Sampler
    Policy that selects a token from processed logits or probabilities.
    Shape
    Ordered list of sizes along a tensor’s axes.
    Softmax
    Exponential normalization that maps logits to probabilities.
    Temperature
    Positive divisor controlling logit-distribution sharpness.
    Tensor
    Rectangular multidimensional collection of numeric values.
    Token
    Vocabulary unit represented by an integer ID.
    Top-k
    Filtering that keeps a fixed number of highest logits.
    Top-p
    Filtering that keeps the smallest high-probability prefix reaching mass p.
    Value
    Projected content vector mixed according to attention weights.
    Vocabulary
    Complete set of token IDs and corresponding pieces.
    Weight tying
    Sharing a parameter matrix between token embedding and output projection.

    Formula sheet

    Write the shapes beside every formula when solving an exercise.

    Softmax

    p_i = exp(z_i − max(z)) / Σ_j exp(z_j − max(z))

    Stable normalization over candidate logits.

    Temperature

    p = softmax(z / T), T > 0

    Lower T sharpens; higher T flattens.

    Embedding lookup

    x_s = E[token_id_s], E:[V,D]

    Select one width-D row per ID.

    Output projection

    z_s = W_out h_s, W_out:[V,D]

    One dot product per vocabulary row.

    Cosine similarity

    cos(a,b) = (a·b)/(||a||₂||b||₂)

    Directional similarity for nonzero vectors.

    Attention

    A = softmax((QKᵀ/√d_h)+M)V

    Scale, mask, normalize each query row, and mix values.

    RoPE pair

    (x'₀,x'₁)=(x₀cosφ−x₁sinφ, x₀sinφ+x₁cosφ)

    Position-dependent two-dimensional rotation.

    KV grouping

    queries_per_kv = H_q / H_kv

    Equal query groups require exact divisibility.

    KV bytes

    2 × L × B × S × H_kv × D_h × bytes

    The leading 2 is for keys and values.

    count([rows,cols]) = rows × cols
