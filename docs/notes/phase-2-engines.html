    First-principles orientation. A CPU is a general-purpose processor optimized for flexible, low-latency control flow. A GPU is a throughput processor containing many simpler arithmetic lanes that perform similar work on many data elements. Neither is universally “faster.” A CPU excels at branching, orchestration, and small serial tasks; a GPU excels when enough parallel arithmetic is available to occupy its lanes. In an inference service, the CPU commonly tokenizes, schedules, and launches work while the GPU executes tensor operations.
    06

    Measure before optimizing

    Ops:byte ratio and the roofline model

    Day 6 gives us a ruler for performance. Instead of saying “the GPU is slow,” we ask whether an operation is waiting for arithmetic units or waiting for bytes. That distinction determines whether to change math, memory traffic, batching, or hardware.

    A beginner analogy: cooks, ingredients, and a narrow pantry door

    Imagine a restaurant with 100 cooks but only one narrow pantry door. If every dish requires one quick stir and ten trips through that door, adding more cooks will not help; they queue for ingredients. That is a memory-bound kitchen. If ingredients arrive in one crate and each dish needs an hour of chopping, the pantry is idle while cooks work; that is compute-bound. A GPU has the same two broad resources: arithmetic capacity and data-movement capacity. Floating-point operations per second describe the cooks. Memory bandwidth describes the pantry door. Arithmetic intensity tells us how much work is done for each byte brought through the door.

    Why it matters

    Roofline reasoning prevents expensive category errors. If decode already waits on HBM, buying more arithmetic peak or deleting a few multiplies may change almost nothing. Reducing weight bytes, reusing them across a batch, or avoiding cache traffic is more promising. Conversely, a compute-heavy prefill may benefit from tensor-core-friendly shapes and precision. The model turns hardware specifications into a testable performance hypothesis before anyone spends weeks rewriting code.

    Definitions from the ground up

    Operation
    A primitive arithmetic action such as an addition or multiplication. Hardware specifications often count a fused multiply-add as two floating-point operations.
    FLOPS
    Floating-point operations per second, a rate. FLOP without the final “S” is a count of work.
    Byte
    Eight bits of stored information. BF16 and FP16 values occupy two bytes; FP32 values occupy four.
    Memory hierarchy
    Storage arranged from tiny and fast to large and slower: registers, shared memory/L1 cache, L2 cache, GPU HBM, then host RAM and storage.
    Bandwidth
    The maximum rate at which bytes move, commonly GB/s or TB/s. It is not the same as latency, which is the delay for one access.
    Arithmetic intensity
    The operation’s work divided by bytes transferred across the memory boundary being studied, measured in operations per byte.
    Memory-bound
    Performance is limited mainly by byte movement; unused arithmetic capacity cannot help until traffic is reduced or reused.
    Compute-bound
    Performance is limited mainly by arithmetic throughput; faster memory alone is unlikely to help.
    I = O / D
    P attainable = min(P peak, I × B)
    I ridge = P peak / B
    • I is arithmetic intensity in operations per byte.
    • O is the number of arithmetic operations performed.
    • D is the number of bytes transferred from the memory level under study.
    • P attainable is the upper-bound performance for this operation.
    • P peak is the hardware’s peak arithmetic rate in operations per second.
    • B is memory bandwidth in bytes per second.
    • I ridge is the break-even intensity where the sloped bandwidth roof meets the flat compute roof.

    Step-by-step: classifying an operation

    1. Choose a boundary. Are you counting traffic from HBM to the chip, from L2 to streaming multiprocessors, or from CPU RAM over PCIe? The answer changes the byte count.
    2. Count useful operations. For a matrix multiplication with shapes M×K and K×N, a common approximation is 2MKN operations.
    3. Count transferred bytes. Include inputs and output, and include repeated reads if the implementation fails to retain data in cache.
    4. Compute intensity. Divide operations by bytes. Keep the units visible so mistakes are obvious.
    5. Compute the ridge point. Divide device peak operations per second by peak bandwidth.
    6. Compare and verify. Below the ridge suggests memory pressure; above it suggests compute pressure. Then profile, because peaks, cache hits, launch overhead, and irregular access make the roofline an upper bound rather than a stopwatch.

    Worked example: one decode projection

    Consider a simplified linear layer with a weight matrix containing 8 million BF16 values. The weights occupy 16 MB because each value uses two bytes. For one request producing one token, suppose the matrix-vector product performs approximately 16 million operations: each weight contributes one multiply and one add. Ignore the much smaller input and output for this toy estimate. Intensity is therefore 16 million ops / 16 million bytes = 1 op/byte. On an imaginary GPU with 100 TFLOP/s peak BF16 throughput and 1 TB/s HBM bandwidth, the ridge is 100 tera-ops/s ÷ 1 tera-byte/s = 100 ops/byte. Our 1 op/byte operation sits far left of the ridge. Its bandwidth roof is only 1 op/byte × 1 TB/s = 1 TFLOP/s, even though the box advertises 100 TFLOP/s.

    Now batch 32 independent decode tokens. The same 16 MB weight matrix can be reused while producing 32 outputs. Work rises to about 512 million operations, but weight traffic can remain near 16 MB if the kernel reuses weights effectively. Intensity approaches 32 ops/byte. That is still below the 100 ops/byte ridge, but thirty-two times better. A batch near 100 would approach the ridge in this idealized model. Real traffic includes activations, cache reads, and imperfect reuse, so measurement is still required. The important insight is that batching changes the numerator much faster than the dominant weight bytes in the denominator.

    Prefill and decode occupy different neighborhoods

    During prefill, many prompt positions pass through large matrix multiplications together. A weight tile fetched once can participate in calculations for many token rows, raising arithmetic intensity. Prefill often leans toward compute-bound behavior, particularly for large batches or long prompts. During decode, each active sequence adds only one position per iteration. The engine repeatedly reads model weights and a growing KV history to produce relatively little new work. Decode therefore tends to be bandwidth-sensitive. This is a tendency, not a law: small prefill batches can waste compute, long-context attention can become memory-heavy, and a large decode batch can raise reuse enough to approach the compute roof.

    Pseudo-code: a five-minute estimate

    def roofline_estimate(operations, transferred_bytes, peak_ops_s, bandwidth_bytes_s):
    intensity = operations / transferred_bytes
    ridge = peak_ops_s / bandwidth_bytes_s
    bandwidth_roof = intensity * bandwidth_bytes_s
    attainable = min(peak_ops_s, bandwidth_roof)
    bottleneck = "memory" if intensity < ridge else "compute"
    return intensity, ridge, attainable, bottleneck

# Toy BF16 projection, batch 32
ops = 2 * 32 * 8_000_000
weight_bytes = 8_000_000 * 2
print(roofline_estimate(ops, weight_bytes, 100e12, 1e12))

    Latency, throughput, and memory tradeoffs

    Increasing batch size usually improves throughput because weight bytes are amortized across requests. Yet a request may wait longer for companions, increasing queueing delay and time to first token. Larger batches also need more activation and KV memory, leaving less room for concurrent sequences. Lower-precision weights reduce bytes and may improve bandwidth-limited decode, but only if the GPU has an efficient kernel for that format and dequantization overhead is controlled. Kernel fusion reduces intermediate traffic without waiting for a larger batch. Capacity planning therefore needs three separate objectives: per-request latency, aggregate tokens per second, and memory headroom. One “utilization” percentage cannot summarize all three.

    When to use roofline reasoning

    Use it before kernel work, hardware selection, quantization, or batching changes. It is excellent for eliminating implausible optimizations and explaining why a high-FLOPS accelerator may underperform on decode.

    When not to stop there

    Do not use a theoretical roofline as proof of measured performance. Very small kernels may be launch-bound; network collectives may dominate distributed inference; poor occupancy, synchronization, or noncoalesced access can sit far below both roofs.

    Common mistakes

    • Mixing decimal TB/s with binary TiB/s while expecting exact agreement.
    • Counting only model weights while forgetting KV-cache and activation traffic.
    • Calling arithmetic intensity a hardware property; the ridge is hardware-specific, while intensity belongs to an algorithm plus implementation and chosen memory boundary.
    • Assuming prefill is always compute-bound and decode is always memory-bound without considering batch, context, model architecture, and precision.
    • Optimizing FLOP count when the operation already waits for bytes.
    Production concept

    Profilers and measured roofs

    Production teams use hardware counters and profilers such as NVIDIA Nsight Compute to measure achieved bandwidth, tensor-core use, occupancy, and stalls. Device specifications provide ceilings, not observed rates.

    Knowledge checks

    1. What does 20 ops/byte mean?

    The implementation performs about twenty counted arithmetic operations for each byte crossing the selected memory boundary. It does not mean the GPU itself has a fixed intensity of twenty.

    2. A device has 60 TFLOP/s and 1.5 TB/s. What is its ridge?

    60 ÷ 1.5 = 40 ops/byte, with matching tera units canceling. Operations below roughly 40 ops/byte are under the bandwidth slope in the ideal roofline.

    3. Why can batching improve decode throughput?

    Multiple token rows reuse a fetched weight tile, increasing operations faster than dominant weight traffic. This raises arithmetic intensity and amortizes launch and scheduling overhead.

    4. Why can batching hurt latency?

    A request may wait for a batch to form, and a larger combined kernel can occupy the GPU longer before any one request receives its result.

    5. Is a memory-bound kernel necessarily badly written?

    No. Some algorithms inherently do little work per byte. The relevant question is whether avoidable traffic remains and whether the measured bandwidth approaches a realistic device limit.

    07

    Turn equations into GPU work

    CUDA kernels, kernel selection, fusion, and FlashAttention intuition

    A model graph says what mathematical functions are required. A kernel says how one of those functions runs on GPU hardware. Performance depends heavily on that “how”: thread layout, tile sizes, memory access, precision, and which intermediate tensors are never written to HBM.

    A beginner analogy: one workshop order or six courier trips

    Suppose a carpenter must cut, sand, paint, and label a board. One plan sends the board to four buildings, with a courier trip after every step. Another plan places all tools in one workshop and moves the board once. Both produce the same board; the second avoids transportation and dispatch paperwork. Separate GPU kernels resemble separate buildings. Each launch has control overhead, and an intermediate may be written to HBM before the next kernel reads it. A fused kernel resembles the shared workshop: values can remain in registers or on-chip shared memory between steps.

    Why it matters

    Transformer decode repeats many small operations across every layer and generated token. A few microseconds of launch overhead or one unnecessary HBM round trip can therefore recur thousands of times in a request. Understanding kernels lets an engineer distinguish an algorithm improvement from an execution-schedule improvement, select realistic benchmarks, and avoid claiming GPU speedups from code that never runs on a GPU.

    CPU, GPU, and kernel vocabulary

    CUDA
    NVIDIA’s programming platform and execution model for GPU computation. CUDA is broader than a single language keyword or library.
    Kernel
    A function launched by the host and executed in parallel by many GPU threads. “Kernel” here does not mean an operating-system kernel.
    Thread / warp / block
    A thread handles one logical lane of work; NVIDIA schedules threads in groups called warps; blocks group cooperating threads that can synchronize and share on-chip memory.
    Grid
    All thread blocks launched for one kernel invocation.
    Register
    Very small, very fast per-thread storage. Too many registers per thread can reduce how many warps fit concurrently.
    Shared memory
    Program-managed on-chip storage shared by threads in a block. It is useful for tiles reused by many threads.
    Kernel launch
    The CPU/runtime operation that queues GPU work. It has a nonzero fixed cost, especially visible for tiny decode operations.
    Kernel selection
    Choosing an implementation and configuration suited to shape, dtype, architecture, layout, and objective.

    Step-by-step: from PyTorch expression to silicon

    1. Python calls an operator such as matrix multiplication, normalization, or elementwise activation.
    2. The framework dispatches by device, dtype, shape, and layout. A library such as cuBLAS may supply a family of candidate kernels.
    3. The runtime launches a chosen kernel. The CPU normally continues asynchronously until synchronization is required.
    4. GPU blocks are assigned to streaming multiprocessors. Warps issue loads and arithmetic instructions.
    5. Data travels from HBM through cache or directly into on-chip storage. Reused tiles stay near compute when possible.
    6. Results are written. A following kernel may read them, or fusion may keep temporary values on chip and write only the final output.
    Unfusedload → op A → HBM
    Unfusedload → op B → HBM
    Fusedload once
    FusedA → B on chip → store
    T total ≈ Σ(T launch,k + max(O k / P effective,k, D k / B effective,k))
    • T total is approximate total time across kernels.
    • T launch,k is launch and dispatch cost for kernel k.
    • O k and D k are operation count and transferred bytes for kernel k.
    • P effective,k and B effective,k are realistic, not advertised-peak, compute and bandwidth rates.
    • Fusion can lower the number of launch terms and lower D by removing intermediate stores and loads.

    Worked example: fusing bias, activation, and multiply

    Take a toy vector with one million FP16 elements, so one vector occupies 2 MB. An unfused gated activation might write a 2 MB biased intermediate, read and write it for an activation, then read that result and a second 2 MB vector for multiplication before writing a final 2 MB vector. Ignoring caches and original input reads, those temporary stages can easily account for roughly 12 MB of intermediate reads and writes. At an achieved 600 GB/s, pure transfer time for 12 MB is about 12 MB ÷ 600,000 MB/s = 20 microseconds. Add three launches at an illustrative 8 microseconds each and fixed overhead reaches about 44 microseconds.

    A fused kernel can load source values, add bias, evaluate the activation, multiply, and write only the 2 MB final output. If its required traffic is 6 MB including source reads and output, transfer takes about 10 microseconds, plus one 8-microsecond launch: roughly 18 microseconds in this simplified model. The arithmetic barely changed. Data movement and dispatch did. The exact numbers vary by GPU and shape, but the accounting method shows why small per-layer savings matter when repeated over dozens of layers and hundreds of decode steps.

    Kernel selection is a matching problem

    There is no universally fastest matrix-multiplication kernel. A tile optimized for large square matrices may waste lanes on a skinny matrix-vector shape. Tensor cores require supported dtypes and alignment. More warps may hide memory latency but consume registers and shared memory. A runtime can use heuristics, benchmark candidates during a build, or generate specialized code. Selection keys often include GPU architecture, dimensions, batch, sequence length, head size, data type, strides, causal mode, and whether quantization scales must be applied. This explains why two mathematically identical executions can have different latency.

    FlashAttention: exact attention with a smaller working set

    Ordinary attention is often taught as three steps: form scores S = QKᵀ / √d, apply row-wise softmax, then compute PV. A straightforward implementation materializes the entire score and probability matrices. For sequence length N, those matrices contain N² entries. FlashAttention changes the schedule, not the desired mathematical result. It loads tiles of queries, keys, and values into on-chip memory, computes partial score tiles, and maintains enough statistics to update softmax incrementally. The full N×N matrix never needs to live in HBM.

    m new = max(m old, max(s tile))
    ℓ new = exp(m old − m new)ℓ old + Σ exp(s i − m new)
    a new = exp(m old − m new)a old + Σ exp(s i − m new)v i
    output = a final / ℓ final
    • s tile contains the score values in the current key tile.
    • m is the running maximum used for numerical stability.
    • ℓ is the running sum of exponentials after rescaling.
    • a is the running value-weighted numerator.
    • v i is the value vector paired with score s i.

    Toy online-softmax calculation

    Suppose one query sees scores [1, 2] in the first tile and score [3] in the second. After tile one, the running maximum is 2 and the sum is exp(1−2)+exp(2−2)=0.368+1=1.368. When score 3 arrives, the new maximum becomes 3. The old sum must be rescaled by exp(2−3)=0.368, giving about 0.503, and the new score contributes 1. The final denominator is about 1.503. This equals evaluating all scores with maximum 3: exp(−2)+exp(−1)+1 ≈ 0.135+0.368+1=1.503. The same rescaling applies to the accumulated weighted values, so tiles combine exactly apart from normal floating-point rounding. 

    # Educational structure, not a CUDA kernel
for query_tile in tiles(Q):

    running_sum = 0
    weighted_values = 0

        tile_max = row_max(scores)
        new_max = maximum(running_max, tile_max)
        correction = exp(running_max - new_max)
        probabilities = exp(scores - new_max)
        running_sum = correction * running_sum + row_sum(probabilities)
        weighted_values = correction * weighted_values + probabilities @ value_tile
        running_max = new_max
    output_tile = weighted_values / running_sum

    Latency, throughput, and memory tradeoffs

    Fusion usually reduces launches and HBM traffic, helping both latency and throughput. It can also increase register pressure, reduce occupancy, or duplicate code across many shape variants. FlashAttention lowers temporary memory dramatically and often speeds long sequences, but short shapes may not amortize setup. CUDA graphs reduce repeated launch overhead by capturing a static execution sequence, yet dynamic batch shapes require padding, multiple captured buckets, or fallback execution. Padding spends compute and memory for regularity. Compilation spends build time and storage to save runtime time. Kernel engineering is therefore a search over the whole workload distribution, not a benchmark of one convenient shape.

    When to use fusion and specialized kernels

    Use them for stable, frequently executed patterns with substantial launch or intermediate-traffic cost. They are especially valuable in repeated decoder layers and fixed production shape ranges.

    When not to use them

    Avoid premature custom kernels when the operation is rare, shapes change constantly, framework kernels already saturate hardware, or maintenance and numerical-validation costs exceed the saved latency.

    Common mistakes

    • Calling a Python function a CUDA kernel simply because it implements the same equation.
    • Assuming fewer kernels always means faster execution; an oversized fused kernel may spill registers or limit occupancy.
    • Timing asynchronous GPU work without synchronization, which measures queueing rather than completion.
    • Thinking FlashAttention approximates attention. The core algorithm computes exact attention up to floating-point ordering differences.
    • Choosing a kernel from model name alone while ignoring shape, dtype, stride, and GPU architecture.

    Knowledge checks

    1. What is a GPU kernel?

    A host-launched function whose many threads run in parallel on a GPU. It encodes an execution strategy for an operation, not merely its mathematical definition.

    2. What two costs can fusion reduce?

    It can reduce fixed launch/dispatch count and HBM traffic for intermediate tensors. The arithmetic count may remain almost unchanged.

    3. Why not keep every tensor in registers?

    Registers are extremely limited and private to threads. Excess demand spills to slower memory and can reduce resident warps, harming latency hiding.

    4. What does online softmax remember between tiles?

    A running maximum, a properly rescaled exponential sum, and a properly rescaled value-weighted accumulator for each query row.

    5. Why does kernel selection depend on shape?

    Shape determines tile fit, parallel work, padding, memory reuse, and whether specialized hardware instructions can be used efficiently.

    08

    Know what the file promises

    PyTorch weights, SafeTensors, ONNX, TensorRT, and execution formats

    “Model format” can mean a bag of numbers, a program-shaped graph, or a compiled plan. Confusing these categories creates security risks, portability surprises, and deployment failures. Day 8 builds a precise vocabulary for moving a trained model into an inference runtime.

    A beginner analogy: ingredients, recipe, kitchen, and prepared meal

    A box of ingredients is like a weight-only file: useful numbers, but no complete cooking procedure. A printed recipe resembles a portable computation graph: it names operations and how outputs feed inputs, but a kitchen must still implement them. The kitchen resembles a runtime such as PyTorch, ONNX Runtime, or TensorRT. A catering line built for one venue resembles a compiled engine: stations, tools, and timing have already been chosen for a target. You cannot ask whether “the model file” is portable until you know which of these objects it is.

    Why it matters

    Deployment failures often begin with an artifact assumption: unsafe loading, missing architecture code, an unsupported ONNX operator, or a plan built for another target. Precise categories make the supply chain auditable. They also reveal where optimization occurs. A smaller or safer weight file changes loading behavior; a graph enables cross-operation analysis; a compiled plan records target-specific execution choices. One does not automatically provide the benefits of another.

    Definitions and layers

    PyTorch module
    A Python object that defines parameters, submodules, and forward behavior. Its meaning depends on Python code and PyTorch semantics.
    State dict
    A mapping from parameter or buffer names to tensors. It stores state, not the Python class implementation needed to use that state.
    Pickle
    Python object serialization capable of reconstructing objects by executing instructions. Loading an untrusted pickle is unsafe.
    SafeTensors
    A non-executable tensor container with metadata and contiguous tensor bytes, designed for safe and efficient loading and memory mapping.
    Memory mapping
    Letting the operating system map file regions into virtual memory so pages are loaded on demand rather than copied through one giant user-space buffer.
    ONNX
    A portable graph representation with standardized operators, tensor types, initializers, and graph connections.
    Runtime
    Software that loads an artifact, allocates memory, selects implementations, executes operations, and manages devices.
    Execution plan / engine
    A compiled, specialized artifact containing target-specific choices such as fused layers, tactics, precision, and workspace assumptions.

    Step-by-step: from checkpoint to serving process

    1. Reconstruct architecture. Load trusted model code and configuration: layer count, hidden size, head layout, vocabulary, positional method, and tensor naming.
    2. Load tensors. Read state from a trusted PyTorch state dict or SafeTensors shards. Validate names, shapes, dtypes, shard indexes, and checksums.
    3. Run an eager reference. Feed known inputs through native PyTorch and store outputs or token-level comparisons as a correctness baseline.
    4. Export a graph if needed. Capture operations, constants, shapes or dynamic dimensions, and supported control flow into an interchange representation such as ONNX.
    5. Compile or optimize. Select target hardware, allowed precision, shape profiles, memory workspace, and candidate kernels or tactics.
    6. Validate again. Compare the optimized runtime with the trusted reference over normal and boundary shapes. Numerical tolerances must reflect chosen precision.
    7. Package the contract. Keep tokenizer, generation configuration, model revision, adapter identity, checksums, runtime version, GPU architecture, and build flags together.

    Worked example: storage, loading, and specialization

    Imagine a tiny transformer with 16 million parameters. In FP32, raw tensor payload is 16,000,000 × 4 bytes = 64 MB. In FP16, it is 32 MB. Container headers add some metadata but do not change the basic scaling. A SafeTensors file can describe each tensor’s dtype, shape, and byte offsets; a loader can map the file and read slices without reconstructing arbitrary Python objects. A PyTorch state dict can contain the same tensor values, but its conventional serialization path belongs to the Python/PyTorch ecosystem.

    Next export an ONNX graph with an input shape like [batch, sequence, hidden]. If batch and sequence are dynamic, the graph is more reusable, but the optimizer must retain implementations that cover a range. If we compile a TensorRT engine for batch 1–8 and sequence 1–2048 on a particular GPU family, the builder can test tactics and reserve workspace for that profile. A request with batch 16 is outside the contract. An engine built for a different GPU architecture or plugin version may not load. The compiled artifact can be faster precisely because it discards some generality.

    Weight bytes = N params × bytes per parameter
    Approximate load floor = bytes read / effective storage bandwidth
    • N params is the number of stored parameter values, not necessarily the model’s operation count.
    • Bytes per parameter follows the storage dtype, such as 4 for FP32 or 2 for FP16/BF16.
    • Effective storage bandwidth includes filesystem, cache, decompression, host memory, and transfer behavior; it is usually below a device’s advertised sequential rate.
    • The equation is a lower-bound intuition. Parsing, allocation, conversion, and device copies add time.

    Latency, throughput, memory, and portability tradeoffs

    Eager PyTorch maximizes debuggability and flexibility but pays dispatch and generality costs. Graph capture and compilation can fuse operations, plan memory, and select kernels, improving latency or throughput after warmup. Builds consume time, may require large temporary workspace, and create artifacts tied to versions and targets. SafeTensors improves loading safety and enables efficient access patterns, but it does not by itself accelerate forward execution. ONNX can cross framework boundaries, but unsupported or custom operators may require graph rewriting or runtime extensions. TensorRT can deliver strong NVIDIA performance, but narrow shape profiles and hardware coupling increase the artifact matrix a team must build, test, store, and roll back.

    Use SafeTensors for distributing weight-only checkpoints safely; native PyTorch for research and dynamic behavior; ONNX when interchange matters and operators are supported; TensorRT when a controlled NVIDIA deployment justifies build and validation effort.

    Manage state as requests change

    vLLM, PagedAttention, and continuous batching

    Serving one sequence is mostly a model-execution problem. Serving many unpredictable sequences becomes a memory-allocation and scheduling problem. vLLM popularized an engine design in which KV state is divided into fixed-size blocks and active batches change after every iteration.

    A beginner analogy: a hotel with rooms instead of one private floor

    Imagine a hotel that promises every guest an entire contiguous floor because it does not know how many friends will arrive later. Most rooms remain empty, and a guest cannot use scattered rooms on two floors even when the hotel has enough total vacancies. Paging changes the promise: each guest receives rooms only as needed, and a card lists the room numbers. The rooms need not be adjacent. A block table is that card. Fixed-size KV blocks are the rooms. The final partly filled room is internal fragmentation; unusable gaps between variable allocations are external fragmentation. Continuous batching is the front desk filling a newly vacant room immediately instead of waiting for every guest in a tour group to check out.

    Why it matters

    KV cache can consume tens of gigabytes and determines how many requests fit beside model weights. Poor reservation wastes that capacity, while a batch that drains slowly wastes compute. Paged allocation and iteration-level scheduling convert freed memory and finished slots into usable capacity quickly. For a busy service, those mechanisms can improve goodput more than a small kernel speedup because they decide whether the GPU has useful work at all.

    Start with batching and the KV cache

    Batching combines work from several requests into one model execution so weights and GPU launches are shared. A static batch is formed once and remains together until completion. If one sequence ends after ten tokens while another needs two hundred, the finished slot may remain wasted or the whole batch may wait. Continuous batching, also called iteration-level batching, reconsideres membership between decode iterations. Finished or paused requests leave; waiting requests enter. The shape still must suit available kernels, but the logical population changes continuously.

    Each transformer layer saves keys and values for every processed token so later decode steps do not recompute them. This KV cache grows with context length and active sequence count. Because generated length is unknown at admission, reserving a maximum contiguous region wastes memory. Allocating variable-size extensions can leave holes and complicate relocation. PagedAttention separates a sequence’s logical token order from physical storage locations.

    KV cache
    Per-layer key and value tensors retained from earlier positions and read by future attention steps.
    Physical block
    A fixed-size region in the cache pool that stores KV entries for a fixed number of token positions.
    Logical block
    A numbered chunk in a sequence’s token order: logical block zero, one, two, and so on.
    Block table
    Per-sequence metadata mapping each logical block number to a physical block identifier.

    Unused space inside an allocated block, normally in a sequence’s final partially occupied block.
    External fragmentation
    Free space split into holes that cannot satisfy a larger contiguous request even though total free bytes are sufficient.
    Continuous batching

    Preemption
    Temporarily removing a request from execution when resources are scarce, potentially recomputing or swapping state later.

    Worked KV-size example

    Consider a model with 32 layers, 8 KV heads, head dimension 128, and BF16 cache values. Per token, KV storage is 2 × 32 × 8 × 128 × 2 = 131,072 bytes, or 128 KiB. A 4,096-token sequence therefore uses about 512 MiB of KV state. Sixty-four such sequences at that length would require about 32 GiB before allocator reserve and workspace. If the model used 32 KV heads instead of 8, the cache would be four times larger. This is why grouped-query attention affects serving capacity even though the number of query heads may remain high.

    Step-by-step PagedAttention flow

    1. Create request state. The engine tokenizes a prompt and creates an empty logical block table.
    2. Allocate blocks. For a block size of 16 tokens, an 18-token prompt needs two physical blocks. Any free block IDs can satisfy the request.
    3. Write KV entries. Kernels use the block table to translate a logical token position into a physical block plus within-block offset.
    4. Schedule execution. A token budget and free-block budget decide which prefills and decodes can run together.
    5. Extend incrementally. Decode fills the final block; when it becomes full, the allocator adds one more physical block rather than moving the whole sequence.
    6. Reclaim promptly. On completion or cancellation, all owned blocks return to the free pool, and the next scheduling iteration can admit more work.

    Toy block-table example

    Let each physical block hold four token positions. The free pool contains block IDs 0 through 7. Request A has token IDs [11, 12, 13, 14, 15, 16]. It receives physical blocks 2 and 7, so its block table is [2, 7]. Logical positions 0–3 live in physical block 2; positions 4–5 occupy the first two slots in physical block 7. Request B can simultaneously use blocks 0 and 5. Noncontiguity is harmless because kernels consult each request’s table.

    A has two unused slots in its final block: at two cache entries of waste, internal fragmentation is less than one block. If A finishes, blocks 2 and 7 immediately become independent free units. Contrast that with a naive allocator that reserved sixteen positions for A: ten positions would remain unused. The paged design pays metadata lookups and potentially less regular addresses to avoid large reservation waste and external holes.

    Latency, throughput, and memory tradeoffs

    Smaller blocks reduce final-block waste but enlarge block tables and increase allocation frequency. Larger blocks reduce metadata and may produce friendlier access patterns but waste more space for short sequences. Continuous batching raises utilization and throughput under load, yet aggressive prefills can delay decode iterations and worsen inter-token latency. Reserving nearly all HBM for KV increases concurrency but risks out-of-memory failures from workspaces and temporary activations. Preemption preserves admission under pressure but can cause later recomputation or transfer, creating latency spikes. A robust engine exposes policies for maximum batched tokens, maximum sequences, memory utilization, chunked prefill, and fairness because no single setting optimizes every service-level objective.

    When to use vLLM-style serving

    It is a strong fit for general autoregressive model serving with many concurrent requests, variable prompt/output lengths, OpenAI-like APIs, and a need for high throughput without building a custom NVIDIA-only engine.

    When not to use it

    A tiny batch-1 offline tool may not benefit from sophisticated scheduling. Highly fixed, latency-critical NVIDIA deployments may justify a more specialized compiled stack. Unsupported models, unusual custom kernels, or strict artifact controls may also dictate another runtime.

    Common mistakes

    • Thinking PagedAttention removes the KV cache; it reorganizes storage and access.
    • Confusing virtual-memory-style terminology with CPU page faults. GPU engine block tables are application-managed metadata.
    • Claiming zero fragmentation. The final block still has bounded internal waste, and allocator reserve still exists.
    • Increasing maximum batch size without budgeting KV blocks and batched tokens.
    • Measuring only tokens per second while decode users experience poor time to first token or inter-token latency.
    • Assuming continuous batching means adding a request in the middle of an executing kernel; membership normally changes at iteration boundaries.

    Knowledge checks

    1. What problem does a block table solve?

    It preserves a sequence’s logical token order while allowing its physical KV blocks to be scattered through the pool.

    2. With block size 16, what is the maximum unused capacity in a final allocated block?

    Fifteen token slots, because a sequence that needs the block must use at least one slot. Average waste depends on length distribution.

    3. Why is GQA useful for capacity?

    Fewer KV heads reduce cache bytes per token while query heads can remain numerous, allowing more tokens or sequences in the same HBM.

    4. How does continuous batching differ from static batching?

    Continuous batching removes finished requests and admits waiting ones between iterations; static membership remains fixed until the batch drains.

    5. What new cost does paging introduce?

    Allocation and block-table metadata, address translation in kernels, and potentially less contiguous memory access. The design wins when saved capacity and flexibility outweigh these costs.

    Reuse shared history and constrain the future

    SGLang, RadixAttention, and structured outputs

    Page allocation reduces wasted cache space. Prefix caching reduces wasted prefill work. Structured decoding prevents wasted generations and retries. SGLang brings these concerns close to its serving scheduler, where cache locality and output constraints can shape execution.

    A beginner analogy: a library path and a fill-in-the-form clerk

    Imagine a library where many readers request books beginning with the same shelf route: entrance, floor two, history aisle, then a specific title. A radix tree stores the shared route once and branches only when destinations differ. New readers reuse the common directions. Prefix KV caching works similarly: token sequences label a path, and nodes refer to reusable cache blocks. Now imagine the checkout clerk must produce a form. Rather than writing arbitrary text and checking it afterward, the clerk sees only legal next fields and punctuation. Structured decoding applies that rule to tokens: invalid next tokens receive no probability mass.

    Why it matters

    Repeated system prompts and session histories can make prefill the same computation performed again and again. Reusing compatible KV state turns that repetition into a cache lookup and improves time to first token. Meanwhile, applications increasingly need JSON or grammar-conforming results. Preventing impossible tokens during sampling avoids many repair and retry loops. Both features move application structure into engine policy, where it can influence scheduling and memory.

    Definitions

    Prefix
    The initial token subsequence of a prompt. Cache identity is based on exact token IDs plus execution context, not visually similar text.
    Trie
    A tree keyed by sequence elements. Paths from the root represent prefixes, making longest-prefix lookup efficient.
    Radix tree
    A compressed trie in which chains of single-child nodes may be stored as token spans, reducing node overhead.
    RadixAttention
    SGLang’s approach to matching and managing reusable KV-cache prefixes with a radix-tree-oriented cache and scheduler integration.
    Reference count
    The number of active users pinning a cache entry. An entry with a positive count must not be evicted.
    LRU eviction
    Removing the least recently used eligible entry when capacity is needed; “eligible” excludes pinned state.
    Structured output
    Generation required to follow a schema or language, such as JSON with fixed fields or a regular expression.
    Constrained decoding
    Masking tokens that cannot legally continue the current grammar state before sampling.
    Saved prefill tokens = Σ requests max(0, matched prefix length)
    Reuse fraction = matched prefix tokens / total prompt tokens
    p′(token i) = exp(z i) / Σ allowed exp(z j), if i is allowed; otherwise 0
    • Matched prefix length is the number of leading tokens whose compatible KV state already exists.
    • Reuse fraction is workload-dependent; it is not an engine constant.
    • z i is the model logit for token i.
    • allowed is the set of tokens with a valid grammar transition from the current state.
    • p′ is the renormalized probability distribution after masking.

    Step-by-step: prefix reuse

    1. Canonicalize the execution key. Record model revision, tokenizer, adapter, KV dtype, positional state, and other factors that affect hidden states.
    2. Tokenize the prompt. A token-ID sequence, not raw text, walks the tree.
    3. Find the longest compatible prefix. Traverse children until the next token is absent. The deepest cached boundary is the reusable portion.
    4. Acquire the entry. Increment its reference count or pin its physical blocks so eviction cannot invalidate an in-flight request.
    5. Prefill only the suffix. Compute remaining prompt tokens using the reused KV state as prior context.
    6. Insert new cacheable boundaries. Add or split branches and attach resulting KV blocks.
    7. Release and evict safely. Decrement references when requests stop using entries; choose cold, unpinned victims when capacity is needed.

    Worked radix example

    Suppose tokenized prompts are A = [10, 20, 30, 40], B = [10, 20, 30, 99], and C = [10, 20, 77]. A tree shares the path [10, 20]. A and B share one additional token, 30, before branching to 40 and 99; C branches at 77. If KV state is cached at prefix [10, 20, 30], request B can reuse three tokens and prefill only token 99 plus any following suffix. Request C reuses only two tokens.

    Now give A an active reference. Even if A’s branch is oldest, its pinned blocks cannot be reclaimed. The evictor must choose another zero-reference entry. If a LoRA adapter changes between A and B, however, equal token IDs do not imply equal keys and values. Their cache identities must differ. Reusing state computed under another model, adapter, tokenizer interpretation, or positional convention is a correctness bug, not a small approximation.

    Step-by-step: structured decoding

    1. Compile a JSON schema, regular expression, or grammar into an automaton-like state representation.
    2. At the current state, determine which token strings can legally continue the output. Token boundaries make this more complex than checking one character.
    3. Set invalid token logits to negative infinity, or otherwise exclude them from the sampler.
    4. Renormalize over allowed tokens and apply temperature, top-k, or other compatible sampling policies.
    5. Consume the selected token and transition the grammar state. Stop only in an accepting state or under an explicit error policy.

    Toy structured-output example

    We want a flat object such as {"age": 7}. At the start, only an opening brace is legal. After a key string, only a colon is legal. At a value state, a string or number token may be legal. If logits for the next token are NUMBER: 2.0, STRING: 1.0, hello: 4.0, and }: 3.0, but the automaton allows only NUMBER and STRING, the tempting hello and closing brace are masked. Renormalization occurs over exp(2) and exp(1). The result is valid by construction under this toy token grammar; semantic requirements such as age range still need validation.

    Latency, throughput, and memory tradeoffs

    Prefix reuse reduces time to first token and prefill compute when a workload repeats exact prefixes. Retaining those blocks consumes memory that might otherwise increase active-sequence capacity. A high hit rate can more than repay that cost; a diverse workload can leave cold branches occupying scarce HBM. Cache-aware scheduling may prioritize high-reuse requests for throughput, but blindly doing so can starve older misses.     When to use SGLang features

    Prefix caching shines with repeated system prompts, few-shot templates, multi-turn session histories, branching agent workflows, or shared document prefixes. Structured decoding is appropriate when downstream software requires machine-readable schemas.

    When not to rely on them

    Prefix caching adds little when prompts share few leading tokens or change model context. Do not treat constrained JSON as trustworthy content; apply range, authorization, provenance, and domain validation after generation.

    Common mistakes

    • Caching by raw text instead of exact token IDs and compatible execution identity.
    • Evicting a prefix while active requests still reference its physical KV blocks.
    • Calling every trie a radix tree without acknowledging path compression differences.
    • Reporting a cache hit rate without weighting by matched token count; many one-token hits may save little work.
    • Assuming schema-conforming JSON is semantically correct, safe, or authorized.
    • Applying token masks after sampling rather than before probability normalization.

    Knowledge checks

    1. Why use longest-prefix matching?

    Only a leading sequence can supply valid prior KV state. The deepest exact compatible prefix maximizes reusable work without skipping unmatched tokens.

    2. Why is a reference count necessary?

    It prevents eviction of cache blocks currently used by active requests, avoiding dangling references and corrupted attention state.

    3. Do equal prompt strings always share a cache entry?

    No. Tokenizer/model revision, adapter, position handling, KV precision, multimodal inputs, and other execution context can change the resulting state.

    4. What does constrained decoding guarantee?

    Given a correct grammar/token integration, it guarantees generated token sequences obey that syntactic constraint. It does not guarantee truthful or domain-valid values.

    5. When can prefix caching reduce throughput?

    When retained prefixes have low reuse and consume memory needed for active KV, or when cache bookkeeping and locality-aware scheduling cost more than the saved prefill.

    Trade flexibility for a prepared path

    TensorRT-LLM compilation, tactics, and plugins

    TensorRT-LLM focuses on highly optimized LLM execution on NVIDIA GPUs. The central lesson is broader than one product: when deployment shapes, precision, topology, and target hardware are known, a build system can move expensive decisions out of the request path.

    A beginner analogy: a custom factory line

    A general workshop can build many products because workers choose tools as each order arrives. A custom factory line is arranged for one product family: jigs fit known dimensions, stations are fused, and material buffers sit at planned locations. The line is fast and predictable, but changing product dimensions may require retooling. Eager execution resembles the workshop. A compiled engine resembles the factory line. Plugins are specialized stations inserted when general machinery cannot deliver the desired operation or performance.

    Why it matters

    Request-time flexibility carries dispatch, search, and conservative memory costs. Stable production deployments can pay those costs once during a controlled build and reuse the result millions of times. That can lower latency and make behavior more predictable. The same decision creates an artifact lifecycle, so performance engineering and release engineering become inseparable: every specialization must be reproducible, validated, compatible, and reversible.

    Build time and runtime are different worlds

    The build phase reads model structure and weights, chooses supported precisions, identifies fusion opportunities, selects or benchmarks implementation tactics, defines shape profiles, plans memory, and serializes an artifact or configuration. It can take minutes and may consume substantial host and GPU workspace. The runtime phase loads the prepared artifact, binds actual input/output buffers that fit its profiles, coordinates KV state and request metadata, and launches the selected operations. A fast runtime can exist because the builder already did search and specialization.

    TensorRT-LLM versions and workflows evolve, so production engineers should follow the documentation matching their installed release rather than memorize one command sequence. Conceptually, however, the separation remains stable: convert or define a model, build with explicit constraints, then run through an LLM-aware runtime that also handles inflight batching, cache management, parallel execution, and communication.

    Step-by-step compilation and execution flow

    1. Pin the target. Record GPU architecture, device count and topology, CUDA and library versions, model revision, tokenizer, and desired precision.
    2. Convert or describe the model. Map checkpoint tensor names and architecture features into the supported TensorRT-LLM representation. Unsupported custom layers need rewriting or plugins.
    3. Choose profiles and limits. Set maximum batch/sequence/token budgets, beam width if relevant, and parallelism. These limits drive memory planning and kernel choices.
    4. Select precision and plugins. Decide FP16, BF16, FP8, INT8, or weight-only modes where supported. Enable attention, GEMM, collective, or quantization plugins that match the model and target.
    5. Build and time tactics. The builder evaluates candidates or uses heuristics/timing caches, fuses legal regions, and plans workspace. Build logs and reproducible flags are operational artifacts.
    6. Serialize and register. Store the engine with a manifest containing checksums, compatibility, profiles, plugins, quality results, and performance baseline.
    7. Load and serve. The runtime creates contexts, manages request batches and KV cache, binds buffers, and invokes prepared operations.
    8. Validate continuously. Compare outputs and service metrics after driver, firmware, library, model, or build changes. A loadable engine is not automatically a correct engine.

    Worked example: why specialization can win

    Suppose a service only accepts batch sizes 1–8, prompts up to 2,048 tokens, and BF16 on one GPU architecture. In an eager path, each layer may perform dispatcher lookups and launch separate normalization, QKV projection, rotary position, attention, and output operations. The runtime must tolerate many shapes. In a specialized build, the compiler can select attention implementations for the supported head dimension, fuse compatible pointwise work, prepare GEMM tactics for representative matrices, and reserve reusable buffers.

    Consider three candidate GEMM tactics measured during build for a common decode shape: tactic A takes 42 microseconds and needs 8 MiB workspace; tactic B takes 36 microseconds and needs 64 MiB; tactic C takes 34 microseconds and needs 256 MiB. If the build allows only 128 MiB workspace, B is selected despite C’s lower isolated time. Across 40 layers, a 6-microsecond improvement over A saves roughly 40 × 6 = 240 microseconds per decode iteration for that GEMM site, before considering other operations. But selecting B based only on one shape can regress batch 8. A representative profile and multi-shape timing matter.

    Common mistakes

    • Using “compile” to imply every decision is static; LLM runtimes still schedule dynamic requests and manage growing KV state.
    • Building only for the maximum shape and assuming it performs well for common small shapes.
    • Ignoring build workspace, runtime workspace, and KV reserve interactions.
    • Benchmarking an engine without including tokenizer, queueing, host-to-device work, or streaming when those belong to the service objective.
    • Reusing artifacts after stack changes without compatibility and numerical checks.
    • Assuming a plugin name guarantees speed on every shape and architecture.

    Knowledge checks

    1. What work moves from runtime to build time?

    Graph optimization, fusion decisions, tactic selection or timing, target specialization, precision choices, and some memory planning can happen before requests arrive.

    2. What is an optimization profile?

    It describes supported dynamic-dimension ranges and representative shapes, constraining execution while guiding the builder’s optimization choices.

    3. Why can the fastest tactic be rejected?

    It may exceed workspace, alignment, precision, determinism, or compatibility constraints, or perform poorly over the full shape distribution.

    4. Why are plugins useful?

    They integrate custom, fused, quantized, or hardware-specific operations that a generic graph/runtime cannot otherwise express or execute efficiently.

    5. What is the main organizational cost of specialization?

    A multiplying set of versioned artifacts that must be built, validated, stored, deployed, monitored, and rolled back for combinations of models, targets, precisions, profiles, and topologies.

    Coordinate engines as a system

    NVIDIA Dynamo and disaggregated serving

    An engine optimizes one worker or replica. A serving fabric decides where requests go, where KV state lives, how work moves, and how capacity changes. NVIDIA Dynamo is a production framework in this orchestration layer, including support for separating prefill and decode work.

    A beginner analogy: a restaurant with prep and service stations

    A small restaurant uses one cook for chopping, cooking, and plating. At low traffic this is simple and efficient. At high traffic, a long preparation job blocks plates that only need a quick finishing step. A larger restaurant separates prep stations from service stations and sends prepared ingredients between them. Disaggregated LLM serving similarly assigns prompt prefill to one worker pool and token-by-token decode to another. The transfer is worthwhile only when specialization and reduced interference save more time than moving KV state and coordinating two pools.

    Why it matters

    Once an organization owns many accelerator workers, local engine speed is only part of user experience. Queueing, placement, phase interference, network paths, failures, and scaling determine whether service-level objectives are met. A control plane can match resources to the very different shapes of prefill and decode, but it can also add more delay and failure modes. First-principles accounting keeps orchestration from becoming complexity without benefit.

    Control plane, data plane, and workers

    The data plane handles live request data: tokens, tensor execution, KV cache reads/writes, state transfer, and streamed outputs. The control plane makes and distributes policy: worker discovery, health, routing, placement, scaling, configuration, and sometimes cache-aware decisions. The boundary is conceptual; implementations may combine components. The key is that a CUDA kernel should not decide fleet size, and an autoscaler should not implement attention math.

    A worker processing prompt tokens and producing initial KV state and first-token logits. Prefill tends to expose substantial parallel compute.
    Decode worker
    A worker repeatedly generating next tokens while reading model weights and growing KV state. Decode commonly stresses memory bandwidth and capacity.
    Disaggregation
    Placing different inference phases on separate worker pools rather than executing the full request on one colocated worker.
    KV transfer
    Moving or making available the prefill-produced key/value state to the decode worker, with identity, layout, and completeness metadata.
    Router
    A component choosing a worker or pool using load, cache/state locality, policy, health, and request requirements.
    Control plane
    Fleet-level coordination for discovery, routing policy, scaling, placement, configuration, and lifecycle.
    Goodput

    Step-by-step request flow

    1. Admit and classify. Validate request size, model, adapter, priority, deadline, and structured-output needs. Estimate prompt work and KV demand.
    2. Choose colocated or disaggregated execution. At light load or for short prompts, one worker may avoid transfer. At high load or for long prompts, separate pools may reduce interference.
    3. Route prefill. Select a healthy worker using queue depth, token budget, model residency, prefix locality, and topology.
    4. Execute prompt. The engine creates layer-wise KV state and first-token state while metrics record queue and compute time.
    5. Publish KV state. Transfer or expose blocks to the chosen decode worker. Send model/revision, block layout, sequence position, dtype, and completion/version metadata.
    6. Route and run decode. The decode worker installs or references state, enters continuous batching, and streams tokens while respecting latency objectives.
    7. Reclaim and observe. Release KV on finish/cancel, report per-stage latency, and feed queue/transfer/capacity signals into routing and autoscaling.

    Worked example: when separation helps

    Consider one colocated GPU. A long prefill occupies it for 400 ms. Ten active decode requests normally receive an iteration every 40 ms, but the blocking prefill stretches one gap to roughly 440 ms. Their inter-token experience suffers even if aggregate tokens per second looks acceptable. A disaggregated design sends the long prompt to a prefill worker while decode continues on a second worker. Suppose prefill still takes 400 ms and KV transfer takes 60 ms. The new request’s time to first decoded token includes that transfer, about 460 ms plus queueing, but the existing decode users avoid the 400-ms interruption.

    The choice is not automatically a win. If the prompt is short and prefill takes only 20 ms while transfer still costs 60 ms, separation adds avoidable latency and network traffic. At low load, two specialized pools can leave one idle while the other queues. A dynamic policy can colocate short or low-load work and disaggregate when prompt size, interference, and pool pressure justify it.

    Routing is more than round-robin

    A least-loaded router needs a definition of load: active sequences, scheduled tokens, predicted prefill FLOPs, free KV blocks, queueing delay, or deadlines. Cache-aware routing may prefer a worker holding a matching prefix, but that worker may be overloaded. Topology-aware routing keeps prefill and decode close enough for efficient KV transfer. Adapter-aware routing prefers workers that already hold required LoRA weights. Health-aware routing avoids workers with stale heartbeats or high error rates. These objectives conflict, so production routing is a cost function and policy, not merely request_number mod worker_count.

    Failure and correctness boundaries

    Distributed state introduces failure cases absent from one process. A prefill worker may fail after reserving destination memory. A transfer may be partial. A decode worker may restart after accepting ownership. Cancellation may race with completion. Robust designs identify requests and state versions, publish only complete KV snapshots, make cleanup idempotent, apply timeouts, and decide whether to retry prefill or fail the request. Exactly-once execution is often less important than exactly-once user-visible streaming and safe reclamation. Observability must correlate one trace across admission, prefill, transfer, decode, and streaming.

    Routing decisions only

    PrefillDecodeRouter chooses the least-loaded string-named worker in each pool and records a source worker. It does not start processes, transfer tensors, discover failures, autoscale, use RDMA, integrate Dynamo, or provide distributed correctness.

    Latency, throughput, memory, and network tradeoffs

    Disaggregation protects decode inter-token latency from long prefills and lets each pool use different batch policy or hardware ratios. It also adds a second queue, transfer delay, network bandwidth demand, duplicated model weights, and more failure surfaces. More prefill workers reduce prompt queues but can overwhelm decode capacity with completed state. More decode workers increase KV capacity but may starve for prefills. KV transfer consumes source, destination, and fabric resources; compressing or quantizing transfer can save bandwidth but adds kernels and validation. Autoscaling too slowly violates latency objectives; scaling too aggressively wastes expensive accelerators and may trigger model-loading storms. The correct objective is usually goodput under TTFT and ITL targets, not maximum isolated tokens per second.

    When to disaggregate

    Consider it at sustained scale with mixed long prefills and latency-sensitive decode, enough traffic to keep both pools useful, a fast interconnect, predictable state transfer, and an operations team capable of distributed tracing and capacity control.

    When not to disaggregate

    Keep phases colocated for small deployments, low utilization, short prompts, slow networks, simple reliability requirements, or when transfer and duplicated model residency cost more than phase interference.

    Common mistakes

    • Calling disaggregation free and omitting KV-transfer bytes from capacity models.
    • Scaling prefill and decode pools independently without modeling the flow between them.
    • Using active request count as the only load signal when prompt lengths and KV sizes differ greatly.
    • Routing to a cached or nearby worker without accounting for its queue and deadlines.
    • Conflating an engine such as vLLM, SGLang, or TensorRT-LLM with the fleet control plane that places and routes engine workers.
    • Reporting average latency while hiding tail queueing and transfer failures.

    Knowledge checks

    1. Why can prefill interfere with decode?

    Long prefill kernels consume compute and occupy the GPU for comparatively long intervals, delaying the frequent small iterations decode needs for smooth token delivery.

    2. What must cross the prefill/decode boundary?

    Compatible KV state plus identity, layout, position, dtype, model/context, ownership, and completion metadata. The token request and tracing context must also continue.

    3. Why might short prompts stay colocated?

    The interference saved may be smaller than the extra queue, reservation, transfer setup, and state movement introduced by disaggregation.

    4. What belongs to the control plane?

    Worker discovery, health, routing policy, placement, scaling, configuration, and lifecycle. Tensor math and live KV reads belong in the data plane/engine path.

    5. Why use goodput instead of raw throughput?

    A system can produce many tokens while missing user-visible TTFT or ITL objectives. Goodput counts only work delivered within the required service envelope.

    Design a phase-2 inference service

    There is no single correct engine choice. A strong answer makes assumptions explicit and connects every choice to measured workload evidence.

    Scenario

    You must serve an 8-billion-parameter chat model. Weights use BF16 initially. The model has 32 layers, 8 KV heads, and head dimension 128. Traffic averages 40 requests per second and peaks at 100. Seventy percent of prompts are 500 tokens and share a 300-token system prefix; twenty percent are 2,000-token retrieval prompts with little shared prefix; ten percent are 8,000-token document prompts.
