    Mental model

    Optimization is resource substitution

    Each technique spends one resource to save another. Name both sides before adopting it.

    Fewer bytes

    Quantization reduces weight traffic and capacity, but spends calibration effort and numerical headroom.

    Fewer target calls

    Speculation spends cheap draft work so one expensive target pass can validate several positions.

    More reuse

    Parallelism adds communication so a model fits or more requests finish per second.

    Disaggregation spends KV-transfer bandwidth to isolate compute-heavy prefill from bandwidth-heavy decode.

    Day 13 · Representation

    Number formats: what a bit buys

    FP32, FP16, BF16, FP8, INT8, INT4, and NVFP4 are contracts between stored bits, arithmetic hardware, and acceptable error.

    Imagine writing every price in a warehouse ledger. A luxurious ledger records $12.347891; a compact one records $12.35; an extremely compact one records “about $12.” The compact ledger is lighter and faster to carry, but two nearby prices may collapse to the same entry. Quantization applies this idea to billions of model values. It does not make the original numbers intrinsically smaller; it chooses a smaller alphabet and records enough scaling information to interpret that alphabet.

    First principles and terminology

    A bit has two states. With b bits, an unsigned integer can name 2b patterns. Floating-point formats divide their patterns into a sign, an exponent that selects a scale, and a fraction (often called a mantissa) that selects a point within that scale. Integers devote nearly all patterns to evenly spaced values. Therefore integers are locally precise over a chosen interval but have no built-in way to span tiny and huge magnitudes simultaneously. Floating point has broad dynamic range but uneven spacing: representable numbers become farther apart as magnitude grows.

    • Precision: how finely nearby values can be distinguished.
    • Dynamic range: the ratio between useful smallest and largest magnitudes.
    • Scale: a multiplier that converts a stored low-bit code back toward a real value.
    • Zero point: the integer code representing real zero in asymmetric quantization.
    • Granularity: which values share a scale: tensor, channel, group, or small block.
    • Saturation: clipping a value beyond the representable minimum or maximum.

    Bit layouts, from broadest to smallest

    IEEE-style FP32 uses one sign bit, eight exponent bits, and twenty-three stored fraction bits. FP16 uses 1/5/10: more fraction precision than BF16, but a much narrower exponent range. BF16 uses 1/8/7, retaining FP32-like range while accepting coarse spacing. That makes BF16 robust when values vary widely. An FP8 E4M3 value uses one sign, four exponent, and three fraction bits; E5M2 trades one fraction bit for one exponent bit. Exact encodings reserve some patterns for special values, so “largest number” is format-specific rather than simply 2 raised to a power.

    SEEEEEEEE23 fraction bits
    FP16 S5E10FBF16 S8E7FFP8 S4E3F

    INT8 usually represents −128 through 127, although symmetric schemes often use −127 through 127 so positive and negative ranges match. INT4 stores sixteen codes in a four-bit nibble; symmetric inference schemes commonly use −7 through 7 and leave one pattern unused or reserved. Two INT4 values pack into one byte. NVFP4 uses a tiny E2M1 floating value for each element plus a shared scale for a small block (commonly sixteen values in the NVIDIA scheme). The shared scale restores local dynamic range. Its metadata means “4-bit” does not imply exactly four total bits per parameter.

    Quantization and reconstruction, step by step

    1 · ObserveFind a range per tensor, channel, group, or block.
    2 · ScaleMap real magnitudes into available codes.
    3 · RoundChoose a code and clip overflow.
    4 · PackStore codes plus scale metadata.
    5 · ComputeDequantize or use a native low-bit kernel.
    Symmetric: q = clamp(round(x / s), q_min, q_max)    and    x̂ = s · q

    Here x is the original value; s is the positive real scale; q is the stored integer; q_min and q_max are legal code bounds; x̂ (“x-hat”) is the reconstructed approximation. A common scale is s = max(|x|)/q_max. Asymmetric quantization adds a zero point z: q = round(x/s)+z and x̂ = s(q−z). Symmetric math is simpler and often favored for weights; asymmetric mapping can use the code range better when data are lopsided.

    Worked numeric example: four weights in INT4

    Take weights [−1.00, −0.20, 0.55, 0.90] and symmetric codes −7…7. The maximum absolute value is 1.00, so s = 1/7 ≈ 0.142857. Divide by the scale and round: [−7.00, −1.40, 3.85, 6.30] becomes q = [−7, −1, 4, 6]. Reconstruct by multiplication: x̂ = [−1.000, −0.143, 0.571, 0.857]. The errors x̂−x are [0, +0.057, +0.021, −0.043]. Mean absolute error is (0 + .057 + .021 + .043)/4 ≈ 0.030.

    Now imagine adding an outlier 8.0 while sharing one scale. The scale becomes 8/7 ≈ 1.143. Our original 0.55 rounds to zero, losing its signal. Smaller groups isolate outliers and improve fidelity, but each group needs metadata and kernels must load it. This single example motivates Day 14.

    Storage is not computation

    Crucial distinction: a model file can store INT4 weights while the GPU kernel unpacks them to FP16, multiplies in FP16, and accumulates partial sums in FP32. Calling the whole operation “INT4 compute” hides three separate choices: storage format, multiply/input dtype, and accumulation dtype.

    A low-bit checkpoint only guarantees capacity savings. Speed requires a kernel that understands its packing, grouping, scales, matrix shapes, and target device. A generic kernel may unpack weights into a temporary buffer and become slower than an optimized FP16 matrix multiplication. Accumulation deserves extra precision because a dot product sums hundreds or thousands of products; small rounding errors can build coherently. Many tensor-core paths multiply low-precision operands but accumulate into FP16 or FP32. Always report all three layers of the contract.

    Choose deliberately

    • Use BF16/FP16 for a quality baseline and when kernels dominate engineering cost.
    • Try FP8 for native recent accelerators and W8A8-style throughput.
    • Try INT8 when portability and predictable accuracy matter.
    • Try grouped INT4 when model fit or decode bandwidth is the hard limit.
    • Consider NVFP4 only when the serving stack and hardware support its actual kernels.

    Common mistakes

    • Counting codes but forgetting scale, zero-point, alignment, and padding bytes.
    • Assuming an INT4 file means INT4 multiplication or a 4× speedup.
    • Using one global scale in the presence of outliers.
    • Comparing quality with different prompts, tokenizers, or sampling seeds.
    • Ignoring accumulation dtype and overflow.
    • Quoting peak hardware FLOPS for a bandwidth-bound decode workload.

    Review questions with answers

    1. Why can BF16 represent larger magnitudes than FP16?

    BF16 keeps eight exponent bits, matching FP32’s exponent width, while FP16 has five. BF16 spends fewer bits on the fraction, so its range is broader but nearby values are coarser.

    2. Why do group scales improve INT4 quality?

    Each group adapts its interval to local magnitudes. One outlier then stretches only its group’s step size rather than reducing precision for an entire tensor.

    3. What are the three dtype questions for a low-bit linear layer?

    Ask how weights/activations are stored, what dtype the multiply kernel consumes or converts to, and which dtype accumulates the products.

    4. Is quantization lossless?

    Usually not. Rounding maps many real values to one code. Lossless packing can reduce representation overhead, but low-bit numerical quantization introduces approximation unless every input is exactly representable.

    5. Why might an INT4 model use more than four bits per parameter?

    It also stores group scales, perhaps zero points, padding, indices, and alignment. Effective bits per parameter include amortized metadata.

    6. When does a smaller checkpoint fail to run faster?

    When the device lacks a matching kernel, unpacking is expensive, batches or shapes are inefficient, metadata loads dominate, or another bottleneck such as networking limits the request.

    Day 14 · Calibration

    Post-training quantization: protect what matters

    GPTQ, AWQ, and SmoothQuant improve on blind rounding by modeling sensitivity, activation importance, or outlier migration.

    Suppose a moving company must round the weight of every box to a whole kilogram. Rounding pillows carelessly changes little; rounding a fragile machine’s counterweight may break it. A plain quantizer sees only kilograms. A post-training quantization algorithm observes how boxes interact and protects the consequential ones. It changes representation after training, using a small calibration set rather than a full retraining run.

    First principles: error must be measured at the output

    For a linear layer, the unquantized output is Y = XW, where rows of X are calibration activations and W is a weight matrix. Replacing W by Ŵ creates output error E = X(W−Ŵ). Minimizing the element-wise weight difference alone ignores X. If one input channel is almost always zero, a large error in its weights may barely affect Y. If another channel is frequently large, a small weight error may matter greatly. PTQ methods use this observation in different ways.

    • PTQ: quantization applied to a trained model without full training.
    • Calibration set: representative inputs used to collect activation statistics.
    • Hessian: a curvature matrix describing sensitivity and interaction of perturbations.
    • Salient channel: a dimension whose activation/weight interaction strongly affects outputs.
    • Weight-only: weights are low-bit while activations remain floating point.
    • W8A8: eight-bit weights and eight-bit activations, commonly with wider accumulation.

    GPTQ: compensate sequential rounding

    GPTQ treats layer quantization as a reconstruction problem. Using calibration activations, a common local curvature approximation is H ≈ 2XᵀX (constants vary by derivation). XᵀX records correlations among input features. GPTQ processes weights in an order or blocks. After quantizing one column, it uses information from the inverse curvature to adjust unquantized columns so their future contribution compensates for the new error. The intuition is like correcting the remaining ingredients after accidentally over-salting a soup.

    δ = (w − q(w)) / [H⁻¹]ⱼⱼ    ;    W_remaining ← W_remaining − δ · [H⁻¹]ⱼ,remaining

    w is the weight or column being quantized; q(w) is its reconstructed low-bit value; w−q(w) is rounding error; H⁻¹ is the inverse approximate Hessian; subscript jj is the current diagonal sensitivity; and the remaining row slice distributes a correction across correlated dimensions. Practical GPTQ works blockwise, adds damping for numerical stability, and uses matrix factorizations rather than literally inverting a giant matrix. Its strength is high-quality weight-only INT4. Its costs are calibration, substantial offline quantization time, and kernels/checkpoint layouts that must agree.

    AWQ: preserve activation-aware channels

    AWQ begins from an empirical fact: a small fraction of channels can dominate output error because their activations are large. Rather than solve a second-order optimization for every weight, it searches for per-channel scaling that makes important weights easier to represent. The equivalent transform must preserve the original linear function before rounding. For diagonal scale matrix S, XW = (XS⁻¹)(SW). AWQ quantizes the scaled weights SW; activations are inversely scaled at runtime or the scaling is fused into neighboring operations.

    sⱼ ≈ aⱼα / wⱼ1−α    ;    Y = (X S⁻¹)(S W)

    Here aⱼ summarizes activation magnitude for channel j, wⱼ summarizes weight magnitude, α balances them, and S is diagonal with entries sⱼ. Exact search objectives differ among implementations. The important idea is not “keep the largest 1% unquantized” as a universal rule; it is to protect output-important channels through activation-aware scaling and group quantization. AWQ is attractive because calibration can be lighter than GPTQ and quality is strong for weight-only 4-bit inference, provided optimized AWQ kernels exist.

    SmoothQuant: move difficulty from activations into weights

    Activation outliers are troublesome for W8A8 because activations change per request and can have channels whose magnitude dwarfs the rest. Weights are static, so per-channel difficulty can be folded into them offline. SmoothQuant chooses a positive scale per input channel, divides activations by it, and multiplies the corresponding weight row by it. Before quantization the products are algebraically identical. After transformation, activation ranges are smoother, so INT8 codes are used more evenly.

    sⱼ = max(|Xⱼ|)α / max(|Wⱼ|)1−α    ;    XW = (X / s)(sW)

    Division and multiplication are channel-wise. max(|Xⱼ|) comes from calibration activations; max(|Wⱼ|) comes from the corresponding weight channel; and α between zero and one decides how much quantization difficulty migrates. α near one strongly smooths activations but makes weights more uneven; α near zero protects weights but leaves activation outliers. The equality holds in real arithmetic, but quantizing both transformed operands introduces a new balance of errors.

    1 · SampleChoose representative prompts and sequence lengths.
    2 · ObserveRecord layer inputs, ranges, and channel statistics.
    3 · TransformCompensate or rescale according to the algorithm.
    4 · QuantizeRound by group and serialize metadata.
    5 · ValidateMeasure quality and real serving kernels.

    Worked numeric example: why activation awareness changes the answer

    Consider one output y = 0.1w₁ + 10w₂ with w₁ = w₂ = 0.60. Suppose a coarse quantizer reconstructs either 0.50 or 0.75. Both weights have the same nearest error if rounded to 0.50: −0.10. Yet their output effects differ. Error from w₁ is 0.1(−0.1)=−0.01; error from w₂ is 10(−0.1)=−1.0. Protecting the second channel is one hundred times more valuable for this sample.

    Scale the important weight by 2 before quantization and its activation by 1/2: y = 0.1w₁ + (10/2)(2w₂). If the scaled 1.20 is represented as 1.25, reconstruction after the paired transform behaves like w₂≈0.625, an error of +0.025 rather than −0.10. The function was identical before rounding; code placement changed after rounding. Real AWQ searches scales across many samples and layers, but this toy arithmetic exposes the mechanism.

Small matrices, odd group sizes, or unsupported batch shapes may fall back to slow kernels.

    Decision guide

    • Start with RTN only as a baseline or at forgiving precision.
    • Choose GPTQ when offline time is acceptable and proven kernels/checkpoints exist for weight-only INT4.
    • Choose AWQ for practical W4A16 deployment with activation-aware quality and strong runtime support.
    • Choose SmoothQuant when W8A8 hardware acceleration is the goal and activation outliers are the obstacle.
    • Keep sensitive layers, embeddings, or output heads at higher precision if evaluation justifies the mixed policy.

    Common mistakes

    • Calibrating only on short, easy, single-language prompts.
    • Calling XᵀX “the exact model Hessian” rather than a layer-local approximation.
    • Applying a scale without its inverse companion, changing the function before quantization.
    • Assuming an algorithm name guarantees a compatible checkpoint layout.
    • Optimizing layer MSE while ignoring generation and product quality.
    • Benchmarking a dequantize-then-FP16 fallback as if it were a native low-bit kernel.

    Review questions with answers

    1. Why is calibration needed?

    Weights alone do not reveal which perturbations matter for actual layer outputs. Representative activations expose channel magnitudes, correlations, and outliers.

    2. What does GPTQ compensate?

    After rounding a weight or column, GPTQ adjusts remaining unquantized weights using approximate inverse-curvature information so correlated dimensions absorb some output error.

    3. How can AWQ scaling preserve the original function?

    Multiplying a weight channel by s and dividing its matching activation channel by s cancels in the dot product before quantization.

    4. What problem does SmoothQuant target?

    Per-channel activation outliers that force a large INT8 scale and erase resolution for ordinary activation values. It migrates some range difficulty into static weights.

    5. Why can two calibration sets produce different checkpoints?

    Their activation ranges, frequencies, and correlations differ, changing sensitivity estimates and selected scales. Calibration is a sampled model of production traffic.

    6. Which method automatically guarantees fastest inference?

    None. Speed depends on device, kernel, shape, packing, fusions, and workload. The PTQ algorithm chooses values; the runtime must execute them efficiently.

    Day 15 · Exact acceleration

    Speculative decoding: draft, verify, correct

    A cheap proposer guesses several future tokens; the authoritative target scores them together, and rejection sampling keeps exactly the target distribution.

    Picture a senior editor who must approve every word but reads much faster in batches than one word at a time. A junior writer drafts a short phrase. The editor checks the entire phrase in one sitting, keeps the valid beginning, corrects the first unacceptable word, and discards the unsupported tail. The junior never becomes the authority. The speedup comes from converting several expensive, sequential target calls into one target verification pass—not from trusting a cheaper model’s answers.

    First principles: why decode leaves hardware idle

    Autoregressive generation factorizes a sequence probability as P(y₁…yₙ|x)=∏ᵢP(yᵢ|x,y<i). Position i cannot be sampled until positions before it are known. At small batches, a target model often loads a huge quantity of weights for one token and performs too little arithmetic to saturate compute units. A target can nevertheless score several already-known candidate positions in parallel: teacher forcing supplies the proposed tokens as inputs. Speculation manufactures those candidates cheaply, allowing verification to use a wider, more compute-efficient pass.

    • Draft distribution q: the cheap proposer’s next-token probabilities.
    • Target distribution p: the authoritative model’s probabilities to preserve.
    • Proposal length K: maximum candidate tokens in one round.
    • Acceptance rate: fraction of proposed positions accepted.
    • Bonus token: a target-sampled token emitted after all K proposals pass.
    • Residual distribution: normalized positive probability mass p−q used after rejection.

    The draft-target flow, step by step

    1 · DraftSample K tokens autoregressively from q and retain each q distribution.
    2 · VerifyRun the target once across candidate positions to obtain p distributions.
    3 · AcceptWalk left to right with probability min(1,p(token)/q(token)).
    4 · CorrectAt first rejection, sample from normalized max(0,p−q).
    5 · CommitEmit accepted prefix plus correction, or all K plus a bonus.

    Verification must stop logically at the first rejection because later target distributions were conditioned on a draft token that will not be in the final sequence. Their logits are no longer valid for the corrected history. If every candidate passes, the target has also computed logits after the Kth candidate, so sampling one bonus token makes full use of the pass.

    Why naïve acceptance changes the distribution

    A tempting shortcut is “accept a draft token whenever the target likes it,” or accept with probability p(token), then sample from p after rejection. Both are biased. The proposal token was already sampled from q, so its chance of appearing includes q. If we accept with probability p rather than p/q, its accepted mass becomes q·p, not the mass target p assigned. Sampling from full p after rejection adds target mass again to tokens that already received accepted proposal mass. Frequent draft tokens are overrepresented and rare target-favored tokens may be underrepresented.

    Exact rejection sampling accounts for how often a token was proposed. A proposal token t is accepted with a(t)=min(1,p(t)/q(t)). Its unconditional accepted mass is q(t)a(t)=min(q(t),p(t)). That covers the overlap between distributions. The target still needs the uncovered mass p(t)−min(p(t),q(t))=max(0,p(t)−q(t)). When any proposal is rejected, drawing a correction from the normalized positive residual supplies exactly that missing mass. Over acceptance and rejection branches together, each token’s total probability is p(t).

    a(t) = min(1, p(t)/q(t));   r(v) = max(0, p(v)−q(v)) / Σᵤ max(0, p(u)−q(u))

    Here t is the proposed token; v and u range over vocabulary items; p is the target probability at the current prefix; q is the draft probability at the same prefix; a is acceptance probability; and r is the correction distribution. If q(t)=0, the draft cannot have sampled t in a well-formed implementation. Numerical code still guards against zero and normalizes imperfect input distributions.

    Worked numeric example: exact mass recovery

    Let vocabulary be {A,B,C}. Draft q=[0.60,0.30,0.10]; target p=[0.30,0.40,0.30]. Acceptance probabilities are A: min(1,.30/.60)=.50; B: min(1,.40/.30)=1; C: min(1,.30/.10)=1. Unconditional accepted mass is q·a=[.30,.30,.10], exactly min(p,q).

    The total rejection probability is 1−(.30+.30+.10)=.30. Positive residual p−q is [0,.10,.20], which normalizes to r=[0,1/3,2/3]. Multiplying by rejection probability adds [0,.10,.20]. Total output mass is [.30,.40,.30]=p. By contrast, accepting with probability p gives accepted mass [.18,.12,.03], and then resampling naïvely from p cannot generally repair the distortion without deriving the missing mass.

    Medusa, EAGLE, and multi-token prediction

    Medusa attaches several prediction heads to target hidden states. Heads predict tokens at different future offsets, producing branches that the target verifies with a tree-aware attention pattern. It avoids loading a separate draft model but requires trained heads, additional parameters, and an engine capable of tree construction and verification. Because future predictions are not independent, tree topology and pruning strongly affect useful acceptance.

    EAGLE drafts in a feature space informed by the target’s hidden states, then maps candidates to tokens and verifies them. Later variants adapt tree expansion or use richer feature prediction. The useful mental distinction is that token-level draft-target predicts only discrete next tokens with a separate model, while EAGLE exploits internal target representations that carry more information. It can increase acceptance but couples the draft artifact to a particular target architecture and serving implementation.

    Multi-token prediction (MTP) trains auxiliary objectives or heads to predict multiple future positions. At inference these predictions can form speculative candidates. MTP is a broad training/design concept; it is not automatically the exact serving algorithm. Exactness still depends on authoritative target verification and a correct acceptance/correction procedure. A head that simply emits several tokens without verification changes the model being sampled.

    N-gram speculation needs no neural draft. It finds the recent token pattern earlier in the prompt or output and proposes what followed. This is powerful for copied text, retrieval contexts, repetitive templates, and code. It is weak on novel prose. The project’s proposer deliberately returns an empty proposal when no repeated context exists, which is preferable to inventing low-quality guesses.

    Expected work, quality, and hardware dependence

    E[accepted prefix] = Σᵢ₌₁ᴷ P(first i proposals all accepted)

    If each position had independent acceptance α, this simplifies to Σᵢ₌₁ᴷ αⁱ. Real positions are correlated, so measure empirical accepted tokens per round. Speedup is not merely accepted tokens. Draft latency, target verification efficiency, KV-cache rollback/commit, sampling overhead, batch interference, and memory occupied by the draft all matter. A large K can waste verification on tails after an early rejection. A draft that is too strong may cost nearly as much as the target; one that is too weak produces little accepted work.

    Exact speculative decoding preserves the target sampling distribution under identical logits-processing rules and mathematically correct sampling. It does not promise bit-identical random-number streams or identical token sequences for a fixed seed, because batching and branch decisions consume random values differently. Greedy “verify matching argmax” can preserve greedy output but is a different guarantee from distribution-preserving sampling. Top-k, top-p, temperature, repetition penalties, grammar masks, and banned tokens must be applied consistently to p and q at each prefix.

    Hardware determines whether verification is cheaper than K target decode steps. On a bandwidth-bound GPU with idle compute, scoring K positions together can be highly efficient. On an already compute-saturated large batch, extra candidate work may reduce fleet throughput. Separate user latency from aggregate throughput: a single request can speed up while shared-server tokens per second decline due to draft work and longer verification batches.

    Review questions with answers

    1. How can a target verify sequential tokens in parallel?

    The proposed tokens are already known, so teacher forcing lets one target pass compute logits for each candidate position under its preceding proposed prefix.

    2. Why is acceptance p/q rather than p?

    The candidate is sampled from q. Dividing by q corrects proposal frequency so accepted unconditional mass becomes min(p,q), not q·p.

    3. What happens at the first rejection?

    Emit a correction from normalized max(0,p−q), discard later proposals, update the real history, and begin a new round.

    4. Why is a bonus token available?

    If all K candidates pass, verification has computed the target distribution following them. Sampling it uses work already produced by the target pass.

    5. Does exact speculation reproduce the same seeded sequence?

    Not necessarily. It preserves the probability distribution, but random draws can be consumed in a different order, producing another valid sample.

    6. When can speculation hurt throughput?

    When acceptance is low, draft cost is high, verification wastes many tail positions, cache bookkeeping is expensive, or ordinary batching already saturates compute.

    Day 16 · Reuse

    Prefix caching: make identical history reusable

    A cached prefix is computed KV state tied to an exact token sequence, model configuration, positions, and numerical execution contract.

    A restaurant prepares the same soup base for many dishes. If every order starts with the identical base, the kitchen reuses one pot and adds the customer-specific ingredients at the end. If a customer’s special ingredient is mixed into the base at the beginning, every later step changes and reuse disappears. Prefix caching is the serving equivalent: stable instructions first, variable content last.

    First principles and cache identity

    During causal attention, key and value vectors at position i depend only on tokens through i. Two requests with exactly the same first k token IDs, positions, model weights, adapters, and relevant execution settings produce reusable KV entries for positions 0…k−1. They may diverge after k without invalidating the shared prefix. A matching substring in the middle is not generally reusable because its vectors were computed with different earlier context and positions.

    • Prefix hit: a cached initial token run that can skip corresponding prefill work.
    • Radix tree/trie: a structure that shares common token paths and finds the longest prefix.
    • Reference count: number of active users pinning an entry against eviction.
    • LRU: least-recently-used eviction among eligible entries.
    • Cache affinity: routing preference for a worker already holding useful state.
    • Re-prefill: recomputing KV instead of retrieving or transferring it.

    A safe cache key includes more than visible text. Tokenizer version and chat template determine token IDs. Model revision, adapter/LoRA identity, KV dtype, positional encoding configuration, multimodal inputs, and sometimes attention backend affect state. Security domains and tenant isolation may forbid sharing even when bytes match. Hashes accelerate lookup, but collision handling or full-key confirmation preserves correctness.

    System flow, step by step

    1 · TokenizeBuild the canonical prompt and exact cache identity.
    2 · RouteEstimate which replica owns the longest warm prefix.
    3 · MatchWalk token blocks or a radix tree to the first mismatch.
    4 · AcquirePin matching KV blocks and prefill only the suffix.
    5 · ReleaseUnpin after use; evict cold entries under pressure.

    Production caches often hash fixed-size token blocks rather than every individual token. Block alignment simplifies paged KV management but means a partial final block may not be reusable. Radix trees naturally represent shared paths and partial prefixes. The project’s learning cache stores whole prefix tuples in a trie, returns the longest stored match, increments a reference count on acquisition, and evicts the oldest unpinned entry. Its capacity is entries rather than bytes, a simplification worth noticing.

    Memory and the offload-versus-re-prefill race

    KV bytes = 2 · L · Hkv · Dhead · T · B · e

    The factor 2 is keys plus values; L is layer count; Hkv is KV-head count; Dhead is dimensions per head; T is cached tokens; B is concurrent sequences or copies; and e is bytes per element. Grouped-query or multi-query attention reduces Hkv. Prefix caching does not make state free: retaining many popular prefixes competes with active sequences and model workspace.

    Worked numeric example: transfer or recompute?

    Take L=32 layers, Hkv=8, Dhead=128, e=2 bytes, and a reusable T=4,096-token prefix. Bytes per token are 2·32·8·128·2 = 131,072 bytes = 128 KiB. Total prefix KV is 536,870,912 bytes = 512 MiB.

    If host-to-device effective bandwidth is 32 GB/s, ideal transfer time is about 0.537/32 = 16.8 ms, before protocol and contention. If the engine prefills 4,096 tokens in 45 ms, transfer wins. If local SSD supplies only 7 GB/s, ideal read time is 76.7 ms, so re-prefill wins unless compute is congested or the data is compressed. The decision is min(fetch latency, recompute latency), not “always offload.” Include queueing, serialization, network contention, and opportunity cost.

    A practical hierarchy may place hottest entries in GPU HBM, warm entries in host memory, colder entries on local NVMe, and durable shared artifacts in remote storage. Moving down tiers increases capacity but also latency and bandwidth contention. Admission should consider expected reuse value: prefix tokens saved × reuse probability × prefill cost, compared with bytes occupied × eviction pressure. Large one-off prompts should not evict small frequently reused system prompts merely because they are recent.

    Cache-aware routing

    Round-robin routing balances request counts but destroys locality: the useful cache may sit on another replica. Pure affinity routing maximizes hits but can overload a popular replica. A production score combines prefix overlap, queue delay, available KV blocks, worker health, and transfer cost. One conceptual score is:

    score(worker) = saved_prefill_ms − queue_delay_ms − transfer_ms − pressure_penalty_ms

    Choose the highest score, not simply the largest hit. A 10,000-token hit on a saturated worker may lose to a 6,000-token hit on an idle one. Directory metadata describing which worker owns which prefix can itself be stale. Systems use leases, bloom filters, approximate ownership maps, or consistent hashing. On failure, correctness falls back to re-prefill; caches are optimization state, not the only copy of user truth.

    Exactness, quality, performance, and hardware

    Reusing KV generated under an identical execution contract should preserve the same model computation, apart from permitted nondeterminism in floating kernels. Reusing state across a different model revision, adapter, RoPE scaling, tokenizer, or attention semantics is a correctness bug, not graceful quality degradation. Multi-tenant reuse adds privacy risks: timing can reveal whether a prefix was warm, and cached user data requires retention and isolation policy.

    Prefix caching primarily improves time to first token and reduces prefill compute. It may increase throughput by freeing compute, but decode time after the divergent suffix remains. A “hit rate” by request is misleading: one hit may save ten tokens and another ten thousand. Track cached tokens, prefill FLOPs avoided, byte residency, lookup latency, eviction churn, and P50/P95/P99 TTFT. Hardware shifts the tier boundary: fast coherent CPU–GPU links make host offload attractive; slow PCIe or oversubscribed networks favor recomputation.

    Review questions with answers

    1. Why are prefixes reusable but arbitrary substrings are not?

    Causal KV at a position depends on every earlier token and its position. A matching prefix preserves that history; a middle substring usually has a different preceding context.

    2. What should a cache identity include?

    Exact token IDs plus all settings that influence KV: model and adapter revision, positional configuration, KV dtype/backend where relevant, multimodal inputs, and security scope.

    They prevent eviction while active requests still depend on cached blocks. An unpinned cold entry is safe to reclaim; a pinned one is not.

    4. Does a high request hit rate guarantee large savings?

    No. Hits vary in prefix length and compute value. Token-weighted hit rate and prefill time avoided are more informative.

    When retrieval, transfer, queueing, and deserialization take longer or consume more valuable resources than prefill on the selected worker.

    6. Why can cache-aware routing reduce balance?

    Popular prefixes attract traffic to their owner. The routing score must price queue delay and memory pressure, and may choose a miss on an idle worker.

    Day 17 · Scale-out

    Parallelism: divide work, then pay to reconnect it

    Tensor, pipeline, data, expert, and context parallelism split different dimensions. Every split creates a communication pattern and a latency/throughput consequence.

    Imagine producing a newspaper. Several printers can each print complete independent editions (data parallelism). Specialists can print different color layers of the same page and combine them (tensor parallelism). Stations can perform layout, printing, folding, and packing in a line (pipeline parallelism). Separate desks can handle sports, finance, and culture articles selected by a router (expert parallelism). A very wide poster can be divided into panels whose boundary information must be exchanged (context parallelism). “Use more workers” is incomplete until we say what is divided and how results reunite.

    First principles: fit, latency, and throughput are different goals

    A model may be sharded because its weights do not fit on one accelerator. That is a capacity requirement. It may be sharded to reduce one request’s latency. That is a critical-path goal. Or it may be replicated to finish more independent requests per second. That is throughput. Adding devices can solve one while harming another. Communication, synchronization, idle bubbles, smaller per-device matrix shapes, and queueing prevent linear scaling.

    • World size: total ranks participating in a distributed plan.
    • Rank: one process/device identity within a communication group.
    • Collective: coordinated communication such as all-reduce or all-to-all.
    • Critical path: operations that determine one request’s completion time.
    • Strong scaling: same work distributed over more devices.
    • Bubble: time a pipeline stage is idle because no microbatch is ready.

    Tensor parallelism (TP)

    TP splits matrix dimensions within each transformer layer. In a column-parallel linear layer, each rank owns a slice of output columns and computes a partial output feature set. In a row-parallel layer, each rank owns input rows and creates a partial sum that must be combined. Attention heads naturally partition when head counts divide the TP degree. TP reduces weight memory per rank and can shorten local GEMMs, but communication occurs repeatedly inside every layer. Decode’s small token dimension makes those GEMMs narrow and synchronization comparatively expensive.

    A common reconnection is all-reduce: every rank contributes an equally shaped partial tensor; the operation sums them and returns the full sum to every rank. Reduce-scatter sums and leaves a different shard on each rank, often paired later with all-gather, which concatenates shards so every rank receives the whole. Efficient implementations overlap communication, fuse collectives, and respect topology. TP usually stays within a high-bandwidth, low-latency node because it communicates on the critical path of many layers.

    Pipeline parallelism (PP)

    PP assigns contiguous layer ranges to stages. Activations flow from stage 0 to stage 1, then onward; the final stage produces logits. Weight capacity scales with stage count, and boundary tensors are smaller than constant TP collectives, making PP suitable across nodes. For one request, however, stages execute serially: splitting layers does not automatically reduce latency and can add transfer overhead. Throughput improves when many microbatches occupy different stages simultaneously.

    Ideal pipeline utilization ≈ m / (m + p − 1)    ;    bubble fraction ≈ (p−1)/(m+p−1)

    p is the number of balanced stages and m is the number of microbatches in a simple schedule. With p=4 and m=1, utilization is 1/4: three stage-slots are bubbles. With m=16, utilization is 16/19≈84%. Real imbalance, decode dependencies, and variable sequence lengths lower it. Continuous inference schedulers do not map perfectly to training microbatch formulas, but the bubble intuition remains.

    Data parallelism (DP)

    DP replicates the complete serving shard group and routes independent requests to replicas. During inference there is usually no per-token gradient synchronization. If one model replica requires TP=4, adding DP=8 creates eight independent four-GPU replica groups, not a 32-way collective for each token. DP is often the cleanest throughput scaling because requests do not communicate across replicas. It multiplies weight memory and does little for the latency of one request. Cache-aware routing, load balancing, and failure domains operate across these replicas.

    Expert parallelism (EP)

    Mixture-of-Experts models activate only selected experts per token. EP places experts on different ranks. A router chooses top-k experts, then tokens travel to owners through all-to-all: each rank sends different token subsets to every other rank and receives different subsets in return. After expert computation, another exchange restores token order. EP saves active compute relative to dense use of every expert and distributes expert weights, but load imbalance is dangerous. A popular expert becomes a straggler; capacity limits may drop or reroute tokens, changing quality or latency.

    All-to-all stresses network bisection bandwidth and produces irregular messages. Locality-aware expert placement, expert replication, balanced routing losses during training, and token batching help. EP and TP can coexist: experts are distributed among groups while each large expert itself is tensor-sharded.

    Context/sequence parallelism (CP/SP)

    Long sequences make activations and KV state large even when weights fit. Context parallelism partitions token positions across ranks. Attention is globally dependent: each query may need keys and values owned elsewhere, so ranks exchange KV blocks or circulate them in a ring. Sequence parallelism can also shard token-wise activations around operations that otherwise replicate them. Names vary across frameworks; inspect the actual tensors and collectives rather than trusting labels.

    Context parallelism reduces per-rank sequence memory and distributes long-context attention work, but adds communication proportional to sequence-related tensors. It is especially relevant to long prefill; decode has only one new query per sequence but reads distributed historical KV, so implementation strategy matters. Ring attention overlaps computation on one KV block with movement of the next; poor overlap exposes the network directly on latency.

    DPIndependent request replicas; route, do not synchronize tokens.
    PPLayer blocks; send activations between stages.
    TPMatrix/head slices; reduce partial results frequently.
    EPExpert ownership; all-to-all dispatched tokens.
    CPToken ranges; exchange or rotate attention state.

    Communication math and a worked plan

    T_comm ≈ latency_steps · ℓ + bytes_transferred / effective_bandwidth

    ℓ is per-step network latency, not model loss; latency_steps depends on the collective algorithm and rank count; bytes include tensors actually sent per rank; effective bandwidth is lower than link peak because of protocol, contention, topology, and message size. Ring all-reduce moves approximately 2(n−1)/n times the tensor bytes per rank across its reduce-scatter and all-gather phases. This volume approaches twice the tensor size as n grows, while step latency also grows.

    Worked numeric example: a 16-GPU serving plan

    A 64-layer dense model needs 240 GiB for weights and reserved runtime state. Each GPU offers 80 GiB, but only 64 GiB is budgeted after safety margin. Capacity needs at least ceil(240/64)=4 GPUs. Suppose we choose TP=4 in one high-bandwidth node. Each rank holds roughly 60 GiB before uneven buffers, so it fits.

    We have 16 GPUs total. With TP=4 and no PP/EP/CP, DP=4 creates four replicas: world size = DP·TP = 16. This does not make one request 16 times faster. At best TP reduces some local math while introducing per-layer collectives; DP lets four replica groups serve independent batches, raising aggregate throughput. If a 2 MiB activation partial is all-reduced over n=4 with an ideal ring, each rank moves 2(n−1)/n·2 MiB = 3 MiB. At effective 150 GB/s, bandwidth time is about 0.021 ms, but collective launch/step latency and 64 repeated layers can dominate small decode steps. Replacing intra-node links with a slower inter-node network can erase TP gains even if capacity still fits.

    Exactness, quality, performance, and topology

    Sharding an exact mathematical operation should preserve model semantics, but floating-point reductions are not associative. Different collective orders can produce small logit changes and therefore different samples. EP capacity overflow, approximate routing, communication quantization, or dropped tokens can create larger quality changes. Report whether parallelism is mathematically equivalent, numerically close, or intentionally approximate.

    Latency and throughput must be charted separately. TP may lower single-request compute time while synchronization raises inter-token latency. PP may raise latency but improve throughput at sufficient concurrency. DP almost linearly raises capacity until routing, memory, host, or network bottlenecks emerge. EP enables sparse models to fit but is sensitive to token distribution. CP enables contexts that otherwise fail but can add network-bound attention. Measure P50/P99 TTFT, inter-token latency, tokens/s/GPU, batch size, collective time, and idle fraction.

    Topology is part of the algorithm. “Eight GPUs” could mean eight devices behind one high-speed fabric, two four-GPU islands crossing PCIe, or eight hosts on a congested network. Place chatty TP groups on fastest links; place lower-frequency PP boundaries across nodes; keep expert communication within high-bisection groups when possible; and replicate with DP across failure domains. Hardware-aware rank mapping often matters as much as the degree values.

    Day 18 · Specialization

    Prefill/decode disaggregation: move state between optimized pools

    Prefill favors parallel arithmetic; decode repeatedly streams weights and KV. Separate pools isolate interference, but the KV handoff becomes a first-class distributed operation.

    A parcel service uses a sorting hub for a huge burst of parallel scanning, then local vans for incremental doorstep delivery. Asking every van to run a sorting warehouse wastes equipment; asking one warehouse to drive every route creates queues. Disaggregated inference assigns prompt processing to prefill workers and token-by-token generation to decode workers. The handoff—the KV cache plus request metadata—is the parcel transfer whose size, route, and timing decide whether specialization helps.

    First principles: two arithmetic regimes

    Prefill processes many prompt positions together. Large matrix multiplications reuse weights across tokens, increasing arithmetic intensity and tensor-core utilization. Its visible metric is time to first token (TTFT), and long prompts can occupy a GPU for substantial bursts. Decode adds one position per active sequence each step. It repeatedly reads model weights and growing KV history for relatively little arithmetic, often making high-bandwidth memory and batching the limits. Its user metric is inter-token latency (ITL), while the fleet also cares about decode tokens per second.

    When both phases share workers, a long prefill can delay decode steps and create ITL spikes. Reserving decode-only workers protects cadence; prefill-only workers can use larger chunks or different tensor-parallel degrees without blocking active streams. The price is duplicated or differently sharded model weights, separate schedulers, more failure modes, and KV transfer.

    • Disaggregation: assigning prefill and decode to separate worker pools.
    • xPyD: x prefill workers paired operationally with y decode workers.
    • KV handoff: transfer of attention cache and metadata after prefill.
    • Goodput: work meeting service-level objectives, not merely completed work.
    • Backpressure: slowing admission when downstream capacity cannot accept work.
    • Rendezvous: coordination that tells sender and receiver where/how to exchange state.

    End-to-end flow

    1 · AdmitClassify prompt/output expectations and choose pools.
    2 · PrefillCompute prompt hidden states, KV blocks, and first-token logits.
    3 · AllocateReserve compatible destination KV pages on a decode worker.
    4 · TransferMove KV directly or through a tier; send block metadata.
    5 · DecodeConfirm ownership, continue positions, sample, and stream.

    The router should select a decode worker before or during prefill so memory can be reserved and transfer can overlap tail computation where supported. The handoff needs request ID, sequence length, block table, model/shard identity, KV dtype/layout, positions, and completion signaling. The receiver must not decode from partially transferred blocks. Retries need idempotent ownership rules: after a timeout, the system must know whether to reuse received blocks, discard them, or re-prefill.

    KV layouts must be compatible. If prefill uses TP=8 and decode TP=2, the cache may need redistribution, not a simple byte copy. Head ownership, layer partitioning, page size, alignment, dtype, and tensor layout determine which source rank sends to which destination rank. A transport library can coordinate GPU-direct movement over NVLink, PCIe, or RDMA, but it cannot remove the volume or topology constraints.

    The transfer equation and break-even condition

    T_handoff = T_queue + T_setup + KV_bytes / B_effective + T_redistribute + T_sync

    T_queue is waiting for a decode destination; T_setup covers rendezvous and registration; KV_bytes follows the Day 16 formula; B_effective is achieved transfer bandwidth; T_redistribute covers reshaping or cross-rank exchange; and T_sync ensures completion and visibility. Disaggregation helps latency only if phase isolation and better specialization save more than this handoff plus added queues. It can still improve SLO goodput by reducing interference even if mean latency barely changes.

    Worked numeric example: 32K prompt handoff

    Use L=80, Hkv=8, Dhead=128, T=32,768, e=2 bytes. Per token: 2·80·8·128·2 = 327,680 bytes. Total: 10,737,418,240 bytes, exactly 10 GiB (about 10.74 GB). At an achieved 800 GB/s, raw transfer is 13.4 ms. At 50 GB/s it is 214.7 ms. Add 3 ms setup and 5 ms synchronization: approximately 21.4 ms versus 222.7 ms, before queueing or redistribution.

    Suppose colocated serving gives a decode request a 180 ms queue/interference penalty after long prefills, while specialization reduces it to 20 ms. The saved 160 ms beats the fast-link 21.4 ms handoff but not the slow-link 222.7 ms handoff. On the slow link, disaggregation might still work for shorter prompts, compressed KV, or much larger interference, but the architecture is not automatically beneficial.

    Capacity planning and routing

    Let λ be request arrival rate, E[T] expected input tokens, E[O] expected output tokens, Rp aggregate sustainable prefill tokens/s per prefill worker, and Rd decode tokens/s per decode worker at the target latency. Rough first estimates are Np ≥ λE[T]/Rp and Nd ≥ λE[O]/Rd, followed by queueing simulation and headroom. Averages are not enough: long prompts and outputs create heavy tails; prompt/output correlation matters; and decode capacity is occupied over time, not in one burst.

    Routing should consider prompt length, deadline, cache locality, predicted output length, destination KV capacity, and pool queues. Least-loaded routing, as demonstrated in the project, is a baseline. Production may reserve short-prompt lanes, prioritize active decode, or choose colocated execution for tiny prompts where transfer setup dominates. Backpressure should begin before decode HBM is exhausted; otherwise prefill completes work that has nowhere to land.

    Pool ratios can change over time. Workloads with huge retrieved contexts and short answers need more prefill capacity. Chat or reasoning traffic with short prompts and long outputs needs more decode capacity. Autoscaling is slower than request fluctuations, so admission and routing need stable fallbacks: colocate, queue, re-prefill elsewhere, shorten cache retention, or reject according to policy.

    Failure and correctness

    Disaggregation should preserve the target model’s computation when KV is transferred losslessly with compatible layout and dtype. Compressing or requantizing KV can introduce quality error and must be evaluated separately. A partial, duplicated, stale, or mismatched cache is more dangerous: positions can shift silently, producing plausible but wrong generation. Include checksums or versioned descriptors, validate token count and model identity, and make state transitions explicit: allocated, transferring, ready, owned, released.

    If the prefill worker fails before transfer completion, retry prefill or resume only from a durable compatible cache. If the decode worker fails after accepting ownership, another worker generally needs the token history and KV; re-prefill is the correctness fallback. Transports can retry chunks, but application-level ownership prevents two workers from streaming divergent continuations. Cancellation must reclaim both source staging buffers and destination blocks.

    Performance and hardware dependence

    Fast GPU fabrics make large handoffs feasible; PCIe, Ethernet, or oversubscribed InfiniBand change the break-even point. GPUDirect/RDMA avoids host copies but requires registration, topology-aware placement, and operational maturity. HBM capacity on decode workers often limits concurrency before compute. Prefill workers value compute throughput and may use higher TP; decode workers value memory bandwidth and may choose a different TP or quantization. Different GPU types can be economically sensible, but checkpoint and KV compatibility complicate operations.

    Measure TTFT, ITL, end-to-end latency, transfer duration and bandwidth, source/destination queue time, KV bytes, allocation failures, prefill/decode utilization, and SLO goodput. A high link utilization is not inherently good if transfers delay decode collectives. Compare against a tuned colocated baseline at the same traffic and quality. Model isolated microbenchmarks do not capture queueing interference—the principal reason to disaggregate.

    1. Why can prefill and decode benefit from different workers?

    KV tensors plus request/position metadata, block ownership/layout, model/shard identity, and a completion signal; often the first sampled token or logits state also participates in the handoff protocol.

    3. Why is bandwidth alone insufficient for transfer time?

    Queueing, setup, registration, redistribution, protocol overhead, contention, and synchronization add latency around the raw bytes/bandwidth term.

    4. What is the correctness fallback after lost KV?

    Re-prefill from the authoritative token history on a compatible worker, then continue decode. Cached KV is derived state.

    5. How should pool ratio be estimated?

    From arrival rate and input/output token demand divided by sustainable phase-specific capacity, then refined with tail distributions, queueing simulation, and headroom.

    6. Can disaggregation improve SLOs without reducing mean compute?

    Yes. Isolating long prefill bursts can reduce decode interference and tail ITL, increasing goodput even after paying handoff overhead.

    Quick reference

    Formula sheet

    Units are part of every equation. Use bytes with bytes/second, and state whether GB is decimal or GiB is binary.

    • Symmetric quantization
      q=clamp(round(x/s),qmin,qmax)
      x: original value; s: real-valued scale; q: code; qmin/qmax: code bounds.
    • Dequantization
      x̂=s·q
      x̂: reconstructed approximation. Error is x̂−x.
    • Asymmetric mapping
      q=round(x/s)+z
      z: zero point. Reconstruction is s(q−z).
    • Linear reconstruction error
      E=X(W−Ŵ)
      X: layer inputs; W: original weights; Ŵ: quantized reconstruction.
    • Smooth scaling identity
      XW=(X/s)(sW)
      s: positive per-channel vector, broadcast along matching dimensions.
    • Speculative acceptance
      a(t)=min(1,p(t)/q(t))
      t: proposal; p: target; q: draft.
    • Residual correction
      r(v)=[p(v)−q(v)]+ / Σu[p(u)−q(u)]+
      [x]+ means max(0,x).
    • KV capacity
      M=2·L·Hkv·D·T·B·e
      keys/values, layers, KV heads, head dimension, tokens, batch, bytes/element.
    • Transfer lower bound
      T=M/BW
      M: bytes; BW: achieved bytes/second. Add queues and fixed overhead.
    • Pipeline utilization
      U≈m/(m+p−1)
      m: microbatches; p: balanced stages.
    • Ring all-reduce volume
      Vrank≈2(n−1)S/n
      n: ranks; S: tensor bytes per rank.
    • World size
      N=DP·PP·TP·EP·CP
      Valid only when configured axes are truly independent rank dimensions.
    • Phase capacity estimate
      Np≥λE[T]/Rp, Nd≥λE[O]/Rd
      λ: requests/s; T/O: input/output tokens; R: worker rates.
    • Throughput speedup
      S=baseline time / optimized time
      State workload, quality, batch, hardware, and percentile.

    Glossary

    Compact definitions for the language used across all six days.

    Accumulation dtype
    The format used to sum products, often wider than operand storage.
    Activation
    An intermediate tensor produced by a layer for a particular input.
    All-gather
    A collective that concatenates shards and gives the complete result to every rank.
    All-reduce
    A collective that reduces values, commonly by sum, and returns the result to all ranks.
    All-to-all
    A collective in which every rank sends distinct data to every other rank.
    Arithmetic intensity
    Useful arithmetic operations performed per byte moved from a memory level.
    AWQ
    Activation-aware weight quantization that protects output-important channels through scaling.
    BF16
    A 16-bit float with eight exponent and seven stored fraction bits.
    Block scale
    A scale shared by a small block of low-precision values.
    Bubble
    Idle pipeline capacity while stages wait during fill, drain, or imbalance.
    Cache affinity
    A routing preference for the worker that holds reusable state.
    Calibration
    Collecting representative activation statistics after training for quantization decisions.
    Collective
    A coordinated communication operation over a group of ranks.
    Context parallelism
    Partitioning sequence positions and exchanging attention state across ranks.
    Data parallelism
    Replicating a model or shard group to serve independent work.
    Decode
    The sequential phase that adds one new token position per active sequence step.
    Disaggregation
    Serving prefill and decode on distinct worker pools.
    Draft model
    A cheap proposer used to create speculative candidates.
    Dynamic range
    The span between smallest and largest useful representable magnitudes.
    EAGLE
    A family of speculative methods that drafts using target-informed feature representations.
    Effective bandwidth
    Measured payload transfer rate after topology and protocol overhead.
    Expert parallelism
    Distributing MoE experts and routing tokens to their owning ranks.
    FP8
    An eight-bit floating family such as E4M3 or E5M2.
    Goodput
    Useful completed work that satisfies specified service objectives.
    GPTQ
    A PTQ method that uses approximate curvature to compensate sequential weight rounding.
    Granularity
    The scope that shares quantization parameters: tensor, channel, group, or block.
    Group size
    Number of adjacent values sharing quantization metadata.
    HBM
    High-bandwidth device memory used for model weights, activations, and KV.
    Hessian
    A matrix of second derivatives describing local curvature and perturbation interaction.
    INT4
    A four-bit integer code, commonly used for grouped weight-only quantization.
    INT8
    An eight-bit integer code used for weights and, with care, activations.
    Inter-token latency (ITL)
    Time between successively streamed output tokens.
    KV cache
    Stored attention keys and values that avoid recomputing prior positions.
    Medusa
    A speculative approach using additional future-token heads and tree verification.
    Microbatch
    A unit scheduled through pipeline stages to keep multiple stages occupied.
    Microscaling
    Very fine-grained block scaling used by formats such as NVFP4.
    MoE
    Mixture-of-Experts model that routes each token to a subset of expert networks.
    MTP
    Multi-token prediction objectives or heads that predict multiple future positions.
    Nibble
    Four bits; two nibbles pack into one byte.
    NVFP4
    A four-bit floating representation paired with fine-grained shared scales on supported hardware.
    Pipeline parallelism
    Assigning consecutive layer blocks to sequential device stages.
    Post-training quantization
    Reducing precision after model training, usually using calibration rather than full retraining.
    Precision
    How finely a numerical representation distinguishes nearby values.
    Prefill
    Parallel prompt processing that creates initial KV and first-token logits.
    Prefix cache
    Reusable KV state indexed by an exact initial token sequence and execution identity.
    Quantization
    Mapping values into a smaller representable set with reconstruction metadata.
    Rank
    One process/device identity in a distributed communication group.
    Reduce-scatter
    A collective that reduces contributions and leaves each rank with one output shard.
    Re-prefill
    Recomputing KV from tokens rather than loading transferred or retained state.
    Residual distribution
    The normalized positive mass p−q sampled after speculative rejection.
    Saturation
    Clipping values that fall outside representable code bounds.
    Scale
    A multiplier relating a low-bit code to an approximate real value.
    SmoothQuant
    A PTQ transform that moves activation-range difficulty into static weights.
    Speculative decoding
    Proposing cheap future tokens and verifying them in parallel with an authoritative target.
    Target model
    The authoritative probability distribution that speculative sampling preserves.
    Tensor parallelism
    Splitting matrix or attention dimensions within model layers across ranks.
    Time to first token (TTFT)
    Latency from request arrival to the first streamed output token.
    Weight-only quantization
    Low-bit stored weights paired with floating-point activations.
    World size
    Total number of participating distributed ranks.
    Zero point
    The integer code mapped to real zero in asymmetric quantization.

    Cumulative system-design exercise

    Design “Atlas,” a long-context assistant

    Combine all six days without assuming every optimization belongs in the first release.

    Scenario

    Atlas serves a 70B dense model. Traffic averages 12 requests/s and bursts to 30. Sixty percent of requests use one of twenty 8K-token system/tool prefixes, followed by 2K user tokens and 300 output tokens. The remaining traffic has 1K input and 800 output tokens. The SLO is P95 TTFT under 800 ms and P95 ITL under 45 ms. You have two eight-GPU nodes with 80 GiB per GPU, a fast fabric within each node, and an achieved 50 GB/s link between nodes. Product evaluation allows at most 0.5 percentage-point regression on tool-call validity and no material safety regression.

    Deliverables

    1. Baseline and measurement: define BF16 colocated baselines for both traffic classes. State batch policy, prompt/output distribution, TTFT, ITL, tokens/s/GPU, quality suite, and profiler evidence needed before changes.
    2. Representation: compare FP8, INT8, AWQ/GPTQ INT4, and mixed precision. Include effective bytes with scales, multiply and accumulation dtypes, supported kernels, model fit, expected decode bandwidth, and calibration corpus.
    3. Speculation: choose between n-gram, draft-target, Medusa/EAGLE/MTP, or none for each traffic class. Specify K, an adaptive disable rule, target-distribution exactness tests, and throughput guardrails.
    4. Prefix reuse: design canonical prompt ordering, cache key, radix/block lookup, byte budget, eviction/refcount policy, and cache-aware routing score. Estimate KV bytes for the shared 8K prefixes.
    5. Parallel plan: propose TP/PP/DP/EP/CP degrees and physical rank placement. Explain model fit, intra- and inter-node collectives, expected single-request latency, aggregate throughput, and whether enough concurrency exists for PP.
    6. Disaggregation: calculate 10K-token KV handoff size and transfer lower bound. Compare saved interference with handoff and queueing. Decide whether to disaggregate, colocate, or use a hybrid threshold by prompt length.
    7. Failure and rollout: define fallbacks for cache misses, low draft acceptance, link congestion, decode allocation failure, rank failure, quality regression, and stale cache identity. Propose canary stages and rollback thresholds.

    A strong answer should reveal tradeoffs, not one magic configuration

    Begin with constraints. Quantization may let a replica fit in fewer GPUs, enabling more DP groups, but quality and kernel evidence decide the format. Shared 8K prefixes make cache-aware routing attractive, yet routing must not overload one replica. N-gram speculation may help tool schemas or copied context while long novel answers may require another draft or no speculation. TP belongs on the fast intra-node fabric; cross-node TP over 50 GB/s needs strong evidence. Disaggregation must price a large KV handoff and may be reserved for the longest prompts rather than applied universally.

    Finally, state how you will know the design worked. Success is not “GPU utilization increased.” It is quality within contract, P95/P99 TTFT and ITL within SLO, stable goodput at burst load, lower cost per accepted output token, and predictable behavior under failures. If one technique improves an isolated benchmark while harming those outcomes, remove it.
