    Orientation

    How to read this page

    Three passes work best: skim the architecture, play the lifecycle, then dive into the chapter for the subsystem you care about.

    If you are new to inference engines

    Read the architecture section first, then press Play on the interactive lifecycle. Each card explains, in plain language, what happens to the request and what data structure carries it. The prefill vs decode walkthrough then puts numbers on the two phases. Unfamiliar words are in the glossary.

    If you already know vLLM

    Jump to the file-by-file trace or to a subsystem chapter.     How the evidence works

    Code links point to github.com/vllm-project/vllm/blob/7b77ed5… with a #L anchor on the line where the class or function is defined.     One sentence to hold onto: vLLM is a loop that, every few milliseconds, decides how many new tokens each active request may process (the scheduler), makes sure there is paged KV-cache memory for them (the KV cache manager), runs one batched forward pass over all of them (the model runner), samples one next token per request, and ships those token IDs back to a different process that turns them into text.

    Big picture

    Processes, sockets, and one busy loop

    The V1 engine splits work across processes so Python overhead in one place never stalls the GPU in another.

    Why separate processes?

    Serving an LLM mixes two kinds of work with very different personalities. HTTP parsing, JSON validation, chat templating, tokenization, image decoding, detokenization, and server-sent-event formatting are CPU-bound Python. The forward pass is GPU-bound and wants to be fed a new batch the instant the previous one finishes. In a single Python process, the global interpreter lock makes those two personalities fight: a burst of tokenization can delay the next kernel launch, and the GPU idles. vLLM's V1 architecture, introduced in early 2025 and now the only engine (the old V0 code was deleted in the 0.11 cycle), puts the scheduler and model execution into a dedicated EngineCoreProc whose only job is to keep the GPU busy, while the API server process does everything that touches text.

    The official architecture overview counts processes the same way: one API server process by default (more with --api-server-count, and automatically one per data-parallel rank), one EngineCore process per data-parallel rank, one GPU worker process per GPU (that is, tensor_parallel_size × pipeline_parallel_size per engine), plus a coordinator process when data parallelism is enabled. A TP=4 deployment therefore runs six processes; TP=2 with DP=4 runs seventeen.

    The three hops a request makes

    1. API server → EngineCore. AsyncMPClient owns a ZeroMQ ROUTER socket; each EngineCore connects a DEALER. Requests are EngineCoreRequest msgspec structs encoded with MsgpackEncoder, sent as multipart frames whose first frame is a one-byte request type (ADD, ABORT, UTILITY, …). Large tensors can travel out-of-band as zero-copy frames.
    2. EngineCore → GPU workers. The MultiprocExecutor broadcasts one (method, args) tuple per step through a shared-memory ring buffer, MessageQueue, and reads results back from per-worker response queues. For execute_model and sample_tokens only the output rank's reply is awaited, unless a KV connector is configured, in which case every rank's reply is gathered so transfer status can be aggregated.
    3. EngineCore → API server. An output IO thread encodes EngineCoreOutputs and pushes them through a ZeroMQ PUSH socket (reusing send buffers); the client's PULL socket feeds an asyncio queue drained by AsyncLLM's background output_handler task.

    The busy loop

    Inside the EngineCore, two helper threads do socket IO so the main thread never blocks on the network. The main thread runs EngineCoreProc.run_busy_loop: drain the input queue (blocking only when there is truly nothing to do), then call the step function, then put any outputs on the output queue. The step function is either EngineCore.step (schedule → execute → sample → update) or, when more than one batch may be in flight, EngineCore.step_with_batch_queue.

    Async scheduling is on by default

    SchedulerConfig.async_scheduling defaults to None, and VllmConfig resolves it to True unless something incompatible is configured (pooling models, executors that do not support it, ROCm DeepEP high-throughput DBO, or V1-runner-only limitations). With it on, the scheduler class becomes AsyncScheduler and max_concurrent_batches becomes 2 for a non-pipelined engine (pipeline size + 1 under Model Runner V2). The engine therefore schedules step N+1 while the GPU is still running step N. Because the scheduler cannot know step N's sampled token yet, it reserves an "output placeholder" for it, and Model Runner V2 reads the real token straight from GPU memory when building step N+1's inputs. The CPU never waits for the GPU between steps.

    Model Runner V2 is the default

    VllmConfig.use_v2_model_runner returns True unless the VLLM_USE_V2_MODEL_RUNNER environment variable says otherwise, Triton is unavailable, or a feature that MRV2 does not yet support is requested (for example a speculative method without a V2 speculator class, EAGLE parallel drafting, heterogeneous-vocabulary draft models, pipeline parallelism under external_launcher, or certain dual-batch-overlap settings). In that case vLLM logs a warning and falls back to the original V1 runner in vllm/v1/worker/gpu_model_runner.py. This page traces MRV2 and points out where V1 differs.

    What happens before the first request

    A request can only be served once the engine knows how much KV-cache memory it owns. That number is measured, not configured, so startup is a small experiment. Reading EngineCore.__init__ top to bottom gives the order:

    1. Spawn the executor. Executor.get_class maps the backend name (uni, mp, ray, external_launcher) to a class; constructing it starts the worker(s), and each Worker initializes its device, sets up NCCL groups, and loads its shard of the weights.
    2. Profile memory. Worker.determine_available_memory runs a dummy forward pass sized at max_num_batched_tokens, records peak activation memory, estimates CUDA-graph memory, and subtracts weights and peaks from gpu_memory_utilization × total (default 0.92). Whatever is left becomes KV cache.
    3. Carve the KV cache. EngineCore._initialize_kv_caches collects every layer's KV-cache spec, divides the free bytes by the bytes per block, and asks every worker to allocate identical tensors so block i means the same thing on every rank.
    4. Compile and capture. The profiling run already traced and compiled the model with torch.compile; once the KV cache exists, workers warm up and record CUDA graphs for a ladder of batch sizes (see CUDA graphs & torch.compile).
    5. Build the scheduler. The engine instantiates AsyncScheduler (or Scheduler), whose KVCacheManager wraps a BlockPool with exactly the number of blocks just measured. It also creates the block-hash function used for prefix caching (sha256 by default).
    6. Say hello. The input IO thread sends an EngineCoreReadyResponse (block count, block size, max model length, parallel sizes) to every API server; only then does the frontend start accepting HTTP traffic.

    Six data structures you will meet everywhere

    Most confusion when reading vLLM comes from not knowing which object you are looking at. Each hop in the diagram above has its own message type, deliberately small so it serializes quickly.

    Worked example

    Prefill vs decode, with real numbers

    One request, followed block by block: how many tokens it costs, which blocks it gets, where each key and value lands, and why the first token is expensive while the rest are cheap.

    Every LLM request has two personalities. The prefill processes the whole prompt at once to build its KV cache and produce the first token. Each decode step processes a single new token, appends one key/value pair per layer, and produces the next token. vLLM does not have separate code paths for the two: the scheduler only ever asks "how many tokens is this request behind?" A prefill is just a request that is a thousand tokens behind; a decode is one that is one token behind. The arithmetic below makes that concrete.

    Step 0: hashing (before scheduling)

    When the EngineCore's input thread builds the Request, the block hasher walks this single-group example in full 16-token hash units:

    full blocks = floor(1000 / 16) = 62 (tokens 0 … 991) partial block = 1000 − 62 × 16 = 8 tokens (tokens 992 … 999, not hashed yet) h_i = sha256( h_{i−1}, tokens[16i : 16i+16], extra_keys ) for i = 0 … 61

    Because each hash includes its parent, h_39 fingerprints the entire first 640 tokens, not just tokens 624 to 639. Two requests can share block 39 only if they agree on everything before it too.

    Step 1: the prefix-cache lookup

    The scheduler calls KVCacheManager.get_computed_blocks. The lookup may cover at most prompt_len − 1 = 999 tokens, because the model must run on at least the last prompt token to produce logits (Request.get_max_cache_hit_length). That allows checking floor(999 / 16) = 62 blocks. FullAttentionManager.find_longest_cache_hit walks h_0, h_1, … through the hash table and stops at the first miss. Blocks 0 to 39 hit (the shared system prompt); block 40 misses because it contains the start of a different user message.

    num_new_local_computed_tokens = 40 × 16 = 640 num_new_tokens = 1000 − 640 = 360 (≤ 8192 budget, so no chunking)

    Step 2: allocating blocks

    allocate_slots needs room for every token whose KV must exist after this step:

    blocks needed = ceil((640 + 360) / 16) = ceil(62.5) = 63 reused = 40 (touch: ref_cnt 1 → 2, removed from the free queue if it was there) new = 63 − 40 = 23 (popped from the head of the free queue) cached = blocks 40 … 61 registered by hash now; block 62 (8/16 full) is not

    The free-block check happens before anything is mutated, so a request that does not fit leaves no partial allocation behind. If the 23 blocks were not available, our new request would simply stay in the waiting queue; running requests are the ones that can trigger preemption.

    Step 3: the prefill forward pass

    The worker receives a batch with one request and 360 query tokens. Model Runner V2 builds positions = [640 … 999], query_start_loc = [0, 360], seq_lens = [1000], and a slot mapping that sends each new key and value to block_id × 16 + offset. Every layer:

    1. projects the 360 hidden states into queries, keys and values (32 query heads, 8 KV heads, head dim 128) and applies rotary position embeddings using the true positions 640 to 999;
    2. scatters the 360 new key and value rows into their slots, which fills blocks 40 to 61 and half of block 62;
    3. runs attention: query row p attends to keys 0 … p, of which the first 640 were written by someone else's request and are reused untouched.

    Only the hidden state at position 999 is projected through the LM head, giving one row of 128,256 logits; the sampler turns it into token 1. A back-of-envelope cost: a dense transformer needs about 2 × parameters FLOPs per token, so 360 × 2 × 8×10⁹ ≈ 5.8 TFLOP. Without the cache hit it would be 1000 × 16×10⁹ = 16 TFLOP. At a few hundred dense bf16 TFLOP/s of achieved throughput, that is the difference between roughly 10 to 15 ms and 25 to 40 ms of time-to-first-token for this step. Prefix caching made the prefill about 2.8× cheaper.

    Step 4: decode steps

    After the prefill, num_computed_tokens = 1000. Decode step k feeds token k at position 999 + k:

    decode 1: token 1 at pos 1000 → block 62, offset 8 (needs ceil(1001/16) = 63 blocks: none new) decode 8: token 8 at pos 1007 → block 62, offset 15 (block 62 now full → hashed and cached) decode 9: token 9 at pos 1008 → block 63, offset 0 (ceil(1009/16) = 64 → allocate 1 block) … decode 63: token 63 at pos 1062 → block 66 (67 blocks total; token 64 is never fed back)

    Each decode step costs one token of budget and, on average, one sixteenth of a block. The per-step FLOPs for our request are tiny (≈ 16 GFLOP), but streaming 16 GB of weights once at 3.35 TB/s already takes about 4.8 ms in an idealized bandwidth calculation. Requests batched in one pass can share those weight reads. Actual step time also depends on batch size, KV reads, arithmetic, kernel efficiency and launch overhead. Graph replay can reduce launch overhead for supported shapes.

    With async scheduling on, the scheduler schedules decode k+1 before the GPU has finished sampling token k. It records an output placeholder, charges one token of budget, and Model Runner V2 reads the real token ID from last_sampled_tokens on the GPU when it builds the next input batch.

    Step 5: how much memory is that?

    KV bytes per token = 2 (K and V) × 32 layers × 8 KV heads × 128 dims × 2 bytes = 131,072 B = 128 KiB KV bytes per block = 16 × 128 KiB = 2 MiB (64 KiB per layer) request A at 1,000 tokens = 63 blocks = 126 MiB, of which 40 blocks (80 MiB) are shared request A at the end = 67 blocks = 134 MiB

    On an 80 GB GPU with gpu_memory_utilization = 0.92, roughly 16 GB of weights and a few GB of activations and CUDA graphs leave on the order of 50 GB for KV cache, which is about 25,000 blocks or 400,000 tokens. vLLM prints the exact figure at startup ("KV cache size: N tokens" and a maximum concurrency estimate, from update_kv_cache_capacity). Without paging, each request would need a contiguous reservation for its maximum length; with paging it holds only ceil(tokens / 16) blocks and wastes at most 15 slots.

    Step 6: the same request in a busy server

    Now suppose 120 other requests are decoding and a request B with a 10,000-token prompt (no cache hit) arrives at the same time as A. One call to schedule() spends the 8,192-token budget like this:

    1. Running first. 120 decodes × 1 token = 120. Budget left: 8,072.
    2. Waiting: A. 360 uncached tokens fit. Budget left: 7,712.
    3. Waiting: B. 10,000 > 7,712, and chunked prefill is on, so B is admitted with a 7,712-token chunk. Budget left: 0.
    4. Next step. B is now running with 2,288 prompt tokens left; it gets them after the decodes, alongside any new arrivals.
    5. Logits. 122 rows are computed (120 decodes, A, B), but B's sampled value is thrown away because its prefill is unfinished; 121 tokens come back.

    That single step does about 8192 × 16×10⁹ ≈ 131 TFLOP of work, so the 120 decoding users see one slow inter-token gap (on the order of a couple of hundred milliseconds) while B's prompt is absorbed. Lowering max_num_batched_tokens shortens that gap at the price of a slower time-to-first-token for long prompts; --long-prefill-token-threshold caps how much of the budget any single prompt may take per step when more than one request is competing.

    Subsystem · EngineCore

    The scheduler and preemption

    Every few milliseconds the scheduler answers one question: which requests may process how many tokens in the next forward pass?

    One rule instead of two phases

    A comment at the top of Scheduler.schedule states the design in plain terms: the scheduler has no notion of a prefill phase or a decode phase. Each request carries num_computed_tokens (how much of it already has KV in the cache) and num_tokens_with_spec (prompt plus output plus any speculative draft tokens). Each step the scheduler hands out tokens so the first number can catch up with the second. A new 1,000-token prompt is 1,000 behind; a decoding request is 1 behind; a request with three draft tokens is 4 behind. Chunked prefill, prefix caching and speculative decoding all fall out of that one rule rather than needing special cases.

    The queues and states

    • Waiting. Built by create_request_queue: a FIFO deque under the default fcfs policy, or a heap ordered by (priority, arrival_time) under priority, where a smaller priority value is served first.
    • KV-holding waiting. A second queue for requests that already own blocks while they wait, such as those whose KV is still arriving from a remote prefill. It is drained first so those blocks are not tied up longer than necessary.
    • Running. A plain list in admission order. Being in it means the request owns KV blocks and a row in the model runner.
    • States. RequestStatus distinguishes WAITING, three special waiting states (grammar compilation, remote KV transfer, streaming input), RUNNING, PREEMPTED, and six finished states. Anything after PREEMPTED counts as finished.

    Walking through schedule()

    1. Running requests first. For each running request the scheduler computes how many tokens it is behind, then caps that by long_prefill_token_threshold (only when more than one request is competing), the remaining budget, and the space left before max_model_len. Multimodal requests may be trimmed further so an image's encoder output fits the encoder budget. Then it calls allocate_slots.
    2. Make room if needed. If allocation fails, the scheduler preempts a victim and tries again: the last request in the running list under FCFS, or the one with the largest (priority, arrival_time) under the priority policy. If the victim turns out to be the request being scheduled, it gives up on that request for this step.
    3. Then waiting requests. Only if nothing was preempted, the scheduler admits waiting requests while there is budget, the running count is below max_num_seqs, and the LoRA limit allows. For each it does the prefix-cache lookup (only when num_computed_tokens == 0), asks the KV connector for externally cached tokens if one is configured, and schedules the uncached remainder, chunked to the budget. With chunked prefill disabled, a prompt that does not fit in the remaining budget simply waits.
    4. Package the plan. Newly admitted requests become NewRequestData (full token lists and block IDs); previously seen ones become a compact CachedRequestData diff.
    5. Advance optimistically. _update_after_schedule adds the scheduled count to num_computed_tokens immediately, so the next call can schedule the next chunk of a long prompt without waiting for this step to finish.

    Note the asymmetry: the running loop uses continue when a request cannot make progress for reasons other than memory (for example an exhausted encoder budget), so later requests still get a chance, while running out of KV memory stops admission altogether. That keeps already-running requests from being starved by newcomers.

    Preemption means recompute

    _preempt_request frees the victim's KV blocks and encoder-cache entries, sets its status to PREEMPTED, resets num_computed_tokens to 0, increments num_preemptions, and pushes it back to the front of the waiting queue. Nothing is copied to CPU memory. When the request is readmitted, its whole token list (prompt plus everything generated so far) is treated as a new prompt. In practice that recompute is often cheap: freed blocks keep their hashes until the pool actually reuses them, so the prefix-cache lookup on readmission frequently recovers most of the sequence. Moving KV to CPU or disk is a separate opt-in feature (see KV offloading). Preemptions are counted in the metrics; a steady stream of them means the KV cache is too small for the load.

    Async scheduling and output placeholders

    With AsyncScheduler, step N+1 is scheduled while step N is still on the GPU, so the scheduler does not yet know the token step N will produce. Its _update_after_schedule therefore bumps num_output_placeholders by one (plus the number of draft tokens) for every decoding request. The running loop counts placeholders as tokens that exist, so a decoding request is "one behind" again and gets scheduled. When the real tokens arrive, update_from_output retires the placeholders. The scheduler also skips scheduling an extra step for a request that is certain to hit max_tokens with the tokens already in flight.

    After the GPU: update_from_output

    update_from_output is the only other hot loop in the EngineCore. Per scheduled request it: subtracts rejected speculative tokens from num_computed_tokens; appends the accepted tokens one by one, running check_stop after each; records per-request spec-decode metrics; and builds an EngineCoreOutput grouped by the API-server client that owns the request. check_stop tests, in order: the EOS token, stop_token_ids, the length limits (max_tokens and max_model_len), and, once min_tokens is satisfied, optional repetition detection. Stop strings are not checked here; the EngineCore never sees text.

    Subsystem · EngineCore + workers

    The KV cache, block pool, and prefix caching

    Paged attention splits every sequence's keys and values into fixed-size blocks, so memory is allocated like pages in an operating system rather than as one contiguous slab per request.

    Two halves of one idea

    The KV cache lives in two places that never share a pointer. In the EngineCore, a block is just metadata: a KVCacheBlock with a block_id, a reference count, an optional hash, and two free-list pointers. In each GPU worker, block i is a slice of real cache storage for participating local layers, allocated at startup. The SchedulerOutput carries block IDs along with scheduling metadata. Workers translate the IDs into their own rank-local storage. Tensor-parallel ranks may own different head shards and pipeline stages own different layers. Trace a logical position to a physical slot.

    How big is a block? For a standard attention layer, AttentionSpec.page_size_bytes works out to num_kv_heads × block_size × (head_size + head_size_v) × dtype bytes. The FlashAttention backend documents its per-layer cache as a tensor shaped [num_blocks, num_kv_heads, block_size, 2 × head_size], keys and values side by side in the last dimension. Choosing --kv-cache-dtype fp8 halves those bytes (and so roughly doubles how many tokens fit), at the cost of some precision.

    The block pool

    BlockPool creates one KVCacheBlock per physical block and threads all of them into a FreeKVCacheBlockQueue. The queue is a hand-written doubly linked list, not a deque, because a prefix-cache hit has to pull a block out of the middle of the free list in constant time. Block 0 is taken out at construction as the null block, a placeholder used for skipped positions (for example tokens outside a sliding window).

    • get_new_blocks pops from the head. If a popped block still carries a hash, that hash is removed from the table first: this is the moment a cached prefix is actually evicted.
    • touch increments the reference count of a cached block and, if it was free, unlinks it from the queue.
    • free_blocks decrements counts. Blocks reaching zero without a hash are prepended (reused soon, which helps locality); blocks with a hash are appended so they survive as long as possible in LRU order. Requests free their blocks in reverse, so the end of a sequence is evicted before its widely shared beginning.

    Prefix caching in detail

    Automatic prefix caching is on by default and works at block granularity. Hashes are computed when a block becomes full, either from the prompt at request creation or as generated tokens fill blocks. Each hash covers the parent hash, the block's token IDs, and extra keys that must also match: LoRA adapter name, multimodal content hashes for image or audio placeholders inside the block, prompt-embedding digests, and a cache_salt on the first block if the request supplied one. A salt is the simple way to stop tenants from observing each other's cache hits through timing.

    The hash function is chosen with --prefix-caching-hash-algo: sha256 (default, pickle-serialized), sha256_cbor (reproducible across languages), or the faster non-cryptographic xxhash and xxhash_cbor. For the non-cryptographic ones vLLM seeds the root hash randomly per process unless PYTHONHASHSEED is set, and logs a warning that hashes will not match across instances.

    Ordinary generation leaves at least the last prompt position to compute its logits. In this dense single-group example, rounding down to a full block can leave up to a block of work even for an identical prompt. Compatible hybrid configurations can support sub-block hit boundaries. Cache hits and queries are recorded per step and exported as the prefix-cache hit-rate metric. The cache can be cleared at runtime through KVCacheManager.reset_prefix_cache (exposed as the development endpoint POST /reset_prefix_cache), which is useful when benchmarking.

    Hybrid models and KV-cache groups

    Not every layer wants the same cache. Sliding-window layers only need the last w tokens; Mamba layers keep a fixed-size state; encoder-decoder models need cross-attention caches. vLLM groups layers with identical specs into KV-cache groups and gives each group its own manager: FullAttentionManager, SlidingWindowManager, MambaManager and others. A coordinator from get_kv_cache_coordinator sits between them and the KVCacheManager: the unitary coordinator for plain models, and HybridKVCacheCoordinator for mixes, which must find a prefix length every group can serve. All groups allocate from one shared block pool, with page sizes made uniform across groups; the design is described in vLLM's hybrid KV cache manager doc.

    Sizing the cache

    • --gpu-memory-utilization (default 0.92) bounds total memory per instance; KV gets whatever is left after weights, peak activations, and CUDA graphs.
    • --kv-cache-memory-bytes sets the KV budget directly and skips the utilization-based calculation.
    • num_gpu_blocks_override forces a block count, mainly for testing preemption.
    • --block-size changes tokens per block. Backends advertise which sizes they support (FlashAttention: multiples of 16); larger blocks mean fewer table entries but coarser prefix hits and more tail waste.

    Subsystem · GPU worker

    The model runner and the input batch

    The model runner turns a scheduling plan made of request IDs and block IDs into GPU tensors, runs the model, and turns logits back into token IDs, while never making the CPU wait for the GPU.

    Why there is a "V2"

    The original V1 runner (vllm/v1/worker/gpu_model_runner.py) kept a persistent batch: CPU-side tensors that were reused across steps and patched in place as requests came and went. That saved Python work but coupled per-request state to the order of rows in the model inputs, which made joins, finishes and especially asynchronous scheduling awkward. vLLM's Model Runner V2 design note explains the rewrite; in short, Model Runner V2 (MRV2, in vllm/v1/worker/gpu/):

    • gives each request a permanent row in fixed-size state tensors for its lifetime (RequestState), and builds each step's inputs by gathering rows on the GPU, so row order no longer matters;
    • applies changes with StagedWriteTensor: diffs are staged on the CPU, packed, copied once, and scattered by a single kernel;
    • keeps very large tables such as every request's token IDs in pinned host memory that GPU kernels read directly through unified virtual addressing (UVA), saving device memory;
    • prepares inputs with small Triton kernels, so values the CPU does not know yet (the last sampled token, accepted draft counts) can be used without synchronizing;
    • treats preemption as finishing, and routes dummy runs for profiling and data-parallel padding through the same execute_model path.

    Inside execute_model

    1. State update. finish_requests and free_states release rows for finished or preempted requests; add_requests claims rows for new ones and registers their sampling parameters; update_requests appends new block IDs for running ones. Then staged writes are applied.
    2. Shape decision. gather_batch_req_state summarizes the batch (token count, prefill or not, uniform decode length), and dispatch_cg_and_sync_dp picks the CUDA-graph descriptor and padded size.
    3. Inputs. prepare_inputs builds the InputBatch in persistent InputBuffers (same addresses every step, which CUDA graphs require).
    4. Attention. prepare_attn gathers block tables and computes slot mappings; the model state builds one metadata object per attention group with the backend's metadata builder.
    5. Extras. LoRA adapters are activated for the batch; multimodal encoder outputs or prompt embeddings are merged into inputs_embeds on the first pipeline rank.
    6. Forward. Replay a FULL graph, or call the compiled model inside set_forward_context (PIECEWISE or eager). Hidden states are stashed in an ExecuteModelState; non-last pipeline ranks return intermediate tensors instead.

    FieldShapeMeaning (worked example, prefill step)

    Why sampling is a separate RPC

    sample_tokens is called after execute_model returns, with the grammar bitmask as its argument. Splitting the step this way lets the EngineCore compute bitmasks for structured-output requests on the CPU while the forward pass runs on the GPU, instead of serializing the two. After sampling, postprocess_sampled updates num_computed_tokens, last_sampled_tokens and penalty counters on the GPU; if speculative decoding is on, the speculator proposes drafts for the next step; then an AsyncOutput starts the device-to-host copy and is returned immediately.

    Model states: one runner, many model families

    Model-family quirks live in small "model state" classes rather than in the runner: DefaultModelState for ordinary decoders, MambaHybridModelState for models that mix attention with state-space layers, EncoderDecoderModelState for Whisper-style models, and helpers for prompt embeddings. Each one knows how to build attention metadata and extra model inputs for its family, which keeps GPUModelRunner itself family-agnostic.

    Subsystem · GPU worker

    Attention backends and the paged KV write

    The model code calls one generic Attention layer. Underneath, a backend chosen at startup decides how keys and values are stored and which kernel reads them.

    Three objects per backend

    Every backend in vllm/v1/attention/backends/ follows the same pattern, illustrated here with FlashAttention:

    • FlashAttentionBackend is a class-level description: supported dtypes and KV-cache dtypes, supported block sizes (multiples of 16 here), whether it handles sliding windows, non-causal attention, and so on. The selector reads these to decide whether the backend can serve a model.
    • FlashAttentionMetadataBuilder runs once per step per attention group and turns the batch description (query_start_loc, seq_lens, block table, slot mapping) into a FlashAttentionMetadata, optionally precomputing kernel scheduling data.
    • FlashAttentionImpl lives inside each layer and does the work: do_kv_cache_update and forward.

    What one attention call does

    LlamaAttention.forward computes Q, K and V with one fused projection, applies rotary embeddings at each token's true position, and calls Attention.forward. That method reshapes the tensors to [tokens, heads, head_dim] and makes two calls, both registered as PyTorch custom ops so that torch.compile treats them as opaque:

    1. unified_kv_cache_update looks up this layer's cache tensor and slot mapping in the forward context and calls do_kv_cache_update, which runs the reshape_and_cache_flash kernel: for each token i, write K[i] and V[i] to slot slot_mapping[i]. Padding tokens carry a pad slot and are skipped.
    2. unified_attention_with_output fetches the layer's metadata and calls FlashAttentionImpl.forward, which runs variable-length FlashAttention with cu_seqlens_q = query_start_loc, seqused_k = seq_lens, and the block table. The kernel walks each request's block table to find its keys, so a request's KV can be scattered across the whole pool.

    The first op returns an empty tensor that is passed into the second. It carries no data; it exists so the compiler sees a dependency and cannot move the attention read ahead of the cache write. The same mechanism handles both prefill rows and decode rows in one launch: the kernel does not care whether a request contributes 360 query tokens or 1.

    How a backend is chosen

    Each Attention layer asks get_attn_backend at construction time. Unless --attention-backend names one explicitly, the platform walks a priority list and takes the first backend that supports the model's head size, dtype, KV-cache dtype, block size and attention type. On NVIDIA GPUs the list comes from _get_backend_priorities. For ordinary (non-MLA) attention it starts with FlashAttention on most GPUs and with FlashInfer on data-center Blackwell (compute capability 10.x), followed by Triton attention and FlexAttention. Models with multi-head latent attention, such as DeepSeek, have their own MLA list (FlashInfer-MLA, CUTLASS-MLA, FlashMLA, Triton MLA and sparse variants, depending on the GPU). AMD GPUs use ROCm-specific backends (AITER, Triton) selected by the ROCm platform. Hybrid models can use different backends for different layer groups, for example a Mamba backend next to FlashAttention.

    Cascade attention is gone. Older vLLM versions could run a special two-pass "cascade" kernel when many requests shared a long common prefix. At this commit the field that fed it, num_common_prefix_blocks, is documented in SchedulerOutput as deprecated and always empty. Shared prefixes are still deduplicated in memory by prefix caching; they are simply read by the normal paged kernel.

    Subsystem · GPU worker

    CUDA graphs and torch.compile

    Two separate optimizations, often confused: torch.compile makes the kernels better; CUDA graphs make launching them nearly free.

    The problem they solve

    A decode step for a small batch does very little arithmetic per kernel, and an 8B-parameter model launches many hundreds of kernels per forward pass. Launching each one from Python costs a few microseconds of CPU time, so for small decode batches the GPU can spend much of the step waiting for the CPU to tell it what to do next. Fusing operations reduces the number of kernels; recording the whole sequence once and replaying it removes the per-kernel CPU cost.

    torch.compile in vLLM

    Models opt in with the @support_torch_compile decorator; Llama applies it to LlamaModel, marking the token dimension of input_ids, positions and the other inputs as dynamic. In the default CompilationMode, VLLM_COMPILE, Dynamo traces the model once into an FX graph, and VllmBackend splits that graph at the attention custom ops (the "splitting ops"). Each piece between two attention calls is compiled by Inductor, with vLLM's own fusion passes (for example RMSNorm plus quantization, or RoPE plus KV-cache write) applied according to the optimization level. Compiled artifacts are cached on disk, so a second start of the same model skips most of this work.

    CUDA graphs and the five modes

    A CUDA graph records a fixed sequence of kernel launches with fixed tensor addresses and replays it with one call. Fixed addresses are why the runner keeps persistent input buffers, and fixed shapes are why batches are padded to one of a set of capture sizes. By default that set is [1, 2, 4], then every multiple of 8 up to 248, then every multiple of 16 up to max_cudagraph_capture_size, which defaults to 512 (1024 on data-center Blackwell). The mode is set by cudagraph_mode:

    Runtime dispatch in Model Runner V2

    Every step, CudaGraphManager.dispatch looks for a captured BatchExecutionDescriptor compatible with the batch: enough tokens, enough request slots, matching uniform-decode length and LoRA count. A uniform decode batch of 37 requests is padded to 40 and replays the FULL graph captured for 40 through run_fullgraph. A mixed batch of 360 tokens is padded to 368 and runs through run_pw_graph, where the compiled pieces replay their own graphs via CUDAGraphWrapper. A batch larger than the largest capture size falls back to the compiled model without graphs. With data parallelism the ranks first agree on a common size, because MoE collectives need every rank to run the same shape.

    The startup bill

    Compilation and capture happen once per server start, after weights load and before the first request. Capturing graphs for every size in the ladder, in both modes, can take tens of seconds for large models and uses GPU memory that would otherwise hold KV cache; the memory profiler measures it so the KV budget accounts for it. Shortcuts when iterating: -O0 or --enforce-eager for fastest startup, a smaller --max-cudagraph-capture-size or an explicit --cudagraph-capture-sizes list to capture fewer graphs, and a persistent compile cache directory so restarts reuse Inductor artifacts. The optimization levels are defined in VllmConfig.optimization_level, with -O2 as the default.

    Subsystem · GPU worker

    Logits, logits processors, and the sampler

    From a hidden state to one token ID per request: which rows become logits, what modifies them, and how a token is drawn without ever materializing a softmax.

    Only some rows become logits

    Projecting a 4,096-wide hidden state onto a 128,256-token vocabulary is expensive, so the runner only does it for rows that will be sampled. logits_indices from the input batch selects the last scheduled position of each request (plus draft positions under speculative decoding), and LlamaForCausalLM.compute_logits passes them through the LM head with LogitsProcessor (vocabulary shards are gathered across tensor-parallel ranks; an optional logit_scale from the model config is applied). With batch-sharded sampling enabled, ranks instead exchange vocabulary shards so each rank samples a subset of requests, which helps very large batches.

    The processing pipeline

    Sampler.apply_sampling_params first checks whether any request in the batch needs processing; a batch of plain requests skips straight to sampling with no extra copy. Otherwise logits are copied to float32 and run through a fixed list whose order matters, because adding a bias and scaling by a penalty do not commute:

    1. Grammar bitmask (applied earlier, in GPUModelRunner.sample): disallowed tokens are set to negative infinity. The mask was computed on the EngineCore by StructuredOutputManager.grammar_bitmask using the configured backend (xgrammar, guidance, outlines or lm-format-enforcer; auto by default).
    2. LogitBiasState: logit_bias, allowed_token_ids, and min_tokens (stop tokens are masked until the minimum length is reached).
    3. PenaltiesState: repetition, frequency and presence penalties, using per-request token counts kept on the GPU.
    4. BadWordsState, then any custom processors loaded with --logits-processors (they implement LogitsProcessor).
    5. ThinkingBudgetState runs last among processors so that forcing the end of a reasoning segment cannot be undone by a later stage.
    6. Temperature, then min-p, then top-k / top-p, from the per-request values in SamplingStates.

    Drawing a token with Gumbel-max

    Instead of computing softmax probabilities and sampling from them, the Model Runner V2 sampler adds Gumbel noise to the (temperature-scaled) logits and takes the argmax. That gives exactly the same distribution as sampling from softmax(logits / T), but it is a single pass over the vocabulary with no normalization step. The noise for each token comes from a hash of the request's seed, the token's position, and the vocabulary index (gumbel_sample), so it is stateless: the same seed and position always give the same draw, which is what makes per-request seed reproducible and lets speculative drafts and their verification agree. At temperature 0 no noise is added and the result is a plain argmax (greedy). When every request in a batch is eligible (top-k or top-p in use, no greedy rows, no explicit seeds), a fused FlashInfer sampling kernel may be used instead.

    Logprobs and speculative decoding

    Logprobs are computed from the raw model logits by default (--logprobs-mode raw_logprobs); other modes return processed logprobs or logits. Model Runner V2 finds the top-k candidates on the logits first and computes the log-softmax only for those, rather than materializing a full-vocabulary logprob matrix. When draft tokens are scheduled, RejectionSampler replaces the plain sampler: it compares target and draft probabilities position by position, accepts a prefix of the drafts, and emits one extra token from the target distribution, so the output distribution is unchanged while several tokens can come out of one forward pass.

    Subsystem · API server

    Detokenization and streaming

    Token IDs leave the EngineCore; text leaves the API server. Everything in between is about doing that conversion incrementally, cheaply, and without blocking HTTP handling.

    The output path, end to end

    1. Socket task. AsyncMPClient runs a task that receives frames from the PULL socket, decodes EngineCoreOutputs, and puts them on an asyncio queue.
    2. Output handler. AsyncLLM's background output_handler takes each batch and processes it in slices of VLLM_V1_OUTPUT_PROC_CHUNK_SIZE (128), yielding to the event loop between slices.
    3. Process. OutputProcessor.process_outputs detokenizes, checks stop strings, updates logprobs and per-request stats, and builds a RequestOutput.
    4. Deliver. The output goes into the request's RequestOutputCollector; the generate() coroutine awaiting it wakes up.
    5. Serialize. The chat stream generator converts it into a chat.completion.chunk and writes a data: line.

    Incremental detokenization

    Decoding tokens one at a time is subtle: a token may be half of a multi-byte character, and some tokenizers add or remove spaces depending on neighbors. The fast path, FastIncrementalDetokenizer, delegates to the Hugging Face tokenizers library's DecodeStream, primed with the prompt tokens so the first output token is decoded in context. Tokenizers without a fast implementation fall back to a Python path that tracks prefix and read offsets. Either way, update appends the new token IDs and returns any newly completed text.

    Stop strings and the hold-back buffer

    Stop strings can only be detected on text, so they are checked here, after detokenization, not in the EngineCore. To avoid streaming the first characters of a stop string before knowing it is one, the detokenizer holds back max(len(stop)) − 1 characters from each delta when the stop string is to be excluded from the output. When a stop string matches, the output text is truncated, the finish reason becomes stop, any tokens generated after the match are dropped, and the request ID is returned in reqs_to_abort; the output handler then sends an ABORT to the EngineCore, which would otherwise keep generating. Stop token IDs and EOS, by contrast, are handled in the EngineCore by check_stop and never cost an extra step.

    Back-pressure: merging deltas

    Each request's collector holds at most one pending output. If the engine produces a new delta before generate() has consumed the previous one (the client is slow, or the event loop is busy), the collector merges the two instead of queuing them. Memory per request therefore stays constant no matter how slow the reader is, and a slow client simply receives fewer, larger chunks. This is why you cannot assume "one SSE chunk = one token" when consuming vLLM streams.

    Shape of the stream

    chat_completion_stream_generator_raw sends, in order: one chunk per choice with delta.role = "assistant" and empty content (plus prompt_token_ids if return_token_ids was requested); content chunks as text arrives, split into reasoning, content and tool_calls deltas by ChatStreamProcessor when parsers are configured; a chunk carrying finish_reason; and, when stream_options.include_usage is set, a usage chunk with prompt, completion and cached-token counts. The outer chat_completion_stream_generator writes each as data: {json}, converts exceptions into an error event, and always ends with data: [DONE]. If the server was started with an SSE keep-alive interval, with_sse_keep_alive inserts comment lines during long silences so proxies do not time out.

    Cancellation

    A dropped connection must free GPU memory quickly. While the handler is still preparing the response, with_cancellation notices the http.disconnect message; once streaming has started, the Starlette response does. Either way generate() is cancelled, and its exception handler calls AsyncLLM.abort, which removes the request from the OutputProcessor and sends an ABORT message. On the EngineCore side the input thread places it on both the input queue and a dedicated aborts queue, and after the current model step Scheduler.finish_requests marks it FINISHED_ABORTED and frees its blocks. With async scheduling, any tokens already in flight for that request are simply ignored when they arrive.

    Scaling out

    Executors, parallelism, and communication

    One GPU runs the model in-process; more GPUs mean choosing how to slice the model, how to launch the worker processes, and which collectives glue them together.

    A model needs more than one GPU for one of two reasons. Either its weights and KV cache simply do not fit in one device's memory, or one device cannot produce tokens fast enough for the traffic you have. vLLM answers both with a small set of parallelism dimensions, all declared in ParallelConfig, plus an executor that decides how the worker processes are started and talked to. The two choices are independent: the parallel sizes say what each GPU holds, the executor says how the EngineCore reaches those GPUs.

    How the sizes multiply

    Inside one engine the number of worker processes is computed in ParallelConfig.__post_init__ as world_size = PP × TP × PCP. Data parallelism multiplies engines rather than workers: DP=4 with TP=2 means four EngineCore processes, each driving two GPUs. Decode context parallelism does not add processes at all; its docstring on decode_context_parallel_size explains that it reuses the TP ranks and only changes how KV pages are laid out across them (token i goes to rank i % dcp_size when the interleave size is 1). Expert parallelism also adds no processes; it re-partitions the MoE layers over the ranks you already have.

You can force a choice with --distributed-executor-backend; otherwise ParallelConfig picks one.

    • uni → UniProcExecutor. Chosen when the world size is 1. The worker lives inside the EngineCore process, so a step costs no inter-process hop.
    • mp → MultiprocExecutor. The default whenever more than one GPU is involved on CUDA, including multi-node runs started with --nnodes, --node-rank and --master-addr. It spawns one WorkerProc per GPU and broadcasts each step's method call through the shared-memory ring buffer MessageQueue.
    • ray → RayExecutorV2. A subclass of MultiprocExecutor whose workers (RayWorkerProc) are placed as Ray actors. Picked automatically when you are already inside a Ray placement group or initialized Ray cluster, or when --data-parallel-backend is ray.
    • external_launcher → ExecutorWithExternalLauncher. For torchrun-style SPMD jobs (common in RL training loops): every launched process is one rank, vLLM does not spawn workers itself, and V1 multiprocessing is switched off.
    • Specialty: CUDACheckpointExecutor extends the multiprocess executor for process-level checkpoint and restore experiments; you opt in by class name.

    The communication layer

    Every parallel dimension gets its own process group wrapper, GroupCoordinator, created once per worker in initialize_model_parallel and fetched by model code through accessors such as get_tp_group, get_pp_group, get_dp_group, get_ep_group, get_dcp_group and get_pcp_group. On NVIDIA hardware the device side of a group is a CudaCommunicator, which holds several all-reduce implementations side by side: vLLM's own CustomAllreduce (a one-shot/two-shot kernel over peer-mapped buffers that beats NCCL for the small messages typical of decode), a symmetric-memory communicator, FlashInfer all-reduce, a ROCm "quick" all-reduce, and the ctypes NCCL binding PyNcclCommunicator as the general fallback. --disable-custom-all-reduce forces the NCCL path, which is a useful first step when debugging hangs.

    In model code, TP is invisible except for layer types: a ColumnParallelLinear (or its fused cousins QKVParallelLinear and MergedColumnParallelLinear) splits output features, the following RowParallelLinear splits input features and ends with tensor_model_parallel_all_reduce, and VocabParallelEmbedding shards the vocabulary. PP is just as mechanical: make_layers uses get_pp_indices to instantiate only the layers this stage owns and fills the rest with PPMissingLayer placeholders; non-final stages return IntermediateTensors instead of logits.

    Data parallelism and the coordinator

    Each DP rank is a full engine. A request goes to exactly one rank, picked in the API server by DPLBAsyncMPClient using the waiting and running queue lengths that the DPCoordinator process collects from every engine. For dense models that is the whole story. For MoE models with EP, every rank must enter the MoE all2all together, so an idle rank cannot simply sleep: DPEngineCoreProc runs dummy batches while peers are busy, and every dp_sync_interval steps (default 16) the ranks all-reduce a single flag in _has_global_unfinished_reqs to decide whether the current "request wave" is over. Three load-balancing layouts exist: internal (one API endpoint balances all ranks; scale the frontend with --api-server-count), hybrid (--data-parallel-hybrid-lb: vLLM balances within a node, your load balancer across nodes), and external (--data-parallel-external-lb: one pod per rank, typical for wide-EP on Kubernetes).

    Expert parallelism in a little more depth

    Without EP, a MoE layer is tensor-parallel like any other: every GPU holds a slice of every expert. With --enable-expert-parallel, the MoE layer built by FusedMoEFactory instead gives each rank a set of whole experts, with the group size derived in FusedMoEParallelConfig from TP × DP (× PCP). Each token's hidden state is sent to the ranks that own its top-k experts and the weighted results are sent back; the "prepare" and "finalize" halves of that exchange are pluggable through FusedMoEPrepareAndFinalize, and the transport is chosen with --all2all-backend. The All2AllBackend literal lists allgather_reducescatter (the default, implemented by AgRsAll2AllManager), DeepEP high-throughput and low-latency kernels (DeepEPHTAll2AllManager, DeepEPLLAll2AllManager), DeepEP v2, AMD MoRI variants, MoonEP, NIXL-EP, FlashInfer NVLink one- and two-sided, pplx, naive and passthrough. Because popular experts overload their owners, --enable-eplb turns on expert-parallel load balancing (EplbState): it tracks per-expert load over a window and periodically re-places experts, optionally with redundant copies of hot ones. A further optimization, --enable-dbo (dual-batch overlap), splits a step into two micro-batches so one computes while the other communicates.

    When to use which: a practical order of operations

    1. Fits on one GPU? Run TP=1 and add DP replicas (or separate instances) for throughput. Nothing beats zero communication.
    2. Does not fit, single node with NVLink? Use the smallest TP that fits weights plus a healthy KV cache, usually 2, 4 or 8. Larger TP also enlarges the KV pool per replica, which raises the batch size you can sustain.
    3. Must span nodes? Prefer TP inside a node and PP across nodes (for example TP=8, PP=2 on two 8-GPU hosts), because PP sends one activation per stage boundary while TP all-reduces in every layer.
    4. Large MoE? Combine DP for attention with EP for experts ("wide EP"), pick an all2all backend that matches your fabric, and consider EPLB once traffic is skewed.
    5. Very long contexts? Look at DCP to stop duplicating KV across TP ranks, and PCP if prefill latency on giant prompts is the bottleneck. Both are newer and model-dependent; check the model's support before relying on them.

    Latency

    Speculative decoding: guess cheaply, verify in one pass

    Decode is memory-bound, so checking several guessed tokens costs almost the same as producing one. vLLM ships a dozen ways to guess.

    During decode the GPU reads every weight once to produce a single token per request, and most of its arithmetic units sit idle. Speculative decoding spends that idle compute: a cheap proposer guesses the next k tokens, the target model scores all k guesses plus one extra position in a single forward pass, and a rejection sampler keeps the longest prefix of guesses the target agrees with, then adds one token of its own (the "bonus" token if all guesses survived, or a corrected token at the first disagreement). Every step therefore emits between 1 and k + 1 tokens. With the default standard verification the output distribution is mathematically the same as sampling from the target alone, so speculation changes speed, not quality.

    How the pieces cooperate

    1. Scheduling. When a running request carries drafts from the previous step, Scheduler.schedule asks for KV slots for 1 + k tokens and records the drafts in scheduled_spec_decode_tokens. Drafts count against the token budget like any other token, which is why max_num_scheduled_tokens can be lower than max_num_batched_tokens.
    2. Verification. MRV2's GPUModelRunner.sample computes logits for every query position, applies the grammar bitmask if any, and, when the batch has drafts, calls the MRV2 RejectionSampler instead of the plain sampler, passing the speculator's cached draft logits for probabilistic verification. (The V1 runner uses vllm/v1/sample/rejection_sampler.py.)
    3. Drafting. In GPUModelRunner.sample_tokens, right after post-processing the sampled tokens, the speculator proposes the next k drafts from the newest token, writing them into per-request GPU state so the next forward pass can consume them without a CPU round trip.
    4. Bookkeeping. EngineCore.step fetches the drafts with take_draft_token_ids and hands them to Scheduler.update_draft_token_ids, which trims them against any structured-output grammar. Scheduler.update_from_output compares drafted with accepted counts and moves num_computed_tokens back by the number rejected. The KV entries written for rejected drafts stay in their slots and are overwritten by the next step, so rollback is a counter decrement, not a memory operation.

    Reading the acceptance metrics

    Per step the scheduler aggregates a SpecDecodingStats (drafts, draft tokens, accepted tokens, and per-position counts) via make_spec_decoding_stats. The console logger SpecDecodingLogging prints three numbers worth memorizing, and SpecDecodingProm exports the counters vllm:spec_decode_num_drafts, vllm:spec_decode_num_draft_tokens, vllm:spec_decode_num_accepted_tokens and vllm:spec_decode_num_accepted_tokens_per_pos so you can compute them in PromQL.

    • Draft acceptance rate = accepted draft tokens ÷ proposed draft tokens. Tells you how good the proposer is.
    • Mean acceptance length = 1 + accepted ÷ drafts. The "+1" counts the token the target always contributes, so this is the average number of tokens emitted per verification step. It is the number that predicts speed-up.
    • Per-position acceptance = how often draft position i survived. It always decays with i; when the tail positions are near zero, lower k.
    Worked example. With k = 4 over 1,000 drafting steps, suppose 2,200 of the 4,000 draft tokens were accepted. The acceptance rate is 55%, and the mean acceptance length is 1 + 2,200 / 1,000 = 3.2 tokens per step. If a verification step costs about 1.25× a plain decode step (four extra query positions and the drafter's own work), the expected decode speed-up is roughly 3.2 / 1.25 ≈ 2.6×. At high batch sizes the per-step cost rises toward compute-bound territory and that ratio shrinks, which is why per-batch-size schedules for k exist. Use --per-request-spec-decode-metrics to get the same numbers per request.

    Constrained generation

    Structured outputs: a bitmask on the logits

    A grammar engine decides which tokens are legal next; vLLM turns that answer into a packed bitmask and zeroes out everything else before sampling.

    "Return valid JSON matching this schema" is a promise the model cannot keep on its own. Structured outputs make it a guarantee by consulting a grammar matcher at every step: given the text so far, which vocabulary tokens keep the output inside the language? The answer is a set of allowed token IDs. vLLM packs it into a bitmask (one bit per vocabulary entry, stored as 32-bit words) and, on the GPU, sets the logit of every forbidden token to negative infinity, so whatever the sampler does, it can only pick a legal token. Nothing about the model changes; only the distribution it samples from is truncated.

    Backends at this commit

    StructuredOutputsBackend accepts auto, xgrammar, guidance, outlines and lm-format-enforcer, each implemented under vllm/v1/structured_output/ against the abstract StructuredOutputBackend (compile a grammar, allocate a bitmask) and StructuredOutputGrammar (accept tokens, validate tokens, roll back, fill a bitmask row, report termination).

    BackendClassNotes
    xgrammarXgrammarBackendFirst choice under auto. Compiles JSON schema, regex, EBNF grammars and structural tags into a pushdown automaton with precomputed token masks.
    guidanceGuidanceBackendBacked by llguidance; Lark-style grammars; needs a fast Hugging Face tokenizer or a Tekken Mistral tokenizer. The auto fallback when xgrammar rejects a schema feature.
    outlinesOutlinesBackendRegex/FSM index; auto uses it when guidance cannot (non-Tekken Mistral tokenizers, or schema features guidance does not support).
    lm-format-enforcerLMFormatEnforcerBackendDeprecated: the config docstring schedules its removal for v0.35.0.

    The backend is chosen once per server through --structured-outputs-config (for example '{"backend": "guidance"}'); per-request backend selection is rejected. With auto, the selection logic in SamplingParams._validate_structured_outputs tries xgrammar first, falls back to guidance, and uses outlines only when guidance is ruled out; Lark grammars for Tekken Mistral tokenizers go straight to guidance. The same config also hosts disable_any_whitespace (compact JSON), disable_additional_properties (guidance only), the reasoning_parser, and enable_in_reasoning, which decides whether the grammar also constrains the model's thinking section or only the answer that follows it.

    Request parameters

    Internally every constraint becomes a StructuredOutputsParams with exactly one of json (a JSON schema), regex, choice (a list of literal strings), grammar (EBNF/Lark), json_object (any JSON) or structural_tag, plus whitespace options. On the OpenAI routes you can send the standard response_format (json_schema, json_object or a structural tag), which structured_outputs_from_response_format translates, or the vLLM extension field structured_outputs for regex, choice and grammar. Forced tool calls can be enforced the same way: vLLM builds an xgrammar structural tag from the tool definitions (vllm/tool_parsers/structural_tag_registry.py).

    Where each step lives in the code

    1. Compile early, asynchronously. When the EngineCore receives a request, EngineCoreProc.preprocess_add_request calls StructuredOutputManager.grammar_init, which submits compilation to a thread pool (the xgrammar backend also keeps a compiled-grammar cache sized by VLLM_XGRAMMAR_CACHE_MB). The request carries a StructuredOutputRequest and starts in WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR, so a slow schema never stalls other requests.
    2. Build the mask on the CPU. After scheduling, Scheduler.get_grammar_bitmask calls StructuredOutputManager.grammar_bitmask. For speculative positions it temporarily advances the matcher through each draft, fills a row, then rolls back. Without speculation, batches of more than 128 constrained requests are filled in parallel on a second thread pool. The result travels as a GrammarOutput alongside the step.
    3. Apply on the GPU. In MRV2, StructuredOutputsWorker.apply_grammar_bitmask scatters the rows onto the right logits and masks in place before the sampler or rejection sampler runs.
    4. Advance the state. update_from_output calls accept_tokens with the newly accepted tokens; trim_spec_tokens cuts fresh drafts at the first token the grammar would reject, so verification slots are not wasted on impossible guesses.
    Practical advice. Compilation is the expensive part and repeated schemas can hit the backend's compile cache, so reuse schemas across requests where possible. Keep max_tokens generous: a constrained answer that hits the length limit is still truncated JSON. And when a reasoning model is in play, configure --reasoning-parser so the grammar starts enforcing only after the thinking block ends (unless you set enable_in_reasoning).

    Many models, one base

    LoRA adapters: batching requests for different fine-tunes

    vLLM keeps one copy of the base weights and mixes several low-rank adapters into the same batch, one adapter per request.

    A LoRA adapter replaces a weight update with two thin matrices, A (d × r) and B (r × d), where the rank r is tiny (8 to 128 is typical). The adapted layer computes x·W + x·A·B. Serving many adapters naively means either merging each into a separate full model copy or running requests for different adapters in separate batches. vLLM does neither: it keeps a fixed number of adapter slots on the GPU and uses batched kernels that let every row in a batch use a different slot.

    The path of an adapter request

    1. Name it. Each request may carry a LoRARequest (name, integer id, path). On the server, adapters registered with --lora-modules appear as extra model names in /v1/models, so clients select one with the ordinary model field.
    2. Schedule within slots. The scheduler counts distinct adapters among running requests and refuses to admit a waiting request whose adapter would exceed max_loras for this step; it simply waits for a slot to free up.
    3. Load and cache. On the worker, LRUCacheWorkerLoRAManager loads adapters from disk or the Hub into a CPU cache of up to max_cpu_loras and activates the ones the batch needs in GPU slots, evicting least-recently-used adapters through LRUCacheLoRAModelManager.
    4. Compute mixed batches. LoRA-wrapped layers (in vllm/lora/layers/) call PunicaWrapperGPU, which groups tokens by slot and runs two Triton kernels: _lora_shrink (x·A, down to rank r) and _lora_expand (·B, back up and added to the base output).
    5. Keep caches honest. Prefix-cache block hashes include the adapter identity (_gen_lora_extra_hash_keys), so two adapters never share KV for the same prompt text.

    Knobs and caveats

    • --enable-lora turns the machinery on; --max-loras (default 1) sets GPU slots, --max-lora-rank (default 16; allowed values 1, 8, 16, 32, 64, 128, 256, 320, 512) sizes every slot's buffers, and --max-cpu-loras sizes the CPU cache.
    • Slots are preallocated at the maximum rank, so a large max_lora_rank × max_loras eats KV-cache memory even when adapters are small.
    • --fully-sharded-loras shards both LoRA matrices across TP ranks, which helps at high TP and large ranks.
    • Runtime loading through POST /v1/load_lora_adapter and /v1/unload_lora_adapter exists only when VLLM_ALLOW_RUNTIME_LORA_UPDATING is set; plugins implementing LoRAResolver can fetch unknown adapter names on demand.
    • Each extra active adapter adds kernel work proportional to its rank, so a batch that mixes eight adapters is somewhat slower than one with a single adapter. Measure with your real adapter mix.

    Beyond text

    Multimodal inputs: placeholders, encoders, and an encoder cache

    Images, audio and video become runs of placeholder tokens in the prompt; a vision or audio encoder fills those positions with embeddings just before they are needed.

    For a vision-language model, an image is not text, but the language model only understands token positions. The trick every multimodal model in vLLM shares is to expand each image into N placeholder tokens in the prompt (N depends on resolution and model), run the encoder to produce exactly N embedding vectors, and splice those vectors into the input embeddings at the placeholder positions. From then on the image is just more context: it occupies KV cache, participates in prefix caching, and can be chunked by the scheduler like a long prompt.

    Front end: turning media into placeholders

    In the API server the renderer downloads or decodes media and hands it to the model's processor, created through the global MULTIMODAL_REGISTRY (MultiModalRegistry). Each model registers a BaseMultiModalProcessor subclass, a BaseProcessingInfo (how many tokens an item needs) and a BaseDummyInputsBuilder (worst-case inputs for memory profiling). The processor returns token IDs with placeholder ranges (PlaceholderRange) and pixel or audio tensors. Every item is fingerprinted by MultiModalHasher; the hash keys a processor cache (lru in-process or shm shared memory, sized by --mm-processor-cache-gb, default 4 GiB) so repeated images skip preprocessing, and it is folded into prefix-cache block hashes by _gen_mm_extra_hash_keys so that two different images behind identical placeholder tokens never share KV. The items ride to the EngineCore as MultiModalFeatureSpec entries on the request.

    Engine: an encoder budget and an encoder cache

    Encoders are expensive, so the scheduler treats them as a second budget. In Scheduler._try_schedule_encoder_inputs it decides, for each request whose next chunk overlaps a placeholder range, whether the corresponding encoder input can run this step within the encoder compute budget and whether its output fits the EncoderCacheManager. Both limits are derived from the model by MultiModalBudget rather than set by hand. If it does not fit, the text chunk is shortened to stop before the image. On the GPU, MRV2's EncoderRunner runs the model's embed_multimodal for the scheduled items, stores the outputs in an EncoderCache, and gather_mm_embeddings slices out exactly the embedding rows that this step's token chunk covers. That is what lets a 2,000-token image be prefetched once and consumed across several prefill chunks.

    Flags worth knowing

    • --limit-mm-per-prompt caps items per modality (for example '{"image": 4, "video": 1}'). Lower limits shrink the worst case used for memory profiling and leave more room for KV cache.
    • --mm-encoder-tp-mode chooses weights (shard the encoder like the LLM) or data (replicate the small encoder and split the batch of images across TP ranks, often faster).
    • --disable-chunked-mm-input forbids splitting a single image across steps; --enable-mm-embeds accepts precomputed embeddings; --language-model-only skips loading the encoder entirely for text-only use.
    • Encoder disaggregation: --ec-transfer-config lets a dedicated encoder instance produce embeddings that an "EC connector" (in vllm/distributed/ec_transfer/) ships to the prefill/decode instance, the multimodal sibling of KV disaggregation below.

    Split the phases

    Disaggregated prefill and the KV connector API

    Run prompt processing and token generation on different instances, and move the KV cache between them with a pluggable connector.

    Prefill is compute-bound and bursty; decode is memory-bandwidth-bound and steady. On one engine they interfere: a 30k-token prompt arriving mid-stream stretches every running request's inter-token latency for several steps, even with chunked prefill. Disaggregation gives each phase its own pool of GPUs (and possibly its own parallelism), so time to first token and inter-token latency can be tuned independently. The price is moving the prompt's KV cache from the prefill instance to the decode instance, which is what a KV connector does.

    The connector contract

    Every connector subclasses KVConnectorBase_V1 and is instantiated twice, once per KVConnectorRole:

    Scheduler side (EngineCore process)

    • get_num_new_matched_tokens: how many prompt tokens can be loaded from outside, and whether that load is asynchronous. Called by the scheduler right after the local prefix-cache lookup.
    • update_state_after_alloc: learn which local blocks were allocated to receive the data.
    • build_connector_meta: package this step's transfer instructions; they ride along with the SchedulerOutput to the workers.
    • request_finished: decide whether blocks must outlive the request (they are being sent) and return kv_transfer_params for the client.

    Worker side (every GPU process)

    • start_load_kv and wait_for_layer_load: begin loads before the forward pass and block per layer only when attention actually needs the data.
    • save_kv_layer and wait_for_save: stream KV out layer by layer, overlapping with compute.
    • get_finished: report requests whose asynchronous sends or receives completed, so the scheduler can free or start them.
    • MRV2 wires these around the forward pass in ActiveKVConnector (pre_forward / post_forward).

Try chunked prefill tuning on a single fleet first.

    More cache than HBM

    KV offloading: spill blocks to CPU and beyond

    GPU memory holds the working set; host memory (and optional slower tiers) remembers prefixes the GPU had to evict, so a returning conversation skips recomputation.

    Prefix caching only helps while the cached blocks are still on the GPU. Under load the block pool evicts least-recently-used blocks constantly, and a user who returns to a long conversation five minutes later pays the full prefill again. KV offloading copies computed blocks to a larger, slower memory and, on a later prefix hit, copies them back asynchronously. Reloading a block over PCIe is usually far cheaper than recomputing it, especially for long prompts on large models.

    Turning it on

    Two flags are enough: --kv-offloading-size (GiB of CPU memory; offloading stays off while it is unset) and --kv-offloading-backend (KVOffloadingBackend: native or lmcache). They are syntactic sugar: VllmConfig._post_init_kv_transfer_config rewrites them into a KVTransferConfig with kv_role="kv_both" and OffloadingConnector (or SimpleCPUOffloadConnector when the environment variable VLLM_USE_SIMPLE_KV_OFFLOAD=1), passing the size as cpu_bytes_to_use; for lmcache it selects LMCacheMPConnector and leaves capacity to the LMCache server. So offloading is "just another KV connector", and it composes with P/D through MultiConnector.

    Inside the native implementation

    The code under vllm/v1/kv_offload/ separates policy from transport:

    • OffloadingSpec describes a medium and builds the other two objects; OffloadingSpecFactory registers CPUOffloadingSpec and TieringOffloadingSpec.
    • OffloadingManager runs in the scheduler process and answers "is this block offloaded?" (lookup), pins blocks for loading (prepare_load), picks what to store and what to evict (prepare_store), and updates recency (touch). The CPU version, CPUOffloadingManager, delegates eviction to a pluggable policy: LRUCachePolicy or ARCCachePolicy (adaptive replacement, which resists one-off scans), registered in CachePolicyFactory.
    • OffloadingWorker runs in every GPU process and executes the asynchronous copies (submit_store, submit_load, get_finished).
    • The connector halves that glue these to vLLM are OffloadingConnectorScheduler and OffloadingConnectorWorker.

    Tiering goes one step further: TieringOffloadingManager keeps the CPU tier as primary and promotes or demotes blocks to secondary tiers created by SecondaryTierFactory, which pre-registers example, fs, p2p, obj and kvcr, with optional backpressure detection so a slow tier cannot stall the GPU. Watch the effect through the vllm:external_prefix_cache_hits and vllm:prompt_tokens_cached_by_source counters described next. The trade-off is pinned host memory (which the OS cannot page out) and PCIe bandwidth shared with other traffic; size the CPU tier to your realistic reuse window rather than to the machine's total RAM.

    Know what the engine is doing

    Metrics, logs, and traces

    The scheduler and the output processor each produce statistics every step; stat loggers turn them into a console line and a Prometheus endpoint.

    Statistics are produced in two places because the information lives in two processes. The EngineCore's scheduler knows queue lengths, KV-cache usage, prefix-cache hits, preemptions and speculative-decoding counts; it attaches a SchedulerStats to the outputs it ships each step. The API-server side output processor knows when each token reached the client, so it builds IterationStats per step and, for each request, a RequestStateStats that becomes FinishedRequestStats when the request ends. Both feed a StatLoggerManager, which fans them out to:

    • LoggingStatLogger: the familiar log line with average prompt and generation throughput, running and waiting requests, KV-cache usage and prefix-cache hit rate, printed every VLLM_LOG_STATS_INTERVAL seconds (10 by default).
    • PrometheusStatLogger: gauges, counters and histograms labeled by model name and engine index, served at /metrics (mounted by attach_router on the registry from get_prometheus_registry, which uses Prometheus multiprocess mode when vLLM runs more than one API server process).
    • Any plugin returned by load_stat_logger_plugin_factories, or a custom StatLoggerBase subclass you pass to AsyncLLM.

    --disable-log-stats silences the console line. Offline users can read the same counters without a server through LLM.get_metrics, which wraps get_metrics_snapshot.

    Traces and profiles

    For per-request traces, point --otlp-traces-endpoint at an OpenTelemetry collector; init_tracer sets up the exporter, incoming traceparent headers are honored, and --collect-detailed-traces adds model-forward and worker timings (model, worker or all) at some overhead. For kernel-level questions, configure a profiler with --profiler-config (torch, cuda for Nsight Systems capture ranges, or proton); the server then exposes POST /start_profile and /stop_profile to capture a window of steps.

    Reading the dashboard together. High TTFT with low KV usage and an empty queue points at prefill compute (long prompts, small batch token budget). High TTFT with a long queue is a capacity problem. High ITL with frequent large prefills points at prefill interference; lower --max-num-batched-tokens or consider disaggregation. A rising preemption counter with KV usage near 1.0 says you are admitting more concurrent requests than memory can hold.

    Two front ends, one core

    Offline LLM versus the online server

    Both paths end in the same EngineCore; they differ in who drives the loop and how outputs come back.

    Offline: the LLM class

    LLM is a convenience wrapper assembled from mixins: OfflineInferenceMixin (shared request plumbing), PoolingOfflineMixin (embed, classify, score, encode), BeamSearchOfflineMixin and an RL mixin for weight updates. You hand generate or chat a whole list of prompts; it enqueues all of them, then _run_engine calls LLMEngine.step until every request has finished, and returns the outputs in input order. Under the hood LLMEngine gets its client from EngineCoreClient.make_client: a SyncMPClient with the EngineCore in a background process when VLLM_ENABLE_V1_MULTIPROCESSING is on (the default), or an InprocClient that runs the EngineCore inside your process when it is off, which is handy for debuggers and profilers. Recent additions blur the line with serving: enqueue plus wait_for_completion let you submit work without blocking, and sleep/wake_up and collective_rpc exist mainly for RL training loops. 

    from vllm import LLM, SamplingParams

llm = LLM(model="Qwen/Qwen3-0.6B")                 # starts EngineCore + workers
params = SamplingParams(temperature=0.7, max_tokens=64)
outputs = llm.generate(["What is a KV cache?", "Define PagedAttention."], params)
for out in outputs:                                  # same order as the prompts
    print(out.outputs[0].text)

    Online: vllm serve and AsyncLLM

    vllm serve (ServeSubcommand) ends up in run_server, which creates an engine client with build_async_engine_client and the FastAPI application with build_app. The client is an AsyncLLM: each HTTP handler awaits AsyncLLM.generate, an async generator fed by a per-request queue, while a single background output_handler task reads every EngineCore output from the AsyncMPClient, detokenizes it and routes it to the right queue. Nobody "calls step": the EngineCore loops on its own, and the server only adds and aborts requests.

    Reference

    Feature catalog

    Each card says what a feature is, why you would care, how vLLM implements it at this commit, the files to read, the flags that control it, and the catch.

    File links point at the line that defines the named class or function; flag links point at the add_argument call in vllm/engine/arg_utils.py or at the frontend dataclass field in vllm/entrypoints/common/cli_args.py that generates the flag. Defaults quoted here come from those definitions; several are resolved later from the model and hardware.

    PagedAttention (paged KV cache)

    What: KV cache stored in fixed-size blocks, mapped per request through a block table, like virtual-memory pages.

    Why: No contiguous per-request reservation, so almost no fragmentation; more requests fit, and blocks can be shared.

    How: The scheduler-side KVCacheManager allocates block IDs from a BlockPool free list; workers translate them into slot indices that attention kernels read and write.

    Caveat: The block size is constrained by the attention backend; hybrid models keep one block table per KV-cache group.

    Key files: vllm/v1/core/kv_cache_manager.py · vllm/v1/core/block_pool.py · vllm/v1/core/kv_cache_utils.py · vllm/v1/worker/gpu/block_table.py --block-size · --gpu-memory-utilization · --kv-cache-memory-bytes

    Continuous batching

    What: The batch is rebuilt every step: finished requests leave and waiting ones join immediately.

    Why: No GPU time is wasted waiting for the slowest request of a static batch; throughput under mixed lengths rises dramatically.

    How: Scheduler.schedule() hands out a per-step token budget across running and waiting requests without separate prefill and decode phases; EngineCore.step() runs one batched forward pass per call.

    Caveat: The two caps interact: max_num_seqs limits requests, max_num_batched_tokens limits tokens per step.

    Key files: vllm/v1/core/sched/scheduler.py · vllm/v1/engine/core.py --max-num-seqs · --max-num-batched-tokens

    Chunked prefill

    What: A long prompt is processed over several steps in chunks that fit the leftover token budget.

    Why: Decodes keep running alongside prefill, so one huge prompt cannot freeze every stream; GPU utilization also evens out.

    How: The scheduler simply grants a request fewer new tokens than it needs; num_computed_tokens advances chunk by chunk. long_prefill_token_threshold optionally caps any one request's share.

    Caveat: Default is decided per model by is_chunked_prefill_supported; smaller budgets lengthen TTFT for long prompts.

    Key files: vllm/config/scheduler.py · vllm/v1/core/sched/scheduler.py --enable-chunked-prefill · --long-prefill-token-threshold

    Automatic prefix caching

    What: Full KV blocks are indexed by a hash of their tokens plus everything before them, and reused by later requests with the same prefix.

    Why: Shared system prompts, few-shot examples and multi-turn chats skip most of their prefill.

    How: hash_block_tokens chains each block's hash to its parent's; extra keys cover LoRA, multimodal hashes and an optional cache_salt. get_computed_blocks walks the chain on admission; freed blocks stay cached until evicted LRU-first.

    Caveat: A dense single-group cache hits on full blocks. Compatible aligned hybrid cache groups can match smaller units. Local hits require resident state; configured KV connectors can bring in external KV. See the alignment rules.

    Key files: vllm/v1/core/kv_cache_utils.py · vllm/v1/core/kv_cache_manager.py · vllm/v1/core/block_pool.py --enable-prefix-caching · --prefix-caching-hash-algo

    Preemption (recompute)

    What: When a running request needs a block and none is free, the scheduler evicts a victim request and requeues it.

    Why: Lets vLLM admit optimistically for high utilization while still guaranteeing forward progress.

    How: _preempt_request frees the victim's blocks, resets num_computed_tokens to 0 and puts it back at the front of the waiting queue; when it resumes, prefix caching often recovers much of its old KV. FCFS evicts the most recently admitted running request; the priority policy evicts the lowest-priority one.

    Caveat: Every preemption is wasted compute; watch vllm:num_preemptions.

    Key files: vllm/v1/core/sched/scheduler.py · vllm/v1/core/sched/request_queue.py --watermark · --num-gpu-blocks-override

    CUDA graphs

    What: Pre-recorded GPU kernel sequences for fixed batch sizes, replayed with one launch.

    Why: Decode steps are tiny; without graphs, Python and kernel-launch overhead can exceed GPU work.

    How: CUDAGraphMode offers NONE, PIECEWISE (graphs between attention ops), FULL, FULL_DECODE_ONLY and FULL_AND_PIECEWISE (the default at -O2). Batches are padded up to the nearest captured size; MRV2's CudaGraphManager captures and dispatches.

    Caveat: Capture costs startup time and memory; the default size cap is 512 (1024 on data-center Blackwell).

    Key files: vllm/config/compilation.py · vllm/v1/worker/gpu/cudagraph_utils.py · vllm/compilation/cuda_graph.py --enforce-eager · --max-cudagraph-capture-size · --cudagraph-capture-sizes

    torch.compile integration

    What: The model's forward is traced by Dynamo once and compiled by vLLM's own Inductor-based backend.

    Why: Fuses elementwise ops (norms, activations, quantization) and enables custom graph passes without hand-written kernels for every model.

    How: CompilationMode.VLLM_COMPILE uses VllmBackend, which splits the graph at attention ops for piecewise CUDA graphs, specializes for sizes, and caches compiled artifacts on disk. --optimization-level (-O0…-O3, default O2) chooses the preset.

    Caveat: First start of a new model/config is slow; use -O0 for quick iteration.

    Key files: vllm/config/compilation.py · vllm/compilation/backends.py · vllm/config/vllm.py --optimization-level · --compilation-config

    Pluggable attention backends

    What: Interchangeable kernels for paged attention, chosen per layer type, GPU generation and KV dtype.

    Why: No single kernel is fastest everywhere: FlashAttention, FlashInfer, Triton, MLA-specialized and sparse kernels each win somewhere.

    How: AttentionBackendEnum has 52 members at this commit, including FLASH_ATTN, FLASHINFER, TRITON_ATTN, FLEX_ATTENTION, TRITON_FLASH_ATTN and TRITON_FLASHINFER; MLA backends FLASHINFER_MLA, CUTLASS_MLA, FLASHMLA, FLASH_ATTN_MLA, TRITON_MLA and TOKENSPEED_MLA; sparse MLA variants (FLASHMLA_SPARSE, FLASHINFER_MLA_SPARSE and DeepSeek V4/V4.1-specific ones); ROCm (ROCM_ATTN, ROCM_AITER_FA, ROCM_AITER_MLA, ROCM_AITER_UNIFIED_ATTN, ROCM_OCTAVE…); CPU_ATTN, CPU_MLA, AMX_MLA; model-specific sparse kernels (MINIMAX_M3_SPARSE, STEP5_DSA, KIMI_K3_KV_BALANCED_MLA…); quantized-KV TURBOQUANT and ULTRAQUANT; plus NO_ATTENTION, TORCH_SDPA (vision encoders only) and CUSTOM for plugins. get_attn_backend walks the platform's priority list; on Hopper for standard attention that is FLASH_ATTN, then FLASHINFER, TRITON_ATTN, FLEX_ATTENTION, while Blackwell (SM10x) prefers FLASHINFER first.

    Caveat: Forcing a backend that does not support your head size, dtype or block size fails at startup.

    Key files: vllm/v1/attention/backends/registry.py · vllm/v1/attention/selector.py · vllm/platforms/cuda.py --attention-backend

    Quantization

    What: Lower-precision weights (and optionally activations and KV cache) through per-method linear and MoE kernels.

    Why: Smaller weights leave more memory for KV cache and speed up memory-bound decode.

    How: QuantizationMethods lists awq, auto_awq, awq_marlin, gptq, auto_gptq, gptq_marlin, fp8, fbgemm_fp8, fp_quant, modelopt, modelopt_fp4, modelopt_mxfp8, modelopt_mixed, humming, compressed-tensors, experts_int8, quark, moe_wna16, torchao, inc, mxfp4, gpt_oss_mxfp4, deepseek_v4_fp8, online, and online shorthands fp8_per_tensor, fp8_per_block, fp8_per_channel, int8_per_channel_weight_only, nvfp4_per_token, mxfp8.     What: Draft several tokens cheaply, verify them in one target pass, keep the agreeing prefix.

    Why: Cuts per-token latency at low and medium batch sizes without changing outputs (standard verification).

    How: Methods ngram, ngram_gpu, suffix, draft_model, eagle, eagle3, 29 MTP variants, dflash, dspark, extract_hidden_states, custom_class; MRV2 speculators plus a rejection sampler; see the chapter.

    Structured outputs

    What: Guarantee that output matches a JSON schema, regex, choice list, grammar or structural tag.

    Why: Reliable machine-readable output for agents and pipelines without retries.

    Multi-LoRA serving

    What: Many low-rank adapters over one base model, mixed in the same batch.

    Why: Serve dozens of fine-tunes for roughly the cost of one model.

    How: Adapter slots on the GPU, an LRU CPU cache, scheduler admission bounded by max_loras, and Punica shrink/expand Triton kernels.

    Caveat: Buffers are sized for max_lora_rank × max_loras; runtime loading needs an env var.

    Key files: vllm/lora/request.py · vllm/lora/worker_manager.py · vllm/lora/punica_wrapper/punica_gpu.py --enable-lora · --max-loras · --max-lora-rank

    Multimodal inputs

    What: Images, video and audio alongside text for vision-language and audio-language models.

    Why: One engine serves both text and multimodal traffic with the same batching and caching.

    How: Per-model processors expand media into placeholder tokens; the scheduler budgets encoder work; an encoder cache stores embeddings that are spliced in at placeholder positions; media hashes keep caches correct.

    Caveat: Worst-case profiling with many large images can shrink the KV cache; cap items with --limit-mm-per-prompt.

    Key files: vllm/multimodal/registry.py · vllm/v1/core/encoder_cache_manager.py · vllm/v1/worker/gpu/mm/encoder_runner.py --limit-mm-per-prompt · --mm-processor-cache-gb · --mm-encoder-tp-mode

    Tensor parallelism

    What: Split each layer's matrices across GPUs; all-reduce partial results.

    Why: Fit models larger than one GPU and pool their memory for a bigger KV cache.

    How: Column- and row-parallel linear layers, vocab-parallel embeddings, and a GroupCoordinator whose CUDA communicator prefers custom all-reduce for small messages and NCCL otherwise.

    Caveat: Needs a fast interconnect; the number of attention heads must divide evenly (KV heads are replicated when fewer than TP).

    Key files: vllm/model_executor/layers/linear.py · vllm/distributed/parallel_state.py · vllm/distributed/device_communicators/custom_all_reduce.py --tensor-parallel-size (-tp) · --disable-custom-all-reduce

    Pipeline parallelism

    What: Assign contiguous layer ranges to different GPUs or nodes.

    Why: Spans nodes with modest bandwidth, since only one activation tensor crosses each stage boundary per step.

    How: make_layers builds only local layers; others become PPMissingLayer; stages exchange IntermediateTensors. The engine keeps several batches in flight (via the batch queue) so all stages stay busy.

    Caveat: The model must implement SupportsPP; uneven layer splits create bubbles.

    Key files: vllm/model_executor/models/utils.py · vllm/sequence.py · vllm/model_executor/models/interfaces.py --pipeline-parallel-size (-pp)

    Data parallelism

    What: Several engine replicas, each with its own scheduler, KV cache and GPUs, behind one endpoint.

    Why: Linear throughput scaling for models that fit in one replica, and the attention half of wide-EP MoE serving.

    How: One EngineCore per rank; the API server's DP client balances by queue length using stats from DPCoordinator; MoE ranks run dummy steps and periodically all-reduce to stay in lockstep.

    Caveat: Prefix caches are per rank, so balancing ignores cache locality unless an external router is cache-aware.

    Key files: vllm/v1/engine/coordinator.py · vllm/v1/engine/core.py · vllm/v1/engine/core_client.py --data-parallel-size (-dp) · --data-parallel-size-local · --api-server-count

    Expert parallelism

    What: Distribute whole MoE experts over GPUs and route tokens to them.

    Why: Expert weights dominate large MoE models; EP avoids slicing every expert across every GPU and scales to dozens of ranks.

    How: MoE layers form an EP group of TP × DP (× PCP) ranks; prepare/finalize stages perform all2all dispatch and combine through a selectable backend; EPLB rebalances hot experts.

    Caveat: Performance depends heavily on the all2all backend and fabric; DP ranks must step together.

    Key files: vllm/model_executor/layers/fused_moe/layer.py · vllm/distributed/device_communicators/all2all.py · vllm/distributed/eplb/eplb_state.py --enable-expert-parallel (-ep) · --all2all-backend · --enable-eplb

    Disaggregated prefill / decode

    What: Prefill and decode on separate instances, with KV cache shipped between them.

    Why: Independent tuning of TTFT and ITL and no prefill interference on decode GPUs.

    How: The KVConnectorBase_V1 API with scheduler-side and worker-side halves; 18 registered connectors including NIXL (pull and push), Mooncake, MoRIIO, LMCache and MultiConnector; requests carry kv_transfer_params.

    Caveat: Requires an external proxy/router and a fast network; benefits depend on prompt and output lengths.

    Key files: vllm/distributed/kv_transfer/kv_connector/v1/base.py · vllm/distributed/kv_transfer/kv_connector/factory.py · vllm/distributed/kv_transfer/kv_connector/v1/nixl/connector.py --kv-transfer-config

    KV-cache offloading

    What: Store evicted or computed KV blocks in CPU memory (and optional file, object, peer or KVCR tiers) and reload them on prefix hits.

    Why: Multiplies effective prefix-cache capacity; returning conversations skip recomputation.

    How: Implemented as a KV connector (OffloadingConnector) driven by an OffloadingSpec, a scheduler-side OffloadingManager with LRU or ARC policy, and asynchronous worker transfers.

    Caveat: Uses pinned host memory and PCIe bandwidth; lmcache mode needs a separate LMCache server.

    Key files: vllm/v1/kv_offload/base.py · vllm/v1/kv_offload/cpu/manager.py · vllm/distributed/kv_transfer/kv_connector/v1/offloading_connector.py --kv-offloading-size · --kv-offloading-backend

    Asynchronous scheduling

    What: Schedule step N+1 on the CPU while the GPU still runs step N.

    Why: Removes the CPU gap between GPU steps, improving both latency and throughput.

    How: AsyncScheduler reserves output placeholders for not-yet-sampled tokens; EngineCore.step_with_batch_queue keeps up to two batches in flight; Model Runner V2 reads the real token from GPU memory when building the next inputs.

    Caveat: On by default (None resolves to enabled) unless an incompatible feature, such as pooling models, forces it off.

    Key files: vllm/v1/core/sched/async_scheduler.py · vllm/v1/engine/core.py · vllm/config/scheduler.py --async-scheduling

    Sampling and logits processing

    What: Turning logits into tokens with per-request temperature, top-k, top-p, min-p, penalties, logit bias, bad words, seeds and logprobs.

    Why: Every request in a batch can use different sampling settings without splitting the batch.

    How: MRV2's Sampler keeps per-request parameters in GPU-resident state and applies penalties, logit bias, bad words, min-p and Gumbel-max sampling with batched kernels; custom logits processors plug in via --logits-processors.

    Caveat: With --generation-config auto (default) the model's generation_config.json supplies default sampling values, which may differ from OpenAI defaults.

    Key files: vllm/v1/worker/gpu/sample/sampler.py · vllm/sampling_params.py · vllm/v1/sample/sampler.py --generation-config · --logits-processors · --max-logprobs · --logprobs-mode

    Streaming and incremental detokenization

    What: Send text to the client token by token as server-sent events.

    Why: Users see output after TTFT instead of after the whole answer.

    How: The API process's OutputProcessor turns token IDs into text with an IncrementalDetokenizer, applies stop strings, and emits DELTA outputs that the chat handler wraps as SSE chunks.

    Caveat: With --stream-interval above 1, tokens are batched per message: less host overhead, choppier streams.

    Key files: vllm/v1/engine/output_processor.py · vllm/v1/engine/detokenizer.py · vllm/entrypoints/openai/chat_completion/serving.py --stream-interval

    Metrics and tracing

    What: Prometheus metrics, a periodic log line, OpenTelemetry traces and on-demand profiling.

    Why: You cannot tune or autoscale what you cannot see: queue depth, KV usage, TTFT and ITL drive most decisions.

    How: SchedulerStats from the EngineCore and IterationStats from the output processor feed StatLoggerManager, which drives the logging and Prometheus loggers; /metrics exposes the registry.

    Caveat: Metric names change across releases; --show-hidden-metrics-for-version eases migrations.

    Key files: vllm/v1/metrics/loggers.py · vllm/v1/metrics/stats.py · vllm/config/observability.py --disable-log-stats · --otlp-traces-endpoint · --kv-cache-metrics

    OpenAI-compatible server

    What: A FastAPI server speaking Chat Completions, Completions, Responses, Embeddings, Audio and Models, plus Anthropic Messages and more.

    Why: Existing SDKs and tools work by changing a base URL.

    How: run_server builds an AsyncLLM and an app whose routers are registered per supported task; serving classes such as OpenAIServingChat render prompts, call AsyncLLM.generate and format responses.

    Caveat: Only a shared API key is built in; put a gateway in front for multi-tenant auth and quotas.

    Key files: vllm/entrypoints/launchers/api_server/routers.py · vllm/entrypoints/openai/chat_completion/serving.py · vllm/entrypoints/openai/chat_completion/protocol.py --host · --port · --api-key · --chat-template · --served-model-name

    Tool (function) calling

    What: Parse the model's native tool-call syntax into OpenAI tool_calls, including while streaming.

    Why: Agents and frameworks expect structured tool calls, but every model family formats them differently.

    How: A ToolParser subclass per family, registered lazily in ToolParserManager.     Caveat: The parser must match the chat template; a mismatch yields tool calls as plain text.

    Key files: vllm/tool_parsers/abstract_tool_parser.py · vllm/tool_parsers/__init__.py --enable-auto-tool-choice · --tool-call-parser · --tool-parser-plugin

    Reasoning (thinking) outputs

    What: Separate a model's chain-of-thought from its final answer into a dedicated reasoning field.

    Why: Clients can hide, log or bill thinking tokens separately, and grammars can start after thinking ends.

    How: A ReasoningParser per family, registered in ReasoningParserManager. The 42 built-in names are: beam, cohere_command3, cohere_command4, deepseek_r1, deepseek_v3, deepseek_v4, deepseek_v41, ernie45, gemma4, glm45, glm47, granite, granite_thinking_parser, hf, holo2, hunyuan_a13b, hy_v3, hy_v4, inkling, k2_horizon, kimi_k2, kimi_k3, ling3, mimo, minicpmv, minimax_m2, minimax_m2_append_think, minimax_m3, mistral, muse, muse_glimmer, musespark1x, nemotron_v3, olmo3, openai_gptoss, plamo3, poolside_v1, qwen3, seed_oss, step3, step3p5, step5.     Caveat: The flag lives in the structured-outputs config because grammar enforcement needs to know where reasoning ends.

    Key files: vllm/reasoning/abs_reasoning_parsers.py · vllm/reasoning/__init__.py · vllm/sampling_params.py --reasoning-parser · --reasoning-parser-plugin

    Pooling models (embed, classify, score)

    What: Run encoder or decoder models that output vectors or scores instead of text.

    Why: One engine for RAG embeddings, rerankers and classifiers, with the same batching and parallelism.

    How: The pooling runner attaches a Pooler (dispatched per task by DispatchPooler); tasks are embed, classify, token_embed, token_classify, plugin and embed&token_classify. --convert embed|classify adapts a generative checkpoint. Routes include /v1/embeddings, /classify, /score and /rerank.

    Caveat: Pooling disables async scheduling; the old score and encode task names were removed.

    Key files: vllm/model_executor/layers/pooler/abstract.py · vllm/model_executor/layers/pooler/special.py · vllm/tasks.py · vllm/config/pooler.py --runner · --convert · --pooler-config

    Sleep mode

    What: Release GPU memory without killing the process, then wake up quickly.

    Why: RL loops alternate training and generation on the same GPUs; multi-model hosts swap models without paying full startup.

    How: With sleep mode enabled, allocations go through CuMemAllocator (the default cumem backend), so weights and KV cache can be unmapped. Level 1 backs weights up to CPU and discards KV; level 2 discards both, for weight updates. Exposed as LLM.sleep/wake_up, AsyncLLM.sleep, and dev-mode HTTP routes.

    Caveat: CUDA and ROCm only; level 1 needs enough CPU RAM for the weights.

    Key files: vllm/device_allocator/cumem.py · vllm/device_allocator/sleep_mode_backend.py · vllm/v1/worker/gpu_worker.py · vllm/v1/engine/async_llm.py --enable-sleep-mode · --sleep-mode-backend

    Context parallelism (DCP and PCP)

    What: Shard one sequence's KV cache (decode CP) or prefill work (prefill CP) across ranks.

    Why: Long contexts on MLA-style models otherwise duplicate KV on every TP rank.

    How: DCP reuses TP ranks and interleaves tokens across them, combining partial attention with all-gather/reduce-scatter or all-to-all; PCP adds ranks that split prefill.

    Caveat: Model and backend support varies; both are newer than TP/PP.

    Key files: vllm/config/parallel.py · vllm/distributed/parallel_state.py --decode-context-parallel-size · --prefill-context-parallel-size · --dcp-comm-backend

    Quantized KV cache

    What: Store keys and values in FP8 (and some lower-precision formats) instead of the model dtype.

    Why: Roughly halves KV memory per token versus BF16, doubling concurrent context.

    How: CacheConfig.cache_dtype selects the format; attention backends that support it read scales handled by BaseKVCacheMethod.

    Caveat: Small accuracy cost; not every backend supports every KV dtype.

    Key files: vllm/config/cache.py · vllm/model_executor/layers/quantization/kv_cache.py --kv-cache-dtype

    Priority scheduling and admission control

    What: Order work by a per-request priority integer (lower runs first) and optionally reject excess load.

    Why: Mix interactive and batch traffic on one deployment without the batch jobs hurting latency.

    How: PriorityRequestQueue replaces the FCFS deque; preemption picks the lowest-priority running request. Queue limits return HTTP 503 before the engine is swamped.

    Caveat: Starvation of low-priority work is possible under sustained load.

    Key files: vllm/v1/core/sched/request_queue.py · vllm/config/scheduler.py --scheduling-policy · --max-num-queued-reqs · --max-num-queued-tokens

    Hybrid KV-cache manager

    What: Different cache managers per layer type (full attention, sliding window, Mamba state…) sharing one memory pool.

    Why: Sliding-window and state-space layers need far less memory than full attention; allocating them equally wastes the pool.

    How: HybridKVCacheCoordinator groups layers by spec and delegates to managers such as FullAttentionManager and SlidingWindowManager, which free out-of-window blocks.

    Caveat: When left unset, vLLM decides from the environment and configuration whether the hybrid manager can be used; the flag forces uniform allocation.

    Key files: vllm/v1/core/kv_cache_coordinator.py · vllm/v1/core/single_type_kv_cache_manager.py --disable-hybrid-kv-cache-manager

    Encoder disaggregation

    What: Run the vision encoder on separate instances and ship embeddings to the language-model instances.

    Why: Image-heavy traffic stops competing with decode for GPU time; encoders scale independently.

    How: An ECConnectorBase implementation (CPU/NIXL, Mooncake, example) with scheduler and worker roles mirrors the KV connector design.

    Caveat: Experimental and deployment-specific; needs a proxy that routes media to encoder instances.

    Key files: vllm/distributed/ec_transfer/ec_connector/base.py --ec-transfer-config

    A throughput-leaning starting point

    Batch jobs or high-QPS APIs where p50 matters more than p99 ITL:

    vllm serve <model> \
  --max-num-seqs 512 --max-num-batched-tokens 16384 \
  --gpu-memory-utilization 0.95 --kv-cache-dtype fp8 \
  --performance-mode throughput --stream-interval 5

    Then watch vllm:num_preemptions and vllm:kv_cache_usage_perc; back off --max-num-seqs if preemptions appear.

    A latency-leaning starting point

    Chat or coding assistants with a strict inter-token SLO:

    vllm serve <model> \
  --max-num-batched-tokens 2048 --long-prefill-token-threshold 1024 \
  --performance-mode interactivity \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 3,
                         "prompt_lookup_max": 4}'

    Check that p99 inter-token latency drops while throughput remains acceptable.

    Measure, do not guess. vllm bench serve replays a dataset at a chosen request rate or concurrency and reports TTFT, ITL, TPOT and throughput; change one flag at a time and compare percentiles, not averages. The defaults above already encode a lot of tuning work by the vLLM team, so a well-sized model on a well-sized GPU often needs only --max-model-len, a parallelism choice and possibly speculative decoding.

    Vocabulary

    Glossary

    Short definitions of the terms used in the second half of this page, in the sense vLLM uses them.

    Tensor parallelism (TP)
    Splitting each layer's weight matrices across GPUs so every GPU computes part of every layer; partial results are combined with all-reduce.
    Pipeline parallelism (PP)
    Assigning consecutive layers to different GPUs (stages) and passing activations from stage to stage.
    Data parallelism (DP)
    Running independent replicas, each with its own scheduler and KV cache, and spreading requests across them.
    Expert parallelism (EP)
    Placing whole MoE experts on different GPUs and sending each token to the GPUs that own its chosen experts.
    Decode context parallelism (DCP)
    Sharding one sequence's KV cache across existing TP ranks so long contexts are not duplicated on every rank.
    Prefill context parallelism (PCP)
    Adding ranks that split the prefill computation of a long prompt.
    World size
    Number of worker processes in one engine: PP × TP × PCP.
    Executor
    The EngineCore-side object that launches workers and invokes methods on them: uni, mp, ray or external_launcher.
    GroupCoordinator
    vLLM's wrapper around a process group for one parallel dimension, holding both CPU and device communicators.
    All-reduce
    A collective in which every rank contributes a tensor and every rank receives the elementwise sum.
    All2all (dispatch / combine)
    A collective in which each rank sends a different slice to every other rank; MoE uses it to route tokens to experts and back.
    Custom all-reduce
    vLLM's own all-reduce kernel over peer-accessible GPU memory, faster than NCCL for the small messages of decode steps.
    EPLB
    Expert-parallel load balancing: periodically moving or replicating hot experts so no GPU becomes the MoE bottleneck.
    Request wave
    A period during which data-parallel engines are collectively running; the DP coordinator tracks waves so idle MoE ranks know when to resume lockstep.
    Speculative decoding
    Guessing several future tokens cheaply and verifying them with one forward pass of the target model.
    Proposer / speculator
    The component that produces draft tokens: proposer in the V1 runner, speculator in Model Runner V2.
    Draft token
    A guessed token awaiting verification by the target model.
    Bonus token
    The extra token the target model produces after the last draft when all drafts are accepted.
    Rejection sampling
    The acceptance test that decides how many drafts to keep so the output distribution matches the target model.
    Mean acceptance length
    Average tokens emitted per verification step: 1 + accepted drafts ÷ drafting steps.
    MTP
    Multi-token prediction: extra prediction modules shipped with a model (for example DeepSeek's) and reused as a built-in drafter.
    EAGLE
    A family of lightweight draft heads that predict next tokens from the target model's hidden states.
    Structured outputs
    Generation constrained by a schema, regex, choice list or grammar so the output is guaranteed to parse.
    Grammar bitmask
    One bit per vocabulary token marking which tokens are allowed next, packed into 32-bit words and applied to logits.
    xgrammar / llguidance
    Grammar engines behind the xgrammar and guidance backends that compile constraints into fast token masks.
    Structural tag
    A constraint that switches grammars inside marked regions of output, used for tool calls embedded in free text.
    LoRA
    Low-rank adaptation: a fine-tune expressed as two small matrices added to selected layers.
    Punica kernels
    Batched "shrink" and "expand" kernels that apply different LoRA adapters to different rows of the same batch.
    Adapter slot
    One of max_loras GPU buffers that can hold an active LoRA during a step.
    Placeholder tokens
    Token positions reserved in the prompt for an image, video or audio item; the encoder's embeddings fill them.
    Encoder cache
    GPU storage for encoder outputs so a multimodal item is encoded once even if its tokens span several prefill chunks.
    Encoder budget
    The scheduler's per-step limit on encoder work, derived from the model by MultiModalBudget.
    Disaggregated prefill (P/D)
    Running prefill and decode on different instances and moving the KV cache between them.
    KV connector
    A plugin implementing KVConnectorBase_V1 that loads KV into, or saves KV out of, vLLM's paged cache.
    kv_transfer_params
    Per-request metadata exchanged between prefill and decode instances that names the remote engine and blocks.
    NIXL
    NVIDIA Inference Xfer Library: a transfer library over RDMA, NVLink and other transports, used by vLLM's most common P/D connector.
    KV offloading
    Copying KV blocks to CPU memory or slower tiers so prefixes evicted from the GPU can be reloaded instead of recomputed.
    ARC
    Adaptive Replacement Cache: an eviction policy balancing recency and frequency, offered for the CPU offload tier.
    TTFT
    Time to first token: from request arrival to the first generated token reaching the client.
    ITL
    Inter-token latency: the gap between successive streamed outputs.
    TPOT
    Time per output token: a request's decode time divided by the number of tokens after the first.
    Prometheus
    The metrics format and scraper ecosystem behind /metrics: gauges, counters and histograms.
    OTLP
    OpenTelemetry protocol: how vLLM exports request traces to a collector.
    SSE
    Server-sent events: the data: … line protocol used to stream chunks over HTTP.
    AsyncLLM
    The asyncio engine client used by the server; it owns input and output processing and talks to the EngineCore over ZeroMQ.
    LLMEngine
    The synchronous engine client behind the offline LLM class; its step() drives progress.
    EngineCoreClient
    The family of clients (in-process, sync multiprocess, async multiprocess, DP-aware) that connect a front end to EngineCore processes.
    Sleep mode
    Releasing weights and/or KV-cache GPU memory without stopping the process, then restoring it on wake-up.
    Pooling model
    A model run for embeddings, classification or scores rather than text generation.
    Optimization level
    The -O0…-O3 preset that trades startup time for compilation and CUDA-graph optimizations.
    Admission control
    Rejecting new requests (HTTP 503) once queue limits are reached, so latency targets are protected.

    Test yourself

    Self-check questions

    Try to answer before expanding. Each answer points back to the code or chapter that settles it.

    With TP=4, PP=2 and DP=2, how many GPU worker processes and EngineCore processes run?

    Each engine has a world size of PP × TP = 8 workers, and DP=2 means two engines, so 16 GPU workers and 2 EngineCore processes (plus API server processes and a DP coordinator).

    Why does vLLM pick the uni executor for a single GPU?

    With a world size of 1 there is nothing to coordinate, so the worker runs inside the EngineCore process and each step avoids an inter-process broadcast through the shared-memory queue.

    Why is TP usually kept inside a node while PP is used across nodes?

    TP all-reduces activations in every layer, which needs NVLink-class bandwidth and latency; PP only sends one activation tensor per stage boundary per step, which slower inter-node links tolerate.

    An idle data-parallel rank of a MoE model keeps launching forward passes. Is that a bug?

    No. Expert-parallel all2all needs every rank in the EP group to participate, so DPEngineCoreProc runs dummy batches while peers are busy and periodically all-reduces an "unfinished" flag to decide when the wave ends.

    A speculative run reports 1,000 drafts, 3,000 draft tokens and 1,800 accepted tokens. What are the acceptance rate and mean acceptance length?

    Acceptance rate is 1,800 / 3,000 = 60%. Mean acceptance length is 1 + 1,800 / 1,000 = 2.8 tokens per verification step, counting the token the target always contributes.

    When drafts are rejected, does vLLM free or copy KV-cache blocks?

    Neither. update_from_output subtracts the rejected count from num_computed_tokens; the stale KV entries are simply overwritten by later tokens.

    Which speculative methods force a fallback from Model Runner V2 to the V1 runner?

    suffix and custom_class: their speculator configs subclass UnsupportedSpeculatorConfig in v1_speculator_configs.py.

    Where is the grammar bitmask computed, and where is it applied?

    It is computed on the CPU in the EngineCore by StructuredOutputManager.grammar_bitmask (called from Scheduler.get_grammar_bitmask) and applied on the GPU to the logits by StructuredOutputsWorker.apply_grammar_bitmask before sampling.

    With the auto backend, what happens if xgrammar cannot handle a JSON schema?

    vLLM falls back to guidance, or to outlines when guidance is ruled out (non-Tekken Mistral tokenizer or unsupported schema features), and remembers that the backend was chosen automatically.

    Two requests use the same prompt text but different LoRA adapters. Can they share prefix-cache blocks?

    No. The adapter identity is part of the block hash's extra keys (_gen_lora_extra_hash_keys), so their blocks hash differently.

    Why can a single image's embeddings be used across several prefill chunks?

    The encoder runs once for the item and stores the result in the encoder cache; each chunk then gathers only the embedding rows that overlap its token range.

    On the decode instance of a P/D pair, what status does a request have while its KV is being transferred?

    WAITING_FOR_REMOTE_KVS. Once the connector's get_finished reports completion, the scheduler treats the transferred tokens like a prefix-cache hit and continues.

    What do --kv-offloading-size 64 --kv-offloading-backend native turn into internally?

    A KVTransferConfig with kv_connector="OffloadingConnector" (or SimpleCPUOffloadConnector if VLLM_USE_SIMPLE_KV_OFFLOAD=1), kv_role="kv_both" and 64 GiB passed as cpu_bytes_to_use.

    TTFT is high, the waiting queue is empty, and KV usage is low. What is the likely cause?

    Prefill compute itself: long prompts processed with a small per-step token budget. Raising --max-num-batched-tokens, improving prefix-cache hits, or adding parallelism helps; capacity is not the issue.

    Why does the server default to a smaller max_num_batched_tokens than the offline LLM class on the same GPU?

    A smaller per-step budget limits how much prefill can share a step with ongoing decodes, protecting inter-token latency for streaming users; offline jobs only care about total throughput.

    Which routes exist only when VLLM_SERVER_DEV_MODE=1?

    The development routes (/reset_prefix_cache, /reset_mm_cache, /reset_encoder_cache, /collective_rpc, /server_info, /sleep, /wake_up, /is_sleeping, /release_kv_cache_memory) and the RL weight-sync routes such as /pause, /resume and /update_weights.

    What is the difference between sleep level 1 and level 2?

    Level 1 backs up weights to CPU memory and discards the KV cache, so waking restores the same model. Level 2 discards both, which suits loading new weights (for example in RL) or hosts without spare CPU memory.

    Your tool calls come back as plain text in content. What two settings do you check first?

    That --enable-auto-tool-choice is set and that --tool-call-parser names the parser matching the model's chat template and tool-call syntax.
