Checkpoint to response

Which decisions move ahead of the request?

Plow is an open-source inference compiler and runtime. For the GPU path, a recipe ties a checkpoint to a particular hardware target, precision, supported shapes and serving settings. The HTTP service can load a matching compiled build and stream text through an OpenAI-compatible chat endpoint. This guide examines the public source at 8e8b0fd7, dated 26 November 2026. Pinned project guide · Example H100 recipe.

  1. Compile the model. The driver reads a model configuration and lowers work for the chosen device and shape buckets. The GPU emitter selects operations such as projections, normalization, attention and fused kernels. The shipped GPU path uses hand-written fusions in devgen. Its egglog rewrite analysis can check that required operations appear in the emitted program. A count of discovered rewrites alone does not establish a faster executable. GPU emission and coverage checks · Compiler implementation status.
  2. Load the bundle. The runtime matches compiled assets and checkpoint weights to the device. The packet describes planned operations and dependencies. The recipe can supply separate prefill shapes and a ladder of supported decode batch sizes. Distribution, offline compilation, model loading and API readiness each consume time at a different point. Model distribution · Packet format.
  3. Admit and prefill. The host still receives requests, tracks sessions and selects work for the available capacity. An eligible prefix-cache hit can reduce the prompt suffix that needs a forward pass. Long prompts may be chunked to fit the available shapes. This portion contributes to time to first token. Runtime multiplexer · Prefix caching · Chunk shapes.
  4. Produce the next token. On supported GPU paths, persistent or segmented interpreters execute planned operations. Dependency counters coordinate producers and consumers of intermediate data. This arrangement can reduce repeated host dispatch and synchronization. A recipe can also select library kernels for particular shapes. The model must still read weights and KV, perform attention and matrix operations, and select an output. Counter protocol · Runtime design · Example segmented and library-kernel settings.
  5. Continue serving. The sampled result can stream to the client while its request is eligible for another decode pass. Queueing, batching, cache pressure and prompt length can dominate latency even with efficient device execution. The appropriate comparison runs the full endpoint and records these costs. Chat handler · Prefill and decode scheduling.

Published measurements

What happens for one active request?

In this publisher-run experiment, both engines decoded Gemma 4 26B-A4B with BF16 on one RTX PRO 6000 Blackwell (96 GB). vLLM was version 0.25.1. Each context depth had 112 timed tokens after warm-up and a correctness check. The quantity below is milliseconds per generated token during decode. It excludes prompt ingestion and time spent in an HTTP queue. Published method and full data.

vLLM measured about 0.44 ms/token faster at 1k. At 32k, Plow measured about 0.63 ms/token faster. The same report’s larger 41% reduction for the dense 31B model compares Plow W8A8 with vLLM BF16. Its FP8-to-FP8 results are much closer and also depend on context depth. These comparisons use vLLM as the baseline; evaluating SGLang requires a third measurement. 26B and 31B precision comparisons.

Serving choices

Which engine capability matters to the workload?

Plow

A source-pinned recipe exposes the hardware target, shape ladders, weight format, KV policy and quality gates. The serving multiplexer already supports batching paths. Qualification varies across model and device combinations. The project’s status matrix distinguishes implemented interpreter paths from planned features and describes Lean verification as optional and feature-gated. Implementation status · Request batching.

vLLM

For mixed lengths and continuous arrivals, inspect EngineCore’s token budget and its KV block allocator. Prefix caching, chunked prefill and configured distributed executors affect how much work can run together. vLLM also uses compilation and CUDA graphs on supported paths, so a host-launch comparison needs the actual graph configuration. Scheduler · Graph modes · Parallelism.

SGLang

For repeated system prompts, tool schemas and agent turns, measure arriving prefix matches and how much KV stays resident. Radix matching, optional cache-aware scheduling and optional hierarchical storage address different pieces of that workload. Structured decoding and parallel serving also affect an application’s choice. Radix cache · Structured output · Distributed execution.

Claims to verify on all three

For a multi-GPU service, record whether requests are independently replicated or one request spans ranks. Then test the specific model, quantization, interconnect, cache policy and failure handling. Build a comparison

A fair three-engine experiment

  1. Freeze the task. Record the exact checkpoint and tokenizer revisions, chat template, prompt token IDs, hardware, clocks, driver and engine versions. Match weight, activation and KV precision, context limit, sampling and output budget. Save every effective backend and engine flag.
  2. Check output before timing. Use held-out prompts and a reference. For greedy deterministic cases compare token IDs and logits. For quantized runs, record distribution differences and task accuracy against a predeclared tolerance. Admit variants separately. Example of a failed quality gate.
  3. Isolate one user. With one in-flight request, sweep short and long contexts and hold generated length fixed. Measure cold startup to API readiness, warm time to first token, per-token decode latency and end-to-end duration as separate intervals. Repeat warm runs and record dispersion.
  4. Replay the service. Test identical request arrivals at several offered rates. Include separate cold-prefix and realistically warm-prefix runs, length distributions and the required structured or multimodal inputs. Record queueing, errors, timeouts, p50/p95/p99 first-token and inter-token latency, generated tokens/s, total tokens/s, memory and cost per successful request.
  5. Compare goodput at the same quality. Count requests that finish within the service’s first-token and output-latency targets. Report both matched-setting runs and separately tuned production runs, recording any unavoidable difference. If an engine lacks a required route, mark that cell unsupported.
