    Request lab

    Follow one reply.

    One chat prompt, 40 input tokens and room for three output tokens. Try the same request with a cold cache and with a shared prefix.

    This is an illustrated request with example tokens. The counts follow one request through ordinary decoding on a single GPU. Open the editable request diagram, then estimate how many concurrent requests fit on one GPU.

    Why does the warm run compute ten positions for a three-token reply?

    The first 32 prompt IDs match earlier work with compatible model and cache settings. Prefill computes the remaining eight positions and supplies scores for the first output. Each of the next two decode passes computes one position. That makes 8 + 1 + 1 = 10, compared with 40 + 1 + 1 = 42 on the cold run. The saved positions still contribute to attention through cached KV.

    How can I trace a scheduler step in Python?

    From a checkout with the package installed, run python examples/engine_walkthrough.py. Follow the request named first through prefill and two decode passes. The teaching callback increments the last token ID, so you can predict the three outputs as 3, 4 and 5. The example prints the request states, token events and final metrics.

    Why the pages are pinned to commits

    Inference engines change weekly. Pinning prevents a diagram from silently drifting away from the code.

    Many blog posts about vLLM and SGLang describe files that have since been renamed, split, or replaced. For example, at the pinned vLLM snapshot the chat-completions HTTP route lives in vllm/entrypoints/openai/chat_completion/api_router.py, not in the older monolithic API-server module. At the pinned SGLang snapshot, decode CUDA graphs are managed by DecodeCudaGraphRunner under model_executor/runner/.

    The rule for this section of the site is simple: a file, class, function, flag, or feature appears only if it was located in the pinned source tree. Line links point to definitions, so you can open the code beside the explanation. When you study a newer release, use the concepts here as a map and search for the same symbols in the new tree.

    Beginner tip: do not try to read either engine from top to bottom. Follow one request. Each time the token crosses a process boundary, ask three questions: what data structure carries it, who owns its KV memory, and what decides when it runs again?

    Architecture

    Where each engine draws process boundaries

    Both isolate HTTP and tokenization work from the GPU loop, but they place detokenization and model execution differently.

    vLLM

    Engine core separated from serving

    The API server owns HTTP, chat templating, tokenization, and output processing. It talks to an EngineCore process through AsyncMPClient. The core runs a busy loop that schedules one engine step at a time. With one GPU, the parallel configuration selects the in-process uni executor; with multiple GPUs it defaults to multiprocessing unless Ray is configured or already active (config/parallel.py).

    SGLang

    Scheduler and model runner co-located

    SGLang’s TokenizerManager tokenizes and tracks request state in the main process. Each scheduler process owns batching decisions, prefix-cache state, memory pools, and its model worker. Generated token IDs go to DetokenizerManager, which returns text to the TokenizerManager for streaming.

    Concepts

    The design choices that matter most

    Both engines solve the same problems. These are the places where their data structures and control flow differ.

    1. Prefix reuse: hashed blocks versus a radix tree

    vLLM stores KV memory in fixed-size blocks; the cache configuration uses 16 tokens as its default block size and enables prefix caching by default (config/cache.py). A full block’s identity depends on its tokens and on the identity of the blocks before it, so two requests that share an entire prefix produce the same chain of block identities. The KV cache manager looks up that chain to find already-computed blocks before allocating new ones. Backend constraints and hybrid groups can change the effective block size and hit alignment. Compare prefix matching with address translation.

    SGLang organizes reusable prefixes as a radix tree. Each path from the root spells a token sequence, and nodes point at KV slots. A new request walks the tree to its longest matching prefix, locks the nodes it uses, and inserts its newly computed suffix when finished. Unlocked leaves can be evicted under memory pressure. This naturally supports branching workloads such as few-shot templates, multi-turn chat, and the parallel branches created by SGLang’s frontend language.

    Beginners should remember the shared invariant rather than the data structure: a cached prefix is valid only when the exact token IDs, model, adapter, and other identity-affecting inputs match. Matching text after detokenization is not enough.

    2. Scheduling: one token budget versus explicit batch types

    vLLM’s V1 scheduler treats each request as “some number of tokens still need computing.” A step assigns tokens from a shared budget to running and waiting requests, which lets prompt chunks and decode tokens share the same step. Its configured policy can be first-come-first-served or priority (config/scheduler.py).

    SGLang forms new prefill (“extend”) batches with PrefillAdder and continues decode batches for running requests. Its policy enum includes cache-aware choices—longest prefix match and DFS weighting—and cache-agnostic choices such as FCFS, longest output first, random, and routing-key ordering (schedule_policy.py). Cache-aware ordering can improve reuse but may require fairness safeguards.

    3. Hiding CPU work behind GPU work

    A synchronous loop schedules, launches the GPU, waits, processes results, and repeats. When GPU steps are short, CPU bookkeeping can leave the accelerator idle. SGLang provides an overlap event loop that prepares the next batch while the current one runs. vLLM exposes an async_scheduling scheduler setting (config/scheduler.py) and an EngineCore batch-queue path for overlapping work. Both techniques trade some implementation complexity for lower per-token overhead.

    4. Structured outputs and speculative decoding are pluggable

    At the pinned commits, vLLM’s structured-output configuration accepts auto, xgrammar, guidance, outlines, and a deprecated lm-format-enforcer backend (structured_outputs.py). SGLang includes xgrammar, Outlines, and llguidance backend modules under srt/constrained/. In both engines, a grammar becomes a mask over allowed next-token IDs before sampling.

    Speculative decoding is similarly modular: vLLM has proposer modules such as EAGLE, draft model, n-gram, and suffix decoding in v1/spec_decode/, while SGLang’s algorithms live under srt/speculative/. The deep dives list the exact algorithms present in each snapshot.

    5. Disaggregation is a KV-transfer problem

    Separating prefill and decode workers only helps if the KV cache can move quickly and reliably. vLLM implements this through KV connectors, including NIXL, Mooncake, LMCache, offloading, and multi-connector modules under kv_transfer/kv_connector/v1/. SGLang has prefill and decode disaggregation managers plus transfer backends such as Mooncake, NIXL, and Mori under srt/disaggregation/.

    Practical judgment

    How to choose without guessing

    Feature lists are a starting point. Your workload and measurements decide.

    Describe the traffic

    Record prompt and output length distributions, concurrency, prefix-sharing rate, structured-output use, and latency targets for TTFT and inter-token latency.

    Match the model

    Check architecture support, quantization formats, attention variants, MoE parallelism, multimodal processors, and tool/reasoning parsers for the exact checkpoint.

    Benchmark fairly

    Use identical models, hardware, precision, prompt sets, sampling settings, and warm-up. Report p50, p95, and p99—not a single best run.

    Prefix-heavy programs

    Agents, branching prompts, and repeated templates benefit from strong prefix reuse. Measure cache hit rate and recomputed tokens in both engines.

    Operational fit

    Consider metrics, deployment tooling, upgrade cadence, routing, disaggregation support, and how easily your team can debug the code paths you depend on.

    Re-test after upgrades

    Both projects evolve rapidly. Defaults, kernels, and supported features can change, so pin versions and rerun the same benchmark before upgrading production.

    Learning path

    A four-session study plan

    Use the animated lifecycles, then confirm each step in code.

    1. Session 1 — admission. Trace rows 1–4 in both engines. Write down the request object at each process boundary.
    2. Session 2 — scheduling and memory. Compare rows 5–8. Explain where a prefix hit is detected and who frees memory after completion.
    3. Session 3 — model execution. Follow rows 9–13. Draw the shapes of input IDs, positions, KV slots, logits, and sampled tokens.
    4. Session 4 — streaming and operations. Follow rows 14–15, then study metrics, structured outputs, speculation, and disaggregation in the feature catalogs.

    Primary sources

    Further reading

    Start with primary sources; use secondary articles for intuition and always check dates.

    • Efficient Memory Management for Large Language Model Serving with PagedAttention Kwon et al. · SOSP · 2023 · paper

      The original vLLM paper explains why contiguous KV reservations waste memory and how block tables enable sharing and higher batch sizes.

    • SGLang: Efficient Execution of Structured Language Model Programs Zheng et al. · NeurIPS · 2024 · paper

      Introduces RadixAttention and the co-design between a programming frontend and a runtime that reuses prefixes across branching LLM calls.

    • vLLM documentation vLLM project · official docs

      The best reference for current deployment options, supported models, flags, and design notes. Compare its version with the pinned source when details differ.

    • SGLang documentation SGLang project · official docs

      Covers server arguments, backends, structured outputs, speculative decoding, parallelism, and deployment recipes for the SGLang runtime.

    • Inference Engineering, chapters 4.3.1 and 4.3.2 Philip Kiely · Baseten Books · 2026 · book

      Places vLLM and SGLang within the larger runtime, infrastructure, and tooling stack. Use it for production context; use the pinned code for implementation details.

    • 100 Days of Inference, days 9 and 10 Companion learning repository

      Hands-on notebooks that accompany the book’s engine chapters and pair well with the side-by-side source trace on this page.
