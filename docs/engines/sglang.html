    Orientation

    How to read this page

    Skim the process picture, play the lifecycle once, then open the chapter for whichever subsystem you need to understand or debug.

    If you are new to inference engines

    Start with the architecture diagram: SGLang is three kinds of process talking over local sockets. Then press Play on the interactive lifecycle, which walks a single request through 22 stages and shows which file runs at each one. The prefill vs decode chapter then works through real numbers: how many tokens a cache hit saves, how a long prompt is chopped into chunks, and where each KV slot comes from.

    If you already know SGLang

    Several internals moved recently. ModelWorkerBatch no longer exists: ForwardBatch.init_new reads the ScheduleBatch directly. Server flags now live in typed namespaces under python/sglang/srt/arg_groups/fields/. The default prefix cache is UnifiedRadixCache backed by a Rust tree core, the model runner dispatches through a runner/ package (eager, decode-graph, prefill-graph runners), and CUDA defaults to breakable CUDA graphs for prefill as well as full graphs for decode.

    About versions

    SGLang does not hard-code a version: python/pyproject.toml declares the version dynamic and lets setuptools-scm derive it from git tags through scripts/release/get_version_tag.py, with a 0.0.0.dev0 fallback. The pinned clone is shallow and carries no tag, so the closest version signal inside the repo is the install guide, which clones tag v0.5.23 as its example. Treat this page as "0.5.23-era main".

    How the evidence works

    Every code link targets github.com/sgl-project/sglang/blob/07a8535… with a #L anchor on the line where the class, function, or config field is defined. Defaults quoted here come from the field declarations and resolution hooks in arg_groups/. When code and older blog posts disagree, the code wins and the difference is called out.

    One sentence to hold onto: SGLang is a loop in a Scheduler process that, every iteration, pulls new requests off a socket, looks up the longest already-computed prefix of each prompt in a radix tree, admits as much new prefill work as the KV memory budget allows (otherwise decodes the running batch), runs one batched forward pass on the GPU, samples one token per request, and pushes the token IDs to a detokenizer process that sends text back to the HTTP process holding the client connection.

    Big picture

    Three process roles, three sockets

    The HTTP server and tokenizer live in the main process; each GPU gets a Scheduler process; one detokenizer process closes the loop.

    Who runs where

    The docstring of launch_server states the layout plainly: the HTTP server, the Engine object, and the TokenizerManager share the main process, while the Scheduler and the DetokenizerManager are subprocesses that talk to it over ZeroMQ. Engine._launch_subprocesses does the spawning. Its helper _launch_scheduler_processes loops over pipeline ranks and tensor-parallel ranks and starts one mp.Process per GPU with run_scheduler_process as its target, and _launch_detokenizer_subprocesses starts one run_detokenizer_process (or several workers behind a small router process when --detokenizer-worker-num is above one). The socket names are generated once in PortArgs and handed to every process.

    Notice what SGLang does not have: there is no separate "engine core" process sitting between the API server and the GPU workers. Each Scheduler process is a GPU worker. It owns a TpModelWorker, which owns a ModelRunner, which owns the model weights and KV cache for that GPU. Scheduling decisions and kernel launches therefore happen in the same Python process, which keeps the hand-off between "decide" and "run" to a function call. The price is that the scheduling code must be cheap, which is why the overlap event loop exists.

    The three socket hops

    1. TokenizerManager → Scheduler. TokenizerManager.init_ipc_channels opens an asyncio ZeroMQ PUSH socket to scheduler_input_ipc_name; the scheduler side, built in SchedulerIpcChannels.create, binds the matching PULL only on rank zero. The payload is a TokenizedGenerateReqInput.
    2. Scheduler → DetokenizerManager. After each forward, rank zero pushes one BatchTokenIDOutput covering every request that has something to report this step. With --skip-tokenizer-init the same socket points straight back at the tokenizer instead.
    3. DetokenizerManager → TokenizerManager. The detokenizer turns IDs into text and pushes a BatchStrOutput to tokenizer_ipc_name, where the TokenizerManager's background handle_loop receives it.

    All three hops go through sock_send. At this commit the environment flag SGLANG_USE_PICKLE_IPC defaults to true, so objects travel as pickles via send_pyobj; turning it off switches to msgspec-based msgpack encoding (the message classes are already msgspec.Struct subclasses so both paths work). Large multimodal tensors can bypass the socket through shared memory or CUDA IPC transports.

    How tensor-parallel ranks stay in lockstep

    Only the rank that owns the socket reads from it. Inside SchedulerRequestReceiver.recv_requests, rank zero drains the PULL socket without blocking, and _broadcast_reqs_across_ranks ships the same Python list to every other rank over a CPU process group (or a shared-memory exchange when one is available). Every rank then executes identical scheduling code on identical inputs, so they all build the same batch and launch the same kernels; the GPUs exchange partial results with NCCL collectives inside the model. This "replicated scheduler" design is why SGLang's cache and policy code must be deterministic: if two ranks disagreed about which request to admit, their collectives would deadlock. Several cache methods carry a @rank_consensus decorator for exactly this reason.

    Why not one process?

    Tokenizing a long prompt, rendering a Jinja chat template, decoding images, assembling JSON for server-sent events, and detokenizing are all CPU-bound Python. If they ran in the scheduler's thread they would delay the next kernel launch and leave the GPU idle. Moving them to the main process (tokenization) and to the detokenizer process (text assembly) means the scheduler only ever handles token IDs. When even the main process becomes the bottleneck, --tokenizer-worker-num runs several tokenizer-manager workers in parallel, and a small router fans results back to whichever worker owns each request.

    Worked example

    Prefill (extend) vs decode, with real numbers

    SGLang calls ordinary prefill an extend pass. With an empty cache it processes the whole prompt. On a prefix hit it processes the suffix.

    In most papers the first forward pass over a prompt is called prefill. SGLang's ForwardMode calls it EXTEND, and the comment on that enum explains why: the beginning of the sequence may already have KV in the cache (for example a shared system prompt), so the pass only extends it. A batch is in DECODE mode when every request contributes exactly one new token, and in MIXED mode when chunked prefill and decode rows share a pass. The other modes (IDLE, TARGET_VERIFY, DRAFT_EXTEND_V2, PREBUILT, DLLM_EXTEND) serve data-parallel padding, speculative decoding, disaggregated decode, and diffusion language models.

    Extend (prefill)Decode

    The setup

    Take Llama-3.1-8B-Instruct in bf16 on one 80 GB H100 with default flags. The resolution hook handle_gpu_memory_settings gives a GPU in the 60–90 GB class a chunked_prefill_size of 8192; max_prefill_tokens defaults to 16384; and _page_size_default resolves the page size to 1 on CUDA. One token of KV for this model costs: 

    KV bytes per token = layers × kv_heads × head_dim × 2 (K and V) × 2 bytes (bf16)
                   = 32 × 8 × 128 × 2 × 2 = 131,072 bytes = 128 KiB

    Suppose the memory profiler sized the token pool at 400,000 slots (about 48.8 GiB of KV). At the moment our request arrives, the allocator reports 140,000 free slots, the radix tree holds 90,000 tokens of unlocked (evictable) cached prefixes, and 48 requests are decoding, each with 600 tokens left before its max_new_tokens.

    Step 1 — radix prefix hit

    The new request has a 12,000-token prompt: a 1,500-token system prompt plus tool schemas that many clients share, followed by a 10,500-token document, and asks for up to 1,024 new tokens. match_kv_cache walks the tree and returns device_prefix_len = 1,500. With page_size 1 the match is not rounded; with a page size of 64 it would be rounded down to 1,472 by RadixKey.page_aligned. 

    prefix_len        = 1,500           (KV reused, no compute, no new slots)
extend_input_len  = 12,000 − 1,500 = 10,500
positions reused  = 1,500 / 12,000 = 12.5 % of prompt positions
existing KV reused = 1,500 × 128 KiB = 187.5 MiB

    The suffix still attends to the reused prefix. The fraction of input positions skipped does not directly predict total FLOPs or latency.

    Step 2 — the memory budget

    PrefillAdder builds a PrefillBudget whose remaining_total is free slots plus evictable tree tokens minus an offset. Each running request adds min(max_new_tokens − generated, 4096) × new_token_ratio to that offset (_get_running_request_total_token_offset): a guess at how much more KV it will need. The ratio starts at 0.7 × schedule_conservativeness, falls by about 0.001 on every decode step without retraction, and never drops below 14% of its start value (environment defaults in new_token_ratio_tracker.py). Say it currently sits at 0.5: 

    running reserve   = 48 × min(600, 4096) × 0.5           = 14,400
remaining_total   = 140,000 free + 90,000 evictable − 14,400 = 215,600
request footprint = extend 10,500 + min(1,024, 4096) + 1 page = 11,525   (< 215,600 → admissible)

    The 4096 clip is CLIP_MAX_NEW_TOKENS: a request asking for 100,000 new tokens is budgeted as if it wanted 4,096, so one greedy client cannot freeze admission. If the estimate proves too optimistic, decode retraction (below) corrects it.

    Step 3 — chunking

    _select_prefill_admission compares the page-rounded extend length with the chunk budget rem_chunk_tokens (8,192). Because 10,500 > 8,192, the request is cut at a page boundary and becomes the scheduler's single chunked_req. A chunk reserves no decode headroom (max_new_tokens counts as 0 until the last chunk) because the request cannot decode yet. 

    chunk 1: extend_len = 8,192 // page_size × page_size = 8,192   positions 1,500 … 9,691
         reserve += 8,192 + 1 page + 0              → total_offset 14,400 + 8,193 = 22,593
         rem_chunk_tokens = 8,192 − 8,192 = 0      → budget_state() = OTHER, stop admitting
         rem_input_tokens = 16,384 − 8,192 = 8,192

    Step 4 — KV slot allocation

    prepare_for_extend calls alloc_for_extend. The request receives a row in ReqToTokenPool (say row 211). Positions 0–1,499 of that row are filled with the slot IDs already stored on the radix path; positions 1,500–9,691 get 8,192 fresh IDs from alloc_token_slots, which pops them from the front of the allocator's free list. Had fewer than 8,192 been free, its make_room callback would first evict that many unlocked tree tokens, least-recently-used leaf first. 

    req_to_token[211, 0:1500]    = tree path slot ids      (shared, locked)
req_to_token[211, 1500:9692] = out_cache_loc[0:8192]   (fresh)
free slots: 140,000 → 131,808          evictions: 0
ForwardBatch: extend_prefix_lens=[1500], extend_seq_lens=[8192], seq_lens=[9692]

    Ignoring attention, an 8B model costs about 2 × 8 × 10⁹ FLOPs per token, so this chunk is roughly 131 TFLOPs: around 0.22 s at an assumed sustained 600 TFLOP/s. The attention kernel additionally reads the 1,500 cached rows for every new query row.

    Step 5 — between the chunks

    After the chunk runs, get_next_batch_to_run calls stash_chunked_request, which uses checkpoint_kv_cache to insert the 9,692 computed tokens into the tree. The request's prefix_len becomes 9,692 and the tree now protects that KV under the request's lock. On the next iteration add_chunked_req runs before any other admission: 

    chunk 2: remaining = 12,000 − 9,692 = 2,308 ≤ 8,192  → not truncated, last chunk
         reserve += 2,308 + 1 + min(1,024, 4096) = 3,333
         rem_chunk_tokens = 8,192 − 2,308 = 5,884   → room for other waiting prompts in this batch
         first output token is sampled at the end of this pass  → TTFT = 2 scheduler iterations

    Step 6 — what decode costs

    By default get_next_batch_to_run prefers a prefill batch whenever one can be formed, so the 48 decoding requests paused for those two iterations. That is the classic trade: shorter TTFT for newcomers, a hiccup in ITL for everyone else. --enable-mixed-chunk folds the running requests into the extend batch as a MIXED pass instead (their tokens are subtracted from the chunk budget up front), and --prefill-decode-interval forces a number of decode rounds between prefills.

    Once our request decodes, every step allocates one slot per running request and reads their active KV. With 48 other requests averaging 3,000 context tokens plus ours at 12,001: 

    KV read per step  ≈ (48 × 3,000 + 12,001) × 128 KiB ≈ 156,001 × 131,072 B ≈ 20.4 GB
weights per step  ≈ 8.03 × 10⁹ params × 2 B          ≈ 16.1 GB
lower bound       ≈ 36.5 GB / 3.35 TB/s HBM          ≈ 10.9 ms per step (≈ 92 tokens/s per request)
slots per step    = 49   →  free list shrinks by 49 every iteration

    If the pool runs dry, check_decode_mem fails, and retract_decode pushes some requests back to the waiting queue (by default those with short outputs and long inputs first, per --retraction-policy length), freeing their slots. The scheduler then resets new_token_ratio from the observed progress, logs "KV cache pool is full. Retract requests.", and requeues them. Retraction frees a request's KV without inserting the decode tokens into the tree (release_kv_cache with checkpoint=False), but its prompt was already checkpointed after prefill, so when it returns the radix tree usually still holds the prompt and only the generated tokens are recomputed.

    Control loop

    The Scheduler and its overlap event loop

    One Python object per GPU decides everything: what to admit, what to run, and what to free. The overlap loop hides that decision time behind the GPU.

    Scheduler is a large class (its file is over 6,600 lines) assembled from mixins and a growing set of helper objects in managers/scheduler_components/: the request receiver, the output streamer, the batch-result processor, the metrics reporter, the new-token-ratio tracker, and more. Its constructor builds, in order, the model worker (which loads weights and sizes the KV pool), the memory pools and tree cache (init_memory_pools), the schedule policy (init_schedule_policy), chunked-prefill state, and the overlap machinery (init_overlap). Its long-lived state is small and worth memorizing:

    • waiting_queue: a Python list of Req objects not yet admitted (new or retracted).
    • running_batch: a ScheduleBatch of requests in the decode phase.
    • chunked_req: at most one request whose prompt is being prefilled across several iterations.
    • last_batch: the batch launched on the previous iteration, merged into running_batch once its prefill completes.
    • tree_cache, req_to_token_pool, token_to_kv_pool_allocator: the memory system (next chapters).

    Choosing a loop

    run_event_loop sets up CUDA streams and calls _dispatch_event_loop_once, which picks one of several loops: pipeline-parallel loops when pp_size > 1, prefill- or decode-specific loops when PD disaggregation is on, an MLX loop on Apple silicon, and otherwise event_loop_overlap (the default) or event_loop_normal (when --disable-overlap-schedule is set or a feature requires it).

    The normal loop is the easiest to read and is the right mental model for one iteration:

    1. Ingest. ingest_requests() receives and dispatches new messages: generate requests become Reqs in the waiting queue; aborts, weight updates, LoRA loads, and profiling commands are handled immediately.
    2. Plan. get_next_batch_to_run() merges the previous prefill batch into running_batch, then returns either a new prefill batch or the updated decode batch.
    3. Run. run_batch() calls the model worker, which returns logits and sampled token IDs.
    4. Process. process_batch_result() appends tokens, checks stop conditions, updates the cache, and streams outputs.
    5. Idle. With nothing to run, on_idle() performs self-checks and may sleep.

    How the overlap loop works

    The overlap loop keeps a result_queue deque. Each iteration it plans batch N+1 and launches it with run_batch before processing the result of batch N, then calls pop_and_process() on the older entry. The CPU therefore spends the GPU's forward time on bookkeeping, radix-tree updates, and output streaming instead of waiting. The LMSYS team described this "zero-overhead batch scheduler" when it shipped in v0.4, crediting the idea to NanoFlow (SGLang v0.4 blog); the code has since been reorganized but the structure is the same.

    Three mechanisms make it safe:

    • Future tokens. When batch N+1 is planned, batch N's sampled token is still on the GPU. FutureMap keeps a GPU buffer indexed by request-pool row; the forward of batch N publishes its sampled IDs into it, and resolve_forward_inputs gathers them as batch N+1's input_ids on the GPU. No device-to-host round trip sits on the critical path.
    • Two streams and kept-alive references. Planning runs on a schedule_stream; run_batch makes the forward_stream wait on it before launching. Because Python could free tensors the GPU is still reading, record_batch_in_overlap keeps the last two batches' fields alive in a two-slot ring.
    • Delayed sampling and opt-outs. A batch with grammars needs the previous batch's tokens to advance its state machine before its vocabulary mask is built, so the worker returns a delay_sample_func and the loop calls launch_batch_sample_if_needed after processing the previous result. is_disable_overlap_for_batch processes the previous result first when two prefill batches arrive back to back and SGLANG_DISABLE_CONSECUTIVE_PREFILL_OVERLAP is set (to cut TTFT) or when speculative decoding with grammars needs a sync.

    One side effect is visible in the code: under overlap a request can be scheduled for one extra decode step after the step that finished it. The result processor skips such rows, and release_kv_cache frees the over-allocated slot.

    Inside get_next_batch_to_run

    get_next_batch_to_run is where continuous batching happens. If the last batch was an extend batch, its requests (minus the in-progress chunked_req, which is stashed into the tree instead) are merged into running_batch. Finished requests are filtered out. Then:

    1. Try a prefill batch. get_new_batch_prefill moves ready grammar requests into the queue, returns early if the batch is full or nothing is waiting, sorts the queue with the policy, continues any chunked_req, and admits requests through the PrefillAdder until a budget runs out.
    2. Otherwise decode. update_running_batch drops rows that finish in flight, checks there is one free slot per request, retracts if not, and calls prepare_for_decode.
    3. Data-parallel attention sync. With DP attention every rank must run the same kind of batch, so the plan is padded or converted (for example an empty rank runs an IDLE batch).

    Retraction, in one paragraph

    Admission budgets decode growth with an estimate, so the pool can still fill up. When check_decode_mem() fails, retract_decode() removes requests from the decode batch, frees their KV (in PD-disaggregated decode it can first back it up to host memory), resets them with reset_for_retract, and returns a new, more conservative new_token_ratio. The scheduler re-queues them with is_retracted=True. Their generated tokens are kept, so the next prefill recomputes prompt plus output, usually with a large radix hit. Frequent retraction warnings are the signal to raise --schedule-conservativeness.

    Queue ordering

    Schedule policies

    The policy only decides the order in which waiting requests are offered to the PrefillAdder. Admission itself is always budget-driven.

    SchedulePolicy sorts waiting_queue in place every time a prefill batch is considered. The CLI field --schedule-policy defaults to fcfs. The code splits policies into two enums: CacheAwarePolicy (needs prefix-match results) and CacheAgnosticPolicy.

Priority ordering is instead switched on with --enable-priority-scheduling, which check_server_args only allows together with fcfs or lof. Higher integers run first by default; with preemption enabled, a newcomer whose priority beats a running request by at least --priority-scheduling-preemption-threshold (default 10) may evict it via preempt_to_schedule.

    Guard rails inside the policy code

    • Fallback when the queue is long. _determine_active_policy switches lpm and hrrn to FCFS whenever more than WAITING_QUEUE_PREFIX_MATCH_MAX (128) requests are waiting, because matching every request against the tree each iteration would cost more than it saves.
    • Fallback when the cache is off. _validate_and_adjust_policy maps every cache-aware policy to FCFS under --disable-radix-cache, except shortest-prefill-first, which refuses to start.
    • In-batch prefix de-duplication. _compute_prefix_matches keeps a second, simulated radix tree of the waiting queue itself. If a request's cache hit is short (≤ 32 tokens) but it shares at least 32 tokens with a request earlier in the queue, it is temporarily deprioritized. The first request computes the shared prefix, inserts it into the real tree, and the followers then hit it instead of computing it in parallel.
    • Matches even for agnostic policies. When the tree supports a fast match, calc_priority still matches every waiting request so the load snapshot can report matched-prefix tokens to routers.

    Prefix caching

    RadixAttention: the radix tree of KV

    The feature SGLang is known for: every finished or in-progress sequence leaves its KV in a tree keyed by tokens, and every new request starts from the longest matching path.

    A radix tree (compressed trie) stores strings so that shared prefixes are stored once. SGLang stores token sequences, and at each edge it keeps the KV-cache slot indices of those tokens instead of the tokens' text. Finding the longest cached prefix of a new prompt is a walk from the root; inserting a finished sequence adds at most one new leaf; and freeing memory means deleting unused leaves. The original LMSYS write-up framed this as automatic KV reuse across few-shot examples, self-consistency samples, multi-turn chat history, and tree-of-thought search, all handled by one structure with LRU eviction and a cache-aware scheduler (LMSYS, Jan 2024).

    Two implementations, one interface

    Both trees implement BasePrefixCache. RadixCache in radix_cache.py is the compact, readable implementation (about 840 lines) and is still used, for example as the scheduler's simulated waiting-queue tree. The tree the scheduler actually serves from is chosen by default_radix_cache_factory, which in the common case calls create_unified_radix_cache and returns a UnifiedRadixCache. That class splits the work in two:

    • Components describe what a tree node owns: full-attention KV (FullComponent), a sliding-window tail for SWA models (SWAComponent), or recurrent-state checkpoints for Mamba-style hybrids (MambaComponent).
    • A tree core does the walking, splitting, and LRU bookkeeping. create_tree_core reads SGLANG_UNIFIED_RADIX_TREE_CORE_BACKEND, whose default is "rust": a native tree from the rust/sglang-radix-tree crate. It falls back to the Python UnifiedTreeCore for session-aware caching, custom components, non-Linux hosts, unsupported PyTorch versions, or devices other than CPU and CUDA.

    The algorithms below are explained with RadixCache because it is short enough to read in one sitting; the unified tree follows the same contract (match, insert or checkpoint, lock, unlock, evict) with more bookkeeping per component.

    Keys, values, and namespaces

    A TreeNode holds children (a dict keyed by the first token, or the first page of tokens), its parent, a key, a value tensor of slot indices, lock_ref, last_access_time, hit_count, and a priority. The key is a RadixKey: token IDs plus an optional extra_key and cache_salt. Two requests with identical tokens but different extra keys (a different LoRA adapter, a different salt supplied by the client) never share nodes, which keeps tenants and adapters from reading each other's KV. With page_size > 1, keys are truncated to whole pages by page_aligned and children are keyed by their first page, because the allocator can only share whole pages. When EAGLE speculative decoding is active the tree stores keys in a bigram view (maybe_to_bigram_view).

    match_prefix: walk and split

    match_prefix page-aligns the key and calls _match_prefix_helper. Starting at the root it repeatedly looks up the child for the next token, counts how many tokens of that child's key match, and descends. If the match ends in the middle of a child's key, _split_node cuts that edge in two so the boundary becomes a real node; the request can then lock exactly the part it uses. Every node visited gets a fresh last_access_time, which is what LRU eviction reads. The result is a MatchResult with device_prefix_len (sum of matched values) and last_device_node; the hierarchical cache adds host and storage hit lengths on top.

    insert and checkpoint: publishing KV

    insert walks the same way through _insert_helper and returns how many leading tokens were already present, creating a new leaf for the rest. That return value matters: if two requests with the same prompt ran concurrently, both computed KV for it, but only one copy can live in the tree. _insert_cache frees the request's own slots for the duplicated span, and checkpoint rewrites the request's row in req_to_token to point at the tree's copy, moves the request's lock to the new deepest node, and advances cache_protected_len so later frees skip the tree-owned part.

    The scheduler calls this checkpoint at three moments: after each prefill chunk (stash_chunked_request), after a request's prefill completes (checkpoint_kv_cache), and when it finishes (release_kv_cache with checkpoint=True). Prompts therefore become shareable as soon as they are computed, not only after the request ends. Each time RadixCache.checkpoint inserts a sequence that extends past the prompt, the prompt boundary is split off as its own node at a slightly higher priority, so eviction can drop the generated tail while keeping the reusable prompt.

    Lock references: what may not be evicted

    A request reading cached KV must stop that KV from being freed under it. lock returns a TreeLock after calling inc_lock_ref, which walks from the node to the root adding one to each lock_ref. A node going from 0 to 1 moves its token count from evictable_size_ to protected_size_. unlock and dec_lock_ref do the reverse. The root is created with lock_ref = 1, so it is never evictable. These two counters are exactly the "evictable" term in the admission budget.

    Eviction

    evict builds a min-heap of the current evictable_leaves keyed by the eviction strategy, pops the lowest, frees its slot indices back to the allocator, deletes the leaf, and pushes the parent if the parent just became an unlocked leaf. It stops once enough tokens are freed. Only leaves are evicted, so a shared prefix always outlives the branches that depend on it. --radix-eviction-policy accepts lru (default), lfu, slru, priority, and tlru (RADIX_EVICTION_POLICY_CHOICES); evict_policy.py also contains FIFO, MRU, and FILO strategy classes.

    Turning it off, and what that costs

    --disable-radix-cache keeps the same tree object but in a disabled state: matches return zero, inserts do nothing, and every request frees all of its KV when it finishes. Cache-aware schedule policies fall back to FCFS. You need it for features that cannot share KV by token identity, such as requests that pass input_embeds (the tokenizer manager raises an error otherwise). For workloads with no repeated prefixes the cost of leaving the cache on is small: a tree walk per admission plus the memory held by finished sequences, which eviction returns as soon as it is needed.

    KV memory

    Memory pools: rows, slots, and buffers

    Two levels of indirection let a request's KV live anywhere in the pool and let different requests point at the same physical slots.

    Level 1: ReqToTokenPool

    ReqToTokenPool is a single GPU tensor req_to_token of shape [size + 1, max_context_len] and dtype int32, plus a Python list of free row numbers. Row 0 is never handed out: CUDA-graph replays pad batches with request index 0, so dummy reads and writes land there harmlessly. alloc gives each new request a row (a continuing chunked request keeps its row), and free returns it. The number of rows caps how many requests can be resident at once, which is why get_num_allocatable_reqs checks it before admission. Attention kernels index this table with req_pool_indices to find every slot of a request's history; that is SGLang's equivalent of a block table, at single-token granularity when page_size is 1.

    Level 2: the token-slot allocator

    TokenToKVPoolAllocator owns the free list of slot indices as a GPU int64 tensor initialized to 1 … size (slot 0 is the padding slot). Its alloc slices the first n entries off the tensor; free concatenates indices back (or, when need_sort is set, parks them in a release list that is merged and sorted into the free list when it runs short). The scheduler brackets result processing with free_group_begin/free_group_end so that many small frees in one step become one concatenation. When page_size > 1, PagedTokenToKVPoolAllocator hands out whole pages: alloc_extend and alloc_decode receive each request's last_loc and first fill the free tail of its last page before taking new pages. All allocators derive from BaseTokenToKVPoolAllocator.

    Callers rarely touch the allocator directly. In alloc_token_slots the request goes through a storage wrapper (take_tokens) together with a make_room callback that evicts from the radix tree on demand. Admission already checked that "free + evictable" covers the request, so this eviction normally succeeds; if it does not, the function logs the tree and raises an out-of-memory error rather than corrupting state.

    Level 3: the KV buffers

    KVCache is the abstract base; MHATokenToKVPool is the standard multi-head (and grouped-query) layout with per-layer key and value buffers sized for size + page_size slots, and MLATokenToKVPool stores DeepSeek-style compressed latent KV instead. Attention backends write with set_kv_buffer and read with get_key_buffer / get_value_buffer. Hybrid models add more pools: sliding-window layers get a smaller SWAKVPool, and Mamba or linear-attention layers get per-request state slots through HybridReqToTokenPool. HiCache mirrors the layout in host memory (MHATokenToKVPoolHost); see HiCache.

    How big is the pool?

    At startup the model runner loads weights, measures free GPU memory, and turns --mem-fraction-static (the share of GPU memory for weights plus KV) into a token count, unless --max-total-tokens pins it. The bytes per token depend on layers, KV heads, head size, and --kv-cache-dtype (an FP8 cache halves the bf16 figure). Space for CUDA graphs and activations is reserved first. If you see out-of-memory errors during graph capture or large prefills, lower --mem-fraction-static; if you see frequent retraction with plenty of GPU memory left, raise it.

    Data structures

    Batch flow: Req → ScheduleBatch → ForwardBatch

    Three objects, three owners. Older write-ups show a fourth, ModelWorkerBatch, in the middle; at this commit it is gone.

    Req: one per request, for its whole life

    Req is created when the request reaches the scheduler and survives retraction, chunking, and many batches. It holds the prompt (origin_input_ids), the growing output_ids, the cache match (prefix_len, last_node, lock), a KV-bookkeeping record (row index, allocated and committed lengths, the protected prefix length), sampling parameters, the optional grammar object, logprob accumulators, and timing stats. init_next_round_input refreshes the cache match before each admission attempt, and update_finish_state evaluates stop conditions after each token.

    ScheduleBatch: the scheduler's working set

    ScheduleBatch is a dataclass whose field groups are labeled in the source: shared resources (pools, tree cache, model config), scheduler-only state (batch_is_full, chunked_req, decoding_reqs), and GPU tensors that cross to the forward pass (input_ids, req_pool_indices, seq_lens, out_cache_loc). It is created by init_new and then shaped by one of two methods:

    • prepare_for_extend: per-request uncached token IDs are flattened into pinned host memory (copied to the GPU later on the forward stream), lengths are recorded, and alloc_for_extend fills rows and slots. It also updates each request's cached_tokens statistic, which is what the API reports as cached prompt tokens.
    • prepare_for_decode: clears prefill-only fields, lets the speculative algorithm take over if one is configured, accumulates penalty state, allocates one slot per request, and creates new seq_lens tensors (rather than mutating in place, so an in-flight overlapped forward still sees the old ones).

    Between iterations the running batch is edited rather than rebuilt: filter_batch drops finished or excluded requests, merge_batch appends a just-prefilled batch, and with --enable-mixed-chunk mix_with_running concatenates decode rows onto an extend batch to form a MIXED batch. Under overlap, batch.copy() snapshots the request list before it is queued, because the next iteration keeps mutating the live batch.

    ForwardBatch: exactly one forward pass

    ForwardBatch is what models and attention backends see. Its docstring is "Store all inputs of a forward pass", and its required fields are the forward mode, batch size, input IDs, request-pool indices, sequence lengths, output cache locations, and their sum. It also carries positions, extend metadata, sampling info, speculative-decoding inputs, multimodal inputs, LoRA IDs, and data-parallel padding information. The attention backend and KV pool are not stored on it; layers reach them through the model runner and the forward context, and the backend keeps its own per-batch metadata. ForwardBatch.init_new now takes the ScheduleBatch itself. The code states the rule that it must not mutate the schedule batch, and a comment records that it took over the grammar wiring "previously done in ScheduleBatch.get_model_worker_batch". In other words, the CPU-side copy step that ModelWorkerBatch used to provide was folded into this constructor; the overlap scheduler instead protects tensors with stream ordering and the kept-alive batch ring described in the scheduler chapter.

    Who decides the mode?

    The scheduler decides: prepare_for_extend and prepare_for_decode set forward_mode, and mix_with_running sets MIXED. Downstream code only branches on it. ModelRunner._forward_raw uses is_cuda_graph() (true for DECODE, TARGET_VERIFY, IDLE, and DLLM_EXTEND) to try a decode graph, EagerRunner.execute runs a MIXED batch as EXTEND on CUDA, and AttentionBackend.forward picks forward_decode or forward_extend.

    Kernels

    Attention backends

    Models call one layer, RadixAttention. Which kernel runs behind it is a server-level choice made once at startup.

    Every SGLang model builds its attention layers as RadixAttention modules that know only their geometry: query heads, KV heads, head size, scaling, layer index, optional sliding window, logit cap, and whether they are cross-attention. Their forward reshapes k and v and hands everything to the active AttentionBackend. That base class defines the contract every kernel family implements:

    • init_forward_metadata(forward_batch) — once per batch, before the layers run: build index arrays (for example per-request KV page lists derived from req_to_token), plan kernel work splits, and compute cumulative sequence lengths. Doing this once instead of per layer is a large share of what makes small decode steps fast.
    • forward(q, k, v, layer, forward_batch) — returns an empty tensor for IDLE, otherwise dispatches to forward_decode or forward_extend. Both normally write k and v into the pool at out_cache_loc first (unless save_kv_cache=False) and then attend over the request's full history.
    • CUDA-graph hooks: init_cuda_graph_state allocates static metadata buffers sized for the largest captured batch, and the out-of-graph / in-graph metadata hooks refill them before each replay.

    How the default is chosen

    If you pass no --attention-backend, get_default_attn_backend decides. Its docstring and branches say:

    • Standard multi-head / grouped-query models (Llama, Qwen…): fa3 on Hopper (with CUDA 12.3+) unless speculative decoding uses top-k > 1; trtllm_mha on SM100-class Blackwell (or fa4 when the model's K and V widths differ); aiter on AMD; torch_native on Apple MPS; otherwise flashinfer when installed and the model has no attention sinks, else triton. A code comment explains that FA3 became the Hopper default after a FlashInfer performance regression on that architecture.
    • MLA models (DeepSeek V2/V3 family): fa3 on Hopper, flashinfer on SM100, aiter on AMD for 16 or 128 KV heads, and triton otherwise.
    • Out-of-tree hardware platforms supply their own default, and some model overrides (Gemma 4, Whisper) force one.

    Prefill and decode can use different kernels: --prefill-attention-backend and --decode-attention-backend take priority over the general flag, and the runner wraps the two in a HybridAttnBackend. Models that mix full attention with linear attention or state-space layers get a further wrapper from attn_backend_wrapper. Some choices constrain other settings: for example the FA4 backend forces page_size 128 for non-MLA models on SM100, and the HPC-Ops backend requires page size 64.

    Why extend attention is the interesting kernel

    A decode kernel has one query row per request and reads that request's whole KV list: a pure gather-and-reduce that is limited by memory bandwidth. An extend kernel has many query rows per request, some of whose keys live in the cache (the matched prefix) and some of which were just computed. Backends handle this either with a single "ragged" kernel over both, or by attending to the prefix and the new tokens separately and merging the partial softmax results (the merge_state.py helper exists for that). Because SGLang's prefixes come from a radix tree, the prefix part of an extend is common, which is why every backend here must support it efficiently rather than assuming an empty cache.

    Launch overhead

    CUDA graphs and torch.compile

    A decode step of a small batch launches hundreds of tiny kernels. Recording them once and replaying them as one graph removes most of the CPU cost.

    A CUDA graph is a recording of a fixed sequence of kernel launches with fixed tensor addresses. Replaying it costs one launch from the CPU. The catch is that shapes and buffer addresses are frozen at capture time, so the runtime must (a) capture one graph per shape it wants to accelerate, (b) copy each real batch into static input buffers before replay, and (c) pad the batch up to a captured shape. At this commit SGLang organizes this into a small framework:

    • CudaGraphConfig holds one PhaseConfig for decode and one for prefill. Each picks a Backend: full, breakable, or disabled (the older tc_piecewise name now raises an error).
    • The defaults are full for decode and, via default_prefill_backend, breakable for prefill on CUDA (disabled elsewhere).
    • Runners live in model_executor/runner/: DecodeCudaGraphRunner, PrefillCudaGraphRunner, and the fallback EagerRunner, all built by ModelRunner.init_cuda_graphs.
    • Capture backends live in runner_backend/: FullCudaGraphBackend records the whole forward; BreakableCudaGraphBackend records segments and breaks at attention and Mamba boundaries.

    Decode graphs

    At startup the decode runner captures one graph per batch size. generate_decode_cuda_graph_batch_sizes produces 1, 2, 4, 8, 12, then every 8 up to 256, every 16 up to 512, and every 32 beyond, up to max_bs (speculative decoding uses a finer grid at small sizes). max_bs itself comes from handle_gpu_memory_settings by GPU memory class: 8 below 20 GB, 32–48 (or 160 with TP ≥ 4) for 20–60 GB cards, 256 (512 with TP ≥ 4) for 60–160 GB cards, and 512 above; it is then capped at --max-running-requests. get_batch_sizes_to_capture drops sizes that violate tensor- or context-parallel alignment and clamps the list to the request-pool size.

    At run time _forward_raw asks can_run_graph: the batch must fit the largest captured size (or match a captured size exactly with --disable-cuda-graph-padding), and features that change shapes per request (embedding overrides, some encoder-decoder and speculative layouts) disqualify it. execute then loads the live batch into the static buffers (padding up to the bucket), lets the attention backend refresh its metadata, replays, and slices outputs back to the real batch size.

    Prefill graphs

    Prefill shapes vary with the number of tokens, not just the number of requests, so prefill graphs are keyed by token-count buckets up to a maximum that defaults to the chunked-prefill size. Attention metadata for an extend batch is too dynamic to freeze, so the default backend is the breakable graph: a BreakableCUDAGraph is a chain of real CUDA graphs separated by eager break points, and RadixAttention runs eagerly at those breaks when it sees it is inside a prefill graph scope. The full prefill backend, which captures the whole forward with a fixed number of request slots, is opt-in. Batches that exceed the captured buckets, request per-token pooling, or use unsupported context layouts run through EagerRunner.

    From logits to a token

    LogitsProcessor, Sampler, penalties, and the grammar mask

    Everything between the last hidden state and the chosen token ID, in the order the code applies it.

    Logits: compute only the rows you need

    Each model ends with a LogitsProcessor. Its forward prunes the hidden states to the rows that need a next-token distribution (the last position of each request in an extend batch, every row in decode), unless input logprobs were requested, then multiplies by the LM head. Under tensor parallelism the vocabulary is sharded, so the per-rank slices are all-gathered. Final-logit soft-capping, logit scaling, and optional FP32 LM-head computation happen here. The output is a LogitsProcessorOutput.

    Per-request knobs become batched tensors

    Sampling parameters arrive per request in SamplingParams (temperature, top-p, top-k, min-p, penalties, stop strings and tokens, constraint specs, logit_bias, and more). When a batch is built, SamplingBatchInfo.from_schedule_batch turns them into GPU tensors with one row per request, plus flags such as is_all_greedy and need_top_p_sampling so the sampler can skip work nobody asked for. The object is filtered and merged alongside the batch, so a request keeps its settings as the running batch changes.

    Penalties

    Penalties need per-request state (counts of tokens generated so far), so they live in a BatchedPenalizerOrchestrator that only activates penalizers some request in the batch needs:

    • BatchedFrequencyPenalizer subtracts frequency_penalty × count(token), accumulated with a scatter-add as tokens are generated.
    • BatchedPresencePenalizer subtracts a flat penalty for any token that has appeared.
    • BatchedRepetitionPenalizer is multiplicative: seen tokens with positive logits are divided by the penalty and negative ones multiplied.
    • BatchedMinNewTokensPenalizer blocks stop and EOS tokens until min_new_tokens have been produced.

    Under the overlap scheduler, additive and scaling penalties are pre-accumulated into tensors by update_penalties; without overlap, the orchestrator applies them directly. Both paths run inside apply_logits_bias, which applies penalties, then the grammar mask, then logit_bias.

    The grammar mask

    For structured output, update_regex_vocab_mask asks the first grammar object in the batch to allocate a vocabulary bitmask, fills the rows of every still-active grammar in one batched call (rows without a grammar stay unconstrained), moves it to the GPU, and wraps it in a GrammarMask whose apply sets every disallowed logit to minus infinity. The mask is released immediately after use; a code comment notes this avoids a slow VRAM leak when the overlap loop keeps sampling closures alive. Grammar compilation, the backends (xgrammar, outlines, llguidance, none in GRAMMAR_BACKEND_CHOICES; default xgrammar per handle_grammar_backend), and the reasoning-aware grammar are covered in constrained decoding.

    The Sampler

    ModelRunner.sample calls _preprocess_logits and then Sampler.forward:

    1. Custom processors and hygiene. Per-request custom logit processors (only when the server runs with --enable-custom-logit-processor) run first; NaN logits are sanitized.
    2. Greedy fast path. If every request has temperature 0 (is_all_greedy), the result is argmax, with no softmax at all.
    3. Stochastic path. Logits are divided by per-request temperatures in place, softmaxed, and sampled. Without top-k/top-p/min-p, a direct multinomial draw is used. Otherwise the FlashInfer kernels (top_k_renorm_prob, top_p_renorm_prob, min_p_sampling_from_probs, or the joint top-k/top-p sampler) run when --sampling-backend flashinfer is active, and top_k_top_p_min_p_sampling_from_probs_torch runs for the PyTorch backend. Per-request seeds and deterministic-inference modes are supported on the PyTorch path.
    4. Logprobs. When requested, log-probabilities (and top-k alternatives or specific token IDs) are computed from the processed distribution, or from the raw logits when SGLANG_RETURN_ORIGINAL_LOGPROB is set.
    5. Rank agreement. With grammars or SYNC_TOKEN_IDS_ACROSS_TP, the chosen IDs are synchronized across tensor-parallel ranks.

    The built-in backends (flashinfer, pytorch, ascend, intel_xpu) all use the same Sampler class with different kernel paths. Plugins can add a custom sampler class under a new backend name with register_sampler_backend; create_sampler checks those registrations first.

    Back to text

    DetokenizerManager and streaming

    Token IDs leave the GPU process as numbers. Turning them into correct, incremental text is subtle enough to deserve its own process.

    Why a separate detokenizer process?

    Detokenizing is pure CPU work over every active request, every step. Doing it in the scheduler would add latency to the critical loop; doing it in the main process would compete with HTTP handling and tokenization. So DetokenizerManager runs alone: its event_loop blocks on the PULL socket from the scheduler, dispatches by message type, and pushes the result to the tokenizer socket. With --detokenizer-worker-num above one, several detokenizer workers sit behind a router process.

    Incremental detokenization, step by step

    Decoding one token at a time is wrong for most tokenizers. SentencePiece-style vocabularies encode a leading space inside the token, byte-level BPE can split one UTF-8 character across two tokens, and some tokenizers merge pieces differently in context. The fix is to decode a small sliding window and emit only the difference. DetokenizeState keeps three offsets into decode_ids: 

    decode_ids:  [ prompt tail (5) | already emitted ... | new ids ]
              ^ surr_offset      ^ read_offset             ^ end
surr_text = decode(decode_ids[surr_offset : read_offset])
read_text = decode(decode_ids[surr_offset : end])
new_text  = read_text[len(surr_text):]

    The state is seeded from a DetokenizeHeader that the scheduler sends only on a request's first output. It contains the last PROMPT_TAIL_LEN (5) prompt tokens as context, plus the request's skip_special_tokens, spaces_between_special_tokens, and no_stop_trim flags. For every incoming row, _decode_batch_token_id_output gathers the two windows for all requests and decodes them with two batch_decode calls, grouped by flag combination (_grouped_batch_decode). Then step decides what to emit:

    • Clean text: commit it, slide surr_offset to the old read_offset and read_offset to the end, and emit it.
    • Text ending in U+FFFD (an incomplete UTF-8 sequence): emit only the printable prefix, remember how much was sent, and do not advance the offsets, so the next token completes the character.
    • Finished: materialize the full text, trim a matched stop string or stop token unless no_stop_trim (trim_matched_stop), emit the remaining tail, and release the state.

    States live in a DetokenizeStateTable capped at SGLANG_DETOKENIZER_MAX_STATES (65,536 by default); past capacity the oldest state is dropped and its later rows are logged as lost text. For tokenizers where batch decoding misbehaves, --disable-tokenizer-batch-decode decodes row by row.

    Back in the TokenizerManager

    handle_loop receives every BatchStrOutput. _handle_batch_output looks up each rid's ReqState, builds meta_info (prompt, completion, cached, and reasoning token counts, finish reason, optional logprobs and timings), appends the text delta to the state's text buffer, and puts an output dictionary on out_list. By default the dictionary's text is the full text so far (filled lazily to avoid quadratic string building); with --incremental-streaming-output it is only the delta. Wake-ups are batched every --batch-notify-size requests (default 16) to limit event-loop churn. On a finished row the state is deleted from rid_to_state.

    The request coroutine sleeping in _stream_one_response wakes, drains out_list in one go (several steps may have queued up while it slept; with incremental output they are coalesced so no token is lost), and yields. It also uses a timeout on the wait to poll request.is_disconnected() and abort abandoned requests.

    Server-sent events

    For the OpenAI chat route, _generate_chat_stream consumes those chunks, computes the per-choice delta against the stream offset it remembers, passes it through the reasoning parser and tool-call parser when configured, and yields data: {chat.completion.chunk} lines, finishing with an optional usage chunk and data: [DONE]. The native /generate route streams its own JSON chunks the same way. Two knobs trade smoothness for throughput: --stream-interval (default 1 token; larger values send fewer, bigger chunks and cut per-token overhead in all three processes) and the per-request stream_interval sampling parameter. Streaming output is also held back for a step when the text so far ends with what could be the beginning of a stop string, so a client never sees a partial stop sequence that is later trimmed.

    Subsystem · Structured outputs

    Constrained decoding: grammars become vocabulary masks

    How SGLang guarantees that a reply matches a JSON schema, regex, EBNF grammar, or structural tag by hiding every token the grammar forbids before the sampler sees the logits.

    A language model never "writes JSON". At every step it scores every entry in its vocabulary and the sampler picks one. Constrained decoding adds one rule: before sampling, any token that would take the output outside the allowed language gets its logit forced to negative infinity, so it can never be chosen. Because the check happens on every step, the finished text is valid by construction; there is no "generate, validate, retry" loop. The hard engineering problems are speed (a vocabulary can have 150k+ entries and the mask must be rebuilt for every request on every step) and bookkeeping (the grammar state must advance, and sometimes rewind, in lockstep with the tokens that were actually accepted).

    Grammar backends present at this commit

    The choice list lives in GRAMMAR_BACKEND_CHOICES and the factory is create_grammar_backend. When --grammar-backend is left unset, the resolution hook handle_grammar_backend fills in xgrammar.

    • xgrammar (default) — XGrammarGrammarBackend compiles JSON schema, regex, EBNF, and structural tags; each request gets an XGrammarGrammar wrapping a matcher that can roll back up to 200 tokens. If the tokenizer is unsupported and strict thinking is off, the factory logs a warning and falls back to no grammar backend.
    • outlines — OutlinesGrammarBackend handles JSON (validated, then converted to a regex) and regex; its EBNF and structural-tag dispatchers just delegate to the base class, which logs them as unsupported.
    • llguidance — GuidanceBackend supports JSON, regex, EBNF, and legacy-format structural tags, with batched bitmask filling.
    • none — no backend; requests that carry a grammar are aborted with an explanatory error, and --enable-strict-thinking refuses to start.
    • Reasoning wrapper — when a reasoning parser is configured and the model exposes think-end token ids, the chosen backend is wrapped by ReasonerGrammarBackend, which leaves the thinking section unconstrained and switches the grammar on once the model leaves its reasoning block.
    • Plugins — register_grammar_backend lets out-of-tree code register a custom backend; registered names are checked before the built-ins.

    The vocab-mask flow, step by step

    1. Admission. When a request with json_schema, regex, ebnf, or structural_tag reaches the scheduler, GrammarManager.process_req_with_grammar builds a cache key such as ("json", schema_text) and asks the backend for a cached grammar or a future.
    2. Compilation off the hot loop. BaseGrammarBackend owns a thread pool; a cache miss submits compilation there and parks the request in a grammar_queue. A cache hit returns a fresh copy of the compiled matcher immediately.
    3. Rank agreement. get_ready_grammar_requests polls the futures, then agrees across tensor/data-parallel ranks (ready means ready everywhere, failed means failed anywhere) and forwards the decision down pipeline stages, so every rank admits the same requests.
    4. Mask build each step. SamplingBatchInfo.update_regex_vocab_mask allocates one mask row per request in the batch (XGrammar uses a pinned, packed bitmask initialised to "all allowed"), fills only the rows that have a live grammar, and copies it to the GPU without blocking.
    5. Apply. apply_logits_bias runs penalties first, then the GrammarMask, then user logit_bias. On CUDA, XGrammar applies the bitmask in place with a Triton kernel (a CUDA kernel on ROCm).
    6. Advance or rewind. After sampling, accept_token moves the matcher forward. rollback(k) matters for speculative decoding: traverse_tree walks the draft tree depth-first, accepting a draft token, filling that node's mask row, descending, and then rolling the token back, so every tree node gets a mask that matches its own path.

    Jump-forward decoding: present as an interface, dormant in the runtime

    LMSYS's compressed finite-state-machine work popularised "jump-forward": when the grammar allows exactly one continuation (for example the literal "name": " inside a fixed schema), append the whole string at once instead of decoding it token by token. At this commit the hook still exists on the grammar interface — try_jump_forward, jump_forward_str_state, and jump_and_retokenize — and each backend implements it (XGrammar's try_jump_forward asks its matcher for find_jump_forward_string; Outlines ships OutlinesJumpForwardMap, although its backend currently constructs grammars with no map attached). However, a search of python/sglang/srt finds no caller outside the constrained/ package, so treat jump-forward as a dormant capability rather than something the scheduler performs today.

    Beginner pitfalls. The first request with a new schema pays compilation latency (later ones hit the cache). An invalid grammar is cached as invalid and aborts every request that uses it. JSON whitespace freedom is tunable with --constrained-json-whitespace-pattern (Outlines and llguidance) and --constrained-json-disable-any-whitespace (XGrammar and llguidance).

    Subsystem · Speculative decoding

    Speculative decoding: draft cheaply, verify in one pass

    Which speculative algorithms exist in python/sglang/srt/speculative, how an EAGLE draft tree is built and verified with a tree attention mask, and how the scheduler hosts a draft worker.

    Decoding one token at a time is memory-bandwidth bound: each step reads all model weights to produce a single token per request. Speculative decoding spends a little extra compute to break that pattern. A cheap drafter guesses several future tokens; the full target model then scores all of them in one forward pass, much like a short prefill. Every guess the target agrees with is kept for free, and the first disagreement is replaced by the target's own token, so quality is unchanged while the number of expensive forward passes per output token drops.

    Algorithms in the code

    The built-ins are members of SpeculativeAlgorithm, and create_worker maps each to a worker class:

    EAGLE drafting builds a tree, verification walks it

    1. Draft. EagleDraftWorker.draft runs --speculative-num-steps small forward passes. At each step every frontier node keeps its --speculative-eagle-topk best next tokens, so the candidate set grows like a tree.
    2. Prune. organize_draft_results keeps the num_draft_tokens − 1 highest-scoring nodes (scores are cumulative draft probabilities) and remembers each node's parent.
    3. Build the tree mask. build_tree_kernel_efficient prepends the last verified ("bonus") token, then produces three things: a boolean attention mask in which each draft token may see the whole prompt plus only its own ancestors; position ids equal to prompt length plus tree depth (siblings share a position); and retrieve_index/next_token/next_sibling arrays used to walk the tree after verification. GPU kernels receive a full mask; the CPU backend gets a compact query-by-query mask.
    4. Verify. EAGLEWorkerV2.verify runs the target once over all draft tokens using that mask (carried in EagleVerifyInput). The accepted path is the longest root-to-leaf chain whose tokens match what the target would sample — greedily, or with rejection sampling when --speculative-use-rejection-sampling is set. The KV of the accepted chain (plus the bonus token) is then copied into the request's real cache slots by move_accept_tokens_to_target_kvcache; entries written for rejected branches are not kept.
    5. Extend the drafter. The accepted tokens' hidden states seed the next draft round (EagleDraftInput); drafting and draft-extend each have CUDA-graph runners such as EAGLEDraftCudaGraphRunner.

    How the scheduler hosts speculation

    Scheduler.maybe_init_draft_worker asks the algorithm for its worker class and wraps the target worker. The comments in create_worker note that the "V2" workers drive both the overlap and the non-overlap event loops (with overlap disabled the scheduler simply calls them synchronously). From the scheduler's perspective a speculative decode step is still "one batch in, a variable number of tokens per request out"; the per-request count shows up in the sglang:spec_accept_length and sglang:spec_accept_rate metrics. Tuning is mostly three numbers: --speculative-num-steps (tree depth), --speculative-eagle-topk (branching), and --speculative-num-draft-tokens (how many nodes the target verifies). Bigger trees raise the chance of a long accepted path but make each verify pass heavier, which hurts most at large batch sizes where the GPU is already busy.

    Subsystem · Distributed execution

    Parallelism: TP, PP, DP, DP-attention, and expert parallelism

    The ways SGLang splits one model, or many copies of it, across GPUs, with the exact flags and the code that builds each process group.

    A beginner-friendly way to think about parallelism is to ask what is being split. Tensor parallelism splits each weight matrix; pipeline parallelism splits the stack of layers; data parallelism copies the whole model and splits the requests; expert parallelism splits the experts of a mixture-of-experts (MoE) layer. SGLang supports all four and can combine them. Process groups are created by initialize_model_parallel, each wrapped in a GroupCoordinator.

    Tensor parallelism (TP)

    --tp-size N (alias --tensor-parallel-size). Attention heads and MLP columns are sharded across N GPUs; partial results are combined with all-reduce. One scheduler process runs per TP rank and all ranks execute the same batch. Best inside one node with fast NVLink.

    Pipeline parallelism (PP)

    --pp-size N. Layers are divided into N stages and micro-batches flow through them, driven by event_loop_pp. Knobs: --pp-max-micro-batch-size, --pp-async-batch-depth, and --enable-dynamic-chunking to keep chunk times even across stages. Useful across nodes where all-reduce would be slow.

    Data parallelism (DP)

    --dp-size N starts N full replicas behind a DataParallelController that dispatches requests using LoadBalanceMethod (auto, round_robin, follow_bootstrap_room, total_requests, total_tokens). Each replica keeps its own radix tree, which is why cache-aware placement is the router's job.

    DP attention

    --attn-dp-size N (the older --dp-size N --enable-dp-attention spelling is registered as deprecated in server_args.py). Attention runs data-parallel inside the TP group — each attention-DP rank has its own scheduler, batch, and KV cache — while the FFN/MoE stays tensor- or expert-parallel. Tokens are exchanged with helpers such as dp_gather_partial and dp_scatter.

    Expert parallelism (EP)

    --ep-size N places different experts on different GPUs. Tokens travel to their experts and back through an all-to-all chosen by --moe-a2a-backend: none, deepep, deepep_v2, mooncake, nixl, mori, pplx, flashinfer, flashinfer_megamoe, megamoe, ascend_fuseep, ascend_ops. DeepEP has normal and low_latency modes (--deepep-mode auto picks per phase), implemented by DeepEPDispatcher.

    Load balancing and overlap for MoE

    Hot experts overload some GPUs. --enable-eplb turns on the EPLBManager, which periodically rebalances expert placement, optionally with --ep-num-redundant-experts replicas. --enable-two-batch-overlap splits a batch into two micro-batches so one computes while the other communicates (TboForwardBatchPreparer).

    Why DP attention exists

    Models with multi-head latent attention (MLA), such as the DeepSeek family, compress keys and values into a single shared latent. Tensor parallelism splits attention by heads, but a single latent cannot be split that way, so every TP rank would hold a full copy of the KV cache and memory would be wasted N times. DP attention gives each rank a different set of requests instead, so the KV cache is partitioned by request, and only the MoE layers — where the weights are huge — are shared via EP. The SGLang documentation's DPA diagram (embedded in Reference diagrams) shows four attention ranks, some prefilling, some decoding, some idle, all feeding one dispatch/combine all-to-all around the expert sub-groups.

    Other axes worth knowing

    • Context parallelism — --attn-cp-size splits long prefills along the sequence; --dcp-size (decode context parallelism) shards decode-time KV.
    • MoE runners — --moe-runner-backend selects the grouped-GEMM implementation (Triton, DeepGEMM, FlashInfer variants, CUTLASS, Marlin, AITER, and others listed in MOE_RUNNER_BACKEND_CHOICES).
    • Multi-node — --nnodes, --node-rank, and --dist-init-addr stitch several machines into one engine.

    Subsystem · Disaggregated serving

    Prefill/decode disaggregation and KV transfer backends

    Running prefill and decode on separate engines, how a request is handed from one to the other, and which transfer backends exist under python/sglang/srt/disaggregation.

    Prefill (processing the prompt) is compute-heavy and bursty; decode (emitting tokens one by one) is memory-bandwidth-heavy and steady. On one GPU they interfere: a long prefill stalls every decoding request in the same batch, which shows up as a spike in inter-token latency. PD disaggregation runs two kinds of engine — started with --disaggregation-mode prefill and --disaggregation-mode decode (DisaggregationMode) — so each pool can be sized and tuned for its own phase. The price is that the KV cache produced by prefill must be shipped to the decode engine over the network, ideally with RDMA so it does not stall either side.

    Transfer backends

    TransferBackend and get_kv_class map each name to a manager, sender, receiver, and bootstrap server built on the abstract classes in base/conn.py:

    • mooncake (default) — MooncakeKVManager, using the Mooncake transfer engine.
    • mooncake_tcp — a CLI choice only; a resolution hook rewrites it to mooncake with the TCP transport forced (pd_disaggregation_hook.py).
    • nixl — NixlKVManager, using the NIXL transfer library.
    • mori — MoriKVManager, built on the mori.io transfer API.
    • ascend — AscendKVManager, a subclass of the Mooncake manager for Ascend NPUs.
    • fake — FakeKVManager for testing; it registers no bootstrap server.

    The hand-off, step by step

    1. Routing. A router (see Router) picks one prefill engine and one decode engine and sends the request to both, tagged with the prefill engine's bootstrap address (port --disaggregation-bootstrap-port, default 8998).
    2. Decode reserves memory. On the decode engine, DecodePreallocQueue creates a receiver, handshakes, and pre-allocates KV slots once there is room. --disaggregation-decode-allocation-policy chooses between reserving early or only after prefill completes.
    3. Prefill waits for the handshake. PrefillBootstrapQueue holds the request until its sender reports that bootstrap is done, then moves it to the normal waiting queue.
    4. Prefill runs and streams KV. The prefill event loops (event_loop_normal_disagg_prefill and its overlap twin) run the forward pass; send_kv_chunk hands finished KV pages to the sender — including for chunked prefills — and an in-flight queue polls until the transfer finishes.
    5. Decode picks it up. DecodeTransferQueue polls receivers; completed requests become a pre-built batch that skips the prefill forward, only filling metadata, before merging into the running decode batch (event_loop_normal_disagg_decode).

    Useful extras

    • --disaggregation-enable-kv-checksum verifies per-request KV page checksums on the decode side (set it on both roles).
    • --disaggregation-decode-enable-radix-cache lets a decode engine keep a prefix cache so repeated prefixes need not be re-sent.
    • --disaggregation-ib-device pins InfiniBand NICs (Mooncake and NIXL UCX); --num-reserved-decode-tokens reserves decode headroom per admitted request.
    • A related split separates the multimodal encoder from the language model: --encoder-only and --language-only, with the encoder side under disaggregation/encoder/.
    • /pd_role_switch is an HTTP route for switching an engine's PD role at runtime (see API surface).

    Subsystem · Memory hierarchy

    HiCache: GPU, host memory, and storage tiers for the radix cache

    How SGLang extends prefix caching beyond GPU memory: a host-memory tier, optional external storage, and the controller that moves KV between them.

    RadixAttention only helps while the shared prefix is still in GPU memory. With many users, long system prompts, and multi-turn sessions, the working set quickly outgrows HBM and the oldest prefixes are evicted — then the next turn of that conversation pays full prefill again. HiCache treats GPU memory as level 1, pinned host DRAM as level 2, and an optional external store as level 3. The radix tree tracks local device and host residency. For storage, the controller queries the configured backend for available pages. A local file path only enables cross-node reuse if the underlying filesystem is shared.

    The moving parts

    • Tree. The default prefix cache is UnifiedRadixCache; when HiCache is on, create_unified_radix_cache calls its init_hicache.
    • Controller. HiCacheController owns the copy streams and background threads: write (device → host), load (host → device), prefetch (storage → host), and write_storage (host → storage). A per-layer done counter lets the forward pass start on layer 0 while later layers are still loading.
    • Host pools. HostKVCache and its MHA/MLA subclasses hold pinned host buffers sized by --hicache-ratio (host/device ratio; defaults to 2.0 in cache mode) or --hicache-size in GB.
    • Storage backends. StorageBackendFactory registers file, sim, nixl, mooncake, npu_memcache, hf3fs, aibrix, eic, simm, mori, shm, tensorcast, and seaweedfs; dynamic loads a user class named in --hicache-storage-backend-extra-config. All implement HiCacheStorage.

    Follow a 4,160-token request through L1, L2 and optional L3, including a partial or late prefetch.

    Policies you can choose

    • Write policy (--hicache-write-policy): write_through (default) backs a node up to host once it has been hit once; write_through_selective waits for a second hit; write_back copies only when the node is about to be evicted from the GPU. The thresholds are set in init_hicache.
    • I/O path (--hicache-io-backend): direct, kernel (default), or kernel_ascend; and layout (--hicache-mem-layout): layer_first, page_first (default), page_first_direct, page_first_kv_split, page_head, page_unified.
    • Prefetch stop rule (--hicache-storage-prefetch-policy): best_effort, wait_complete, or timeout (default) — how long a waiting request may hold off scheduling while its prefix streams in from storage.
    • Host mode (--hicache-host-memory-mode): cache keeps host memory as a real tier; buffer_only treats it as a staging buffer in front of storage.

    Storage can be attached, inspected, and detached at runtime through PUT, GET, and DELETE on /hicache/storage-backend. Two third-party integrations are also selectable: --enable-lmcache (an LMCache-backed unified radix cache) and --enable-flexkv.

    Subsystem · Adapters

    Multi-LoRA serving

    Serving one base model with many LoRA adapters in the same batch, with GPU slots, CPU residency, eviction, and dynamic load/unload.

    A LoRA adapter adds a low-rank update B·A to selected weight matrices, so a fine-tuned variant costs megabytes instead of gigabytes. Serving many of them on one base model is attractive, but a batch may contain requests for ten different adapters plus some for the plain base model. SGLang keeps the base weights shared and applies each request's adapter with segmented (grouped) matrix-multiply kernels, so mixed batches still run as one forward pass.

    • LoRAManager loads adapters (load_lora_adapter) and, each batch, prepare_lora_batch builds the per-segment adapter indices the kernels need.
    • LoRAMemoryPool owns GPU adapter slots. --max-loras-per-batch (default 8) counts distinct adapter ids including "no adapter"; --max-loaded-loras caps CPU residency; --lora-eviction-policy is lru (default) or fifo.
    • Kernel backends are registered in register_lora_backend: triton, csgmv (chunked SGMV, the CLI default), triton_v2, ascend, torch_native, plus an internal uno_cublas that is not a CLI choice.
    • Adapters can be added or removed while serving via /load_lora_adapter, /load_lora_adapter_from_tensors, and /unload_lora_adapter (or the matching Engine methods); names are tracked by LoRARegistry. --enable-lora-overlap-loading overlaps host-to-device adapter copies with compute.
    • Prefix caching stays correct across adapters because a RadixKey carries an extra_key namespace (and an optional cache_salt) in addition to token ids: identical tokens under different adapters produce different KV and must not share a tree path.

    Subsystem · Vision, video, audio

    Multimodal inputs

    How images, video, and audio become token positions that the scheduler, radix cache, and model can treat like text.

    1. Per-model processors. Each family has a processor under multimodal/processors/ (Qwen-VL, LLaVA, Gemma 3/4, InternVL, Kimi-VL, DeepSeek-VL2, Phi-4-MM, Pixtral, MiniCPM, Whisper, and many more), all derived from BaseMultimodalProcessor. They run in the tokenizer process, load media, and run the Hugging Face preprocessing. The Modality enum has IMAGE, VIDEO, and AUDIO; inputs may also arrive as processor output or precomputed embeddings.
    2. Content-addressed placeholders. Each MultimodalDataItem is hashed and set_hash derives "pad values" from that hash. The placeholder positions in input_ids are filled with those values, so two requests that send the same image produce identical token sequences and can share radix-cache prefixes, while different images never collide.
    3. Embedding at forward time. general_mm_embed_routine calls embed_mm_inputs, which obtains encoder embeddings for the batch's media items and scatters them into the placeholder positions. Embeddings are looked up by item hash in a MultiModalStaticCache (created by init_mm_embedding_cache), which also lets a chunked prefill reuse an image's embedding across chunks instead of re-encoding it.
    4. Knobs. --enable-multimodal and --mm-attention-backend (the vision tower's attention kernel). Several encoders have their own CUDA-graph runners (for example multimodal/vit_cuda_graph_runner.py), and encoder/LLM disaggregation is available through --encoder-only/--language-only.

    Where they run

    • In OpenAIServingChat the reasoning parser splits text first (_process_reasoning_stream), and the remaining content goes to the tool parser (_process_tool_calls). Streaming parsers buffer partial markers so a half-emitted tag is never shown to the client as plain text.
    • For tool_choice="required" or a named function, the parser can supply a constraint (get_structure_constraint), typically a structural tag or JSON schema, which the grammar backend then enforces — the bridge between this section and constrained decoding.
    • --enable-strict-thinking uses the grammar backend's token filter to block model-specific forbidden tokens (such as tool-call markers) while the model is still thinking.
    • Both parsers are also exposed directly as POST /parse_function_call and POST /separate_reasoning.

    Subsystem · Fleet routing

    Router and model gateway (Rust)

    Two Rust projects at the repository root decide which engine gets each request; this is where cache-aware load balancing lives.

    Inside one engine, RadixAttention reuses prefixes. Across many engines it only helps if requests that share a prefix land on the same engine — and if no engine is overloaded in the process. That balancing act belongs to a router in front of the fleet. At this commit the repository contains two Rust code bases (both verified with git ls-files):

    • sgl-router/ — described in its README as a slim, KV-aware router for one model. Engines publish load reports and KV events; the router renders and tokenizes the request, chooses a bucket (for example short- vs long-context pools), lets that group's policy pick an engine that passes admission limits, and retries elsewhere if dispatch fails before any response. Routers keep no shared state, so you scale them by adding replicas.
    • sgl-model-gateway/ — a broader gateway (README) with a worker-registry control plane, HTTP/PD/gRPC data planes, an OpenAI-compatible proxy to external providers, MCP tool integration, conversation storage, retries, circuit breakers, and rate limiting.

    Observability

    The offline Engine API

    Using the full runtime from Python without an HTTP server — for batch jobs, evaluation, and RL rollouts.

    sglang.Engine (a lazy import of entrypoints/engine.py::Engine) is the same runtime the server uses, minus FastAPI. Its docstring spells out the layout: the TokenizerManager lives in your Python process, while the scheduler(s) and the DetokenizerManager run as subprocesses connected by ZeroMQ (_launch_scheduler_processes, _launch_detokenizer_subprocesses). The constructor takes the same keyword arguments as ServerArgs, so every flag on this page has a Python spelling (--tp-size 2 becomes tp_size=2). 

    import sglang as sgl

engine = sgl.Engine(model_path="Qwen/Qwen3-8B", mem_fraction_static=0.85)

prompts = ["Explain KV caching in one sentence.", "Name three prime numbers."]
params = {"temperature": 0.0, "max_new_tokens": 64}

for out in engine.generate(prompts, params):        # one dict per prompt
    print(out["text"], out["meta_info"]["completion_tokens"])

shown = 0
for chunk in engine.generate("Count to five:", params, stream=True):
    text = chunk["text"]          # cumulative unless --incremental-streaming-output
    print(text[shown:], end="", flush=True)
    shown = len(text)

engine.shutdown()
    • generate / async_generate accept a prompt or batch, input_ids, image/audio/video data, logprob options, lora_path, a custom logit processor, and stream.

    Because there is no network hop or JSON encoding per token, the offline engine is the simplest way to measure raw throughput and the natural choice inside training frameworks that need to generate rollouts and then push new weights into the same process group.

    Interface · Programs

    The frontend language: gen, select, fork

    SGLang's original idea — LLM programs written as Python — and the specific ways the interpreter arranges requests so RadixAttention can reuse their prefixes.

    "SGLang" began as a structured generation language: a small embedded DSL in python/sglang/lang for programs that interleave fixed text, model calls, choices, and parallel branches. A decorated function receives a state s; appending strings adds prompt text, sgl.gen asks the model to continue, and results are read back by name. The interpreter runs on the client side and talks to a backend such as RuntimeEndpoint (an SGLang server) or API backends (OpenAI, Anthropic, LiteLLM, Vertex AI). 

    import sglang as sgl

@sgl.function
def review(s, essay):
    s += sgl.system("You are a strict writing tutor.")
    s += sgl.user("Essay:\n" + essay)
    forks = s.fork(2)                                   # two branches share everything above
    forks[0] += sgl.assistant("Clarity: " + sgl.gen("clarity", max_tokens=48))
    forks[1] += sgl.assistant("Evidence: " + sgl.gen("evidence", max_tokens=48))
    forks.join()
    s += sgl.user("Overall grade?")
    s += sgl.assistant(sgl.select("grade", choices=["A", "B", "C"]))

sgl.set_default_backend(sgl.RuntimeEndpoint("http://localhost:30000"))
state = review.run(essay="...")
print(state["grade"])

    The primitives

    • function wraps a Python function into an SglFunction with run and run_batch.
    • gen creates an SglGen with sampling options and, optionally, regex or json_schema (enforced server-side by the grammar backend). Passing choices turns it into a select.
    • select creates an SglSelect; the decision rule is pluggable (TokenLengthNormalized by default, plus greedy-token and unconditional-likelihood variants).
    • fork clones the executor state into N branches that run concurrently; join merges them back.

    How the interpreter feeds RadixAttention

    1. Fork commits the shared prefix first. When forking into more than one branch with non-empty text, StreamExecutor.fork submits an SglCommitLazy; the endpoint's commit_lazy_operations sends that text to /generate with max_new_tokens: 0. The server prefills it once and inserts it into the radix tree, so every branch that follows starts with a cache hit instead of N identical prefills racing each other.
    2. Select scores choices on top of a cached prefix. RuntimeEndpoint.select first sends the current text with zero new tokens (caching it), then sends one request per choice — prefix + choice — asking only for prompt logprobs. Each of those requests reuses the cached prefix and computes just the few choice tokens.
    3. Batches pre-warm their common prefix. run_program_batch calls cache_program, which traces the program with placeholder arguments (extract_prefix_by_tracing) to find the constant text before the first argument-dependent part, and — if it is longer than 64 characters — caches it via cache_prefix before launching the batch.

    None of this needs a special server mode: the frontend simply shapes ordinary /generate traffic so the server's prefix cache does the heavy lifting. It does require the radix cache to be on, which is the default.

    RadixAttention prefix cache

    What: A radix tree keyed by token ids whose nodes point at KV-cache slots, so any request whose prompt starts with cached tokens skips recomputing them.

    Why: System prompts, few-shot examples, multi-turn history, and agent loops repeat prefixes constantly; reuse cuts prefill compute and time-to-first-token.

    How: Tree nodes hold a key segment, a KV-index tensor, a lock count, and access times. Matching walks children and splits nodes on partial matches; finished and in-progress requests insert their KV; only unlocked leaves are evicted. The default cache is UnifiedRadixCache, which tracks full, sliding-window, and Mamba-state components; the classic RadixCache remains (and also powers simulated matching in the scheduler). Eviction policies: lru, lfu, slru, priority, tlru.

    mem_cache/radix_cache.py::RadixCache · unified_radix_cache.py::UnifiedRadixCache · registry.py::default_radix_cache_factory --disable-radix-cache --radix-eviction-policy --page-size

    Caveats: Reuse is exact-token: a single different token early in the prompt ends the match. With page sizes above 1, only whole pages are shared.

    Continuous batching

    What: Requests join and leave the running batch at every iteration instead of waiting for a whole batch to finish.

    Why: Output lengths vary wildly; static batches leave GPUs idle while the longest request finishes.

    How: Each loop iteration, get_next_batch_to_run first tries to form a prefill ("extend") batch from the waiting queue within token and memory budgets; otherwise it advances the running decode batch via update_running_batch, which can retract requests back to the queue when KV memory runs out.

    scheduler.py::get_next_batch_to_run · update_running_batch · schedule_batch.py::ScheduleBatch --max-running-requests --max-prefill-tokens --schedule-conservativeness

    Caveats: Retraction wastes work; frequent retractions mean admission is too optimistic (raise conservativeness or lower concurrency).

    Overlap ("zero-overhead") scheduler

    What: CPU scheduling for batch N+1 runs while the GPU is still computing batch N.

    Why: Python scheduling, tree matching, and result processing can take a meaningful fraction of a small decode step; hiding it keeps the GPU busy.

    How: event_loop_overlap launches the current batch, pushes it onto a result queue, and only then processes the previous batch's results. Future token ids stand in for not-yet-sampled tokens through FutureMap. is_disable_overlap_for_batch falls back to synchronous processing in specific cases: consecutive prefills when SGLANG_DISABLE_CONSECUTIVE_PREFILL_OVERLAP is set (to protect TTFT), and some speculative-decoding batches whose grammar state must advance first.

    scheduler.py::event_loop_overlap · overlap_utils.py::FutureMap · event_loop_normal --disable-overlap-schedule

    Caveats: Anything that needs the last token before preparing the next step (grammar masks in particular) must wait for it; that is why sampling for the current batch is launched only after the previous batch's results have been processed.

    Chunked prefill

    What: Long prompts are split into chunks processed over several iterations.

    Why: One giant prefill would block decoding requests and spike memory; chunks bound both.

    How: PrefillAdder fills a token budget; a request that does not fit is truncated to the remaining budget and remembered as the chunked request, then resumed next iteration via add_chunked_req. With mixed chunks enabled, decode tokens ride in the same batch.

    schedule_policy.py::PrefillAdder · add_chunked_req --chunked-prefill-size --enable-mixed-chunk

    Caveats: -1 disables chunking. Smaller chunks protect inter-token latency but lengthen long-prompt TTFT.

    Schedule policies

    What: The order in which waiting requests are admitted.

    Why: Admitting requests that share a cached prefix together raises cache hits; other orders trade fairness or latency.

    How: SchedulePolicy.calc_priority sorts the waiting queue. Cache-aware: lpm (longest prefix match), dfs-weight, hrrn (response-ratio aging), shortest-prefill-first. Cache-agnostic: fcfs (default), lof (longest output first), random, routing-key. lpm/hrrn fall back to FCFS when the queue is very long, and cache-aware policies fall back to FCFS when the radix cache is disabled.

    schedule_policy.py::CacheAwarePolicy · CacheAgnosticPolicy · calc_priority --schedule-policy --enable-priority-scheduling

    Caveats: The CLI choice list also includes priority, but neither policy enum defines it at this commit; per-request priorities come from --enable-priority-scheduling layered on FCFS or LOF.

    CUDA graphs

    What: Pre-recorded GPU launch sequences replayed for fixed batch sizes.

    Why: Decode steps launch hundreds of small kernels; replaying a graph removes per-kernel CPU launch overhead.

    How: Separate decode and prefill runners capture graphs for a list of batch sizes (padded up at run time). Each phase can use a full, breakable, or disabled backend, configured per phase or via --cuda-graph-config JSON.

    Caveats: There is no single --cuda-graph-max-bs at this commit (it is per phase); --disable-cuda-graph survives only as a deprecated alias. Graphs cost memory, so raising the max batch may require lowering --mem-fraction-static.

    torch.compile

    What: PyTorch's graph compiler fuses and specialises model code.

    Why: Helps small models at small batch sizes, where Python and unfused elementwise ops dominate.

    How: When enabled, the CUDA-graph capture list is split: batch sizes up to --torch-compile-max-bs (default 32) are compiled before capture; larger ones are captured eagerly. A compilation/ package provides the compile entry points and piecewise backends.

    Speculative decoding

    What: A drafter proposes several tokens; the target verifies them in one pass.

    Why: Converts memory-bound single-token steps into fewer, larger verify steps, cutting per-token latency.

    How: Built-ins EAGLE, EAGLE3, NEXTN (alias of EAGLE), STANDALONE, NGRAM, FROZEN_KV_MTP, DFLASH, DSPARK, UNO, plus plugins. EAGLE-style workers build a draft tree and verify it with a tree attention mask (see Speculative decoding).

    Structured outputs

    What: Guarantee output matches a JSON schema, regex, EBNF grammar, or structural tag.

    Why: Tool calls and data extraction need machine-parseable output without retries.

    How: Grammars compile asynchronously and are cached; each step fills a per-request vocabulary bitmask applied to the logits before sampling. Backends: xgrammar (default), outlines, llguidance, none, optionally wrapped for reasoning models.

    Caveats: First use of a schema pays compile time; jump-forward hooks exist but no runtime caller was found at this commit.

    What: Many LoRA adapters served on one base model, mixed in the same batch.

    Why: Per-customer or per-task fine-tunes without a GPU per model.

    How: A GPU slot pool, CPU residency cap, LRU/FIFO eviction, segmented-GEMM backends (csgmv default, triton, triton_v2, ascend, torch_native), dynamic load/unload over HTTP.

    Multimodal inputs

    What: Images, video, and audio alongside text for vision-language and audio models.

    Why: Modern assistants are multimodal; prefix caching should still work for repeated media.

    How: Per-model processors in the tokenizer process; content-hash pad tokens in input_ids; encoder embeddings scattered into those positions at forward time, with an embedding cache keyed by hash.

    Tensor parallelism

    What: Each layer's weights are split across GPUs.

    Why: Fits models larger than one GPU and cuts per-token latency.

    How: Column/row-parallel linear layers with all-reduce; one scheduler process per rank executing identical batches; groups built by initialize_model_parallel.

    parallel_state.py::initialize_model_parallel · get_tp_group --tp-size

    Caveats: All-reduce cost grows with TP size and is painful across nodes; for MLA models, TP alone duplicates the KV cache (see DP attention).

    Pipeline parallelism

    What: Layers split into sequential stages on different GPUs or nodes.

    Why: Only activations cross stage boundaries, so it tolerates slower links than TP.

    How: A dedicated PP event loop keeps several micro-batches in flight; optional dynamic chunk sizing balances stage times for long prefills.

    scheduler_pp_mixin.py::event_loop_pp · get_pp_group --pp-size --pp-max-micro-batch-size

    Caveats: Pipeline bubbles waste time when there are too few micro-batches; grammar readiness and other decisions must be propagated stage to stage.

    DP attention

    What: Data-parallel attention inside a tensor-parallel group.

    Why: Avoids replicating MLA's single-latent KV cache on every TP rank, multiplying effective KV capacity.

    How: Each attention-DP rank runs its own scheduler and batch; hidden states are gathered/scattered around the shared MLP/MoE layers.

    dp_attention.py::initialize_dp_attention · dp_gather_partial --attn-dp-size --enable-dp-attention (deprecated)

    Caveats: Ranks must stay in lockstep for the shared layers, so idle ranks still run padded steps; the prefill delayer and DP-aware routing help keep ranks balanced.

    Expert parallelism and MoE

    What: Experts of MoE layers distributed across GPUs with token all-to-all.

    Why: Huge MoE models (hundreds of experts) need many GPUs' memory and bandwidth, with each token touching only a few experts.

    How: Pluggable all-to-all backends (DeepEP v1/v2, Mooncake, NIXL, MORI, PPLX, FlashInfer, MegaMoE, Ascend), grouped-GEMM runners, EPLB rebalancing with redundant experts, and two-batch overlap.

    Caveats: All-to-all latency dominates at small batch sizes; DeepEP's low-latency mode exists for decode, normal mode for prefill.

    PD disaggregation

    What: Separate prefill and decode engines with KV transfer between them.

    Why: Removes prefill/decode interference and lets each pool use its own parallelism and batch sizes.

    How: Bootstrap handshake, decode-side KV preallocation, chunked KV push, polling queues. Backends: mooncake (default), mooncake_tcp, nixl, mori, ascend, fake.

    disaggregation/utils.py::TransferBackend · prefill.py · decode.py --disaggregation-mode --disaggregation-transfer-backend --disaggregation-bootstrap-port

    Caveats: Needs a router that understands P/D, fast interconnects, and matching KV layouts on both sides (mismatches disable checksum verification).

    HiCache (hierarchical KV cache)

    What: Host-memory and storage tiers behind the GPU radix cache.

    Why: Keeps long-lived prefixes (sessions, documents, agent histories) reusable after they no longer fit in HBM.

    How: The radix tree tracks device/host/storage residency; a controller backs up, loads layer by layer, prefetches, and writes to storage backends (file, mooncake, hf3fs, nixl, aibrix, eic, simm, mori, shm, tensorcast, seaweedfs, npu_memcache, sim, dynamic).

    Caveats: Per-rank host pools compete for the same node memory budget (see --hicache-host-memory-fraction); loading from host is fast but not free, so tiny prefixes may not be worth it.

    Sampling and logit processing

    What: Turning logits into tokens: temperature, top-p, top-k, min-p, penalties, logit bias, seeds, stop conditions, n, beam width.

    Why: Different applications need determinism, diversity, or repetition control.

    How: SamplingParams per request; SamplingBatchInfo holds batched tensors; a penalizer orchestrator accumulates frequency/presence/repetition/min-new-tokens penalties; optional custom logit processors; the Sampler module runs the chosen kernel backend (flashinfer, pytorch, ascend, intel_xpu).

    Caveats: --sampling-defaults model (the default) reads the checkpoint's generation_config.json, so "defaults" can differ between models.

    Why: Users perceive latency by the first visible words, not the full reply.

    Caveats: No chat template is applied — you send the exact prompt text or token ids.

    Function (tool) calling

    What: Extracting structured tool_calls from model-specific output formats.

    Why: Agents need reliable tool invocation in OpenAI format regardless of model family.

    How: Per-family detectors with streaming parsing; optional structural-tag/JSON constraints for required or named tool choice; about 45 parser names.

    function_call_parser.py · base_format_detector.py · parser_names.py --tool-call-parser

    Caveats: The parser must match the model's chat template; a mismatch silently yields plain text instead of tool calls.

    Reasoning separation

    What: Splitting a thinking model's reasoning from its final answer into reasoning_content.

    Why: Clients usually hide or summarise reasoning; tool and grammar logic should apply to the answer only.

    How: Per-family reasoning detectors (streaming-aware); grammar wrapper that activates constraints after the think block; strict-thinking token filtering; a stand-alone /separate_reasoning route.

    parser/reasoning_parser.py · reasoner_grammar_backend.py · /separate_reasoning --reasoning-parser --enable-strict-thinking

    Caveats: Strict thinking requires a grammar backend with token filtering (XGrammar); --grammar-backend none refuses to start with it.

    Router / model gateway

    What: A Rust front door that spreads requests across engines.

    Why: Cache-aware, load-aware placement across replicas and P/D pools beats naive round-robin.

    How: sgl-router (KV-event-fed prefix index, buckets, admission caps, P/D) and sgl-model-gateway (control plane, gRPC, approximate text trees, MCP, history). In-process --dp-size offers simpler balancing.

    sgl-router/src/config/types.rs::PolicyKind · policies_reorg/cache_aware.rs · sgl-model-gateway policies/factory.rs sgl-router --policy --load-balance-method

    Caveats: Router flags belong to the Rust binaries, not ServerArgs; session bindings live in each router replica's memory.

    Frontend language

    What: A Python-embedded DSL (@sgl.function, gen, select, fork) for multi-call LLM programs.

    Why: Expresses branching, choices, and constrained fields concisely, and arranges calls so prefixes are cached.

    How: A client-side interpreter commits shared prefixes before forks, scores choices on cached prefixes, and pre-caches traced batch prefixes.

    lang/api.py::gen · interpreter.py::fork · runtime_endpoint.py::select --disable-radix-cache (keep off)

    Caveats: No dedicated server flag: it is ordinary /generate traffic. select on RuntimeEndpoint requires temperature 0.

    Offline engine

    What: sglang.Engine, the runtime as a Python object.

    Why: Batch inference, evaluation, and RL rollouts without HTTP overhead.

    How: Starts scheduler and detokenizer subprocesses, keeps the tokenizer manager in-process, and exposes sync, async, and streaming generation plus weight-update and LoRA methods.

    entrypoints/engine.py::Engine · EngineBase.py · sglang/__init__.py Engine(**ServerArgs fields)

    Caveats: Present at this commit. Call shutdown() (or use a with block) so subprocesses exit; the sync API drives an asyncio loop internally, so use async_generate inside existing event loops.

    Appendix · Terms

    Glossary

    Short, SGLang-flavoured definitions of the vocabulary used on this page.

    Prefill (extend)
    Processing prompt tokens in parallel to build their KV cache; SGLang calls a prefill batch an "extend" batch because it extends cached prefixes.
    Decode
    Generating one new token per request per step, reading the whole KV cache; usually memory-bandwidth bound.
    KV cache
    Stored attention keys and values for past tokens so they are not recomputed each step.
    Token-to-KV pool
    The GPU memory pool of KV slots; ReqToTokenPool maps each request's positions to slot indices.
    Page size
    Number of tokens per KV allocation unit; 1 means token-granular sharing.
    RadixAttention
    SGLang's automatic prefix caching: a radix tree over token ids indexes reusable KV.
    Radix tree
    A compressed trie whose edges hold token sequences; nodes split when a new sequence diverges midway.
    Lock reference
    A per-node count of running requests using that KV; locked nodes cannot be evicted.
    Eviction policy
    Rule for choosing which unlocked leaves to free: lru, lfu, slru, priority, or tlru.
    Cache salt / extra key
    Namespaces on a RadixKey so identical tokens under different contexts (for example LoRA adapters) do not share KV.
    Continuous batching
    Adding and removing requests from the running batch at every iteration.
    Chunked prefill
    Splitting long prompts into token-budgeted chunks across iterations.
    Mixed chunk
    Running decode tokens in the same forward pass as a prefill chunk.
    Retraction
    Pushing a running request back to the queue when KV memory runs out, freeing its slots.
    Schedule conservativeness
    A multiplier on predicted future token usage that controls how boldly new requests are admitted.
    Overlap scheduler
    Event loop that prepares the next batch on the CPU while the GPU runs the current one.
    FutureMap
    Placeholder token ids for results not yet sampled, used by the overlap scheduler.
    CUDA graph
    A recorded sequence of GPU kernel launches replayed with one call to cut launch overhead.
    Breakable CUDA graph
    A graph backend that allows breaks between captured regions, configurable per phase.
    Attention backend
    The kernel family that implements attention over the paged KV cache (FlashInfer, FA3/FA4, Triton, TRT-LLM MLA, AITER, and others).
    MLA
    Multi-head latent attention: keys and values compressed into a shared latent, as in DeepSeek models.
    Grammar backend
    The library that compiles constraints and produces token masks: XGrammar, Outlines, or llguidance.
    Vocabulary bitmask
    One bit per vocabulary entry per request marking which tokens are allowed next.
    Structural tag
    A constraint that enforces a schema only between begin/end markers, used for tool calls inside free text.
    Jump-forward
    Appending a grammar-forced string in one step instead of decoding it token by token; hooks exist at this commit but no runtime caller.
    Speculative decoding
    Drafting several tokens cheaply and verifying them with one target forward pass.
    Drafter
    The cheap proposer: an EAGLE head, MTP layers, a small model, an n-gram trie, or a LoRA-adapted copy of the target.
    EAGLE / EAGLE-3
    Draft heads that predict next tokens from the target model's hidden states; EAGLE-3 uses features from several layers.
    MTP / NEXTN
    Multi-token-prediction layers shipped with some models; in SGLang the name NEXTN resolves to the EAGLE algorithm.
    Tree attention mask
    Mask letting each draft token see only the prompt and its own ancestors during verification.
    Accept length
    Average number of tokens committed per verify step; exported as sglang:spec_accept_length.
    Tensor parallelism (TP)
    Splitting each weight matrix across GPUs with collective communication per layer.
    Pipeline parallelism (PP)
    Splitting the layer stack into stages and streaming micro-batches through them.
    Data parallelism (DP)
    Running independent replicas and spreading requests across them.
    DP attention
    Data-parallel attention inside a TP group so MLA KV caches are partitioned, not replicated.
    Expert parallelism (EP)
    Placing MoE experts on different GPUs and routing tokens to them with all-to-all.
    DeepEP
    An all-to-all communication library for MoE with normal (prefill) and low-latency (decode) modes.
    EPLB
    Expert-parallel load balancer that periodically reassigns and replicates hot experts.
    Two-batch overlap (TBO)
    Splitting a batch into two micro-batches so communication of one hides behind computation of the other.
    PD disaggregation
    Running prefill and decode on separate engines and transferring KV between them.
    Bootstrap server
    A small service on the prefill engine that decode engines contact to set up a KV transfer.
    Transfer backend
    The library that moves KV between engines: Mooncake, NIXL, MORI, Ascend, or a fake backend for tests.
    HiCache
    Hierarchical KV cache adding host-memory and storage tiers behind the GPU radix cache.
    Write-through / write-back
    Backing a cache node up to host when it becomes hot versus only when it is evicted from the GPU.
    Load-back
    Copying host-resident KV to the GPU, layer by layer, so the forward pass can start early.
    LoRA
    Low-rank adapters that fine-tune a model by adding small matrices to selected weights.
    SGMV / csgmv
    Segmented gather matrix-vector kernels that apply different adapters to different rows of one batch; csgmv is the chunked variant and the default LoRA backend.
    Tool-call parser
    A detector that turns a model's native tool-call syntax into OpenAI tool_calls.
    Reasoning parser
    A detector that separates thinking text from the answer.
    TokenizerManager
    The front-end component (in the HTTP or Engine process) that tokenizes, tracks request state, and receives decoded text.
    Scheduler
    The per-rank subprocess that owns batching, the radix cache, and the model worker.
    DetokenizerManager
    The subprocess that incrementally converts output token ids to text.
    ServerArgs
    The configuration record; at this commit assembled from typed field groups under arg_groups/fields.
    Router / model gateway
    Rust front ends (sgl-router, sgl-model-gateway) that place requests on engines.
    Cache-aware routing
    Sending a request to the engine most likely to hold its prefix, unless that engine is overloaded.
    Power of two choices
    Sampling two candidate engines and choosing the less loaded; cheap and robust.
    Frontend language
    SGLang's Python DSL of gen, select, and fork for multi-call LLM programs.
    TTFT / ITL
    Time to first token and inter-token latency, the two user-facing latency metrics.

    Practice · Questions

    Self-check Q&A

    Try to answer before opening each item; answers point back to the code.

    Why is constrained decoding "valid by construction" rather than "validated afterwards"?

    Because forbidden tokens are masked to negative infinity before sampling on every step (apply_logits_bias applies the GrammarMask), the sampler can never pick a token that leaves the grammar, so no retry loop is needed.

    What happens to the first request that uses a brand-new JSON schema?

    It misses the grammar cache, so compilation is submitted to the backend's thread pool and the request waits in grammar_queue. Once every rank agrees it is ready, it joins the waiting queue. Later requests with the same schema get a copy of the cached matcher immediately.

    Does the scheduler perform jump-forward decoding at this commit? How would you check?

    The grammar classes implement try_jump_forward and friends, but searching python/sglang/srt for callers finds none outside constrained/. So the capability is dormant; a grep for the method name is the quickest verification.

    What three things does build_tree_kernel_efficient produce for verification?

    A tree attention mask (each draft token sees the prompt plus its ancestors), position ids derived from tree depth, and the retrieve_index/next_token/next_sibling arrays used to walk the tree and find the accepted path.

    Why do two sibling draft tokens get the same position id?

    They are alternative candidates for the same next position in the sequence. The mask keeps them from seeing each other, so sharing a position is exactly right for rotary embeddings.

    You pass --speculative-algorithm NEXTN. Which worker runs?

    NEXTN is a reserved alias that SpeculativeAlgorithm.from_string maps to EAGLE, so EAGLEWorkerV2 runs (or MultiLayerEagleWorkerV2 if --enable-multi-layer-eagle is set).

    When is DP attention a better choice than plain TP?

    For MLA models (DeepSeek-style) at high concurrency: TP would replicate the single-latent KV cache on every rank, while DP attention partitions requests so each rank stores different KV, multiplying usable cache. At tiny batch sizes the benefit shrinks.

    Why can't --dp-size alone give you cache-aware routing across replicas?

    Each replica's scheduler owns its own radix tree and the DataParallelController only has load-oriented methods (round_robin, total_requests, total_tokens, …). Prefix-aware placement needs a router that tracks prefixes, such as sgl-router fed by KV events.

    In PD disaggregation, why does the decode engine pre-allocate KV before the prefill finishes?

    The prefill side needs destination addresses to write KV into. DecodePreallocQueue reserves slots and completes the handshake so send_kv_chunk can push pages directly; --disaggregation-decode-allocation-policy prefill_complete delays this when memory is tight.

    What is mooncake_tcp?

    A CLI convenience: the PD resolution hook rewrites it to the mooncake backend with the TCP transport forced, useful where RDMA is unavailable.

    How do HiCache's write_through, write_through_selective, and write_back differ?

    Write-through backs a node up to host after its first hit; the selective variant waits for a second hit; write-back copies only when the node is about to be evicted from the GPU. The hit thresholds are set in init_hicache.

    Two users send the same image with different questions. Can they share prefix KV?

    Yes, up to the point where their text diverges. Placeholder tokens are filled with pad values derived from the image's content hash (MultimodalDataItem.set_hash), so identical images yield identical token sequences in the radix tree.

    Why must the radix key include more than token ids when LoRA is enabled?

    The same tokens processed under different adapters produce different keys and values. RadixKey.extra_key (and optional cache_salt) namespace the tree so KV is shared only within the same context.

    In a streaming chat response, which runs first: the reasoning parser or the tool-call parser?

    The reasoning parser. OpenAIServingChat separates reasoning text first, and only the remaining answer text is fed to the tool-call parser.

    How does s.fork(n) in the frontend language exploit RadixAttention?

    Before cloning state into N branches it commits the shared text with a zero-token /generate call, so the server caches that prefix once; every branch then starts with a radix-tree hit instead of N duplicate prefills.

    Raising --cuda-graph-max-bs-decode caused an OOM. Why, and what is the fix?

    Each captured graph reserves memory for its batch size, which comes out of the headroom left after --mem-fraction-static. Lower the static fraction slightly (shrinking the KV pool) or capture fewer large sizes.

    Which single metric tells you whether speculative decoding is paying off?

    sglang:spec_accept_length (with sglang:spec_accept_rate): if the average accepted length per verify pass is close to 1, the drafter is mostly wasted work.

    With --schedule-policy lpm, what happens when the waiting queue grows very long?

    _determine_active_policy temporarily switches to FCFS because prefix-matching and sorting a huge queue would cost more than it saves.

    How do the cache-aware policies of sgl-router and sgl-model-gateway learn what is cached?

    sgl-router builds its prefix index from engine-published KV events (or an external indexer). The gateway keeps an approximate per-worker tree of the request text it has routed, without querying engines.

    How can you run SGLang without any HTTP server?

    Create sglang.Engine(**server_args) in Python. The tokenizer manager lives in your process, scheduler and detokenizer subprocesses are started for you, and generate/async_generate return results directly.

    Perspective · Two engines

    SGLang versus vLLM: same problem, different shapes

    A conceptual comparison focused on prefix caching, process layout, and scheduling. For vLLM details, see the vLLM deep dive.

    Both engines solve the same core problems — paged KV memory, continuous batching, CUDA graphs, speculative decoding, structured outputs, disaggregation — and they borrow ideas from each other quickly. The interesting differences are in how they index reusable KV and how they split work across processes. Claims about vLLM below are limited to what this site's vLLM page and its pinned source show.
