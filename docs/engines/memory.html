Where does a token live?

A token in the seventh position can occupy slot 22 in GPU memory. Two requests can even read some of the same slots. Follow the numbers from the prompt to an attention layer.

Inspect a token address

Request A has computed A B C D E F G H I J. Request B arrives with A B C D E F X Y Z K. Letters stand for individual vocabulary IDs. Allocation IDs below are invented, and the four-token page makes the arithmetic small. Both requests use the same dense causal model, weights and cache context on one GPU.

Each slot holds a key vector and a value vector for each local KV head at a particular layer. The number 22 is an index in a cache layout. Turning it into byte addresses also requires the layer, head, dimension, strides and data type. Grouped-query attention can have more query heads than stored KV heads. Before allocation

Which positions can B borrow?

  1. Match from the beginning. A difference in the first ID changes the context for every later ID. Identical suffix text alone cannot reproduce earlier contextual keys and values. Check compatible model, adapter, positional settings and any cache namespace as well as rendered token IDs.
  2. Leave input for next-token logits. For ordinary generation both pinned implementations cap the candidate hit at prompt length minus one. A ten-token exact repeat can therefore use up to nine positions before alignment. Prompt log probabilities and specialized execution paths can lower the limit further. vLLM hit cap · SGLang hit cap.
  3. Round down to the reusable boundary. In our single-group vLLM example and SGLang four-token layout, six matching IDs yield four reusable positions. For an exact repeat, nine eligible positions yield eight. In SGLang's one-token layout these examples yield six and nine.
  4. Allocate the remaining positions. A and B may both contain E and F, yet the four-token layout gives B its own page for E F X Y. Each attention pass reads shared KV, computes the uncached suffix and writes fresh values into B’s assigned slots.
When can vLLM match inside a physical block?

At this pin a single cache group uses its resolved block size as the hit unit. Multiple groups can have different physical block sizes. The scheduler aligns across groups, while chained hashes may use a smaller common divisor. Aligned Mamba state checkpoints and compatible managers can enable finer-grained hits. The manager checks lookup support for the other participating groups. A configured hash granularity alone does not establish a usable checkpoint. vLLM V1

Two lookups, two jobs

Find reusable computation

The first key summarizes the prefix ending in A B C D. The next key combines that first hash, E F G H and applicable extra inputs. Group identity distinguishes entries for different KV cache groups. A compatible second request can find physical block 7 by the first key. Multiple physical blocks may temporarily carry equal keys. Block hashing · Block lookup.

Find a token for attention

After allocation the worker has B’s ordered table of physical block IDs. With equal kernel and allocator page sizes and no context sharding, the slot for position p is table[p // size] × size + p % size. The slot-mapping kernel reads integer block numbers. Prefix hashes stay out of this per-token arithmetic. Slot-mapping kernel.

SGLang runtime

A request row points to token locations

  1. Claim a row. B’s external request ID is used for routing. Internally the allocator might give it row 8; A already holds row 3. ReqToTokenPool.req_to_token is an integer tensor with shape [size + 1, max_context_len]. Real requests use nonzero rows, with row 0 reserved for padded graph work. Request-row pool.
  2. Match and protect a path. The radix index compares the token-ID prefix and returns an ordered vector of existing KV slot indices and a matching node. With one-token pages A and B share A–F. The path may branch into G… for A and X… for B. Locking the matched path protects shared state during use. Prefix matching · Path locks.
  3. Fill the row. The token allocator supplies suffix locations. In the one-token view, A and B’s first six columns hold the same location IDs, and req_to_token[8, 6] = 106. The four-token allocator expands page numbers to consecutive slots within each page and can extend a partially used final page. The row contains the resulting token locations in both layouts. Token allocation · Paged allocation.
  4. Read and append. Attention backends consume past locations or derive backend-specific page metadata; current writes use out_cache_loc. For dense MHA, local layers store separate K and V buffers indexed by token location. A latent-attention model can store a compressed representation, and hybrid models need additional state. Layer storage layouts.
  5. Finish or cancel. Release the request row and its active path locks. Reusable cached locations can remain owned by the tree. Eviction frees eligible locations for future requests. Reusing row 8 for a different request does not grant that request access to the finished conversation. Radix insertion and eviction.

Default and exceptions. On ordinary CUDA, the fallback page size is one unless a model or backend overrides it. FlashMLA uses 64, and the TensorRT-LLM MLA path resolves unsupported values to 64 from its allowed set of 32 or 64. Page size governs match alignment and allocation. The prefix tree and the integer request row serve different purposes at every size. Backend rules · Page-size fallback.

SGLang HiCache

Recover a prefix from another tier

HiCache extends prefix reuse beyond the accelerator. The scheduler checks local residency, can stage storage pages in host memory, and restores usable KV to GPU slots before attention reads it. The host cache and backing store are optional. Pinned architecture and sharing scope.

L1 · deviceGPU KV slots

Attention reads here. A resident hit skips both transfer and prefix recomputation.

L2 · hostHost memory pool

A local hit avoids storage lookup. Transfer the needed layer data to L1 and coordinate readiness before computing.

L3 · storageOptional backend

Prefetch matching pages into host memory. Sharing across replicas depends on compatible keys and a shared backend.

One request, three possible outcomes

Suppose a 4,160-token prompt shares 4,096 leading IDs. Assume 64-token pages, an eligible prefetch, and enough per-rank space. If 1,024 positions remain in L1, another 1,024 are only in L2, and the next 2,048 are in L3, the device can immediately reuse 1,024. Loading the host span raises that to 2,048. A successful storage read and GPU restore bring the prefix to 4,096, leaving 64 fresh positions.

If only 1,024 of the storage positions become usable before the deadline, the usable contiguous prefix is 3,072. The model then processes 1,088 positions. If no storage span arrives in time, it processes 2,112 positions after the L2 restore. Transfer and bookkeeping have a cost; a short hit can take longer to restore than to recompute. These counts assume the device prefix remains present while transfers complete.

What determines whether a transfer pays off?

Setting or eventWhat it changes
Enable and size tiersHiCache defaults off. --enable-hierarchical-cache enables it. In cache mode the host pool retains reusable data. buffer_only uses transient staging and requires storage. The configured host size can override the ratio.
Backup from devicewrite_through is the default policy. The selective variant raises the reuse threshold; write_back can defer backup until eviction. Compare host bandwidth spent with the amount reused later.
Prefetch stop ruletimeout is the default. best_effort can admit with what is available; wait_complete can spend longer waiting for the load. Missing, late or unusable pages leave suffix work for prefill.
Controller and storageThe configured transfer backend moves data between host and GPU. The storage backend handles persistence and reads. A local file directory usually serves one node. Mooncake, 3FS or NIXL integrations require their own compatible infrastructure. L3 defaults to unset.

Try the repository’s CPU implementation

With the project installed, run this example in Python. Interleaved requests A and B force A’s second logical block into physical block 2. The toy cache keeps a Python list of entries per block. Its separate prefix-cache exercise does not install shared production KV references.

from mini_infer.engine.block_allocator import BlockAllocator
from mini_infer.engine.paged_kv_cache import PagedKVCache

cache = PagedKVCache(BlockAllocator(3), block_size=2)
for request, value in [("A", 1), ("B", 9), ("A", 2), ("A", 3)]:
    cache.append(request, [value], [value])
print(cache.block_table("A"))                 # (0, 2)
print([e.key[0] for e in cache.entries("A")]) # [1, 2, 3]
cache.free("A")
